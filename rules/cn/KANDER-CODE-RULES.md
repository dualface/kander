# 架构与代码质量规则

## 架构与边界

- 保持既有架构和模块边界, 禁循环或逆向引用. 依赖遵循项目声明方向; 未声明则单向. 必须改变时先说明影响, 由用户决策.
- 跨模块只经公开 API, DTO 或事件; 禁访问对方内部状态, 私有存储或实现细节.
- 共享抽象须有至少两处稳定需求; 单点不提前抽象. 禁为方便穿透层级, 复制领域逻辑或建全局可变状态.
- 改公共接口, 跨模块数据模型或依赖图前, 列影响模块和兼容方案.
- 删或合并模块前, 确认调用方已清退, 迁移路径与回滚风险.

## 代码质量

- 保证正确, 可读, 可维护.
- 性能优化须有测量或瓶颈证据.
- 函数和类型单一职责.
- 命名表达业务意图, 禁含糊缩写或无意义通用名.
- 边界校验输入, 处理空值与异常.
- 禁吞错误, 静默降级或用默认值掩盖失败.
- 资源, 并发, 取消须明确所有权和生命周期, 避免泄漏, 竞态, 无界重试或队列.
- 日志和错误信息禁泄露凭据, 个人数据或内部敏感信息.
- 测试覆盖直接影响的行为, 失败路径和回归点, 验证契约.
- 沿用项目格式化, lint, 错误处理和日志规范; 禁无说明地禁用检查或压低告警.
- 复杂判断注释说明原因, 不逐行复述. 临时代码本任务移除或明确隔离.

## 验证记录

- 运行能直接证明改动的最小验证.
- 测试或环境失败记录实际命令与错误, 禁标通过; 既有环境故障同理.
- 敏感值替换为 `[REDACTED]`, 其余错误文本原样保留.
