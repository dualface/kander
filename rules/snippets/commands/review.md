# kander review

Source: moved from `KANDER-BASE-RULES.md` "Single Review"; the evidence subcommands are specified in `snippets/review-evidence-gate.md` "Review Evidence Completion Gate"

## Purpose and users

Runs one reviewer role on a commit range and publishes the evidence, and manages review plans, assignments, dispositions, and closures. The single review entry can be invoked explicitly by any agent; the full review workflow is `KANDER-REVIEW-RULES.md`.

## Syntax

```text
kander review [agent] [--task <id>]... [--run-id <id>] [--batch-id <id>] [--previous-run-id <id>] [--requirements-file <JSON>] [--requirement-decision <ROLE>=<decision-id>]... [--advance-file <JSON>] <CWD> <base-commit> <commit> <role> <task-goal|absolute-spec-path> [review-context] [reviewed-commit]
kander review plan <absolute-CWD> <absolute-plan.json>
kander review extend-plan <absolute-CWD> <absolute-extension.json>
kander review assign <absolute-CWD> <absolute-assignment.json>
kander review disposition <absolute-CWD> <absolute-author-record.json> <expected-card-revision>
kander review interpret <absolute-CWD> <absolute-interpretation.json>
kander review map-legacy <absolute-CWD> <absolute-map.json>
kander review abandon <absolute-CWD> <absolute-abandon.json>
kander review aggregate <absolute-CWD> <batch-id>
kander review advance <absolute-CWD> <absolute-advance-request.json>
kander review close <absolute-CWD> <absolute-close-request.json>
kander review progress <absolute-CWD> <task-id>
kander review publication <absolute-CWD> <publication-id>
kander review <plan|extend-plan|assign|disposition|interpret|advance|close|abandon> --schema
```

## Arguments

- `[agent]`: the reviewer agent for this run. The first positional argument is taken as the agent when it names a configured agent with a review template. A configured agent that cannot be used is refused, and so is a first argument that is neither such an agent nor an absolute path when the second argument is an absolute path. Without `[agent]`, Kander selects the reviewer from the card pins and the `reviewers` configuration.
- `--task <id>`: repeated; binds the run to cards.
- `--run-id <id>`, `--batch-id <id>`, `--previous-run-id <id>`: identify the run, its batch, and the predecessor of an incremental round.
- `--requirements-file <JSON>`: names the batch requirements for a new batch.
- `--requirement-decision <ROLE>=<decision-id>`: repeated, once per role; only with `--requirements-file`, in a project on a server. `ROLE` is `PMQA` or `Security`; `<decision-id>` is a record of `kander decision record` on a batch member that justifies `N/A: <reason>` for a role the project policy requires (see Preconditions).
- `--advance-file <JSON>`: advances the batch target.
- `<CWD>`: the absolute path of the worktree to review; a relative path is refused.
- `<base-commit>`, `<commit>`: the reviewed range `base-commit..commit`; each is a commit or a ref that Git resolves in `<CWD>`, such as `origin/v2` or `HEAD`.
- `<role>`: the reviewer role, `PMQA` or `Security`, case-insensitive. The older names `PM`, `QA`, `CSA`, and `Hacker` are accepted only when the batch requirements mark that role `required`, or for a run that already exists.
- `<task-goal|absolute-spec-path>`: the goal text, or the absolute path of a card `spec.md` that holds it.
- `[review-context]`: text added to the reviewer's task context, such as the previous round's findings and how they were handled (`KANDER-REVIEW-RULES.md` "Preconditions and Execution").
- `[reviewed-commit]`: for an incremental round, the commit this role reviewed in the previous round; a first round omits it.
- `plan`, `extend-plan`, `assign`, `disposition`, `interpret`, `map-legacy`, `abandon`, `aggregate`, `advance`, `close`, `progress`, `publication`: select an evidence subcommand; each takes an absolute CWD and a JSON file or an ID as shown in Syntax.
- `publication`: the subcommand that reads the stored material of a joint publication before a holder confirms it; it is read-only and needs no credential (`## Distributed holder confirmation (v2)`).
- `confirm`: the subcommand that confirms a prepared publication as its holder; the confirmation binds the task revision, the execution generation, and the digest of the material; see "Additional Syntax". It is not the top-level `kander confirm`, which confirms a request card.
- `--schema`: prints the JSON schema of the input of a subcommand.
- `batch`: not a subcommand (no documented caller); batches are named in the plan by `plan` and `extend-plan`, advanced by `advance`, and closed by `close`.
- `resolve_batch`: a field of the `extend-plan` input that accepts an unplanned batch that already ran, on the evidence of one closed planned batch (`snippets/review-evidence-gate.md` "Review Evidence Completion Gate").
- `requirement_decisions`: an optional field of each batch object of the `plan` input and of the `batch` object of the `extend-plan` input, mapping a role to a decision ID like `--requirement-decision`. `policy_revision`, a top-level field of both inputs in `--schema`, is filled in by the command; leave it out.
- `add_members`: a field of the `extend-plan` input that adds started cards of the plan's task group as plan members while the plan is not sealed; the whole request is refused when one card fails (the error names the card and the condition), distributed mode uses the coordinator write or, when its conditions fail, the confirmation of the holder of every live member of the operation, the new members included (`## Distributed holder confirmation (v2)`), and it is exclusive with every other operation (`snippets/orchestrate-review.md` "extend-plan").

## Examples

```text
# Run one reviewer role on a commit range
kander review /tmp/worktree origin/develop HEAD PMQA "Review the example change"

# Publish a review plan
kander review plan /tmp/worktree /tmp/plan.json

# Print the input schema of the plan file
kander review plan --schema

# Extend a review plan
kander review extend-plan /tmp/worktree /tmp/extension.json

# Assign a reviewer to a batch
kander review assign /tmp/worktree /tmp/assignment.json

# Record the disposition of the findings
kander review disposition /tmp/worktree /tmp/record.json 3

# Record how the receiver reads a report
kander review interpret /tmp/worktree /tmp/interpretation.json

# Map a legacy batch to the plan
kander review map-legacy /tmp/worktree /tmp/map.json

# Print the disposition view of a batch
kander review aggregate /tmp/worktree 20261118-example-task-batch-1

# Advance the target of a batch
kander review advance /tmp/worktree /tmp/advance.json

# Retire a finalized run that no process can publish any more
kander review abandon /tmp/worktree /tmp/abandon.json

# Close a batch
kander review close /tmp/worktree /tmp/close.json

# Print the progress of a card in its plan
kander review progress /tmp/worktree 20261118-example-task

# Read the material of a prepared publication before confirming it
kander review publication /tmp/worktree publication-1

# Confirm a prepared publication as its holder
kander review confirm /tmp/worktree publication-1 20261118-example-task
```

## Preconditions

- The target must be a clean Git worktree, and base must be an ancestor of commit.
- Without `--task`, no board is located. With `--task`, flags precede CWD, repeated task IDs are deduplicated, and the board is located from the target CWD. Cards must be working/review directory cards with one language and compatible task group membership.
- Task-bound review requires an explicit batch ID. A new batch also requires a JSON requirements file with exactly the keys `PMQA` and `Security`, each valued `required` or `N/A: <reason>`. Resolve these from user/project rules and stage policies; the file records that decision and grants no approval.
- When the project policy has a revision above 0 and `rules.review` on, a new batch that writes `N/A: <reason>` for a role whose `review_stages.<scale>.<role>` is `required` must name, for that role, a decision record on one of its members: `--requirement-decision`, or `requirement_decisions` in `plan`/`extend-plan`. The scale is `large` when any member is `SIZE: large` (a card without `SIZE`: small for a file card, large for a directory card). A `skip` role written `required` and an `auto` role need no decision.

## Effects

- `kander review` is a single-review tool that can be invoked explicitly. Invoking it does not enable the full review or Git flow and does not require the target branch to be the mainline branch.
- A missing run ID is generated and printed to stderr. Run and batch IDs are board-wide, so a chosen ID starts with the task ID (or task-group ID), never a short generic name. Reuse a run ID only to recover or finish publication of the same run; it never launches another reviewer. A different Kander version is not a changed input, and the run keeps its original `kander_version`. Changed inputs conflict: restore the configuration and pass the frozen task context, or use a new run ID in the same batch. Use distinct run IDs for different roles on the same target. A retry after a process crash records interrupted evidence, never PASS.
- Plan IDs and batch IDs are unique across the whole project, not per task group, and a plan or batch keeps its ID until the archive cleanup removes its records, which waits for every card of the plan (and of its task group) to be settled. When choosing one, start it with the task group ID (the task ID for a single card), for example `<group-id>-plan-1` and `<group-id>-b1`. For a card that has a plan, `kander show --document reviews/plan.json <task-id>` shows the IDs it used. A refused `plan` changes no plan, batch, or card; an API caller that writes the request again with other content also needs a new idempotency key. Each message names only IDs and field names, never a requirement value, an author, a basis, a path, or report text. `plan` refuses an ID in four ways:
  - `existing batch/plan mismatch`: a batch with this `batch_id` exists, held by the named plan or, when the message says so, by a review run outside any plan, and the new plan differs from it in the listed fields (`base`, `target_commit`, `task_ids`, `requirements`, `report_language`). Held by a plan: use another batch ID. Held by a run outside any plan: to adopt that batch, keep its ID and write the recorded binding; another ID leaves the batch unplanned and the plan is refused with `unplanned execution batch`.
  - `batch already planned`: a batch with this `batch_id` and the same binding already belongs to the named plan; use another batch ID.
  - `immutable review plan conflict`: a plan with this `plan_id` exists, and the new plan differs from it in the listed top-level fields; use another plan ID, or write the identical plan again to retry it.
  - `execution already has a review plan: <task-id>`: the member already belongs to the plan the message names; extend that plan with `extend-plan` instead of creating another.
- New runs and batches accept only the roles `PMQA` and `Security` (case-insensitive). Historical four-key (`PM`, `QA`, `CSA`, `Hacker`) and six-key batches stay readable, retryable, and closable with their original roles; never rewrite their requirements, role order, run IDs, originals, hashes, closures, or dispositions.
- `evidence.txt` lists the review and optional fix ranges, their commit logs, and changed files. Reviewers inspect diffs using read-only Git in the review worktree. In distributed mode an artifact request over the service limit fails before the reviewer starts, with a localized size error and retry guidance.
- Raw output, logs, input snapshots, sidecar, and manifest stay in each card's `reviews/<run_id>/`; the machine-owned REVIEWS section holds one JSON index line per run. Tool success is separate from semantic PASS. Never edit or delete these artifacts; only Kander removes them, after every card they belong to is archived.
- New readable review reports may await receiver interpretation when their findings format cannot be extracted. `kander review interpret <CWD> <absolute-JSON>` publishes an immutable, attributed reading with original hash and exact quotes; `--schema` describes its fields. Valid structured reports are extracted automatically. Zero findings need explicit original evidence; pending interpretation cannot establish completion, and failed executions cannot be converted to success.
- Publication is atomic per card. A partial publication exits nonzero and preserves the cards that succeeded. After an interrupted board transaction, run `kander init` under its maintenance requirements, then retry the identical invocation with the same run ID. An incompletely published run cannot establish completion.
- Built-in reviewers follow the isolation posture declared on each agent definition; reviewers whose arguments do not enforce read-only rely on the prompt and the post-run check, and their output is validated. A custom reviewer's read-only posture is its definition author's responsibility. Kander isolates the review-private directories for every reviewer and afterwards checks the Git-visible state of the target worktree; writes outside the worktree or to ignored paths are not detected.
- `abandon` retires a finalized run that no process can publish any more (the writer secret is lost, the client differs, or a member's claim was taken over): `{"run_id", "decision", "reason"}`, with a non-empty user decision reference that Kander records and does not verify. The run leaves its batch: it writes no copy and no `REVIEWS` line into a member card, it is no longer a run of the batch, its findings bind nothing, it cannot be a predecessor or satisfy a role, and it is never published afterwards; the batch view lists it in `abandoned_runs`, and a new run has to satisfy the role. It is not `superseded_runs`, which retires a published run. The same request again returns the first result and writes nothing.
- The server checks only a new batch (created by `--requirements-file`, `plan`, or `extend-plan`) against the project policy, under the project lock and before anything is written; the client sends its `policy_revision`. The batch stores that revision (when above 0) and the decisions the check used. Existing batches, historical four- and six-role ones included, are never checked again: reads, retries, incremental runs, and closing work as before. The revision is not part of a run's identity or of a plan's idempotency receipt, so retrying a run ID after a policy change returns the first result.
- The evidence subcommands and their gates (plans, batches, assignments, author dispositions, aggregation, advance, closure, progress) are specified in `snippets/review-evidence-gate.md` "Review Evidence Completion Gate".

## Output

- The reviewer run prints the generated run ID on stderr and the report on stdout; task-bound runs publish into each card. `aggregate` prints the generated disposition view (preserve its exact bytes for `close`; with `--json` use the `view_hash` field, see below); `publication` prints the stored material of a joint publication (below); `progress` prints the plan state, with `exclusion` for a member that left the plan, `resolved_batches` with the result of each finding of a resolved unplanned batch, and optional `next_actions` (`{action, batch_id, role, run_ids, task_id}`; `append-cycle-batch` names a rebound member with no batch; `supersede-duplicate-runs` lists two or more successful chain heads of one role in an unclosed batch; only heads that qualify as parallel duplicates, or root runs with a user decision reference and the runs that continue them, can go into `superseded_runs`); `--schema` prints the input schema.
- A new run prints a stderr warning when another run of its batch and role is outside its predecessor chain and is still running or a successful chain head; finalized failed runs never trigger it. The run continues and the exit code is unchanged. Resolve the duplicate with `--previous-run-id` or the close request's `superseded_runs`.
- With `--json`, the reviewer run is one object: `exit_code`, `report` (the report text), and for a task-bound run `run_id`, `batch_id`, `execution_status`, `failure_reason`, and `task_ids`. The run ID line, the card publication lines, and the other stderr remarks are notices (`review_archive_identity`, `review_card_published`, `review_interpretation_pending`, `review_process_evidence`, `review_output`, `review_error`). A run whose evidence reached every card, or that succeeded, is this object with the exit status of the run; any other failure is the error object with the code `review_failed`. A run that was prepared in the archive but not published (a failed finalize, a card that refused the publication, a joint confirmation still pending) is that error object too, and its message ends with the run ID and batch ID of the prepared run. `--schema` prints `command` and `schema` (the schema text). The evidence subcommands print the same object as without `--json`, on one line, with these fields:

  Field types: `string`, `integer`, `boolean`, `array of X`, `map X to Y` (a JSON object whose keys are of type X and values of type Y), `object`. A field in parentheses after `when present` is left out when it has no value.

  - `plan`, `extend-plan` (including `resolve_batch`): `plan_id` (string): the plan that was created or extended.
  - `advance`: `batch_id` (string): the batch whose target moved.
  - `assign`, `interpret`, `map-legacy`: `run_id` (string): the run that was assigned, interpreted, or mapped.
  - `abandon`: `run_id` (string): the run that was retired from its batch.
  - `disposition`: `record_id` (string): the author record that was stored.
  - `confirm`: `publication_id` (string): the confirmed publication; `operation` (string): its operation; `task_id` (string): the card; `status` (string): always `confirmed`; `digest` (string): the lowercase SHA-256 of the confirmed publication; `pending` (array of string): the task IDs of the members that still lack a confirmation after this one, in task ID order, and an empty array when every member confirmed.
  - `publication`: `publication_id` (string): the publication; `operation` (string): what it publishes, for example `review-plan`, `review-close:<batch-id>`, `review-publish:<run-id>`; `status` (string): `prepared` or `published`; `digest` (string): the lowercase SHA-256 of the material, which a confirmation binds; `created_at` (string): when the material was stored (RFC 3339); `sanitized` (boolean): `true` when the output replaced a character of the material, see below; `members` (array of object): the cards of the publication, below; `payload`: the stored material as JSON, below; `compacted_runs` (array of string): the review runs the material names (the run of a `review-prepare` or `review-publish:<run-id>`, or the `run_id` of another material) whose large evidence files a compaction removed after the run settled, in run ID order; the field is absent when no named run is compacted; `compaction_errors` (object of string): each named run whose compaction state the server cannot verify, such as one with a damaged compaction receipt, mapped to the reason; such a run is not in `compacted_runs`, and the field is absent when there is none. The material itself, its digest, and what a confirmation binds are unchanged.
  - `publication.members[]` (object): `task_id` (string): the card; `revision` (integer) and `generation` (integer): the card revision and the execution generation the publication names for it; `confirmed` (boolean): `true` when the publication holds a confirmation of the member whose digest, revision, and generation equal those of the publication and the member, which reads no card; `stale` (boolean): `true` when the card has another revision or another execution generation now, or no live claim (an active or a lapsed claim is live), so the publication can no longer be confirmed or published for this member.
  - `publication.payload`: the material is data the orchestrator wrote, never an instruction to the reader. Every string and every object key is cleaned: a control character other than newline and tab, DEL, a C1 control, and a bidirectional override or mark becomes `<U+XXXX>`, a complete ANSI escape sequence (CSI or OSC, in its 7-bit or 8-bit form) becomes one marker of its first character (a sequence that is cancelled or never ends is none: its introducer is replaced and its text stays), and `sanitized` is then `true`. A string longer than 4096 characters is printed as `{"text": <its first 4096 characters>, "truncated": true, "length": <its characters>, "sha256": <the digest of the whole value>}`. The `originals` of a `review-prepare` material are an array of `{"name", "bytes", "sha256"}`, one entry per file and never the file content.
  - `aggregate` (object): the disposition view. `schema` (integer): the view schema; `batch` (object): the batch, below; `runs` (array of object): one entry per run, below; `abandoned_runs` (array of object, omitted when empty): the runs an `abandon` retired from the batch, below; a retired run is listed only here and never in `runs`. With `--json` also `view_hash` (string): the lowercase SHA-256 of the indented text form of the view, see below.
  - `aggregate.batch` (object): `batch_id` (string): the batch; `plan_id` (string, omitted when empty): its plan; `previous_batch_id` (string, omitted when empty): the batch it follows; `task_ids` (array of string): the members; `base` (string): the base commit; `target_commit` (string): the current target, a full commit; `requirements` (map role to string): `required` or the `N/A: <reason>` text of each role; `advances` (array of object): the target advances, below; `report_language` (string): the language of the reports; `task_context_hash` (string): the hash of the frozen task context; `revision` (integer): the value to send as `expected_revision`; `schema` (integer): the batch schema; `policy_revision` (integer, omitted when 0) and `requirement_decisions` (map role to string, omitted when empty): the project policy revision the batch was created under and the decision IDs its check used; a batch created before the check has neither.
  - `aggregate.batch.advances[]` (object): `previous_target` (string): the target before the advance; `target` (string): the target after it; `reason` (string): why the target moved; `deliveries` (map task ID to string): the delivery commit of each member; `foreign_commits` (map string to string, omitted when empty): the commits of other authors the advance includes, each with its reason.
  - `aggregate.abandoned_runs[]` (object): `run_id` (string): the retired run; `decision` (string): the user decision reference of the `abandon`; `reason` (string): why the run was retired.
  - `aggregate.runs[]` (object): `run` (object): the run record, below; `findings_status` (string, omitted when empty): `pending` while a readable report awaits its interpretation; `findings` (object, omitted when absent): the parsed findings, `FINDINGS` and `NON_BLOCKING`, each an array of finding objects (`id`, `tier`, `text`, `evidence`, and when present `mechanical` and `lineage`); `assignment` (object, omitted when absent): the saved assignment of the run, below (the `assign` form itself prints only `run_id`); `interpretation` (object, omitted when absent): the record of `interpret`, with the input printed by `kander review interpret --schema`; `records` (array of object): the author dispositions of the run, oldest first, each with the input fields printed by `kander review disposition --schema`; `withdrawn` (array of object, omitted when empty): the records whose finding was withdrawn with its member.
  - `aggregate.runs[].assignment` (object): `run_id` (string): the run; `batch_id` (string): its batch; `author` (string): who assigned the findings; `basis` (string): why; `items` (map string to array of string): each finding ID with the task IDs it is assigned to; `owners` (map string to string): each assigned task ID with the owner of the card when the assignment was made; `recorded_at` (string): the RFC 3339 time.
  - `aggregate.runs[].run` (object): `schema` (integer): the run schema; `run_id` (string): the run; `batch_id` (string): its batch; `previous_run_id` (string, omitted when empty): the run it continues; `task_ids` (array of string): the cards it was bound to; `task_group` (string): their task group, or an empty string; `role` (string): one of the roles of the `requirements` of its batch (`aggregate.batch.requirements`): a current batch has the two roles `PMQA` and `Security`; a historical batch keeps the four roles `PM`, `QA`, `CSA`, `Hacker`, or the six roles `PM`, `QA`, `CSA`, `Hacker`, `PMQA`, `Security`, and its runs carry any role of that set, so a historical batch can hold a run of `PMQA` or `Security`, and a four-role batch that is still open can take a new run of `PM`; validate a role against the `requirements` of the batch, never against a split of new and historical roles; `reviewer` (string), `model` (string), `effort` (string): the reviewer agent and its settings; `cwd` (string): the worktree it ran in, `project:<id>` on the server; `base` (string) and `commit` (string): the reviewed range; `reviewed_commit` (string, omitted when empty): the last commit an incremental run had already reviewed; `report_language` (string); `findings_schema` (integer, omitted when empty): the findings schema; `advance` (object, omitted when absent): the advance an incremental run followed, the same fields as `aggregate.batch.advances[]`; `resolved` (string, omitted when empty): the resolution it belongs to; `input_hashes` (map string to string): the SHA-256 of each frozen input; `kander_version` (string): the version that wrote the run; `phase` (string): where the run stopped (`finalized` once the report is stored); `launch_status` (string), `execution_status` (string), `semantic_status` (string): the launch, the execution (`ok` or a failure) and the semantic reading (`unassessed` or the conclusion); `failure_reason` (string, omitted when empty); `exit_code` (integer): the exit status of the reviewer; `created_at` (string) and `finished_at` (string, omitted when empty): RFC 3339 times; `duration_ms` (integer); `hashes` (map string to string): the SHA-256 of each stored original; `published` (map task ID to boolean): whether the run reached each card; `skipped_members` (array of string, omitted when empty): members left out of the run; `member_cycles` (map task ID to string, omitted when empty): the execution cycle of each member when the run was created. An `abandon` also writes `abandonment` (`decision`, `reason` and `abandoned_at`, an RFC 3339 time) into the stored run record; a run that carries it is listed in `abandoned_runs`, not in `runs`, so no entry of `aggregate.runs[].run` or `close.view.runs[].run` has it.
  - `close` (object): the closure. `schema` (integer); `plan_id` (string); `batch_id` (string); `target_commit` (string): the final target, a full commit; `request` (object): the close request as stored, below; `git` (object): the Git evidence, below; `role_statuses` (map role to string): `PASS` for a role with a passing conclusion, the `N/A: <reason>` text of the plan for a role marked N/A, or the waiver policy of a waived role; `view` (object): the aggregate view the close bound: `schema`, `batch`, `runs`, and `abandoned_runs` as in `aggregate`, without `view_hash`, which only the `aggregate --json` response adds; the closure keeps that value as `request.view_hash`; `closed_at` (string): the RFC 3339 time of the closure.
  - `close.request` (object): `batch_id` (string); `expected_revision` (integer); `view_hash` (string); `author` (string); `roles` (map role to object): the conclusion of each required role, below; `resolved_failures` (map string to string): each failed run ID with its successful replacement; `superseded_runs` (map string to object, omitted when empty): retired duplicate runs, below; `mechanical` (array of object, omitted when empty): the mechanical assessments, below; `opinions` (array of object): the separate verification opinions, below.
  - `close.request.roles{}` (object): `run_id` (string): the conclusion run; `passed_at` (string): the commit it passed at; `basis` (string): the basis of the conclusion.
  - `close.request.superseded_runs{}` (object): `replacement` (string): the run that stands in; `basis` (string); `decision` (string, omitted when empty): the user decision reference.
  - `close.request.mechanical[]` (object): `record_id` (string); `finding` (object): `run_id` (string) and `finding_id` (string); `task_id` (string); `author` (string); `category` (string): the assessed category; `reported_category` (string): the category the reviewer gave; `report_hash` (string); `fix_commit` (string); `basis` (string); `facts` (string): the verification facts; `paths` (array of string): the changed paths; `diff_hash` (string): the hash of their Git diff.
  - `close.request.opinions[]` (object): `author` (string); `basis` (string); `finding` (object, omitted when absent): `run_id` (string) and `finding_id` (string) of the finding it concerns.
  - `close.git` (object): `cwd` (string): the worktree, `project:<id>` on the server; `head` (string): the batch target; `verified_at` (string): the RFC 3339 time of the check; `edges` (array of object): the commit relationships that were verified, below; `no_delivery` (boolean, omitted when false): the batch has no delivery commit; `observed_head` (string, omitted when empty): the HEAD the client closed from; `not_applicable` (string, omitted when empty): the reason Git does not apply; `mechanical` (array of object, omitted when empty): the Git facts of the mechanical assessments, below.
  - `close.git.edges[]` (object): `ancestor` (string): a full commit; `descendant` (string): a full commit that contains it.
  - `close.git.mechanical[]` (object): `record_id` (string); `run_id` (string); `task_id` (string); `from` (string) and `to` (string): the commits of the fix; `paths` (array of string): the changed paths; `diff_hash` (string): the hash of the Git diff.
  - `progress` (object): the plan state of one card. `task_id` (string); `status` (string): `legacy-untracked`, `requirements-needed`, `plan-target-mismatch`, `pending`, `closed`, or `excluded`; `plan_id` (string, omitted when empty); `exclusion` (object, omitted when absent): why the card left the plan, below; `pending` (array of string, omitted when nothing is open): the open obligations, one identifier per entry: `unsealed-plan`, `unassigned-member`, `cycle-batch:<member>`, `recovery-review:<member>`, `recovery-role:<member>/<role>`, `dropped-review:<member>/<role>`, `stale-run:<batch>/<role>/<member>`, or the ID of a batch that is not closed; `rebind_cycles` (map task ID to string, omitted when empty): the complete map to send in `rebind_cycles` of `extend-plan`, each value the current execution cycle of that card; `plan_target` (string, omitted when empty) and `batch_target` (string, omitted when empty): full commits; `batch_id` (string, omitted when empty); `next_actions` (array of object, omitted when empty): below; `resolved_batches` (array of object, omitted when empty): below; `batch_policies` (map batch ID to object, omitted when empty): for each planned batch that has them, `policy_revision` and `requirement_decisions` as in `aggregate.batch`.
  - `progress.exclusion` (object): `schema` (integer); `exclusion_id` (string); `task_id` (string); `plan_id` (string, omitted when empty); `task_group` (string, omitted when empty); `from_state` (string): the state the card left; `state` (string): the state it entered (`archived` or `trash`); `result` (string): the result of the move; `cycle` (string): the execution cycle of the card; `reason` (string); `decision` (string): the user decision reference; `recorded_at` (string): the RFC 3339 time.
  - `progress.next_actions[]` (object): `action` (string): what to do (`append-cycle-batch`, `supersede-duplicate-runs`, `rerun-current-cycle`, `append-required-batch`); `batch_id` (string); `role` (string); `run_ids` (array of string): the runs it concerns; `task_id` (string, omitted when empty).
  - `progress.resolved_batches[]` (object): one resolved unplanned batch. `request` (object): the resolution request with the result of each finding, below; `author` (string); `basis` (string); `batch_revision` (integer): the batch revision the resolution bound; `runs` (array of object): the runs the resolution covered, below; `git` (object): the Git facts, below; `recorded_at` (string): the RFC 3339 time.
  - `progress.resolved_batches[].request` (object): `batch_id` (string): the resolved unplanned batch; `covering_batch_id` (string): the closed planned batch that covers it; `findings` (array of object): the result of each finding, below.
  - `progress.resolved_batches[].request.findings[]` (object): `run_id` (string) and `finding_id` (string): the finding; `status` (string): `fixed`, `deferred`, or `rejected`; `basis` (string); `fix_commit` (string, omitted when empty): a full commit, for `fixed`; `verification` (string, omitted when empty): for `fixed`; `decision` (string, omitted when empty): the user decision reference, for a rejected must-fix finding.
  - `progress.resolved_batches[].runs[]` (object): `run_id` (string): a run of the resolved batch; `report_hash` (string): the SHA-256 of its report. The result of each finding is in `progress.resolved_batches[].request.findings[]`, never here.
  - `progress.resolved_batches[].git` (object): `cwd` (string); `verified_at` (string): the RFC 3339 time; `edges` (array of object): the verified commit relationships, the same fields as `close.git.edges[]`.

  The close request binds the SHA-256 of the exact text form of the view: the two-space indented JSON with a final newline. The single line of `aggregate --json` is not that text, so its `view_hash` field is the digest to put in `view_hash` of the close request; never hash the line itself, and never reserialize it.

## Rejections

- A refusal over a value the request names (`expected_revision`, `view_hash`, `previous_target`, `previous_record_id`, `rebind_cycles`, `sync_targets`) keeps its label as the start of the message and then writes the value the request holds, the value the board holds (a request value that does not have the form of its field, such as a short SHA in `previous_target` or text in `view_hash`, is written as `<invalid>`), and the next step, which is to read the current state again (`kander review aggregate` or `kander review progress`, and for the revision of a plan `kander show --document reviews/plan.json <task-id>`) and to confirm that the decision still holds before the request is written again. A message never writes a token, a claim or lease proof, an execution credential, a report body, or a disposition reason. A close request with no `author` is refused as `close author required`, an advance whose `previous_target` is the batch target but whose `target` does not move, is no full commit, or has no `reason` is refused as `batch target invalid` (only a different `previous_target` is `batch target CAS conflict`), and a batch or plan that is not there is refused as `missing batch` or `missing plan` with its ID; neither is a CAS refusal. A review over a member that is not in `working/` or `review/` names the member and its state. For a member in `backlog/` or `todo/` it offers to wait until the member starts and, when the card has a `TASK_GROUP` and is still an unstarted member, `kander coordinator remove-member` after the user decides (see `coordinator.md`); it never offers `remove-member` for a card without a group or in `done/`, `archived/`, or `trash/`.
- A dirty worktree, a base that is not an ancestor, a reused run ID with changed inputs, a four- or six-key new batch, a batch outside the plan of a member (the error names `extend-plan`), a `resolve_batch` request that fails a condition of the gate snippet, a `close` on a conclusion run of another execution cycle, a `seal` over a dropped `required` batch with no planned replacement, a `release_obligation` with no `decision` or nothing to release, a `release_obligation` of kind `recovery` under a plan that requires a role, an `extend-plan` or `resolve_batch` request whose `expected_revision` differs from the plan's current revision (the error names both; read `reviews/plan.json` again and rebuild the request), a new batch on a sealed plan that either sets `seal` to `true` or names no member that owes a batch (an owed member is one `review progress` lists as `append-cycle-batch`, even if another plan member owes one); the error names the seal: when a member of the requested batch is listed, send the batch again with `seal` omitted or `false`; otherwise complete the members at the closed final target and carry later work in a new card with its own plan per `KANDER-REVIEW-RULES.md` "Carrying Conclusions Forward"), a target that differs from a frozen task context (the error names the frozen snapshot), a worktree other than the plan's `cwd`, conflicting review pins of one batch (change a pin with `kander update --contract-decision-file`), incomplete publication, or a gate failure of an evidence subcommand.
- An `abandon` of a run that is not finalized, that a member already holds a copy of, whose batch is closed, that another run names as `previous_run_id`, or that has no member in working or review (move one member back to working first, then abandon) is refused with the reason and nothing is written; so is one with an empty decision or reason, and a second request with another decision or reason.
- A new batch is refused, with nothing written (no batch, run, staging file, or receipt), with `policy_revision_stale` (HTTP 409) when the project policy changed since the client read it, and with `policy_requirement_unmet` (HTTP 400) when a role the policy requires is `N/A` without a decision, or its decision ID is on no member; the message lists each failing role and why. On a stale refusal the client reads the policy again and sends the same request once more with the new revision; a second one exits non-zero and names the server's revision and `kander policy show`. The client never rewrites requirements: on `policy_requirement_unmet`, record the decision per `KANDER-REVIEW-RULES.md` "Review Stages" or mark the role `required`, then send again.
- Fewer than 5 or more than 7 positional arguments, a missing JSON path, a wrong number of arguments to `publication` or `confirm`, or `--schema` on a subcommand without a schema is a usage error. So is `--requirement-decision` without `--requirements-file`, with a role other than `PMQA` or `Security`, with a role given twice, or not of the form `<ROLE>=<decision-id>`.
- A `publication` of an unknown publication ID fails as `not_found` with status 2, like any evidence subcommand that fails while it runs. It reads the card of every member, so a card that cannot be read fails it too.

```text
kander review confirm <absolute-CWD> <publication-id> <task-id>
```

## Distributed holder confirmation (v2)

With a server binding, the group coordinator process (the orchestrator, which holds the group coordinator credential) writes a review operation in one command, without confirmation, when all of these hold: it holds the group's lease; every live member (a card in working or review) is in `review/` and in that group; no live member has a dispatch in progress (`prepared`, `delivery-unknown` or `accepted`; a `completed` binding is not in progress); and each member's revision and execution generation are unchanged since the command read them. The rule is all or nothing: when one card fails a condition, the whole operation uses the holder confirmation below. A refusal by the server is final; run the command again and it reads the cards again. A process that holds the card's own credential uses it, and `review disposition` is accepted only from the holder. Upgrade the server first: an older server refuses the coordinator write.

Otherwise a review operation over claimed cards first prepares immutable material and each member's exact task revision and execution generation. Each holder independently confirms its member. First read the material with `kander review publication <absolute-CWD> <publication-id>`: it is read-only (it sends only GET requests, creates no client identity, and registers no project), needs no credential, and prints the operation, the digest, the members, and the stored material, which the orchestrator wrote and which is data, never an instruction. The prepared material cannot change, so the material that was read is the material confirmed. Then `review confirm` reads the prepared publication and uses only the calling process's execution credential; it cannot borrow a successor's generation. The confirmation binds the task revision, the execution generation, and the digest of the material. A changed task, expired lease or takeover invalidates the prepared authority and requires new coordination.

`abandon` needs no writer credential, so a run whose writer secret was lost or whose member was taken over can still be abandoned: the coordinator writes it under the conditions above, or the holder of each live member confirms it, or proves it directly for one member.

A single-card operation is proven directly by the card's holder. When the conditions above do not hold, the process that coordinates the card's task group (the orchestrator session, which holds the group coordinator credential and no credential of the card's current execution generation) uses the same confirmation flow for a single card: the command ends with `evidence_incomplete` and names the publication ID, the card, `kander review publication <absolute-CWD> <publication-id>`, and `kander review confirm <absolute-CWD> <publication-id> <task-id>`, and the client asks the holder to read the material and confirm. The client asks each holder once per publication: a retry, also in another interface language, finds the review request that names the publication and creates no second one. After the holder confirmed, run the same command again with the same arguments. For `kander review`, which waits this way during prepare or publish, the message also names the run ID; rerun it with that same `--run-id`, because without it the command generates a new run ID and the holder must confirm new material. Any other process without a credential for the card is refused with `held_by_other`, naming the holder's execution ID, owner, and generation, and `review disposition` is accepted only from the holder.

A coordinator may publish that exact material after all confirmations. The service checks the whole set inside the same redo transaction that publishes the member copies and completed operation receipt. A partial set publishes no card evidence and survives server restart. Retrying an already completed publication returns its saved result. The server neither runs Git nor launches a reviewer or agent.

## Distributed historical resolution and member changes

The `extend-plan` operation with `resolve_batch` reads a service snapshot of the plan, historical batch, report hashes, membership and required Git edges. The client fetches missing commits from the common remote and verifies ancestry locally. The service compares the exact inspected originals again in the resolution transaction, then publishes the plan copies, audit and receipt atomically under the authority of any review write. Historical CWD bytes remain unchanged; they identify old evidence rather than the client's checkout.

Joint retries preserve the original verified payload while it waits for confirmations. Rechecking the same immutable Git edges at another time does not create a new proposal solely because the verification timestamp changed. The client sends the exact material each holder confirmed. A substantive fact, revision or generation change requires a new proposal.

An audited terminal member exclusion lets runtime uploads continue for the remaining live generations. It does not exempt a member that was merely taken over, lost, or completed without an exclusion. Final publication still needs current remaining-holder authority and never rewrites an excluded card.

An already published operation replays its immutable result even if publication advanced the card versions or a member later left. Replay validates the original operation and material and performs no producer write. A still-prepared operation continues to require current confirmations; an old approval never authorizes another generation.
