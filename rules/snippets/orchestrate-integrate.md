# Orchestrating a Task Group: Integration and Wrap-Up

Source: moved from `KANDER-TASK-GROUP-RULES.md` "Merge-Back and Cleanup Preconditions", the orchestrator's part of "Integration and Wrap-Up", "Orchestrator Wrap-Up on Behalf", and "Cleanup Failures".

## Group Integration Branch

**Merge-Back and Cleanup Preconditions**

- Once all deliveries are in the group branch, all members have reached at least `review/`, and applicable reviews are complete, the orchestrator checks integration authorization per the Git rule file `snippets/git-integrate.md` "Integration and Cleanup". It then rebases onto the latest `develop`, re-verifies, and merges back. Successor groups in the same orchestration unlock once every member of this group has entered `done/` and its final group HEAD is confirmed in `develop`. Never wait for all groups before integrating.
- The orchestrator records the group HEAD before and after integration and the mapping to each card's commit. When `develop` advances, the one-time review gate applies.
  - The bound wrap-up evidence accepts the rebased group line only when its complete patch equals the closed reviewed patch. After a rebase that applied cleanly, compare the complete patch of the reviewed range with the rebased range before pushing, normalizing only index lines and hunk offsets (the same comparison the wrap-up evidence applies). A differing patch, for example from changed context lines upstream, is handled exactly like a conflict.
  - When any commit conflicts or the patch differs, abort the rebase and keep the reviewed group HEAD. The orchestrator then resolves the conflict itself, in a merge commit, which leaves the reviewed history and patch intact. In the group worktree, merge the latest `develop` into the group branch and resolve feature point by feature point per `snippets/git-integrate.md` "Integration and Cleanup" without replacing whole files. Then re-verify, push the group branch, and fast-forward `develop` to the merge commit. The wrap-up evidence then uses the closed final target as `source_commit` and the merge commit as `target_commit`, with no `rebased_base`.
  - A merge whose hand-resolved conflicts touch only Markdown or other non-code files needs no review. When a conflict in a code file was resolved by hand, the merge commit is reviewed before `develop` moves: a new batch in the still unsealed plan, from the closed final target to the merge commit. With a sealed plan, or when the resolution would change a user-set direction or an external contract, keep the group state and report with numbered options: `1. Integrate as resolved`, `2. Stop integration and keep the group state`.
  - Record the conflicting paths, the resolution, and the verification in the group working state and the `Integration` field of the orchestration summary. This is the only conflict the orchestrator resolves and the only code it writes; it never rewrites delivered group history and never dispatches executing agents to do so.
- Before cleanup, confirm the final group changes have entered the actual local or remote `develop`: for direct integration `git merge-base --is-ancestor` with the post-rebase group HEAD; for a PR the merged criteria from the Git rule file.
  - The wrap-up evidence needs a Git mapping binding the range from the first planned batch's base to the closed final target of the last batch (`snippets/review-evidence-gate.md` "Review Evidence Completion Gate"). When `develop` contains the group history unchanged (fast-forward without rebase, or a merge commit), `source_commit` is that closed final target. When history was rewritten (integration rebase then fast-forward, or a squash or rebase merge), `source_commit` is the last replayed commit on `develop` and `rebased_base` is the parent of the first replayed commit. In that case the evidence passes only when the complete patch of the replayed range equals the closed range's patch. Choose the PR merge method with that in mind. If not satisfied, keep the group and task working state and report.
- Once satisfied, dispatch the original executing agents to clean up their own working state per "Integration and Wrap-Up"; the group worktree and branches are removed per "Cleanup Failures" after all of the group's cards enter `done/`.

### Integration and Wrap-Up

- Once the group meets "Merge-Back and Cleanup Preconditions", the orchestrator completes the authorized integration and local sync per the Git rule file `snippets/git-integrate.md` "Direct Integration and PRs", recording N/A for review when disabled. Never merge back while any card of the group is still in `working/` or has an unreceived delivery; receiving other ready deliveries continues meanwhile.
- When integration fails (rebase, verification, push, or ff incomplete) or the user asks to pause or not merge back, all in-group cards stay in `review/`. In that case, the group branch, task branches, and worktrees are kept, and the orchestrator records the blocker and the release conditions and reports card by card per the enabled `KANDER-REPORTING-RULES.md` template (truthfully when disabled) with the state `review (blocked)`. Use `notify` only for genuine dispatch items (task branch sync, rebase conflicts, review findings, wrap-up after successful integration). The original executing agent moves itself back to `working/`, and the orchestrator never moves cards by hand to signal a blocker.
- After successful integration, dispatch the original agents to wrap up in dependency order, in parallel when there is no conflict, using only `kander notify <task-id> --kind wrap-up --evidence-file <JSON> --base <source_commit> --message-file <wrap-up notice>`, passing the evidence's `source_commit` as `--base` because the default base is the HEAD of the current directory. The only other entrance that creates a wrap-up intent is `dispatch authorize-wrap-up` under "Orchestrator Wrap-Up on Behalf"; a same-ID `resume --agent` follows the command protocol's user-authorization rule.
- The notice states how the group branch was integrated into `develop`, the full SHA, and this card's final commit (with the before/after mapping when a rebase rewrote it). It also states role conclusions or N/A, applicable batches and fix rounds, this card's unresolved items, and the `snippets/wrap-up.md` "Executing Agent Wrap-Up" checklist. For PR integration, it also states the PR identifier, merged status, and target branch evidence. The orchestrator never modifies card bodies or moves cards by hand. When dispatch is impossible, go through the gate in "Orchestrator Wrap-Up on Behalf"; impossibility alone grants nothing.

**Orchestrator Wrap-Up on Behalf**

- When a wrap-up does not close, the orchestrator may complete that card's wrap-up and report as the one who finished it, but only after the durable wrap-up authority gate grants it. The triggers that lead to the gate, none sufficient on its own, are: no usable `WINDOW`/`SESSION` record; `notify` exited non-zero; the executing agent exited after the dispatch-back and the card has not entered `done/`.
- Each trigger only starts reconciliation: reconcile the same dispatch, create a bound wrap-up intent when absent, and apply `kander dispatch authorize-wrap-up <request.json>` only after confirmed executor exit or an already-authorized reclaim followed by a valid stopped observation. A missing SESSION/WINDOW, a nonzero notify result, a timeout, or an expired lease alone grants nothing. When exit cannot be established, preserve the card and report.
- Keep the original OWNER and author conclusions. Record the actual on-behalf author and reason in the dedicated grant, accept its new epoch, and use only its cleanup and append-only record scope; never send a wrap-up-only token to another executor or upgrade it to ordinary code authority. Complete with the same dispatch and verified integration source; the original completion and review gates stay in force. State "wrap-up done by the orchestrator on behalf" and the reason in the `Wrap-Up` part of the card's completion report and in the `Wrap-up` field of the orchestration summary.
- This is the only exception to "not fixed by the orchestrator on its behalf" in `snippets/orchestrate-review.md` "Review Batches and Dispatch-Back": wrap-up changes no code. Findings that require code changes are never fixed by the orchestrator.

**Cleanup Failures**

- When cleanup fails partway (a card's branch or worktree deletion fails): cards already in `done/` stay there. The failed card stops in its actual state (`working/` if wrap-up was dispatched, `review/` if not), keeping only the worktree and branch that still remain; the group branch is kept. Report card by card by real state. For the failed card, give the failed step, the error, and the release conditions, with the state `working (blocked)` or `review (blocked)`. The code is already in `develop`, so never re-integrate. After release, only continue the unfinished wrap-up.
- After all members of a group enter `done/`, stop that group's subscription, delete the group worktree, local group branch, and applicable remote group branch, and continue scheduling the remaining groups. After all groups finish wrap-up, run `kander check` once without targets; success counts only when the full check passes. When any card enters `archived/` with a result other than `completed`, or `trash/`, wait for the user to change the group contract or terminate the group.
- At the end of orchestration, issue the orchestration summary once. With `rules.reporting=true`, use the `KANDER-REPORTING-RULES.md` "Orchestration Summary" template and its field rules. With reporting disabled, give the same content truthfully in free form: the execution order, parallelism, applicable review batches and rounds or N/A, and integration results; then per card (with its task ID) the known defects, verification gaps, follow-up tasks, and the blockers resolved on the orchestrator's own decision per `snippets/orchestrate-sessions.md` "Handling Blocked Executing Agents"; write "None" when empty. Only when review applies, also classify unresolved review items per `KANDER-REVIEW-RULES.md` "Conclusions and Failure Handling". On termination, report the unfinished cards one by one per the enabled `KANDER-REPORTING-RULES.md` completion report template (truthfully when disabled), then issue the orchestration summary with the termination decision.
- The orchestrator asks once whether to exit the executing agents and close their herdr tabs or tmux windows. It asks only when all in-group cards have entered `done/`, all group worktrees and branches are deleted, `kander check` has passed, and the orchestration summary has been issued. The question uses numbered options such as `1. Dismiss the executing agents and close the corresponding containers`, `2. Keep the sessions and containers`; a text reply with the same clear intent is valid. Without explicit confirmation, perform no exit or close action; if the user declines, keep everything and end the orchestration.
- After confirmation, call `kander dismiss <task-id>` exactly once per in-group card; never send exit instructions to agents or close windows directly, and never bypass the command's identity, topology, and graceful exit gates. Each result is independent: on a non-zero return keep that card's working state, record the reason, and continue with the rest; then summarize per card. This is optional terminal cleanup; failure rolls back no completed card, restores no deleted branch or worktree, and changes no report already issued.
