# Executing a Task Group Member

Source: moved from `KANDER-TASK-GROUP-RULES.md` "Git Branches and Worktrees" and the executing agent's part of "Delivering a Task Branch to the Group Branch".

This snippet extends `snippets/execute-single.md`: read that one first, then this one. It covers what a task group member does differently: its branch comes from the group branch, it delivers to the group branch and waits for `notify`, and it never integrates. When the member-card start entry of `snippets/orchestrate-start.md` "Entering Through a Member Card" makes this agent the orchestrator instead, read `snippets/orchestrate-start.md`.

## Git Branches and Worktrees

- A single card's executing agent creates a dedicated task branch and `<repo-root>/worktrees/<task-name>/` worktree per the Git rule file, with its integration target (`KANDER-GIT-RULES.md` "Branches and Worktrees") as the source branch.
- A task group uses two layers: the orchestrator holds the group branch `group/<task-group-id>` and the worktree `<repo-root>/worktrees/<task-group-id>/`, used to receive deliveries, run group-level verification and applicable reviews, and integrate. Each member's executing agent still creates its own task branch and worktree.
- In-group task branches are created from the latest group branch, with `group/<task-group-id>` as the source branch, not from the mainline branch; on the remote path fetch `origin/group/<task-group-id>` first. Other naming, paths, and user change protection follow the Git rule file.
- The executing agent changes only its own card's worktree and does its own rebases and conflict fixes there. The orchestrator operates only on the group worktree and the integration target and never modifies task branches or code on a member's behalf.

**Delivering a Task Branch to the Group Branch**

- After implementing, verifying, and committing by concern, the executing agent rebases its task branch onto the latest group branch, re-verifies, and updates the task branch per the Git rule file; in distributed mode that means committing in the worktree, because the move into `review/` publishes the delivery and nothing is pushed. Between deliveries it keeps the branch current per `snippets/git-sync.md` "Keeping a Task Branch Current" with the group branch as `SOURCE`, which also fixes the re-verification scope; the final delivery commit carries the full verification. Record in `IMPLEMENTATION` the task branch's final full SHA, the group branch SHA it is based on, and the verification result. Tick each met acceptance criterion as `- [x]` through update and leave an unmet one as `- [ ]` with the reason in `IMPLEMENTATION` (`snippets/card-content.md` "Contract and Records"), then `move review` and end the current response turn. The executing agent never updates the group branch.

## Author Records After a Rebase

A rebase rewrites commits. An author record with status `fixed` names a `fix_commit`, and `kander review close` needs that commit in the history of the batch. This section applies when both of these hold: this card has a latest `fixed` record in a batch that is not closed, and a rebase in this round rewrote commits of the task branch. A sync round, a fix round, and a self-executed group all meet it. Do the steps below after the last rebase of the round and before `kander move <task-id> review`.

**Finding the Records to Check**

- Read the `REVIEWS` index of the card with `kander show <task-id>`. Each line gives a run ID and its `batch_id`.
- A batch is not closed when `kander show --document reviews/batches/<batch_id>/closed.json <task-id>` fails with the error code `not_found` (with `--json`, the `error.code` of the failure; the card itself exists, because the `REVIEWS` index named the batch). Keep only the runs of those batches.
- Take the record IDs from the card-relative record paths that `IMPLEMENTATION` holds (`snippets/fix-round.md` requires them). When a path is missing, stop the correction and report the gap to the orchestrator, who decides from the review records of the batch. Never guess a record ID. Never list a directory through the path that `kander show` prints.
- Read each record with `kander show --document reviews/<run_id>/dispositions/<record_id>.json <task-id>`. For each `(run_id, finding_id)`, follow `previous_record_id` to the last record of the chain, and keep it when its `status` is `fixed`. `kander review progress` lists no author records and cannot replace this step.
- For each kept record, run `git merge-base --is-ancestor <fix_commit> <new delivery commit>`. The record is invalid when the exit code is not 0, or when the commit no longer exists in the repository. When the orchestrator's message names a record with a failed relation from `kander review close`, check exactly that relation, with the same two commits in the same direction. A relation that says the `fix_commit` is the reviewed commit of its run is checked by comparing the two commits for inequality, because `git merge-base --is-ancestor` accepts equal commits. A record that passes every check needs no correction.

**Appending the Correction Record**

- Append one correction record for each invalid record through `kander review disposition` (`snippets/orchestrate-review.md` "disposition"). Use a new `record_id`. Set `previous_record_id` to the invalid record. Keep the `status`. Set `fix_commit` to the rewritten commit that carries the same fix. In `basis` and `verification`, write the old commit, the new commit, the result of the `git patch-id --stable` comparison, and the ancestry check. Add the `authorization` of this round when the card has an active dispatch; a correction round of distributed mode always has one. Only the current `OWNER` appends records, and an earlier record is never edited.
- Default mapping: the new `fix_commit` is the commit whose `git patch-id --stable` equals that of the old `fix_commit`.
- Re-check path: use it when the correction names another commit (for example the old record named the branch head, and another commit carries the fix), or when the commits do not map one to one (a conflict resolution changed the patch, a commit was split or merged, or a commit was dropped because the source branch already holds the fix). Verify the finding again on the new delivery commit per `snippets/fix-round.md` "Main Agent Verification Duty", and write the evidence that the chosen commit carries the fix in `basis`.
- The new `fix_commit` must satisfy every Git relation that closing needs. It is a strict descendant of the reviewed commit of its run. It is an ancestor of the batch target. For a must-fix finding of a run that is not the conclusion run, it is an ancestor of the reviewed commit of the conclusion run. For a mechanical fix of the conclusion run, it is an ancestor of `passed_at`. Never name a commit outside the batch history. The new delivery commit stands for the batch target here: the orchestrator receives it onto the group branch, and `kander review close` checks the relations again.

**A Sync Round for Corrections Only**

- Use these steps when the sync message asks only for correction records, because the task branch needs no rebase. Do not rebase, commit, or push. Append the correction records. Write one `IMPLEMENTATION` entry with the card-relative paths of the records and the unchanged delivery commit. Then run `kander move <task-id> review` with the unchanged delivery commit as the delivery commit. When a record the orchestrator named passes every check, correct nothing for it and say so in the `IMPLEMENTATION` entry: the cause is then in the close request, not in the record.

**Distributed Mode**

- The section above applies in distributed mode with these differences. The task branch is not pushed, so no step pushes it, and the delivery of a round is the commit that `kander move <task-id> review` publishes. A correction round starts as a proposal: the holder first runs `kander dispatch prepare` for it and then the bound `kander move <task-id> working --dispatch-id <id> --execution-epoch <epoch>` (`snippets/commands/notify.md` "Holder steps for a proposal"), and every correction record carries the `authorization` of that round. In a round for corrections only, the `kander move <task-id> review` that ends the round registers the unchanged delivery commit again for the current card version, under the current execution generation of the holder (`snippets/commands/dispatch.md` "Distributed authority"). It publishes the immutable reference of that generation only when the reference does not exist yet. That is expected: it creates no new commit, and no step pushes the task branch.
