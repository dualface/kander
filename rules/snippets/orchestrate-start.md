The later phases of a task group are `snippets/orchestrate-review.md` and `snippets/orchestrate-integrate.md`; `KANDER-LOADING-RULES.md` "Phase Snippets" lists them.

## Task Orchestration

**Entering Through a Member Card**

- A request to start a specific card first reads that card's `TASK_GROUP` and `PREREQUISITES` before claiming it. When `TASK_GROUP` is non-empty, also read every member of the group and resolve the complete dependency graph. Never treat the card as standalone.
- Verify each prerequisite per "Dependencies Between Task Cards": an in-group predecessor must have its latest delivery accepted into the group branch, an out-of-group card or group must be complete in `develop`. A column name alone is not evidence.
- Before assuming orchestration, inspect the durable coordinator record and any group working state and reconcile it under "Durable Coordinator Recovery". Another live coordinator remains the orchestrator. Never displace its claim, create a competing orchestration, or launch another copy of a member.
- If any prerequisite is unmet, or the group has no recorded working state from "Creation and Reuse", the current agent becomes the orchestrator once the coordinator claim permits. Treat the start request as an instruction to start or continue the group orchestration, not as permission to bypass a dependency. Never ask the user to choose another member or restate the request. The new orchestrator follows "Starting and Subscribing" through group review, authorized integration, wrap-up, and successor groups, and never starts the requested card before it becomes ready.
- If the group already has a working state and the requested card's prerequisites are satisfied, use the reconciled coordinator state before starting it. Never create a second group branch or launch the same member twice.
- For a task with only a single card, starting, manual claiming, and the tracking responsibilities of different launchers follow `snippets/commands/start.md` "Choosing the Card and Coordinating After Launch" and `snippets/execute-single.md`. The executing agent verifies delivery preconditions, creates the dedicated worktree, implements, verifies, runs applicable reviews, and integrates back into the source branch under obtained authorization. Without authorization or with an unmet gate, it keeps `working/`, records the pending items, and reports.
- For a task group, the current agent becomes the orchestrator and schedules all groups and cards by dependency. It integrates and wraps up each group under obtained authorization once its gates are satisfied, and unlocks successor groups. After the whole orchestration, it summarizes per `snippets/orchestrate-integrate.md` "Integration and Wrap-Up" and asks whether to dismiss the executing agents. When the session also executes the members itself, `snippets/self-executed-group.md` "Self-Executed Groups" applies.

### Roles and Responsibilities in a Task Group

- The orchestrator validates dependencies and creates and cleans up the group branch and worktree. It fast-forwards task branch deliveries onto the group branch and releases dependencies after verification. It subscribes to notifications. It inspects executing agents at every heartbeat and resolves or escalates blockers per `snippets/orchestrate-sessions.md` "Handling Blocked Executing Agents". It arranges reviews, summarizes results, and dispatches findings back. It integrates and wraps up the group.
- The orchestrator does not implement subtasks or modify subtask code, worktrees, or commits; `snippets/orchestrate-integrate.md` "Orchestrator Wrap-Up on Behalf" allows cleanup and records only. A self-executed group (`snippets/self-executed-group.md` "Self-Executed Groups") is the one case where a single session holds both roles.
- The executing agent of an in-group card prepares its workspace, implements, verifies, commits by concern, and rebases, re-verifies, and updates the task branch per `snippets/execute-group-member.md` "Delivering a Task Branch to the Group Branch". It writes the delivery, acceptance, and verification parts of `IMPLEMENTATION` and `SUMMARY`, and fills in `TASK_BRANCH` and the final delivery SHA. It runs `kander move <task-id> review`, then ends the current response turn and keeps the interactive CLI session. It neither exits the process nor closes the terminal container ("Exit" in the task file means the same; when a non-interactive invocation ends naturally, later recovery is left to `notify`). It then waits for `notify`. On a wrap-up notice it completes the wrap-up, reports, ends the turn, and keeps the session; otherwise it acts on the notice.
- The executing agent does not trigger reviews, update the group branch, merge it back into `develop`, or clean up its worktree and task branch before the wrap-up notice.

### Starting and Subscribing

- Before starting, the orchestrator reads all of the group's cards: verify IDs, dependencies, contracts, and modification scopes, parse every `PREREQUISITES`, and classify the direct references into in-group cards, out-of-group cards, and out-of-group groups. Run `kander check <all member task-ids>...` as a targeted check. Missing cards or group references, dependency cycles, or resource conflicts that cannot be isolated block the affected cards; preserve the working state and report. Environment problems that do not affect start conditions are only recorded. An unavailable agent, launcher, configuration dependency, board, or required Git workspace still blocks, and the `start` pre-checks are never bypassed.
- Use `kander move <task-id> todo` (or `kander pick`) to move confirmed `backlog` cards into `todo/`; the transition requires the `SELF_REVIEW:` and `CARD_REVIEW:` records from "Task Splitting and Task Groups". Cards already in later states stay as they are.

**Waiting for External Dependencies**

- While out-of-group dependencies are unmet, never create the group branch or start cards; the not-yet-started group stays in `todo/`, and cards in later states during recovery keep their state.
- Tell the user the gap and the dependency targets, then wait by reading the subscription file of a background `kander subscribe <task-group> <all member task-ids>... --watch <out-of-group task-id|task-group-id>...` per `snippets/commands/subscribe.md` "Reading the event stream", repeating `--watch` per direct reference. `--watch` is only for targets outside this orchestration. A prerequisite group owned by the same orchestrator releases its successor per `snippets/orchestrate-integrate.md` "Merge-Back and Cleanup Preconditions". A prerequisite standalone card handed to the same session is followed through that session's own card subscription, whose events trigger the same `develop` containment check.
- After an out-of-group card reaches `done/` (or `archived/` with `RESULT: completed`), or all members of a referenced group do, apply the `develop` containment check of "Dependencies Between Task Cards". When a watched card enters `archived/` with any other result, or `trash/`, stop waiting and hand the decision to the user.
- State events trigger targeted re-checks of external dependencies. With no `working/` members, the heartbeat only confirms the subscription is alive; when resuming with `working/` members present, check their `liveness` per "Handling State Changes" and never take over out-of-group agents.
- Once all external dependencies are satisfied, stop this waiting subscription, create the group working state from the then-latest `develop` per "Creation and Reuse", and start. When the same orchestrator also owns the prerequisite group, keep advancing it; a successor's waiting subscription does not stop that scheduling. With no external blocker, create the group working state directly before starting the first card.

**Starting Ready Cards**

- Start each ready `todo` card with `kander start <task-id>`; the agent comes from configuration by card scale, the launcher defaults to the configuration, and `--launcher` overrides only this run. Use one launcher within a group; when it is unavailable on the current platform, report the blocker.
- In the first round, start cards with no in-group `PREREQUISITES`; afterwards start only cards whose in-group prerequisites are all in `review/` or `done/` with their latest deliveries in the current group branch. Start cards that are ready at the same time and have no file-level resource conflicts (per "Running Task Cards in Parallel") in parallel; never start early by skipping dependencies.
- The task file for `start` is written by the command with the task ID and fixed requirements; the orchestrator appends no card body and fabricates no other task context. The executing agent learns it follows the task group flow from the card's `TASK_GROUP` field and these rules.
- Immediately after the first card starts, tell the user that this session is the task group orchestrator and must be kept until all groups in this orchestration have run in dependency order. Also tell the user that ending early loses dependency validation, ordered starts, applicable group-level reviews, and integration. The session lasts until the orchestration succeeds or the user explicitly terminates it.
- After the first round starts, the orchestrator reads the subscription file of a background `kander subscribe --heartbeat 600 <task-group> <task-id>...` per `snippets/commands/subscribe.md` "Reading the event stream". The file holds first a `snapshot`, then a `state-change` per state change. Each `state-change` carries the group ID, the states before and after, and a snapshot of the whole group. Use the initial snapshot to catch up on moves made before subscribing. Never rely on historical events.

**Handling State Changes**

- Consume versioned subscription facts as observations and feed each into the coordinator checkpoint per "Durable Coordinator Recovery". A `task-update` requires re-reading the affected delivery record even when its state is unchanged; revision is not a dispatch completion receipt. On restart, compare the new snapshot with saved task revisions and membership versions, not the process-local sequence number.
- A `membership-change` requires re-checking the complete dependency set; a removed or regrouped member never automatically satisfies its former obligation. When `reconciliation_required` is true, reconcile the contract and delivery before releasing dependencies. A terminal `membership-unknown` or `read-error`, or `membership_complete: false`, stops dependency release for that subscription: preserve the last facts, report the diagnostic, and follow explicit recovery requirements; never infer completion from omitted tasks or repair the board automatically.
- On a `state-change`, run `kander check <task-id>...` only on the changed card and the direct successors it may release, read those cards, and verify dependencies. `review/` cards in the initial snapshot get the same delivery verification. A card entering `review/` is first received per "Delivering a Task Branch to the Group Branch", also when review is disabled; only after success decide whether successors are ready, and start them with `kander start` in the established order. A received `review/` card enters the pending review set when review applies; otherwise it waits for the group integration gate.
- A bound wrap-up closes only when the same dispatch ID/epoch has a completed receipt binding the final delivery and integration evidence, and the card is `done/`. A snapshot can prove this after a fast round trip or restart; the column alone cannot.
- After a new member starts or a card is dispatched back via `notify`, restart the subscription with `--heartbeat 600` naming the explicit set of members that still need monitoring, and continue from the new initial snapshot.
- The subscription emits a `heartbeat` every 15 minutes by default. The orchestrator always subscribes with `--heartbeat 600`, so it checks every executing agent every 10 minutes, handling each heartbeat per `snippets/orchestrate-sessions.md` "Handling Blocked Executing Agents". Slow probes do not block scanning. Output backpressure beyond the bounded queue terminates explicitly; after that, reconnect and reconcile the new snapshot. Read the `liveness` carried by the event directly, checking revision/identity, observation age, validity, and collection state. Pending, uncollected, and stale observations remain `unknown`. `alive` proves presence only and extends no deadline. `stopped` or `drifted` is handled per `snippets/failure-recovery.md` "Failure Recovery" (unbound and bound cards differ there). `unknown` is handled per `snippets/orchestrate-sessions.md` "Handling Blocked Executing Agents".
- While handling heartbeats and state events, never run a board-wide `kander check` or re-read unrelated cards; the single untargeted `kander check` in `snippets/orchestrate-integrate.md` "Integration and Wrap-Up" runs only after every group has wrapped up. Agent messages or user input may trigger an extra liveness check of the same scope without changing the next heartbeat.

**Handling Blocked Executing Agents**

- Handle every heartbeat per `snippets/orchestrate-sessions.md` "Handling Blocked Executing Agents": inspect each monitored card's liveness, latest `IMPLEMENTATION` entry, and pane tail, resolve blockers within the limits stated there, and report the rest to the user in this session.
- Between state events, keep reading the subscription file per `snippets/commands/subscribe.md` "Reading the event stream"; short-period polling of the board, the cards, or the executing agents is forbidden, and the 10-minute heartbeat is the only periodic check of them. Waiting on the subscription file itself follows that section. Only a new complete line in that file (a state event, a heartbeat, or a terminal error) or an explicit failure or exit of the subscription process triggers handling; no new line and long waits are not anomalies. A running process whose file has not been read is not handled.

## Group Integration Branch

**Creation and Reuse**

- The orchestrator first confirms the whole group's external dependencies per "Starting and Subscribing" and initializes `main` and `develop` per the Git rule file. Once all external dependencies are satisfied, create the group branch and worktree before starting the first card. With `origin` and not local-only, fetch, create from the latest `origin/develop`, and `git push -u origin group/<task-group-id>`. Otherwise, create from the local `develop` and report that the remote is not synced. If the fetch or creation fails, preserve the working state and never start members.
- Record the group branch, the group worktree path, and the full `develop` SHA used for creation. That SHA is the group's anchor and doubles as the first batch's review base when review applies. When resuming orchestration, verify and reuse the existing group working state. Never overwrite the branch or regenerate the anchor.
- Pre-plan sync: while no review plan exists and no member is inside a sync round, the orchestrator may move the anchor forward. To do so, it rebases the group branch onto the latest `origin/develop` (local `develop` on the local path) and updates the remote group branch with `--force-with-lease`. This is the only rewrite of a group branch that `snippets/git-integrate.md` "Integration and Cleanup" allows.
  - The sync is required when `develop` gained commits that touch files the group changes (the overlap check of `snippets/git-sync.md` "Keeping a Task Branch Current" with the group branch as `HEAD` and `develop` as `SOURCE`). Run that check at the latest right before the review plan is created. Without such overlap the sync is optional.
  - Record the new and previous anchor SHAs in the group working state. Then dispatch every member with an already received delivery through the `sync` round of "Delivering a Task Branch to the Group Branch" so it re-delivers on the new head. Members still working rebase onto the new group head at their next sync point.
  - The orchestrator resolves no conflicts on the group branch: when the rebase conflicts, abort it and keep the old anchor. It may then reset the group branch to the new anchor with no deliveries on it and dispatch `sync` rounds in dependency order, so each member rebases its own task branch, resolves its own conflicts, and re-delivers. This reset is allowed only while the plan does not yet exist and every member with a received delivery has a live executing agent. When these conditions do not hold, keep the old anchor and report.
- Once the review plan exists, never rebase the group branch before final integration and never rewrite reviewed group history. The base chain for review batches is maintained per the review rule file and starts at the anchor recorded at plan creation.

**Delivering a Task Branch to the Group Branch**

- On receiving `review/`, the orchestrator reads the delivery record and verifies integration authorization and that the task branch head (remote branch after a fetch on the remote path, local branch otherwise) matches the recorded final commit. Deliver that commit to the group branch per the Git rule file `snippets/git-integrate.md` "Direct Integration and PRs" and sync the group worktree. On the remote path, push the final commit first and ff the local group branch only after success. When the same commit is already contained, only verify and sync. Without authorization, keep `review/` and the working state, report, and never release dependencies.
- When the group branch has advanced and the task branch cannot ff, the orchestrator calls `kander notify <task-id> --kind sync --message-file <sync requirements>` once per logical dispatch (see `snippets/orchestrate-review.md` "Durable Dispatch Identity") to have the original executing agent rebase, resolve conflicts, and re-verify. If `notify` exits non-zero, stop and report. After the new delivery returns to `review/`, verify again. Never carry the old delivery's conclusion forward.
- First confirm that the card's latest delivery commit is in the actual local or remote group branch. Also confirm that the group worktree is synced to that head. Only then does the orchestrator add the card to the pending review set or release its direct successors. If the push, ff, or verification fails, keep `review/` and the working state and release nothing. If the group branch shows unexpected changes or divergence, report and never overwrite the remote or rewrite reviewed history.
- Deliveries are received serially, without merge commits. When review applies, no batch opens before every member has started, because closing a batch needs the review plan and the plan can be created only then; until then deliveries are received freely in dependency order. Afterwards receive only while no batch is open. Each batch covers all deliveries received since the previous closed target up to its HEAD. Nothing else is mixed into the group branch while it runs, because closing needs the worktree clean at its final target. Other `review/` cards queue until the batch closes; in-batch fixes are received after the reviewer exits and then re-reviewed. A single received large delivery may open a batch immediately only when no other independent delivery is ready to receive; never hold a ready delivery merely to manufacture serial per-card batches. Without review, receive directly in dependency order.

**Topology Freeze**

- While any review batch of a group is open, the orchestrator never re-splits the group, adds members, moves cards between groups, changes a card's owner, or accepts a contract change. A user-authorized takeover of a card whose executing agent has stopped (`snippets/failure-recovery.md` "Failure Recovery") is not such an owner change: it proceeds inside the open batch, and the successor OWNER continues the fix round and its dispositions.
  - A user request for any of these first closes the open batch. To close it, its remaining required roles still run on the current target, before the change is applied. Findings the pending change supersedes are disposed as `rejected` with the user's quoted decision and stay on the unresolved list. A batch in which a reviewer has run is never abandoned, because every planned batch must close before its members can complete. After the close, the request applies the change and starts a new batch in the same still unsealed plan, reviewing only the work after the closed target.
  - Re-reviewing the closed range under the new contract, a change that alters the base chain, or a change after the plan is sealed, continues as new cards per `snippets/orchestrate-review.md` "Group-Level Review for Task Groups".
  - Applying such a change mid-batch invalidates the batch and is reported as wasted rounds, never silently absorbed.
  - The review plan fixes the group's members and worktree when created: it cannot take a new member later or follow a card into another group. Work discovered afterwards becomes a successor group or an independent card, and a re-split after the plan exists means terminating the affected cards under the user's decision and creating new ones; report both as topology changes.

### Durable Coordinator Recovery

- The commands and their JSON are in `snippets/coordinator-checkpoints.md` "Coordinator Checkpoints". Before recording group progress, run `kander coordinator claim` with the explicit full member set (waiting members included), a unique session token, owner, and authority basis. On recovery, read `coordinator show <group-id>` and CAS-claim its current revision/epoch with a new token only under existing coordination authority, never repeatedly to override another live writer. The token fences checkpoint writes only and grants no takeover, integration, transport, or cleanup authority. A checkpoint never grants on-behalf wrap-up (only the fenced `dispatch authorize-wrap-up` grant does).
- Feed every observation (initial snapshot, task update, state change, heartbeat or attention event, subscriber restart) through `kander coordinator reconcile` with the same full member set and each expected dispatch ID/epoch/base, naming the exact receipt delivery SHA for completed rounds. Events wake the consumer; sequence numbers, state strings, and column names are never completion evidence, and stale epochs, revisions, wrong rounds, unknown members, or damaged originals stop the affected reconciliation.
- A start attempt is not a start: launcher metadata keeps the member waiting until its durable success result exists, rollback evidence restores waiting, and an unknown launcher outcome is never promoted to success. A first delivery without a dispatch receipt is recorded only from the task branch, `review/`, an explicit delivery SHA, and its actual branch HEAD in the supplied absolute `cwd`; group reception and dependency release still need their own Git verification. Never invent a dispatch receipt.
- Keep subscription heartbeat, dispatch confirmation deadline, and task progress separate. Receipt acceptance ends confirmation waiting but proves no delivery. No other event renews a dispatch deadline. An alive but unchanged member may need a progress report, never an automatic new executor or fabricated completion.
- On EOF or output failure, reconcile once from current facts and reopen the subscription once when committed facts are valid. Only a diagnosed managed pending transaction enters the explicit `init` maintenance recovery, at most once before rereading. Lock contention or deadline exhaustion is an unavailable observation, not stopped execution; no new line in the subscription file by itself is not a failure. Never retry duplicate entries, reparse points, corrupt records, or unknown artifacts; report and preserve evidence.
- During wrap-up recovery, reconcile the same dispatch and consume its bound integration artifact, role conclusions, immutable author dispositions, sealed plan, and closed batch chain; recheck actual Git ancestry in the recorded repository or a surviving worktree `cwd`. Partly archived completed members keep their receipts: continue only unfinished work, never reintegrate or repeat cleanup. A changed member set or execution cycle requires explicit reconciliation of the governing contract; never drop members or reset an epoch to bypass evidence.
