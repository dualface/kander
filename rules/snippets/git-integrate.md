# Integration and Cleanup

Source: moved from `KANDER-GIT-RULES.md` "Integration and Cleanup".

## Integration Target

- The integration target is the branch a card's delivery finally enters: the mainline branch, or the branch named by the optional header line `- INTEGRATION_TARGET: <branch>`. Syntax: parts separated by `/`, each part starting with a letter or digit and then holding letters, digits, `.`, `_` and `-`; at most 100 bytes; no `..`; no part ending in `.lock` or `.`; never `HEAD`, `refs/...`, or `group/...`. An empty value counts as no line. In `main-develop` mode `main` is not a valid value, because `main` advances only from `develop`. A value equal to the mainline branch works but is redundant. The line sits after `TASK_BRANCH` and is frozen from `todo/` on like the other contract fields (`snippets/card-content.md` "Contract and Records").
- Wherever a rule says "mainline branch" for the branch creation, sync (fetch, overlap check, rebase source), review base, merge-back, dependency containment check, or wrap-up evidence of a card or group, it means that card's or group's integration target.
- Every member of a task group carries the same value. A dependency on an out-of-group card or group is contained when its delivery is in the integration target of the dependent card. Never change the value once a wrap-up dispatch exists.
- A branch named by the field that is not the mainline branch must exist, locally or on `origin`, before `kander pick`. Executing agents and orchestrators never create it or push it first. The mainline branch, also when the field names it, follows `KANDER-GIT-RULES.md` "Initializing Branches" unchanged.
- Wrap-up evidence `target_ref` is `refs/heads/<integration target>` or `refs/remotes/origin/<integration target>`; Kander verifies only the ref the evidence names, so a local-only integration needs no origin ref. `kander check` reports a duplicate or invalid line and group members whose values differ.

## Integration and Cleanup

- Before integrating, verify the authorization per `KANDER-GIT-RULES.md` "Commit and Push" and any PR, acceptance, or pause requirement from the user or project. Without authorization or with an unmet gate, keep the branch and worktree and report the specific pending items; a kanban single card stays in `working/`, and a task group keeps its actual state per the group rules.
- The source branch is the delivery target recorded when the task branch was created. A kanban card records it in the card's `IMPLEMENTATION`; any other task records it in the task's own delivery record. The target is the integration target ("Integration Target" above) for a single card or a group branch, and the group branch (the "group integration branch") for an in-group task branch. Integrate only into that target; the checked-out branch or a temporary rebase never changes it.
- Fetch the target on the remote path or read its local tip on the local path. If the delivery contains the target tip, use the delivery as the candidate. If histories diverge, prepare an ordinary merge in an isolated worktree at the observed target tip and verify the combined tree. If the target already contains the delivery, only finish verification and sync. Stop on a failed required fetch.

**One-Time Review Gate**

- Review is triggered and executed per `KANDER-REVIEW-RULES.md` only when the review module is enabled or the user explicitly asks for a full review this time. Otherwise record N/A and never load the disabled module.
- An applicable review is a one-time gate before integration; the base is frozen during the review. When the source branch advanced after the review, integration keeps the closed reviewed patch intact, for a single card and a task group alike. The integration rebase is used only when it applies cleanly and leaves the patch unchanged: compare the complete patch of the reviewed range (review base..closed final target) with the rebased range before pushing, normalizing only index lines and hunk offsets. Such a rebase only redoes verification. For a single card the executing agent performs this comparison itself; for a task group the bound wrap-up evidence enforces it.
- If an optional rebase conflicts or changes the patch, return to the saved pre-rebase commit and prepare a merge preserving both histories. Resolve conflicts feature by feature and re-verify. After a merge, handle later target advances by merging again. A task group follows `snippets/orchestrate-integrate.md` "Merge-Back and Cleanup Preconditions".
- A merge whose hand-resolved conflicts touch only Markdown or other non-code files needs no review. When a conflict in a code file was resolved by hand, or the user asks, the merge commit is reviewed before the source branch moves: a new batch in the still unsealed plan, from the closed final target to the merge commit. A single card under review therefore keeps its review plan unsealed until integration and local sync succeed, then seals it with `kander review extend-plan` before completing. With a sealed plan, or when the resolution would change a user-set direction or an external contract, keep the working state and report with numbered options in the `agent_language`, with this meaning and order: `1. Integrate as resolved`, `2. Stop integration and keep the working state`. Record the conflicting paths, the resolution, and the verification in the card's `IMPLEMENTATION` or the group working state.
- An explicit N/A plan waives reviewer runs. A group still needs its closed range for wrap-up: preserve its commits in a merge, or prove patch equality for rewritten history before publication.
- For a task group, this gate constrains merging the group branch back into the mainline branch; delivering a task branch to the group branch prepares the group-level review and does not wait for it.

**Direct Integration and PRs**

- On the remote path, push the verified candidate with `git push origin <candidate>:refs/heads/<source branch>` before advancing the local source branch. If the remote advances concurrently, fetch, check for an already integrated delivery, otherwise rebuild against the new tip, re-verify, repeat the applicable group preflight and push normally.
- After a successful push, fetch and run `git merge --ff-only origin/<source branch>` in the worktree that owns the source branch. When the remote already contains the recorded final delivery commit, do only this sync. If the local branch is missing, create it from the remote branch. Verify that the local and fetched tips match even when Git reports already up to date. If the local mainline branch or `main` (`<branch>` below) has commits outside `origin/<branch>` (for example after the remote history was rewritten with `--force-with-lease`), reset the local branch to the remote without losing local work:
  1. When the worktree has uncommitted or untracked changes, save them with `git stash push --include-untracked -m <unique tag>`, record the full SHA of the entry it created (`git stash list --format='%H %gs'`, matched by the tag), and confirm the entry holds everything, per `KANDER-GIT-RULES.md` "Local Change Protection". With a clean worktree, save and restore nothing.
  2. When `git rev-list origin/<branch>..<branch>` is not empty, create the local branch `backup/<branch>-<YYYYMMDD-HHMMSS>` at the old local HEAD and confirm it points there. Never push it, rebase it, or merge it; list its name and commits in the report for the user to decide.
  3. Only after steps 1 and 2 are confirmed and the working tree is clean, run `git reset --hard origin/<branch>`.
  4. When step 1 saved changes, restore exactly that entry: when `stash@{0}` is still the recorded SHA, run `git stash pop --index`; otherwise run `git stash apply --index <recorded SHA>` and, only after everything is confirmed restored, drop that entry, found again by its tag. Resolve conflicts per "Local Change Protection"; never restore an entry this flow did not create.
  When any step fails, stop and report without running the later steps. Any other sync failure (working tree, a group or task source branch, other) preserves the working state, reports "integrated on remote, local not synced", and handles only the sync problem afterwards without resetting or discarding local commits.
- On the local path, publish the verified candidate in the worktree owning the source branch. Compare the target with the tip used to build the candidate. If it moved, rebuild and verify against the latest tip. Fast-forwarding to a prepared merge commit publishes the entire merge. Never push on this path.
- Direct integration accepts both fast-forwards and verified merge commits. Fast-forward-only synchronization after remote publication protects unrelated local work. `main` and the mainline branch never have their remote history rewritten with plain `--force`; `--force-with-lease` is permitted for them under `KANDER-GIT-RULES.md` "Commit and Push", but no step of this flow requires it. A group branch is never rewritten, with one exception: the orchestrator's pre-plan sync in `snippets/orchestrate-start.md` "Group Integration Branch", which uses `--force-with-lease` only while no review plan exists; no other agent and no later stage rewrites it. Save and restore user changes per `KANDER-GIT-RULES.md` "Local Change Protection" around any operation on the main worktree.
- When the user or project requires a PR, follow its review, CI, merge method, and authorization requirements; never bypass it with direct integration. Integration is complete only when the PR is merged, its target is the recorded source branch, and the final delivery is contained in the merge result. Confirm squash and rebase merges by this evidence, without requiring the pre-merge commit to remain an ancestor. For a task group, the durable wrap-up evidence additionally needs the Git mapping in `snippets/orchestrate-integrate.md` "Merge-Back and Cleanup Preconditions".

**Cleanup Preconditions**

- Only after integration, verification, applicable push, and local sync all succeed, verify that the final delivery entered the actual target: for direct integration `git merge-base --is-ancestor <final delivery commit> <origin/source branch or local source branch>` with the full SHA after the integration rebase or of the merge commit, for PRs the merged criteria above. If this cannot be confirmed, preserve the working state and report.
- A single card that meets the preconditions cleans up its task branch and worktree; the remote task branch only on a non-local path. An in-group card keeps its working state after delivering to the group branch. It keeps that state until the orchestrator confirms the whole group entered the mainline branch and sends the wrap-up notice. The orchestrator cleans up the group worktree and branch after the whole group wraps up.
