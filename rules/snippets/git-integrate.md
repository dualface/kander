## Integration and Cleanup

- Before integrating, verify the authorization per `KANDER-GIT-RULES.md` "Commit and Push" and any PR, acceptance, or pause requirement from the user or project. Without authorization or with an unmet gate, keep the branch and worktree and report the specific pending items; a kanban single card stays in `working/`, and a task group keeps its actual state per the group rules.
- The source branch is the delivery target recorded when the task branch was created. A kanban card records it in the card's `IMPLEMENTATION`; any other task records it in the task's own delivery record. The target is `develop` for a single card or a group branch, and the group branch for an in-group task branch. Integrate only into that target; the checked-out branch or a temporary rebase never changes it.
- Before integrating, fetch the source branch (remote path) or read the local source branch (local path), rebase if needed, and re-verify per `snippets/git-sync.md` "Keeping a Task Branch Current". After a review batch closed on the branch to deliver, the "One-Time Review Gate" below decides between rebase and merge commit. If the fetch fails, stop and report. On rebase conflicts, prefer the task branch's changes but never replace whole files outright; resolve feature point by feature point, and ask the user when the resolution would be a major change. After a successful rebase, only the dedicated task branch may `--force-with-lease` its pushed history; if the lease fails, stop and report.

**One-Time Review Gate**

- Review is triggered and executed per `KANDER-REVIEW-RULES.md` only when the review module is enabled or the user explicitly asks for a full review this time. Otherwise record N/A and never load the disabled module.
- An applicable review is a one-time gate before integration; the base is frozen during the review. When the source branch advanced after the review, integration keeps the closed reviewed patch intact, for a single card and a task group alike. The integration rebase is used only when it applies cleanly and leaves the patch unchanged: compare the complete patch of the reviewed range (review base..closed final target) with the rebased range before pushing, normalizing only index lines and hunk offsets. Such a rebase only redoes verification. For a single card the executing agent performs this comparison itself; for a task group the bound wrap-up evidence enforces it.
- On any conflict, Markdown included, or a changed patch, abort the rebase, keep the reviewed HEAD, and integrate through a merge commit. For a single card, the executing agent merges the latest source branch into the task branch in its worktree, resolves feature point by feature point per "Integration and Cleanup" without replacing whole files, re-verifies, and pushes the task branch without force; the merge commit is the final delivery commit. A task group follows `snippets/orchestrate-integrate.md` "Merge-Back and Cleanup Preconditions". Once the branch to deliver holds such a merge commit, a later advance of the source branch is merged again under this gate, never rebased.
- A merge whose hand-resolved conflicts touch only Markdown or other non-code files needs no review. When a conflict in a code file was resolved by hand, or the user asks, the merge commit is reviewed before the source branch moves: a new batch in the still unsealed plan, from the closed final target to the merge commit. A single card under review therefore keeps its review plan unsealed until integration and local sync succeed, then seals it with `kander review extend-plan` before completing. With a sealed plan, or when the resolution would change a user-set direction or an external contract, keep the working state and report with numbered options in the `agent_language`, with this meaning and order: `1. Integrate as resolved`, `2. Stop integration and keep the working state`. Record the conflicting paths, the resolution, and the verification in the card's `IMPLEMENTATION` or the group working state.
- When no review applied (the explicit N/A plan), no reviewed patch exists to keep: the integration rebase resolves conflicts per "Integration and Cleanup" and needs no merge commit.
- For a task group, this gate constrains merging the group branch back into `develop`; delivering a task branch to the group branch prepares the group-level review and does not wait for it.

**Direct Integration and PRs**

- Remote direct integration first pushes the complete commit: `git push origin <final delivery commit>:refs/heads/<source branch>`; never advance the local source branch before this succeeds. When the remote rejects because it advanced concurrently, fetch, bring the branch to deliver onto the latest `origin/<source branch>` per the "One-Time Review Gate" (rebase, or merge commit when the gate requires it), re-verify, and retry; an in-group task branch is handled by its original executing agent, the orchestrator only dispatches back and receives.
- After a successful push, fetch and run `git merge --ff-only origin/<source branch>` in the worktree that owns the source branch. When the remote already contains the recorded final delivery commit, do only this sync. If the local branch is missing, create it from the remote branch. If the sync fails (local divergence, working tree, other), preserve the working state, report "integrated on remote, local not synced", and handle only the sync problem afterwards without resetting or discarding local commits.
- Without `origin`, or with local-only explicit: run `git merge --ff-only <final delivery commit>` in the worktree that owns the source branch. If it fails because the local source branch advanced, bring the branch to deliver onto it per the "One-Time Review Gate", re-verify, and retry; never push.
- Direct integration and local sync never create merge commits, except the conflict-resolving merge commit of the "One-Time Review Gate" (a single card's task branch or the orchestrator's group merge-back). The source branch itself only fast-forwards. `main` and `develop` never have their remote history rewritten with `--force` or `--force-with-lease`. Neither does a group branch, with one exception: the orchestrator's pre-plan sync in `snippets/orchestrate-start.md` "Group Integration Branch", which uses `--force-with-lease` only while no review plan exists; no other agent and no later stage rewrites it. Save and restore user changes per `KANDER-GIT-RULES.md` "Local Change Protection" around any operation on the main worktree.
- When the user or project requires a PR, follow its review, CI, merge method, and authorization requirements; never bypass it with direct integration. Integration is complete only when the PR is merged, its target is the recorded source branch, and the final delivery is contained in the merge result. Confirm squash and rebase merges by this evidence, without requiring the pre-merge commit to remain an ancestor. For a task group, the durable wrap-up evidence additionally needs the Git mapping in `snippets/orchestrate-integrate.md` "Merge-Back and Cleanup Preconditions".

**Cleanup Preconditions**

- Only after integration, verification, applicable push, and local sync all succeed, verify that the final delivery entered the actual target: for direct integration `git merge-base --is-ancestor <final delivery commit> <origin/source branch or local source branch>` with the full SHA after the integration rebase or of the merge commit, for PRs the merged criteria above. If this cannot be confirmed, preserve the working state and report.
- A single card that meets the preconditions cleans up its task branch and worktree; the remote task branch only on a non-local path. An in-group card keeps its working state after delivering to the group branch. It keeps that state until the orchestrator confirms the whole group entered `develop` and sends the wrap-up notice. The orchestrator cleans up the group worktree and branch after the whole group wraps up.
