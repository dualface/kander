# Self-Executed Groups

Source: moved from `KANDER-TASK-GROUP-RULES.md` "Self-Executed Groups".

### Self-Executed Groups

- A group is self-executed only when the user chose the self-execution flow of `KANDER-TASK-INTAKE-RULES.md` (option 1, or a later start instruction for members whose `DISCUSSION` carries the `EXECUTION_MODE: self` line) or explicitly asks the orchestrating session to execute the members itself. That session then holds both roles for every member it claims. A session launched by `kander orchestrate` never self-executes (`snippets/orchestrate-sessions.md` "Orchestrator Sessions"). Without that request the separation stays in force.
- Some clauses in this file, `KANDER-KANBAN-RULES.md`, `KANDER-REVIEW-RULES.md`, and `KANDER-GIT-RULES.md` bar the orchestrator from implementing, fixing, moving, or editing a member card, or from submitting its dispositions. Others require `notify` or a dispatch for a round. Each such clause binds a session that is not the card's `OWNER`. In a self-executed group the session is the `OWNER` of every member it claimed: it does those things as the author, and its dispositions carry `author` equal to the card `OWNER`.
- Only a member that never carried a `DISPATCH_ID` can be self-executed; the binary rejects a plain move on a bound card. A previously dispatched member stays on the dispatch protocol, or is released and reclaimed per `snippets/commands/move.md` "Reclaiming".
- The orchestrator duties are unchanged: dependency validation, the group working state per `snippets/orchestrate-start.md` "Creation and Reuse", `kander coordinator claim` and `reconcile` per `snippets/orchestrate-start.md` "Durable Coordinator Recovery", fast-forwarding each delivery onto the group branch, review batches, integration, and group cleanup. The executing-agent duties also apply per member: its own task worktree and task branch, delivery per `snippets/orchestrate-start.md` "Delivering a Task Branch to the Group Branch", the delivery, acceptance, and verification records, and `kander move <task-id> review`.
- After `kander pick`, claim each member with `kander move <task-id> working --owner <agent>` and implement it, one member at a time. Claim a member only after each in-group predecessor's delivery is accepted onto the group branch; members without such a dependency follow plan order. Member `start`, member monitoring subscriptions and heartbeats, `notify`, `dispatch prepare`, and `snippets/orchestrate-sessions.md` "Handling Blocked Executing Agents" do not apply, and `WINDOW`/`SESSION` stay empty; `snippets/orchestrate-start.md` "Waiting for External Dependencies" still applies.
- There is no event stream, so reconcile after every transition this session performs (claim, `review`, reception onto the group branch, move back, `done`) and on session restart, never with a dispatch ID, epoch, or base. Name `delivery_commit` with the absolute `cwd` only in an observation where the member is in `review/` with a new or re-delivered task-branch head; omit it in every other state, because the checkpoint keeps the last recorded SHA.
- Review batches run as in `snippets/orchestrate-review.md` "Review Batches and Dispatch-Back" with the configured reviewers; holding both roles never makes the session its own reviewer. The review plan needs every member in `working/` or `review/`, so create it after the last member is claimed and open the first batch after the last delivery is received. For every member with assigned items, must-fix or non-blocking, run plain `kander move <task-id> working` (the unbound flow of `snippets/commands/notify.md` "Delivery and Recovery"). Verify each item and fix what is confirmed in the member's task worktree. Submit every disposition while the card is in `working/`, redeliver when code changed, then run `kander move <task-id> review`. Dispositions omit the `authorization` field.
- No wrap-up evidence is produced, so the binary verifies none of it. The session itself performs the patch-equality comparison and the ancestry checks of `snippets/orchestrate-integrate.md` "Merge-Back and Cleanup Preconditions" and records the `source_commit`/`rebased_base` mapping in the group working state and in each member's `SUMMARY`.
- After successful integration, wrap up each member in dependency order in this session: plain `kander move <task-id> working`, then the checks, cleanup, and records of `snippets/wrap-up.md` "Executing Agent Wrap-Up", then `kander move <task-id> done --result completed` and the targeted `kander check <task-id>`. An unbound completion carries no `--dispatch-id`, `--execution-epoch`, `--delivery-commit`, or `--disposition`; the completion and review gates stay in force. No wrap-up notice is sent, `snippets/orchestrate-integrate.md` "Orchestrator Wrap-Up on Behalf" does not apply, and there is no executing agent to dismiss.
- A later user instruction may hand a member that was never claimed to a separate executing agent with `kander start`; that member then follows the ordinary dispatch protocol and the separation clauses.
- When the session stops mid-group, a successor continues only under user authorization and CAS-claims the coordinator per `snippets/orchestrate-start.md` "Durable Coordinator Recovery". A self-executed card has no `SESSION`, so `resume --agent` cannot take it over. A successor session of the same configured agent continues a `working/` member under the recorded `OWNER` from the card, the task worktree, and the Git state. A different agent needs an explicit user decision. A `review/` member is reclaimed per `snippets/commands/move.md` "Reclaiming". A `working/` member is first delivered to `review/` by a session acting under the recorded `OWNER`, or terminated by the user's decision.
