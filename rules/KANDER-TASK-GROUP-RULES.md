# Task Group Orchestration Rules

Task group orchestration is enabled only when `rules.task_groups=true` and `rules.git=true`; task groups always use `KANDER-GIT-RULES.md`, and a custom group integration contract with Git disabled is not supported.

- First read the enabled `KANDER-GIT-RULES.md` and the command protocol `KANDER-KANBAN-RULES.md`. If the configuration does not satisfy the dependencies, keep the cards and workspaces and report which switches need adjusting.
- Without `origin`, or when the user asks for local-only, skip every push and remote branch cleanup in this file and report that the remote is not synced.
- The orchestration plan must spell out the steps for delivering task branches to the group branch and for merging each group back into `develop` in dependency order. Integration authorization follows `KANDER-GIT-RULES.md` "Integration and Cleanup": a plan confirmed through `KANDER-TASK-INTAKE-RULES.md` that names the group and its merge-back step is such authorization, whether the cards start immediately or later; merely starting cards is not. Do not ask again when authorization exists.
- Three clauses apply to the whole file, whether or not review applies:
  - Every `notify` that dispatches a round carries the `--kind` of that round (`sync`, `fix`, `wrap-up`) and, for `fix` and `wrap-up`, the `--evidence-file`; a `--message-file` alone is the legacy spelling and is not sufficient. Status messages and takeovers for `working/` cards follow `KANDER-KANBAN-RULES.md` "Failure Recovery", which distinguishes unbound cards (a plain message without `--kind`) from bound cards (same-ID handling, or a disposed round and a new dispatch). "Once" in this file means one logical dispatch ID: same-ID reconciliation is allowed, exactly-once external side effects are not promised. Column transitions are scheduling hints; verify the dispatch receipt before treating a bound round as accepted or complete.
  - Wherever this file requires `done/`, a card in `archived/` with `RESULT: completed` counts the same; wherever it requires `review/`, a card already in `done/` or in `archived/` with `RESULT: completed` counts the same.
  - Whenever this file says the executing agent "moves back to `working/`", it means the ID/epoch-bound move command from the generated dispatch prompt (`KANDER-KANBAN-RULES.md` "Durable Dispatch"); a plain `kander move <task-id> working` accepts no dispatch and authorizes no work.
- Review batches, dispatching findings back, and review gates apply only when `rules.review=true` or the user explicitly asks for a full review this time. Otherwise do not load `KANDER-REVIEW-RULES.md`: after implementation and verification, enter the group integration flow under integration authorization and the project's delivery gates, record review as N/A, build no review base chain, and satisfy `KANDER-KANBAN-RULES.md` "Review Evidence Completion Gate" with the explicit N/A plan before any member completes.
- The fixed report format is read from `KANDER-REPORTING-RULES.md` only when `rules.reporting=true`; when off, report progress, deliveries, and unresolved items truthfully, and in-card records and state gates still apply.
- External dependencies are satisfied only per "Dependencies Between Task Cards", including its `develop` containment check. External work enters a group only through the group branch's anchor: the branch is created after every member's external dependencies are satisfied, may be synced to `develop` per "Creation and Reuse" before its review plan exists, and picks up no external work after that until final integration.

## Task IDs

- A task ID is `YYYYMMDD-short-slug-task`, unique across the board; it is the file card's entry name without `.md` or the directory card's directory name.
- `short-slug` is lowercase ASCII letters, digits, and single hyphens between them; no leading, trailing, or consecutive hyphens.

## Task Splitting and Task Groups

- Unless the user explicitly asks for a single card or a task group, the agent decides; do not put the choice to the user as a question (presenting the decision inside a plan per `KANDER-TASK-INTAKE-RULES.md` is not such a question). Judge by the number of goals: one goal is one card, however large; several goals are one card per goal. A goal is a result the user can accept on its own; a step that only makes sense as part of another goal gets no card. The only exception is the contract card below. Do not split a goal to pad the count or merge goals to save cards. State the choice and its reason in one sentence, in the plan when intake guidance is on, otherwise when reporting the created cards.
- Each card focuses on one goal and spells out `EXPECTED_OUTCOME` and `ACCEPTANCE_CRITERIA`.
- When the request splits into several cards:
  - Cards form a task group only when they are related: one depends on another, or they share an integration contract that must be verified together. Unrelated goals from the same request become independent single cards.
  - A group should have no more than 3 cards; one above 5 is split into several groups along goals and dependencies. The goal count decides how many cards exist; these counts only decide how they are grouped. A group of 4 or 5 is acceptable only when its dependency chain is linear or its members share one integration contract, with the reason recorded in the `DISCUSSION` of the first card in dependency order; otherwise split it.
  - A task group ID is `YYYYMMDD-short-slug-group`, unique across the board. Each member's `- TASK_GROUP:` metadata holds its group ID; non-members leave it empty. A group is a relationship between cards and adds no board entry or state.
  - Members of one group share the same `LANGUAGE`; create them with the same `--language` or under the same configuration.
- Card count follows goals, not size; choose SIZE per `KANDER-KANBAN-RULES.md` "Task Scale and Grouping", assessing every member independently. Grouping grants no SIZE exemption, and a contract card is always `large`. Clarify shared interfaces or data contracts first; when they need separate delivery, create a contract card as a prerequisite.
- When creating a group, list all members and the dependency graph, and rule out missing references, dependency cycles, overlapping responsibilities, and overlapping files: list for every member the paths it is expected to change (directories are acceptable), and treat two members that share a path as an ordering dependency, not parallel work (see "Running Task Cards in Parallel"). Once in `todo/`, group relationships are frozen per the kanban protocol. The legacy Chinese `任务组: ...` line in `DISCUSSION` on old cards stays compatible as a literal marker.
- After creating the members, complete `KANDER-KANBAN-RULES.md` "Post-Creation Self-Review" card by card; members must also obtain the `CARD_REVIEW:` record from an independent card review (one independent agent may review all members in one session, reading only those cards and the user's original requirement). Then check that the members fully cover the group's goals and the created cards fully cover the request, with no overlapping or missing boundaries, and that prerequisite deliveries satisfy the later cards' constraints and acceptance. Fix and re-check before advancing to `todo/`. `kander pick <task-id>` and `kander move <task-id> todo` are the same transition (`KANDER-KANBAN-RULES.md` "Command Contract"); the orchestrator performs it in "Starting and Subscribing", or the creator performs it right after the checks when the user asked to start immediately.

## Dependencies Between Task Cards

- An in-group card's dependencies on cards or groups are written in a standalone code block at the start of its `DISCUSSION`, field name `PREREQUISITES`, IDs separated by ASCII commas, card and group IDs mixable; `PREREQUISITES: N/A` in the same position when there are none:

```text
PREREQUISITES: 20260905-contract-task,20260905-foundation-group
```

- An old card missing this line has no dependencies. A group reference expands to all current members of that group; referencing the card's own group or forming a cross-group cycle is not allowed.
- An in-group prerequisite is satisfied only when it has reached `review/` or `done/` and the orchestrator has confirmed its latest delivery commit is contained in the current group branch; the column alone does not release it.
- Out-of-group cards and all members expanded from group references must reach `done/` (or `archived/` with `RESULT: completed`) with their deliveries confirmed contained in the current `develop`. An `archived/` card with any other result, or a `trash/` card, never satisfies a dependency; hand the decision to the user. Non-group cards get no automatic dependency resolution; their executing agent verifies delivery preconditions against the task contract.
- Out-of-group references of any member block the whole group, because the group branch is not rebased once its review plan exists and the pre-plan sync of "Creation and Reuse" is the only other point at which external work enters. When one late member would hold up the others for long, move it into a successor group that depends on the external target instead of starting the group early. This regrouping is a planning decision before the cards enter `todo/`; afterwards it is a frozen-relation change that needs an explicit user decision per `KANDER-KANBAN-RULES.md`.

## Running Task Cards in Parallel

- Note explicitly which cards can run in parallel.
- Run in parallel only cards that are ready at the same time and whose modified resources can be isolated at file level, not by module name. When the same resource cannot be isolated, record the dependency and run serially, and never share an execution worktree.
- Hotspot files, which many cards must touch to deliver anything (generated code, lock files, IDE project files, shared contract or schema files, per-locale string tables), are assigned to exactly one member, or the members that touch them run serially; never let two parallel cards edit one hotspot file.
- Split a change that spans several endpoints or clients by delivery slice, not by layer: one slice carries one transport or contract change through every endpoint it affects, is verifiable on its own, and the slices run serially in dependency order. Slicing by layer makes every card touch the same endpoint modules and test harnesses and guarantees conflicts.

## Git Branches and Worktrees

- A single card's executing agent creates a dedicated task branch and `<repo-root>/worktrees/<task-name>/` worktree per the Git rule file, with `develop` as the source branch.
- A task group uses two layers: the orchestrator holds the group branch `group/<task-group-id>` and the worktree `<repo-root>/worktrees/<task-group-id>/`, used to receive deliveries, run group-level verification and applicable reviews, and integrate; each member's executing agent still creates its own task branch and worktree.
- In-group task branches are created from the latest group branch, with `group/<task-group-id>` as the source branch, not from `develop`; on the remote path fetch `origin/group/<task-group-id>` first. Other naming, paths, and user change protection follow the Git rule file.
- The executing agent changes only its own card's worktree and does its own rebases and conflict fixes there; the orchestrator operates only on the group worktree and the integration target and never modifies task branches or code on a member's behalf.

## Group Integration Branch

**Creation and Reuse**

- The orchestrator first confirms the whole group's external dependencies per "Starting and Subscribing" and initializes `main` and `develop` per the Git rule file. Once all external dependencies are satisfied, create the group branch and worktree before starting the first card: with `origin` and not local-only, fetch, create from the latest `origin/develop`, and `git push -u origin group/<task-group-id>`; otherwise create from the local `develop` and report that the remote is not synced. If the fetch or creation fails, preserve the working state and do not start members.
- Record the group branch, the group worktree path, and the full `develop` SHA used for creation. That SHA is the group's anchor and doubles as the first batch's review base when review applies. When resuming orchestration, verify and reuse the existing group working state; do not overwrite the branch or regenerate the anchor.
- Pre-plan sync: while no review plan exists and no member is inside a sync round, the orchestrator may move the anchor forward by rebasing the group branch onto the latest `origin/develop` (local `develop` on the local path) and updating the remote group branch with `--force-with-lease`.
  - Do it when `develop` gained commits that touch files the group changes (the overlap check of `KANDER-GIT-RULES.md` "Keeping a Task Branch Current" with the group branch as `HEAD` and `develop` as `SOURCE`), and at the latest right before the review plan is created.
  - Record the new and previous anchor SHAs in the group working state, then dispatch every member with an already received delivery through the `sync` round of "Delivering a Task Branch to the Group Branch" so it re-delivers on the new head; members still working rebase onto the new group head at their next sync point.
  - The orchestrator resolves no conflicts on the group branch: when the rebase conflicts, abort it and keep the old anchor. It may then, still before the plan exists and only while every member with a received delivery has a live executing agent, reset the group branch to the new anchor with no deliveries on it and dispatch `sync` rounds in dependency order, so each member rebases its own task branch, resolves its own conflicts, and re-delivers; otherwise keep the old anchor and report.
- Once the review plan exists, do not rebase the group branch before final integration and never rewrite reviewed group history. The base chain for review batches is maintained per the review rule file and starts at the anchor recorded at plan creation.

**Delivering a Task Branch to the Group Branch**

- After implementing, verifying, and committing by concern, the executing agent rebases its task branch onto the latest group branch, re-verifies, and updates the task branch per the Git rule file. Between deliveries it keeps the branch current per `KANDER-GIT-RULES.md` "Keeping a Task Branch Current" with the group branch as `SOURCE`, which also fixes the re-verification scope; the final delivery commit carries the full verification. Record in `IMPLEMENTATION` the task branch's final full SHA, the group branch SHA it is based on, and the verification result, then `move review` and end the current response turn. The executing agent never updates the group branch.
- On receiving `review/`, the orchestrator reads the delivery record and verifies integration authorization and that the task branch head (remote branch after a fetch on the remote path, local branch otherwise) matches the recorded final commit. Deliver that commit to the group branch per the Git rule file "Direct Integration and PRs" and sync the group worktree; on the remote path push the final commit first and ff the local group branch only after success. When the same commit is already contained, only verify and sync. Without authorization, keep `review/` and the working state, report, and do not release dependencies.
- When the group branch has advanced and the task branch cannot ff, the orchestrator calls `kander notify <task-id> --kind sync --message-file <sync requirements>` once per logical dispatch (see "Durable Dispatch Identity") to have the original executing agent rebase, resolve conflicts, and re-verify. If `notify` exits non-zero, stop and report. After the new delivery returns to `review/`, verify again; do not carry the old delivery's conclusion forward.
- Only after confirming that the card's latest delivery commit is in the actual local or remote group branch and the group worktree is synced to that head does the orchestrator add the card to the pending review set or release its direct successors. If the push, ff, or verification fails, keep `review/` and the working state and release nothing. If the group branch shows unexpected changes or divergence, report; do not overwrite the remote or rewrite reviewed history.
- Deliveries are received serially, without merge commits. When review applies, no batch opens before every member has started, because closing a batch needs the review plan and the plan can be created only then; until then deliveries are received freely in dependency order. Afterwards receive only while no batch is open: each batch covers all deliveries received since the previous closed target up to its HEAD, and nothing else is mixed into the group branch while it runs, because closing needs the worktree clean at its final target. Other `review/` cards queue until the batch closes; in-batch fixes are received after the reviewer exits and then re-reviewed. A single received large delivery may open a batch immediately only when no other independent delivery is ready to receive; never hold a ready delivery merely to manufacture serial per-card batches. Without review, receive directly in dependency order.

**Topology Freeze**

- While any review batch of a group is open, the orchestrator does not re-split the group, add members, move cards between groups, change a card's owner, or accept a contract change.
  - A user request for any of these first closes the open batch (its remaining required roles still run on the current target; findings the pending change supersedes are disposed as `rejected` with the user's quoted decision and stay on the unresolved list; a batch in which a reviewer has run is never abandoned, because every planned batch must close before its members can complete), then applies the change, then starts a new batch in the same still unsealed plan, reviewing only the work after the closed target.
  - Re-reviewing the closed range under the new contract, a change that alters the base chain, or a change after the plan is sealed, continues as new cards per `KANDER-REVIEW-RULES.md` "Group-Level Review for Task Groups".
  - Applying such a change mid-batch invalidates the batch and is reported as wasted rounds, never silently absorbed.
  - The review plan fixes the group's members and worktree when created: it cannot take a new member later or follow a card into another group. Work discovered afterwards becomes a successor group or an independent card, and a re-split after the plan exists means terminating the affected cards under the user's decision and creating new ones; report both as topology changes.

**Merge-Back and Cleanup Preconditions**

- Once all deliveries are in the group branch, all members have reached at least `review/`, and applicable reviews are complete, the orchestrator checks integration authorization per the Git rule file "Integration and Cleanup", rebases onto the latest `develop`, re-verifies, and merges back. Successor groups in the same orchestration unlock once every member of this group has entered `done/` and its final group HEAD is confirmed in `develop`; do not wait for all groups before integrating.
- The orchestrator records the group HEAD before and after integration and the mapping to each card's commit. When `develop` advances, the one-time review gate applies.
  - The bound wrap-up evidence accepts the rebased group line only when its complete patch equals the closed reviewed patch. After a rebase that applied cleanly, compare the complete patch of the reviewed range with the rebased range before pushing, normalizing only index lines and hunk offsets (the same comparison the wrap-up evidence applies); a differing patch, for example from changed context lines upstream, is handled exactly like a conflict.
  - When any commit conflicts or the patch differs, abort the rebase, keep the reviewed group HEAD and the whole group state, and report with numbered options: `1. Integrate the reviewed group HEAD unchanged through a PR or a user-authorized merge into develop, which keeps the reviewed patch intact`, `2. Stop integration and keep the group state`.
  - The orchestrator neither resolves group-branch conflicts itself nor dispatches executing agents to rewrite delivered group history.
- Before cleanup, confirm the final group changes have entered the actual local or remote `develop`: for direct integration `git merge-base --is-ancestor` with the post-rebase group HEAD; for a PR the merged criteria from the Git rule file.
  - The wrap-up evidence needs a Git mapping binding the range from the first planned batch's base to the closed final target of the last batch (`KANDER-KANBAN-RULES.md` "Review Evidence Completion Gate"): when `develop` contains the group history unchanged (fast-forward without rebase, or a merge commit), `source_commit` is that closed final target; when history was rewritten (integration rebase then fast-forward, or a squash or rebase merge), `source_commit` is the last replayed commit on `develop` and `rebased_base` is the parent of the first replayed commit, and the evidence passes only when the complete patch of the replayed range equals the closed range's patch. Choose the PR merge method with that in mind. If not satisfied, keep the group and task working state and report.
- Once satisfied, dispatch the original executing agents to clean up their own working state per "Integration and Wrap-Up"; the group worktree and branches are removed per "Cleanup Failures" after all of the group's cards enter `done/`.

## Task Orchestration

**Entering Through a Member Card**

- A request to start a specific card first reads that card's `TASK_GROUP` and `PREREQUISITES` before claiming it. When `TASK_GROUP` is non-empty, also read every member of the group and resolve the complete dependency graph; do not treat the card as standalone.
- Verify each prerequisite per "Dependencies Between Task Cards": an in-group predecessor must have its latest delivery accepted into the group branch, an out-of-group card or group must be complete in `develop`. A column name alone is not evidence.
- Before assuming orchestration, inspect the durable coordinator record and any group working state and reconcile it under "Durable Coordinator Recovery". Another live coordinator remains the orchestrator; do not displace its claim, create a competing orchestration, or launch another copy of a member.
- If any prerequisite is unmet, or the group has no recorded working state from "Creation and Reuse", the current agent becomes the orchestrator once the coordinator claim permits. Treat the start request as an instruction to start or continue the group orchestration, not as permission to bypass a dependency, and do not ask the user to choose another member or restate the request. The new orchestrator follows "Starting and Subscribing" through group review, authorized integration, wrap-up, and successor groups, and never starts the requested card before it becomes ready.
- If the group already has a working state and the requested card's prerequisites are satisfied, use the reconciled coordinator state before starting it. Never create a second group branch or launch the same member twice.
- For a task with only a single card, starting, manual claiming, and the tracking responsibilities of different launchers follow `KANDER-KANBAN-RULES.md` "Claiming, Starting, and Coordination". The executing agent verifies delivery preconditions, creates the dedicated worktree, implements, verifies, runs applicable reviews, and integrates back into the source branch under obtained authorization; without authorization or with an unmet gate, it keeps `working/`, records the pending items, and reports.
- For a task group, the current agent becomes the orchestrator, schedules all groups and cards by dependency, integrates and wraps up each group under obtained authorization once its gates are satisfied, unlocks successor groups, and after the whole orchestration summarizes per "Integration and Wrap-Up" and asks whether to dismiss the executing agents.

### Roles and Responsibilities in a Task Group

- The orchestrator: validates dependencies; creates and cleans up the group branch and worktree; fast-forwards task branch deliveries onto the group branch and releases dependencies after verification; subscribes to notifications; inspects executing agents at every heartbeat and resolves or escalates blockers per `KANDER-KANBAN-RULES.md` "Handling Blocked Executing Agents"; arranges reviews, summarizes results, and dispatches findings back; integrates and wraps up the group.
- The orchestrator does not implement subtasks or modify subtask code, worktrees, or commits; "Orchestrator Wrap-Up on Behalf" allows cleanup and records only.
- The executing agent of an in-group card: prepares its workspace, implements, verifies, commits by concern, and rebases, re-verifies, and updates the task branch per "Delivering a Task Branch to the Group Branch"; writes the delivery, acceptance, and verification parts of `IMPLEMENTATION` and `SUMMARY`, and fills in `TASK_BRANCH` and the final delivery SHA; runs `kander move <task-id> review`, then ends the current response turn and keeps the interactive CLI session, neither exiting the process nor closing the terminal container ("Exit" in the task file means the same; when a non-interactive invocation ends naturally, later recovery is left to `notify`); then waits for `notify`: on a wrap-up notice it completes the wrap-up, reports, ends the turn, and keeps the session; otherwise it acts on the notice.
- The executing agent does not trigger reviews, update the group branch, merge it back into `develop`, or clean up its worktree and task branch before the wrap-up notice.

### Starting and Subscribing

- Before starting, the orchestrator reads all of the group's cards: verify IDs, dependencies, contracts, and modification scopes, parse every `PREREQUISITES`, and classify the direct references into in-group cards, out-of-group cards, and out-of-group groups. Run `kander check <all member task-ids>...` as a targeted check. Missing cards or group references, dependency cycles, or resource conflicts that cannot be isolated block the affected cards; preserve the working state and report. Environment problems that do not affect start conditions are only recorded; an unavailable agent, launcher, configuration dependency, board, or required Git workspace still blocks, and the `start` pre-checks are never bypassed.
- Use `kander move <task-id> todo` (or `kander pick`) to move confirmed `backlog` cards into `todo/`; the transition requires the `SELF_REVIEW:` and `CARD_REVIEW:` records from "Task Splitting and Task Groups". Cards already in later states stay as they are.

**Waiting for External Dependencies**

- While out-of-group dependencies are unmet, do not create the group branch or start cards; the not-yet-started group stays in `todo/`, and cards in later states during recovery keep their state.
- Tell the user the gap and the dependency targets, then wait with `kander subscribe <task-group> <all member task-ids>... --watch <out-of-group task-id|task-group-id>...`, repeating `--watch` per direct reference. `--watch` is only for targets outside this orchestration: a prerequisite group owned by the same orchestrator releases its successor per "Merge-Back and Cleanup Preconditions", and a prerequisite standalone card handed to the same session is followed through that session's own card subscription, whose events trigger the same `develop` containment check.
- After an out-of-group card reaches `done/` (or `archived/` with `RESULT: completed`), or all members of a referenced group do, apply the `develop` containment check of "Dependencies Between Task Cards". When a watched card enters `archived/` with any other result, or `trash/`, stop waiting and hand the decision to the user.
- State events trigger targeted re-checks of external dependencies. With no `working/` members, the heartbeat only confirms the subscription is alive; when resuming with `working/` members present, check their `liveness` per "Handling State Changes" and do not take over out-of-group agents.
- Once all external dependencies are satisfied, stop this waiting subscription, create the group working state from the then-latest `develop` per "Creation and Reuse", and start. When the same orchestrator also owns the prerequisite group, keep advancing it; a successor's waiting subscription does not stop that scheduling. With no external blocker, create the group working state directly before starting the first card.

**Starting Ready Cards**

- Start each ready `todo` card with `kander start <task-id>`; the agent comes from configuration by card scale, the launcher defaults to the configuration, and `--launcher` overrides only this run. Use one launcher within a group; when it is unavailable on the current platform, report the blocker.
- In the first round, start cards with no in-group `PREREQUISITES`; afterwards start only cards whose in-group prerequisites are all in `review/` or `done/` with their latest deliveries in the current group branch. Start cards that are ready at the same time and have no file-level resource conflicts (per "Running Task Cards in Parallel") in parallel; never start early by skipping dependencies.
- The task file for `start` is written by the command with the task ID and fixed requirements; the orchestrator appends no card body and fabricates no other task context. The executing agent learns it follows the task group flow from the card's `TASK_GROUP` field and these rules.
- Immediately after the first card starts, tell the user: this session is the task group orchestrator and must be kept until all groups in this orchestration have run in dependency order; ending early loses dependency validation, ordered starts, applicable group-level reviews, and integration. The session lasts until the orchestration succeeds or the user explicitly terminates it.
- After the first round starts, the orchestrator blocks reading the line-by-line JSON from `kander subscribe --heartbeat 600 <task-group> <task-id>...`: first a `snapshot`, then a `state-change` per state change, each carrying the group ID, the states before and after, and a snapshot of the whole group. Use the initial snapshot to catch up on moves made before subscribing; do not rely on historical events.

**Handling State Changes**

- Consume versioned subscription facts as observations and feed each into the coordinator checkpoint per "Durable Coordinator Recovery". A `task-update` requires re-reading the affected delivery record even when its state is unchanged; revision is not a dispatch completion receipt. On restart, compare the new snapshot with saved task revisions and membership versions, not the process-local sequence number.
- A `membership-change` requires re-checking the complete dependency set; a removed or regrouped member never automatically satisfies its former obligation. When `reconciliation_required` is true, reconcile the contract and delivery before releasing dependencies. A terminal `membership-unknown` or `read-error`, or `membership_complete: false`, stops dependency release for that subscription: preserve the last facts, report the diagnostic, and follow explicit recovery requirements; never infer completion from omitted tasks or repair the board automatically.
- On a `state-change`, run `kander check <task-id>...` only on the changed card and the direct successors it may release, read those cards, and verify dependencies. `review/` cards in the initial snapshot get the same delivery verification. A card entering `review/` is first received per "Delivering a Task Branch to the Group Branch", also when review is disabled; only after success decide whether successors are ready, and start them with `kander start` in the established order. A received `review/` card enters the pending review set when review applies; otherwise it waits for the group integration gate.
- A bound wrap-up closes only when the same dispatch ID/epoch has a completed receipt binding the final delivery and integration evidence, and the card is `done/`. A snapshot can prove this after a fast round trip or restart; the column alone cannot.
- After a new member starts or a card is dispatched back via `notify`, restart the subscription with `--heartbeat 600` naming the explicit set of members that still need monitoring, and continue from the new initial snapshot.
- The subscription emits a `heartbeat` every 15 minutes by default; the orchestrator always subscribes with `--heartbeat 600`, so it checks every executing agent every 10 minutes, handling each heartbeat per "Handling Blocked Executing Agents". Slow probes do not block scanning; output backpressure beyond the bounded queue terminates explicitly, after which reconnect and reconcile the new snapshot. Read the `liveness` carried by the event directly, checking revision/identity, observation age, validity, and collection state: pending, uncollected, and stale observations remain `unknown`; `alive` proves presence only and extends no deadline; `stopped` or `drifted` is handled per `KANDER-KANBAN-RULES.md` "Failure Recovery" (unbound and bound cards differ there); `unknown` per "Handling Blocked Executing Agents".
- While handling heartbeats and state events, do not run a board-wide `kander check` or re-read unrelated cards; the single untargeted `kander check` in "Integration and Wrap-Up" runs only after every group has wrapped up. Agent messages or user input may trigger an extra liveness check of the same scope without changing the next heartbeat.

**Handling Blocked Executing Agents**

- Handle every heartbeat per `KANDER-KANBAN-RULES.md` "Handling Blocked Executing Agents": inspect each monitored card's liveness, latest `IMPLEMENTATION` entry, and pane tail, resolve blockers within the limits stated there, and report the rest to the user in this session.
- Between state events, keep blocking on the subscription output; short-period polling of your own is forbidden, and the 10-minute heartbeat is the only periodic check. Only a state event, a heartbeat, or an explicit failure or exit of the subscription process triggers handling; lack of output and long waits are not anomalies.

### Durable Coordinator Recovery

- The commands and their JSON are in `KANDER-KANBAN-RULES.md` "Coordinator Checkpoints". Before recording group progress, `kander coordinator claim` with the explicit full member set (waiting members included), a unique session token, owner, and authority basis; on recovery, read `coordinator show <group-id>` and CAS-claim its current revision/epoch with a new token only under existing coordination authority, never repeatedly to override another live writer. The token fences checkpoint writes only; it grants no takeover, integration, transport, or cleanup authority, and a checkpoint never grants on-behalf wrap-up (only the fenced `dispatch authorize-wrap-up` grant does).
- Feed every observation (initial snapshot, task update, state change, heartbeat or attention event, subscriber restart) through `kander coordinator reconcile` with the same full member set and each expected dispatch ID/epoch/base, naming the exact receipt delivery SHA for completed rounds. Events wake the consumer; sequence numbers, state strings, and column names are never completion evidence, and stale epochs, revisions, wrong rounds, unknown members, or damaged originals stop the affected reconciliation.
- A start attempt is not a start: launcher metadata keeps the member waiting until its durable success result exists, rollback evidence restores waiting, and an unknown launcher outcome is never promoted to success. A first delivery without a dispatch receipt is recorded only from the task branch, `review/`, an explicit delivery SHA, and its actual branch HEAD in the supplied absolute `cwd`; group reception and dependency release still need their own Git verification. Never invent a dispatch receipt.
- Keep subscription heartbeat, dispatch confirmation deadline, and task progress separate: receipt acceptance ends confirmation waiting but proves no delivery, no other event renews a dispatch deadline, and an alive but unchanged member may need a progress report, never an automatic new executor or fabricated completion.
- On EOF or output failure, reconcile once from current facts and reopen the subscription once when committed facts are valid. Only a diagnosed managed pending transaction enters the explicit `init` maintenance recovery, at most once before rereading. Lock contention or deadline exhaustion is an unavailable observation, not stopped execution; no output by itself is not a failure. Do not retry duplicate entries, reparse points, corrupt records, or unknown artifacts; report and preserve evidence.
- During wrap-up recovery, reconcile the same dispatch and consume its bound integration artifact, role conclusions, immutable author dispositions, sealed plan, and closed batch chain; recheck actual Git ancestry in the recorded repository or a surviving worktree `cwd`. Partly archived completed members keep their receipts: continue only unfinished work, never reintegrate or repeat cleanup. A changed member set or execution cycle requires explicit reconciliation of the governing contract; never drop members or reset an epoch to bypass evidence.

### Review Batches and Dispatch-Back

- Bind each role invocation to all batch members with repeated `--task` flags. Keep one batch ID across its fix rounds, distinct run IDs per role and invocation, and explicit predecessor run IDs for incremental re-review. Follow the minimal tool protocol for fixed requirements, CAS target advancement, and same-run publication recovery.
- Before treating a role report as available, confirm all its card publications are complete. Execution success alone is not semantic PASS; failed or interrupted evidence and incomplete publication cannot close a batch.
- This section runs only when review applies. A dispatch-back solely for task branch sync or integration conflicts is handled per "Group Integration Branch" and does not enable the review module.
- The orchestrator decides batch boundaries by choosing when to receive deliveries: a batch opens at a point it picks (a module, a milestone, a dependency-chain step), never before every member has started, and covers every delivery received on the group branch since the previous closed target. Deliveries wanted in a later batch stay queued in `review/` unreceived, but deferral never delays a successor: a delivery whose in-group successor is otherwise ready is received as soon as no batch is open and belongs to the next batch. Neither whole-group nor one-card batches are mandated; a received delivery is never left out of the batch that follows it. Determine the CWD, base, task context, and role flow per `KANDER-REVIEW-RULES.md` "Group-Level Review for Task Groups". Each batch is independent: a later batch's base is the closed target of the previous one, and only in-batch fixes get incremental re-review. A batch in which a reviewer has run is never abandoned; it is closed per "Topology Freeze" before the next batch names it as predecessor.
- Default batching: every delivery received since the previous closed target joins the same batch. A single-card batch arises only when that delivery was the only one received in between, for example at the end of a dependency chain. Serial per-card batches for independent cards are forbidden; holding independent ready deliveries unreceived merely to review them one by one counts as such.
- Findings are attributed by the orchestrator by modification scope: whichever card's `GOAL`/`OUT_OF_SCOPE`/actual changes a finding hits gets it. Cross-card integration findings are assigned through `review assign` to every batch card whose scope they hit; a card outside the batch cannot be assigned, so when a finding also hits a card reviewed earlier, report that membership gap and plan that card's part as a later batch or a successor card. When no member's scope matches, attribute the finding to the in-batch card whose delivery introduced the interaction (the later delivery in dependency order, or the later-received one when independent); its executing agent disposes it as `rejected` beyond contract with a follow-up card suggested, unless it reaches `blocking` or `high`, which goes to the user per `KANDER-REVIEW-RULES.md` "Main Agent Verification Duty". If the user includes it, that is a contract change: close the open batch per "Topology Freeze", apply the decision, then open a new batch in the still unsealed plan. The orchestrator never adds a fix card to a running group; such work becomes a successor group or an independent card.

**Durable Dispatch Identity**

- Use `notify --kind fix --evidence-file <JSON>` for findings, `--kind sync` for task-branch synchronization, and `--kind wrap-up --evidence-file <JSON>` after integration. Bind the actual review run, finding, assignment, and existing author originals for fix, and verified `develop` integration for wrap-up, per the command protocol. Record the printed dispatch ID, frozen baseline, and original message; retries reuse the same ID and payload.
- Read `kander dispatch show <task-id> <dispatch-id>` to reconcile uncertainty. State changes and terminal echo do not replace accepted or completed receipts. Before working, the executing owner uses the ID/epoch move command from the generated prompt; a replayed receipt authorizes no duplicate work. Completion carries the same grant and the final delivery and evidence references.
- When `notify` returns nonzero, preserve the actual dispatch state, report the reason, and do not invent a new round or invoke `resume` to escape uncertainty; a same-ID retry follows the command protocol's persisted deadline, readiness, and stopped/unknown rules.

**Dispatching Findings Back**

- A dispatch-back calls `kander notify <task-id> --kind fix --evidence-file <JSON> --message-file <findings>` once per logical dispatch and checks the exit code; channel selection, recovery, and window/document rollback happen inside the command, and a non-zero exit means stop and report. The fix evidence binds the card's gate findings (`blocking`, `high`, `medium`, including `[mechanical]`) and its assigned non-blocking findings (`low`, `recommend`, `suggest`) when either set is present, and the message lists every item with role and tier, non-blocking items marked "disposition only". A card with only non-blocking findings still uses `--kind fix` with those `NON_BLOCKING` references bound, never a sync workaround. Non-blocking items never open a fix round, and a dispatch that lists no concrete items or asks the author to "triage" is forbidden.
- The message file states the reviewer role, tier, the findings verbatim, and facts known to the orchestrator, never the orchestrator's own conclusions, and is written in the target card's `LANGUAGE`.
- On receiving the notice, the original executing agent first moves back to `working/` with the ID/epoch-bound move command, then verifies each finding, fixes, commits, rebases onto the group branch head and re-verifies, updates the task branch, submits the dispositions through `review disposition`, writes in `IMPLEMENTATION` one entry with the counts per status, the card-relative record paths, and the latest delivery SHA (never the finding list itself), then `move review` and ends the turn.
- A dispatch stays pending until its immutable accepted or completed receipt is verified for the expected ID, epoch, and base; the initial snapshot and every later event use the same reconciliation path. Missing a `review -> working` edge does not block a proven receipt; observing an edge or terminal echo proves nothing. Until the receipt exists, do not release dependencies, queue the fix delivery for review, or create another logical dispatch. Respect the original confirmation deadline and inspect attention and liveness facts without inferring exit from timeout.
- After reconciling the round's completed receipt and final delivery, receive and sync the fix delivery per "Delivering a Task Branch to the Group Branch", consume the author originals, and trigger applicable incremental re-review. An already-contained delivery is verified and synced only; duplicate, lost, or reordered events never create a new fix round.
- Findings the executing agent judges invalid or outside the contract return to the orchestrator with the reasoning; the orchestrator does not rewrite them and includes them in the unresolved items for the user per `KANDER-REVIEW-RULES.md` "Main Agent Verification Duty".
- When a dispatched-back card has not entered `review/` and its executing agent has exited, or the same finding fails to close in two rounds, apply the round cap in `KANDER-REVIEW-RULES.md` "Conclusions and Failure Handling": record the state and report with numbered options per `KANDER-KANBAN-RULES.md` "Failure Recovery"; do not reassign or fix on the orchestrator's own, and a user-decided takeover follows that section.

### Integration and Wrap-Up

- Once the group meets "Merge-Back and Cleanup Preconditions", the orchestrator completes the authorized integration and local sync per the Git rule file "Direct Integration and PRs", recording N/A for review when disabled. Do not merge back while any card of the group is still in `working/` or has an unreceived delivery; receiving other ready deliveries continues meanwhile.
- When integration fails (rebase, verification, push, or ff incomplete) or the user asks to pause or not merge back: all in-group cards stay in `review/`, the group branch, task branches, and worktrees are kept, and the orchestrator records the blocker and the release conditions and reports card by card per the enabled `KANDER-REPORTING-RULES.md` template (truthfully when disabled) with the state `review (blocked)`. Use `notify` only for genuine dispatch items (task branch sync, rebase conflicts, review findings, wrap-up after successful integration); the original executing agent moves itself back to `working/`, and the orchestrator never moves cards by hand to signal a blocker.
- After successful integration, dispatch the original agents to wrap up in dependency order, in parallel when there is no conflict, using only `kander notify <task-id> --kind wrap-up --evidence-file <JSON> --base <source_commit> --message-file <wrap-up notice>`, passing the evidence's `source_commit` as `--base` because the default base is the HEAD of the current directory. The only other entrance that creates a wrap-up intent is `dispatch authorize-wrap-up` under "Orchestrator Wrap-Up on Behalf"; a same-ID `resume --agent` follows the command protocol's user-authorization rule.
- The notice states how the group branch was integrated into `develop` and the full SHA, this card's final commit (with the before/after mapping when a rebase rewrote it), role conclusions or N/A, applicable batches and fix rounds, this card's unresolved items, and the "Executing Agent Wrap-Up" checklist; for PR integration also the PR identifier, merged status, and target branch evidence. The orchestrator does not modify card bodies or move cards by hand. When dispatch is impossible, go through the gate in "Orchestrator Wrap-Up on Behalf"; impossibility alone grants nothing.

**Executing Agent Wrap-Up**

- On a wrap-up notice, the executing agent first moves back to `working/` with the ID/epoch-bound move command, then confirms per `KANDER-GIT-RULES.md` "Integration and Cleanup" that its changes are in `develop`: for direct integration `git merge-base --is-ancestor` with the final group HEAD plus the notice's statement that this card's changes are included; for a PR the merged criteria and the `source_commit`/`rebased_base` mapping given in the notice. Never judge ancestry with the pre-rebase SHA. If not satisfied, preserve the working state and report to the orchestrator.
- Once satisfied, delete this card's worktree, local task branch, and applicable remote task branch, without touching the group worktree or branch; complete the summary's review and wrap-up parts (role conclusions or N/A, applicable rounds, final commit, group branch and `develop` integration results); publish records through the controlled update entrance; run the completion command from the dispatch prompt, `kander move <task-id> done --result completed --dispatch-id <id> --execution-epoch <epoch> --delivery-commit <final-full-SHA>` with the applicable `--disposition`, and the targeted `kander check <task-id>`; report per the applicable `KANDER-REPORTING-RULES.md` template or the user's format; end the turn and keep the interactive CLI session waiting for the dismiss decision.
- The orchestrator does not modify the delivery, acceptance, and verification records written before the card moved into `review/`.

**Orchestrator Wrap-Up on Behalf**

- When a wrap-up does not close, the orchestrator may complete that card's wrap-up and report as the one who finished it, but only after the durable wrap-up authority gate grants it. The triggers that lead to the gate, none sufficient on its own, are: no usable `WINDOW`/`SESSION` record; `notify` exited non-zero; the executing agent exited after the dispatch-back and the card has not entered `done/`.
- Each trigger only starts reconciliation: reconcile the same dispatch, create a bound wrap-up intent when absent, and apply `kander dispatch authorize-wrap-up <request.json>` only after confirmed executor exit or an already-authorized reclaim followed by a valid stopped observation. A missing SESSION/WINDOW, a nonzero notify result, a timeout, or an expired lease alone grants nothing. When exit cannot be established, preserve the card and report.
- Keep the original OWNER and author conclusions. Record the actual on-behalf author and reason in the dedicated grant, accept its new epoch, and use only its cleanup and append-only record scope; never send a wrap-up-only token to another executor or upgrade it to ordinary code authority. Complete with the same dispatch and verified integration source; the original completion and review gates stay in force. State "wrap-up done by the orchestrator on behalf" and the reason in the `Wrap-Up` part of the card's completion report and in the group-level summary.
- This is the only exception to "not fixed by the orchestrator on its behalf" in "Review Batches and Dispatch-Back": wrap-up changes no code. Findings that require code changes are never fixed by the orchestrator.

**Cleanup Failures**

- When cleanup fails partway (a card's branch or worktree deletion fails): cards already in `done/` stay there. The failed card stops in its actual state (`working/` if wrap-up was dispatched, `review/` if not), keeping only the worktree and branch that still remain; the group branch is kept. Report card by card by real state; for the failed card give the failed step, the error, and the release conditions, with the state `working (blocked)` or `review (blocked)`. The code is already in `develop`: do not re-integrate; after release, only continue the unfinished wrap-up.
- After all members of a group enter `done/`, stop that group's subscription, delete the group worktree, local group branch, and applicable remote group branch, and continue scheduling the remaining groups. After all groups finish wrap-up, run `kander check` once without targets; success counts only when the full check passes. When any card enters `archived/` with a result other than `completed`, or `trash/`, wait for the user to change the group contract or terminate the group.
- At the end of orchestration, summarize the execution order, parallelism, applicable review batches and rounds or N/A, and integration results, then list per card (with its task ID) the known defects, verification gaps, follow-up tasks, and the blockers resolved on the orchestrator's own decision per `KANDER-KANBAN-RULES.md` "Handling Blocked Executing Agents"; write "None" when empty. Only when review applies, also classify unresolved review items per `KANDER-REVIEW-RULES.md` "Conclusions and Failure Handling". On termination, report the unfinished cards one by one per the enabled `KANDER-REPORTING-RULES.md` template (truthfully when disabled), then list the termination decision.
- Only when all in-group cards have entered `done/`, all group worktrees and branches are deleted, `kander check` has passed, and all group-level summaries are complete does the orchestrator ask once whether to exit the executing agents and close their herdr tabs or tmux windows, with numbered options such as `1. Dismiss the executing agents and close the corresponding containers`, `2. Keep the sessions and containers`; a text reply with the same clear intent is valid. Without explicit confirmation, perform no exit or close action; if the user declines, keep everything and end the orchestration.
- After confirmation, call `kander dismiss <task-id>` exactly once per in-group card; never send exit instructions to agents or close windows directly, and never bypass the command's identity, topology, and graceful exit gates. Each result is independent: on a non-zero return keep that card's working state, record the reason, and continue with the rest; then summarize per card. This is optional terminal cleanup; failure rolls back no completed card, restores no deleted branch or worktree, and changes no report already issued.

## Machine Aggregation and Author Boundaries

- The plan, batch, assignment, disposition, aggregate, advance, and close commands and their gates are in `KANDER-KANBAN-RULES.md` "Review Evidence Completion Gate". Whether or not review applies, the orchestrator creates the group's review plan once every member is in `working/` or `review/` and before any batch runs (the explicit N/A plan when review is off, before any member wraps up), appends each later batch after its predecessor closed and before its first run, and seals the plan before wrap-up.
- Findings go to their original executing owners through the controlled assignment command, shared findings naming every affected card; each owner submits its own immutable dispositions. The orchestrator may record its own verification opinion under its own author identity but never rewrites or impersonates execution-side conclusions. `kander review aggregate <CWD> <batch-id>` publishes the complete disposition to all members mechanically; it is not author verification, and a member without findings is not dispatched merely to copy a report.
- Close a batch only through the closure command with every required role, author disposition, and final Git relation satisfied, and release the next batch only from that exact closed target. When `review progress` reports `requirements-needed` after a reclaim changed a member's execution cycle, rebind the plan before continuing.
