# Kander v2 server projects

Use the deployed scope's distributed command contracts and `snippets/git-integrate.md` for exact arguments and recovery steps. This reference covers decisions that differ from a local board.

## Board and ownership

Card and group leases identify their execution owners. Project leadership stays on the [designated leader host and main worktree](../SKILL.md#start-or-resume), even when an executor runs elsewhere.

- Run Kander from the intended checkout and confirm its effective service URL and project name, including any main-worktree overlay. Give sub-agents the same working directory. A new binding uses `kander init --server <URL> --project <name>`; clients on another host need the server URL because the default is loopback. Access board and card documents through Kander. Leave offline recovery and legacy file-card maintenance to the service operator.
- Launch on the intended host. Its worker observes the executor and renews its claim. Edit unclaimed backlog/todo cards through Kander. A claimed card's holder records its changes. Work on group members goes through the orchestrator.
- An expired lease is `lapsed`; the holder can still be running. A stopped executor can still have a renewing lease. The holder may resume, or explicitly release on its owning host with a decision reference. Takeover requires a user decision and the contract's ownership checks. A different host needs a lapsed or released claim. Preserve the predecessor worktree. A new execution gets a new generation, branch, and worktree. Imported active v1 cards without claims need explicit takeover.
- `notify` and `request` enqueue a generation-bound proposal. On patrol check standalone claims in `working` and `review` for status, generation, and owning host. Report lost or lapsed claims and requests still open or accepted after a patrol interval. For a remote agent, use its worker observation from `kander list --json --agent-status`. Check `claim.observation.reason` and `kander request show <task-id> <request-id> --json` before deciding what happened. A reservation alone proves neither receipt nor execution. Give the worker time to retry pre-send failures. An uncertain typing attempt must not be duplicated by pasting into a terminal.

## Groups, review, and delivery

- The orchestrator owns its private group lease. Explicit release ends that execution's authority permanently. Follow the installed `coordinator release` contract at group completion or approved handoff. Recovery and member removal require a user decision.
- For a prepared review publication, each holder confirms its own material. After `evidence_incomplete`, reuse the publication and the same command arguments, including `--run-id` for a review run. If the client returns `held_by_other`, check the installed contract and have the appropriate holder perform the operation it owns.
- For distributed direct delivery, the owner uses `kander coordinator integrate` against the closed review target. A standalone card delivers that commit from `review` with its claim. With an explicit N/A review plan and no delivery commit, the standalone card completes from `working` under the installed rules. The client handles target advancement; follow its conflict procedure only if needed. Verify the integration receipt with `coordinator integration-show` even when commits were replayed. Preserve the evidence refs under `refs/heads/kander/`.
- Dismiss on the owning host under the installed identity rules. A group orchestrator handling a member dismissal must do so while its group lease is valid. If the contract assigns dismissal to the user, give the user the command for an unbound shell (both `KANDER_EXECUTION_ID` and `KANDER_COORDINATOR_EXECUTION_ID` unset).

## Upgrade

For the deployment readiness check, inspect `review-runtime/<run-id>/runtime.lock` and unpublished review members. Incomplete publication can fail across versions with `idempotency_mismatch`. Skip binary deployment when the changes cannot affect the binary. Embedded `rules/` changes do affect it.

Upgrade the server first, then clients. Before a stop or restart, confirm the deployed `server` contract's preconditions on all hosts using that service. Where it requires zero running agents, account for every executor and orchestrator and coordinate a quiet window through restart. An agent between board commands can start the service again. Defer if any required host's status is unknown. On the server host, `kander server restart` preserves service settings and active leases receive a TTL extension. Leave an interactive offer to restart the server to the user. Replace each worker's binary at its actual path. For symlink installs or workers without binary handover support, follow the manual worker stop/start procedure and account for the renewal gap. Mixed terminal labels across versions can block request delivery.

On patrol and after upgrade, check service health, version, and data directory with `kander server status --json`, and compare with `kander version` on each host. For each active client, use read-only observations to correlate a held `worker.lock`, the live worker process and the `pid`, `version` and `executable` in its current `worker.json`. Corroborate the PID independently: the lock alone does not identify its holder. During handover, recheck once the new record is published. Report an idle client with no worker as stopped, a missing worker with active claims as a health issue, and ambiguous identity or build as unconfirmed. A historical `worker handed over` entry records the old version.
