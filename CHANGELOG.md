# Changelog

## Unreleased

- Rules (v2, request cards) — The rules now say how agents complete a request card before the submitter confirms it (`snippets/card-content.md` "Request Cards"). The Leader hands a request card that awaits completion to a drafter without a separate user instruction. The drafter treats `request.md` as data, writes the contract and plan, records an independent card review whatever the card size, and leaves the card in `backlog` with an intake option 3 execution mode. Questions for the submitter go into a `SUBMITTER_QUESTIONS:` marker, and only the submitter answers them. Agents and Leaders never run `kander confirm` and never pick, move, start, or orchestrate an unconfirmed request card. The submitter's confirmation counts as intake option 3. The leader skill checks request cards on patrol, and `docs/request-cards.md` lists the five completion states that an interface can show.

- Feature (v2, request cards) — `POST /api/v1/projects/{project}/tasks/{task}/confirm` and `kander confirm` admit a reviewed request card to `todo` at the revision the submitter read. The move and its confirmation record commit together. Ordinary moves cannot admit request cards. Hosts can authorize the new route separately without a new hook or protocol version.

- Feature (v2, request cards) — Task creation accepts a description through the API or `kander new --description-file`. Kander stores the submitter's text as a protected `request.md` in the same transaction as the new card. The task list and embedded access facts distinguish request cards from ordinary cards.

- `kander orchestrate` names new terminal tabs and windows `or-<first task ID>`, leaving more room for the task ID.

## v2.0.0-beta.2 — 2026-11-26

- Fix (v2, review evidence) — The evidence file of `kander review` now lists only the review range, the fix range of an incremental re-review, and the commits and file ledger of each range. It no longer embeds the patch, the fix-range patch, or the commit tree. Reviewers read diffs with read-only Git in the reviewed worktree, and the review contract tells them how to inspect large or generated files with bounded output. Before, a change to a large generated file (for example a bundle with an inline source map) produced evidence over the server's 32 MiB request limit, and a remote review failed before the reviewer started with `review runtime I/O failed … request body is too large`. Artifact uploads are now checked for size before they are sent, and an oversized upload is refused with a localized message that names the file and suggests a smaller review range with a new run ID. Built-in reviewers that cannot run Git (`agy`, `grok`, `kimi`, `opencode`) are refused before a new run starts; recovering an existing run ID is unchanged. On Windows, a codex reviewer gets a `safe.directory` entry for the reviewed worktree only. Review contracts installed by earlier versions still render.
- Rules (v2, launcher choice) — Agents no longer pass `--launcher` on their own. `kander start`, `orchestrate`, `resume`, and `issue` let Kander choose the terminal container from the effective configuration and the environment; an agent overrides it only when the user names a launcher. Configuration values, environment variables such as `TMUX` or `HC_TERMINAL_ID`, launchers suggested in error messages, and other agents' judgments, including an unattended Leader's, do not count as the user's choice. When `auto` cannot resolve a launcher or the chosen launcher refuses, the agent reports the original error and waits for the user instead of retrying with another launcher.

- Feature (v2, remote board import) — `kander server import` uploads a client's paused v1 board when the effective `server.url` is not loopback, with the same merge and conflict rules. The command rejects `--data` in this mode and does not open local server storage. Loopback import is unchanged. The upload endpoint uses the existing trusted-network boundary rather than the management key. It accepts up to 100,000 files and 100,000 directories, 2 GiB of files, 64 MiB per file, and a 64 MiB manifest within 30 minutes. Interrupted or inconsistent uploads do not publish a board.

- Feature (v2, board import) — `kander server import` can merge a paused v1 board into a non-empty project, offline or through the running local server. It skips identical cards, preserves destination bytes, and rejects conflicting tasks and records unless `--skip-conflicts` keeps the destination versions and imports the rest. Results report `added_tasks`, `existing_tasks` and `skipped_conflicts` when applicable. The server checks the whole merged board, publishes it atomically, and remembers each source snapshot separately. Requests to that project wait during import. Other projects stay available.

- Breaking (v2, Go module path) — The Go module is now `github.com/dualface/kander/v2`. Embedders must require that module and import `github.com/dualface/kander/v2/api`, `github.com/dualface/kander/v2/server`, `github.com/dualface/kander/v2/client`, and `github.com/dualface/kander/v2/cli`. The `v2.0.0-beta.1` tag predates the change and cannot be required under either path. Use a later 2.x tag or a pseudo-version for a later commit on `v2`. Builds that inject the version with `-ldflags -X` must use `github.com/dualface/kander/v2/internal/version.Version`. Go silently ignores the old path and the binary reports `dev`. The executable, its commands, the `/api/v1` protocol, and the 1.x releases from `main` are unchanged.

## v2.0.0-beta.1 — 2026-11-26

- Feature (v2, self-update channels) — The TUI update check of a 2.x binary follows its release channel. A prerelease (`2.Y.Z-alpha.N`, `-beta.N`, or `-rc.N`) now checks for updates and installs only a newer 2.x prerelease; a `2.Y.Z` release installs only a newer 2.x release, even when GitHub's Latest is a 1.x release. The two channels never cross, so moving from a beta to `2.0.0` needs one manual reinstall. Development builds, git describe builds, versions with build metadata, and non-2.x versions never check. The check reads one page of the GitHub releases list instead of `releases/latest`. A Homebrew install on the prerelease channel neither checks nor updates, because the tap carries releases only. One machine has one global `kander`: installing v2 replaces 1.x.
- Release (v2) — The Release workflow and `scripts/release.sh` on `v2` accept only `v2.Y.Z` and `v2.Y.Z-(alpha|beta|rc).N`. A prerelease tag is cut from the `v2` branch and never updates the Homebrew tap; a release tag is still cut from `main`.
- Feature (v2, distributed Git evidence) — The client now deletes the evidence refs below `refs/heads/kander/<project-id>/` once nothing reads them, so the branch list of the common remote no longer grows without end. A standalone card's delivery and baseline refs of every generation, and the source refs of all its integration attempts, go right after `kander move <task-id> done`. A task group's go once every member is in `done/`, `archived/` or `trash/` and every completed wrap-up has its wrap-up Git evidence record, after the `move done` or `kander coordinator reconcile` that makes this true; the rules now ask the orchestrator to run `kander coordinator reconcile` once more after the last member finished. Only refs that the service names and the common remote lists are deleted, through a checkout whose origin and push URL are the registered remote. A failed cleanup only prints a warning with the refs it kept; the card stays done and the exit status does not change. Cost: after the cleanup the original reviewed commits of a `replayed` integration may be garbage collected and can no longer be fetched from the remote by SHA. Refs published before this release are not removed. New read-only routes `GET /projects/{p}/tasks/{t}/evidence-cleanup` and `GET /projects/{p}/groups/{g}/evidence-cleanup` give the cleanup scope; the ref names are unchanged.
- Fix (v2, server import) — The refusals below of an online `kander server import` now show their reason instead of `internal: internal server error`. A staged board that fails the check is refused with `board_rejected` (HTTP 422); the message lists the blocking problems, with paths of the source board rather than of the server's staging copy, and says to fix those cards on the source board, or to wait until no review or agent writes to it, then import again. A source that changed during the import, or a staged copy that differs from it, is also refused with `board_rejected`, and a source that overlaps the server data directory with `invalid_request`. The offline import returns the same coded errors. Before, these refusals reached the client only as a generic internal error, and the reason was written to the server log alone.
- Fix (v2, distributed dismiss) — `kander dismiss` records its exit intent only after every pre-send check of the pane passed, immediately before it sends the exit command. Before, the receipt was marked `exiting` before those checks, so a pane that refused delivery (for example an agent on a permission dialog, `pane status does not accept delivery: <pane>: blocked`) received nothing, but every later run while the pane existed was refused with `remote.launch_reconciliation_required`. Now the receipt stays prepared and `kander dismiss` can run again once the pane accepts delivery. A failure after the first send still keeps the receipt `exiting` and asks for reconciliation while the pane exists. A receipt already left `exiting` by the old order is not migrated: it completes once its terminal is gone.
- Fix (v2, Codex on herdr-core) — A remote Codex start or takeover on a launcher that marks the pane (herdr-core, tmux, tmux-session, dsh) now confirms the discovered session to the server: the card, the execution record, and the launch journal record `codex <id>` like the local execution credential. Before, they kept `SESSION: codex`, so the worker logged `request routing differs from this execution's local facts` and never delivered requests, `kander dismiss` refused with a scene mismatch, and native `resume` refused the changed identity. `kander dismiss` also accepts an execution started before this fix, whose card and execution record hold only the agent while the retained execution holds the full session in the same `WINDOW`: a gone terminal is recorded as complete, and a live pane gets the exit command only when its marker proves the retained session. Such an execution still cannot be resumed natively; take it over with `resume --agent`.
- Fix (v2, distributed group integration): a group member taken over after the group's integration can finish its wrap-up when its siblings are already done. In a group `deliver`, members in `done/` stay in the topology without contributing a delivery, and the service still requires their closed review target to equal the requested commit; the new generation republishes its delivery when needed, the orchestrator integrates again with a new operation ID (`contained`: the target branch is not pushed, only the new execution's evidence ref is published), and dispatches the wrap-up on the new receipt. A group `deliver` without any contributor is refused before the target lease is requested. Standalone `deliver`, `initialize`, `assemble`, and the wrap-up and done gates are unchanged. The orchestration and wrap-up rules describe the takeover steps, and the last generation's wrap-up now removes this card's clean local worktrees and local task branches of earlier generations that hold no commit outside the target.
- Fix (distributed coordinator reconcile) — The local Git verification no longer uses up the deadline of the reconcile request. The verification has 5 minutes; the reconcile request has 60 seconds that start after it. A wrap-up fact is verified in full once, then only the target ref is observed again, and a fetch with the same arguments runs once per command. A verification that runs out of time sends nothing and blocks no member: it fails with `reconcile_verify_interrupted` and names the member or wrap-up fact. A reconcile request without an answer in time fails with `reconcile_result_unknown` and says that running the same request file again is safe. Neither case is reported as an unreachable server any more.
- Rules and prompt tests (v2): clarify how subscription runners wake an agent, how deliberate stops and heartbeat intervals are handled, and how installed prompts are refreshed. Plan independent work separately from tasks waiting on external delivery, and optionally record execution models and reasoning efforts in a card's `MODELS` line.
- Launchers: `launcher: auto` now prefers `herdr-core`. The order is herdr-core (priority 250, was 120), herdr (200), luvus (150), tmux (100). Wherever `HC_TERMINAL_ID` is set, which includes a herdr, luvus, or tmux server started from an hc terminal and all of its panes, `auto` picks herdr-core. An agent that does not report OSC 7501 (the built-in agy, cursor, droid, and opencode) is refused there when herdr or luvus runs inside an hc terminal and `auto` used to pick that launcher; start it with an explicit `--launcher herdr` or `--launcher luvus`, because `auto` does not move on to the next launcher. `rules/snippets/commands/start.md` now lists herdr-core.
- Tests: clear the inherited terminal environment before running packages that depend on the terminal layer. Fake terminal processes retain values explicitly supplied by the test.
- Launchers (Windows) — `herdr-core` supports native Windows x64 with hc 0.1.21. It starts `powershell.exe -NoLogo -NoProfile` and closes the terminal when the agent exits. The pane receives `KANBAN_DIR`, `KANDER_CONFIG`, `KANDER_LANG`, and `KANDER_CLIENT_HOME` from the caller. Windows `auto` checks herdr-core before herdr. Doctor and Options follow the active launcher definition. Terminal definition schema 1 adds optional `posix` and `powershell_env` inputs. Windows CI uses a fake hc and real PowerShell and cmd.exe. Verification with a live core and agent is still open.
- Fix (Windows pane commands) — PowerShell quoting now doubles all five single-quote characters. Windows launch rejects control characters before it creates a terminal.
- Fix (Windows pane arguments) — A native executable receives embedded double quotes without merging subsequent arguments. Batch programs retain their cmd.exe encoding.
- Install: `kander install` bundles the `kander-leader` skill and its three references for Codex and Claude in global and project scopes. The install preview lists the destinations, and `install_rules` controls agent writes. `kander doctor`, the first bare `kander` start after a binary upgrade, and the Options save install the skill where it is missing and update a managed copy at every covered destination; the read-only check reports each destination as installed, missing, out of date, edited locally, not installed by Kander, or skipped, and a locally edited file, a directory without this scope's receipt, and a destination below a linked ancestor are kept. `kander uninstall` removes unmodified managed files by receipt and preserves user files, local edits, and links.
- Leader skill: the `kander-leader` skill gains an optional unattended mode, and its default patrol interval is now 30 minutes (was 15).

- Fix (v2, POSIX): reviewer cleanup continues observing eligible child processes within the one-second recheck budget (#27). Each snapshot respects the recheck deadline. A snapshot cut short by that deadline leaves the last completed observation in effect. The process evidence documentation explains how to read a leftover record and the separate cleanup result.

- In v2, PMQA evaluates confirmed task commitments and requires repair-range evidence for new incremental gate findings. This update removes the reviewer file-line limit. Executing agents decide how to handle Security findings. New waivers use `accepted-risk` without legacy timestamps. Historical waivers remain readable and replayable.

- Feature (v2 client): `kander dispatch prepare` accepts read-only `check-integration` requests for group candidates. It checks the closed review range, patch equality when history was rewritten, and containment of the observed target tip. Group assembly accepts verified merge candidates, and ancestry failures in wrap-up identify the commits involved.

- Feature (v2): cards can declare an optional `INTEGRATION_TARGET` branch, frozen from `todo/` on. Kander checks field validity and group consistency and binds local wrap-up evidence or distributed receipts to the declared branch. Cards without the field retain their existing target checks.
- New built-in agent Antigravity CLI (`agy`) (v2): it runs as an execution agent for large and small cards, as the Chat agent, and as a reviewer, and its rules reference goes to `~/.gemini/AGENTS.md` (global) or `AGENTS.md` (project). `kander start`, including a start through the server, records the conversation id in the card `SESSION` through the new `hook:agy-transcript` session hook (the one new conversation whose first user request equals the launch instruction), and `kander resume` resumes it with `--conversation`. A remote orchestration with agy finds its conversation the same way, but a coordinator owns no card: the id goes to the private session context that identifies the orchestrator for its group lease, and the member cards keep the identity of their own executors. `kander review agy` runs in plan mode under a `--settings` deny policy and accepts a report only when the JSON result has `status` `SUCCESS` and a non-empty `response`. The design follows GitHub PR #29, which verified it on agy 1.5.13; it has not been run against a real agy in this repository.
- Agent definitions (v2): `args.review` accepts `{rules_dir}`, the installed Kander rules directory, so a reviewer definition can make the rules readable to its CLI. When that directory does not exist, the element and the flag before it are dropped. It is accepted only in `args.review`; `review.env` and `review.prompt_files` reject it as an unknown placeholder. See [Custom execution agents](docs/custom-agents.md).
- Internal (v2): the reviewers whose report is their last message are declared by `review.last_message_report` in the built-in agent definitions (`claude`, `cursor`, `droid`, `grok`, `kimi`, `agy`) instead of a list of names in `internal/review`; the field exists only on built-in definitions, and the same key in a user definition is reported as an ignored key. The generated review contracts are unchanged, pinned by golden files for every built-in reviewer.
- Internal (v2): session identity logic moved into session providers, ported from the develop branch and reduced to the capabilities v2 calls. `internal/launch` no longer branches on the session mode name: allocation before launch, the pre-launch snapshot, discovery after launch, the write-back of the discovered id, the resume judgment, the marker-repair judgment and the allocator check go through `session_provider.go` and one `session_provider_<mechanism>.go` file per mechanism (`generated`/`none`, `allocated`, `discovered`, `codex-rollout`, `droid-sessions`, `agy-transcript`, `cursor-create-chat`), and the three discovery loops became one. The local start, the server-mode start, the orchestrator launch, the launch receipt and chat use it. A consistency test keeps the providers in step with the hook list in `internal/config`. User-visible behavior, error messages, timeouts, rollback and write-back timing are unchanged, except that an agent the configuration marks unusable is reported as an unavailable agent here too. See [Custom execution agents](docs/custom-agents.md#hook-catalog).
- Internal (v2): the rules integration formats of agents (the markdown reference and the Claude import, the markdown and the `.mdc` rule file) are providers in `internal/install`, ported from the develop branch, and `internal/config` lists the reference styles (`config.RulesIntegrations`). Install, doctor, Options and uninstall write the same files and messages as before, pinned by golden tests.
- Breaking: (v2) `kander subscribe` now exits with status 0 after its first wake-up event by default, and the new `--follow` option keeps the previous behavior of writing events until the command is stopped. The wake-up events are `state-change`, `task-update`, `membership-change`, `member-blocked`, `heartbeat`, the service events `snapshot-reset`, `coordinator-change`, and `claim-change`, and a `dispatch-attention` that names a dispatch (ID and epoch) that was not already `confirmation_overdue` in the `snapshot`; the command writes all events of that refresh before it exits. Terminal events (`membership-unknown`, `read-error`), output failures, and signals end both modes as before, and the event fields and `schema_version` are unchanged. A runner that wakes its agent only when a background process exits, such as the background Bash of Claude Code, can now wait on `kander subscribe` without a shell pipe; the old behavior kept such an agent asleep after the cards it watched had finished. A consumer that reads events continuously must add `--follow`, and one that restarts the command after each exit must reconcile the new `snapshot` against its saved revisions. `--until-event` is an unknown option.
- Rules and prompts (v2): the rules now say how a session is woken while it waits. `snippets/commands/subscribe.md` has a new "Waking Up" section: a session must hold a wake-up source before it ends its turn; the default wait loop runs the single-event subscription (in the background for runners that wake on process exit, such as Claude Code's background Bash, in the foreground otherwise); `--follow` is only for runners that report each output line, such as Claude Code's Monitor. Each restart of the wait loop passes the remaining heartbeat seconds (at least the smaller of the interval and 15; a `--follow` subscription keeps its full interval) and compares the new `snapshot` with the saved states, revisions, `blocked`, `membership_versions`, and overdue dispatches. A subscription is stopped only through the runner's handle or its own process ID, never with `pkill -f`, and is never piped through a shell filter. The orchestration snippets and `docs/coordinator-recovery.md` apply a deliberate stop first, treat a default-mode status-0 exit with a wake-up event anywhere after the snapshot as a wake-up, and reconnect once only on failure; `snippets/execute-single.md` requires long commands to run in the foreground or in a background mode the runner reports. The start, resume, and takeover prompts carry a fixed English waiting reminder (new `templates/prompt/waiting.md`), and the orchestrate prompt carries an orchestration waiting reminder, neither controlled by a module switch; the service-backed `notify` carries no rules preamble and so no reminder. Installed rules and prompt templates take precedence over the embedded copies: after a binary-only upgrade the execution prompts show the waiting reminder at once (the installed set has no `waiting.md`, so the embedded one is used), but an installed `orchestrate.md` keeps the old orchestrate prompt and the installed rule files keep the old text; run `kander install` or `kander doctor` to refresh an existing installation.
- Fix: a user agent definition whose program does not resolve no longer makes the whole configuration invalid. Config loading used to look up `agents.<name>.path`, `review.path`, and `session.allocate[0]` on PATH and failed every command with `must resolve on PATH or be an existing executable absolute path` when one was missing, for example `kander config` from a non-interactive ssh whose PATH lacks the directory of an agent no role uses. Loading now checks only the form (a command name or an absolute path, no relative path with separators, no control characters). A missing program is reported where it is used, as for a built-in agent whose CLI is not installed: `start`, `resume`, and session allocation report that the program is not in PATH, `kander review` reports the reviewer CLI as unavailable, and `doctor` shows the agent as not installed when its `path` is missing, or without the review capability and with its configured review roles unavailable when only its review program is missing.
- Change (v2 client): the client keeps the local server and the worker running without a service manager. When a command opens a session and the loopback server is unreachable, the client starts it itself, without a question and for every caller (interactive, Agent, `--json`, without a terminal, TUI), when the project board directory exists in the default data directory; it uses the default data directory, TTL and renew interval and prints one notice (`server_self_started`). A held data directory lock stops the self-start with the unreachable error and a line about the lock, after a 750 ms wait for a server that a concurrent client is still starting (on top of the usual connection attempt). Without the board directory the question and the noninteractive failure are unchanged, and a remote URL is never started. When the client home holds a renewable credential (not released, not lost) and no process holds `worker.lock`, any session open also starts the worker. The detached server and worker no longer inherit `KANDER_EXECUTION_ID` and `KANDER_COORDINATOR_EXECUTION_ID`, and run in the data directory and client home instead of the caller's directory (a worker therefore no longer sees terminal definitions that exist only in the project install share directory of the checkout that started it); this holds for `kander server start`, `restart`, and the workers started after a claim too. `kander server stop` leaves no mark, so with Agents running it acts as a restart. A test binary never self-starts unless a test supplied a starter. See [Distributed server](docs/distributed-server.md).
- Fix (v2 client): a holder can read the material of a joint review publication before confirming it. `kander review publication <absolute-CWD> <publication-id>` is a read-only command that needs no credential and creates nothing: it prints `publication_id`, `operation`, `status`, `digest`, `created_at`, `sanitized`, `members` (`task_id`, `revision`, `generation`, `confirmed`, `stale`) and the `payload`. The material is written by the orchestrator, so every string and key is cleaned (control characters, ANSI escape sequences and bidirectional marks become `<U+XXXX>` and set `sanitized`), a string above 4096 characters is cut to its start with its length and digest, and the files of a `review-prepare` material are printed as name, length and digest only. `kander review confirm` also prints `operation` and `pending`, the members that still lack a confirmation. The confirmation request and the wait message now name the new command and say that a confirmation binds the task revision, the execution generation and the digest of the material (they said only the first two). A client no longer creates a second review request for a publication that already has one, so retrying the same command after an upgrade or in another interface language does not fail with `idempotency_mismatch`; the key of a new request now also names its text. The server, its routes, the protocol and the API types do not change.
- Change (v2 server and client): a group coordinator writes the review evidence of members in `review/` without the holders' confirmation. The server accepts a review write under a group lease token when all of these hold for every live member of the operation (a card in `working` or `review` with a standing claim): the writer holds the group's lease (a lease that lapsed on the clock but was not taken over still counts); every live member is in `review/` and belongs to that group; no live member has a dispatch in progress (`prepared`, `delivery-unknown` or `accepted`; a `completed` binding does not count); and the revision and execution generation that the request declares in the new header `Kander-Coordinator-Basis` are current for every live member, which the write transaction checks again. It covers `review plan`, `extend-plan` (also `add_members` and `resolve_batch`), `advance`, `assign`, `interpret`, `map-legacy`, `abandon`, `aggregate`, `close`, and the preparation and publication of a `kander review` run; the run's private writer secret is still required. The rule is all or nothing: one card that fails a condition sends the whole operation back to the joint publication, where every holder confirms with `kander review confirm`, as before. `review disposition` is still only the holder's, a holder's own proof still comes first, and `dispatch prepare` of another process is still a proposal. The holder loses its veto over this evidence but keeps the card revision check, `review disposition` and the card state. Each such write leaves one server log record (operation, group, group generation, members, no token), and the task events it raises carry generation 0. When the server refuses a coordinator write, the client neither retries nor falls back to the joint publication: its error says to run the command again, which reads the cards again and selects the flow anew. A joint publication prepared before the upgrade and not yet published stays as an unused request; the holder's later confirmation fails on the changed revision, which does no harm. The protocol version is still 2. Upgrade the server before the clients: an older server ignores the new header and refuses the group token as any write without the card's own proof (an error of the claim path such as `held_by_other`, `taken_over` or `lease_invalid`).
- Fix (rules, v2 worker and server): the rules of `kander dispatch` now show a complete fix evidence file and a `dispatch prepare` intent, with the field rules, and the rules of `kander notify` and the fix round list the steps a holder takes for a proposal (`request show`, `dispatch prepare`, then the dispatch-bound `move`). The line the worker types for a `fix`, `sync` or `wrap-up` proposal now says to run `kander dispatch prepare` first and not to use a bare `kander move`. `kander dispatch show` on a dispatch that has no record, but is named by a proposal, now points at that request. No command syntax, argument, exit code or acceptance rule changes.
- Breaking (v2): `--json` is one global flag of the root command, next to `--lang`, and every command except the bare `kander` and the internal `worker` accepts it (`kander --json` and `kander worker --json` are argument errors, exit status 2). The commands no longer declare `--json` themselves, and the contract Syntax lines do not list it. With `--json` a command writes one result object and a newline to stdout, with snake_case field names and no wrapper, and nothing to stderr; the fields of each form are in the `## Output` section of its contract. [JSON output](docs/json-output.md) lists the conventions, the error codes and the notices.
- Breaking (v2): with `--json` a failure writes nothing to stdout and one object to stderr, `{"error":{"code":"...","message":"..."}}`, with the exit status the command had without `--json`. `code` is a stable value (`usage`, `interactive_required`, `not_configured`, `unreachable`, the service or board code, `issue_<kind>`, `check_<kind>`, `failed`, and a few commands' own); `message` follows `--lang`. A remark that a command prints on stderr without `--json` is an entry of the `notices` array of the result object (and of the error object); the completion report template of `kander move` is the field `completion_report`.
- Breaking (v2): `kander check delivery --json` and `kander check overlap --json` no longer write the `"status":"error"` object to stdout when the check could not finish (exit status 2 or 3). They write the error object to stderr with the code `check_invalid_ref`, `check_not_ancestor`, `check_not_repository`, `check_git_unavailable`, `check_no_merge_base`, `check_output_limit`, `check_parse` or `check_internal` (the former `error.code` with `-` written as `_` and the prefix `check_`). The result objects of `pass`, `fail`, `review-required` and `action-required` did not change.
- Breaking (v2): `kander request show` prints JSON with and without `--json`; it no longer rejects a call without it. `kander request list --json` prints `requests`, an array, in an object.
- Breaking (v2): `kander config --json` prints the configuration on one line instead of indented, and the agent warnings that went to stderr are the `notices` field. `kander server status --json` on a server that is not running fails with the code `server_not_running` and the object on stderr.
- Breaking (v2): `kander issue triage` and `kander issue result` follow the same convention; `kander issue repo|list|show|import --json` write failures as the error object instead of the text line.

- Fix (v2 client, Windows): reading a file that is being replaced atomically no longer fails with `unsafe path: protected path identity changed while opening`. A rename that landed between the two opens made them differ, and the read returned that error even though the file was whole. - Fix (v2 client, Windows): reading an execution record no longer fails at once with `The process cannot access the file because it is being used by another process`. The package turns off file and registry write virtualization so agents outside the package can read the task files kander writes under `%TEMP%`; it needs Windows 10 2004 (build 19041) or later. The Store's package version rules start the version line at 1.0.0, because a Store version cannot begin with 0.
- A kander installed from Microsoft Store leaves updates to the Store: the board's startup update check makes no network request and shows no update dialog, and a self-update is refused before anything is downloaded or written. It also never copies itself onto PATH: bare `kander` asks no copy question and `kander install` copies no binary, because the execution alias is already on PATH. Other installs are unchanged.
- Releases: for a stable tag the Release workflow also builds the Store upload bundle on a Windows runner and attaches it to the GitHub Release once the `KANDER_MSIX_IDENTITY_NAME`, `KANDER_MSIX_PUBLISHER`, and `KANDER_MSIX_PUBLISHER_DISPLAY_NAME` repository variables are set; until then it skips with a notice. The new MSIX workflow can also be run by hand. See `docs/windows-msix-store.md`.
- Fix (notify, #19): tmux and tmux-session delivery now waits 500ms between the typed instruction and the `Enter` that submits it. Codex treated an Enter that arrived right after the text as part of a paste, so the instruction stayed in its composer and notify reported the acknowledgement as unconfirmed. The wait applies to every agent and to every tmux delivery: direct notify, durable dispatch, pane-mode start prompts, `dismiss` exit commands, and `kander terminal test`. herdr and luvus keep their own `agent prompt` and are unchanged.
- Terminal definitions: a step may declare `delay`, a Go duration (at most 5s) that the backend waits before running the step's command. The wait is outside the step `timeout`, a skipped step does not wait, and a cancelled context ends the wait.

## v0.9.14 — 2026-10-28

- Fix (notify, #18): direct notify no longer reports `acknowledgement=confirmed` when the pane only shows the delivered instruction, for example in an agent composer that never submitted it. The `# kander-notify:` line no longer contains the acknowledgement marker. It names the private message file and asks the agent to output the acknowledgement line that file names. The message file now starts with a fixed request followed by `KANDER-NOTIFY-ACK:<32 hex>`, so the marker reaches the pane only after the agent read the file. This applies to tmux, tmux-session, and luvus polling and to herdr `wait-output`. Durable dispatch writes the same request and is still settled only by its accepted receipt. When no marker appears, notify waits for `--timeout`, prints the existing "delivered, not confirmed" warning, and reports the acknowledgement as unconfirmed.

## v0.9.13 — 2026-10-27

- Review recovery: when two runs of the same role ran in parallel by mistake, the agent can close the batch instead of being blocked. `kander review close` accepts an optional `superseded_runs` map that names each extra run, its replacement run, and the basis. A run qualifies only as a parallel twin of a run on the conclusion chain (same commit, same reviewer, same previous run), or as the successor of a superseded run whose commit and reviewer match the conclusion run. Each entry adds the Git edge from the superseded run's commit to the replacement's, and the superseded run's findings still need dispositions. A close that meets an unlisted run fails with a hint that names the run, the conclusion run, and the entry to add. Runs that used a different reviewer, or a full first-round rerun after a fix, still cannot be superseded; the rules tell the agent to report them to the user.
- `kander review progress` adds `next_actions`, which lists duplicate runs to supersede before close is tried. Starting a review run while another run of the same role is not linked into the chain still runs and prints a warning on stderr.
- `kander update` keeps its error codes and texts, and adds one line that says where the rejected content belongs and which command writes it: managed fields, managed sections, managed paths, duplicate headings, resolved pins, and frozen contract changes.

## v0.9.11 — 2026-10-23

- Fix (subscribe): a subscription read that exhausts its 2-second board lock wait no longer ends the subscription at once. It emits nothing, keeps the last snapshot, and retries after a full `--refresh` interval. Only lock wait timeouts that continue for 30 seconds emit the terminal read-error (`read_status=maintenance`). The initial snapshot follows the same rule.
- Fix (coordinator): `kander coordinator reconcile` no longer runs Git while it holds the exclusive board lock, so concurrent subscription reads no longer time out during a reconcile. Reconcile collects Git facts under shared locks, verifies them with no lock held, and commits only verified facts. A member, checkpoint, or Git fact that changed in between is reported as a conflict. An invalid member card is still reported before Git runs.
- Rules (Git, review): a reviewed single card now integrates the way a task group does. The integration rebase is used only when it applies cleanly and leaves the reviewed patch unchanged. On any conflict or a changed patch, the agent merges the latest `develop` into the task branch instead, and later advances are merged again. A merge commit whose code conflicts were resolved by hand, or one the user asks about, is reviewed in a new batch, so a single card keeps its review plan unsealed until integration succeeds and then seals it. A task group merge-back is also re-reviewed when the user asks.

## v0.9.7 — 2026-10-16

The new `issue.result_on_done` setting (`auto` by default, `ask`, or `off`; the project overlay may override it, and the Options rules page edits it) decides whether that session publishes the result comment directly, asks first, or skips the handoff. - Agent config directories. Install, `kander doctor`, and repair resolve every global agent rules target and the Pi extension below the agent's config directory: `agents.<name>.config_dir` in the scope config first, then the variable the agent reads (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `GROK_HOME`, `KIMI_CODE_HOME`, `PI_CODING_AGENT_DIR`, `OPENCODE_CONFIG_DIR`, `XDG_CONFIG_HOME`), then the default. - Extended launch timeouts. The new optional `extended_launch_timeouts` setting (`false` by default; the project overlay may override it, and the Options "Execution and models" page edits it below the launcher) raises every launch-time wait shorter than 120 seconds to 120 seconds: the launcher pane readiness (15 seconds), session discovery (the agent's `session.discovery.timeout_ms`, default 10 seconds, and the Codex rollout wait), and pane prompt-delivery readiness (`prompt_delivery.ready.timeout_ms`). Longer waits are kept, and with the setting off every wait is unchanged. A terminal definition's `wait_ready` may read the readiness budget as `{timeout_ms}`, as the embedded herdr and luvus definitions now do; `kander terminal test` always uses 15 seconds.
