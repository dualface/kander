# Changelog

## Unreleased

- New launcher `dsh` (POSIX only): runs the executing agent inside a DeepSeek Harness host (dsh Web or dsh Desktop) through the new `kander-dsh` plugin in `integrations/kander-dsh/`. Install the plugin with `dsh plugin --profile web add <path>` (or `--profile desktop`); it is not published to npm. Select the launcher with `launcher: dsh` or `kander start --launcher dsh`; `auto` never picks it. `WINDOW` is `dsh:<container>:<pane>`. `kander check`, `kander notify`, `kander resume`, `kander dismiss` and `kander terminal test dsh` work on these cards; the agent ends with the dsh host. Kander drives the plugin socket `$DSH_HOME/kander/mux.sock` (`~/.dsh/kander/mux.sock` without `DSH_HOME`) with `curl` through the embedded definition `dsh.json`, and `start` and `resume` fail before creating a pane when the plugin and Kander speak different protocol versions, naming the side to upgrade. When several dsh hosts share one `DSH_HOME`, the first holds the socket and another takes it over without a restart once the first exits. See `docs/dsh-launcher.md`.
- The `kander-dsh` plugin now has the Kander view in dsh Web and dsh Desktop: **Kander** in the sidebar's global panel list and a **Kander** button in every session header open the board of the selected workspace (one entry per Git main worktree, with a board selector). The board tab shows backlog, todo, working, review, and done with agent status and a needs-attention mark, and starts a `todo` card with `kander start --launcher dsh`. Every dsh agent opens in a terminal tab of its own; several tabs stay open and receive output while hidden, input arrives in typing order, the tabs come back after a reload, and a `kander` focus request opens the agent's tab. A dsh host that does not hold the plugin socket shows dsh agents by status only and enables Start and terminals once it takes the socket over. The view finds `kander` through the plugin setting `kander`, then `<main worktree>/.kander/bin/kander`, then `PATH`. See `docs/dsh-kander-view.md`.
- `kander list --json --agent-status` now observes cards on `dsh`, `tmux` and `tmux-session` with the `kander check` rules for panes that report their foreground command (for example `alive` or `stopped`, with `runtime_state` `unknown`), instead of reporting `unknown`. The TUI agent status marks are unchanged.
- New launcher `herdr-core` (POSIX only): runs the executing agent in a new terminal of herdr-core, the terminal runtime behind Herdr App, through its CLI `hc`. `WINDOW` is `herdr-core:<terminal>`, for example `herdr-core:t8`. The terminal starts with `hc run --bg --no-parent --rm` in the startup directory, with a unique `--name` and the label `kander-window=<window name>`, and receives the `PATH`, `KANBAN_DIR`, `KANDER_CONFIG` and `KANDER_LANG` of the Kander process, because the core's own environment does not carry them. The agent starts by its resolved absolute path. `kander check`, `kander notify`, `kander dismiss`, takeover cleanup and the TUI agent status marks work on these cards; focus is not supported. The launcher is an embedded terminal definition that uses only `hc … --json`.
- herdr-core identifies agents only by their OSC 7501 (Program Status Protocol) reports: the agent is the reported `status.app`, and the agent status is the reported state, with `error` shown as `blocked` and the reason `error`. A `finished` or `lost` terminal counts as stopped; a terminal that has not reported yet is `unknown` and `notify` waits for it. Kander never derives a herdr-core agent state from the screen, the output or the foreground process. A prompt delivered into the pane waits until the terminal reported the agent's declared app.
- New agent field `program_status` (`{"reports": true, "app": "claude-code"}`): every built-in agent declares it. claude, codex, pi, grok, kimi and devin report; cursor, opencode and droid declare `reports: false`. A custom agent may declare its own and otherwise inherits its dialect's. Under `herdr-core`, every start entrance refuses an agent without a reporting declaration before any side effect.
- `launcher: auto` picks `herdr-core` inside an hc terminal (`HC_TERMINAL_ID` set) when neither herdr nor luvus applies; its priority is 120, below herdr (200) and luvus (150) and above tmux (100). `kander start --launcher herdr-core` also works outside an hc terminal.
- `kander doctor` reports `hc`, whether herdr-core is running (by connecting to the core socket the way `hc` resolves it, because every `hc` command starts a missing core), and, when the launcher is `herdr-core`, the configured execution and chat agents that do not report through OSC 7501. The options panel offers `herdr-core` once `hc` is installed. Kander does not install `hc`.
- Terminal definitions (schema version 1, optional fields only): an `address` may omit `container` (the pane is its own container); an environment requirement may be `auto_only`; the capability `program_status` and the `pane_facts` result `agent_app` describe OSC 7501 terminals; `create_container` receives `label_name`.
- New `kander list --json [--agent-status] [<state>]`: prints a machine-readable board snapshot (`schema_version` 1) with every card's header fields, `revision`, the `launcher` part of `WINDOW`, and a `change_token` that changes whenever a listed card or an observed agent changes. `--agent-status` adds the executing agent's `status`, `runtime_state`, `reason`, `observed_at` and `valid` for `working` and `review` cards with a `WINDOW`; without it no terminal is probed. The table output of `kander list` is unchanged. See `docs/board-snapshot.md`.
- `kander notify --pane` now addresses a pane of the card's own `WINDOW` terminal when that terminal reports agent identity, and herdr otherwise.
- Git branch mode: the new `git.branch_mode` setting (`main-develop` by default, or `main-only`) selects the mainline branch that single cards and task group branches integrate into. In `main-only` mode the released Git rules create task and group branches from `main`, merge finished work straight back into `main` under the card's own authorization, and never create `develop`. `kander config`, `kander doctor`, the project overlay, and the Options rules page handle the setting; a config without it keeps the `main` + `develop` workflow. Wrap-up integration evidence must target the configured mainline branch, read from the integration checkout's project overlay.
- Git rules: `main` and the mainline branch may now be rewritten on the remote with `--force-with-lease` pinned to the just-fetched commit, in both modes; plain `--force` stays forbidden, and no flow requires such a push. When the local sync of the mainline branch or `main` fails because the local branch is no longer an ancestor of the remote, the rules reset it to the remote after stashing any uncommitted changes (and restoring only that stash entry) and saving unpushed commits on a local `backup/<branch>-<timestamp>` branch.
- Fix (review): mechanical closure now refuses unreported files in each role's conclusion-commit-to-`passed_at` repair range, fixed dispositions beyond `passed_at`, and added lines in `dead-code` or `redundant-test` paths unless a `documentation` assessment also declares the file. Refusals identify the affected files or findings and direct the closer to complete declarations, correct `passed_at`, or run an incremental review. Historical closure verification and saved evidence formats are unchanged.
- Rules (review): mechanical-only rounds skip reviewer re-runs only when the repair range contains qualifying mechanical fixes alone. Non-blocking fixes that change production logic require incremental review by the reporting role. Redundant-test findings must identify retained coverage for every assertion; closure requires an assertion correspondence table. Dead-code fixes that delete tests must identify existing coverage the reviewer asked to preserve. Adding or moving tests to preserve coverage requires incremental review.
- Fix (`kander notify`): the direct delivery channel in the progress and result lines is now named after the terminal definition, as `<definition>-direct`. luvus used to report `tmux-direct`, and a user definition whose binary differs from its name reported two different channels. herdr and tmux output is unchanged.
- Rules: new task cards must save the detailed plan confirmed by the user and agent before creation self-review, including cards left in backlog for later execution. Small cards use `IMPLEMENTATION`; large cards use `plan.md` linked from `spec.md`. The saved plan preserves the technical approach, ordered steps, constraints, decisions, and verification needed by an agent that did not join the discussion. Existing cards need no backfill and are not blocked by a missing plan.
- Rules: card templates, content requirements, scope declarations, conditional workflow fields, and creation checks now have one definition in `snippets/card-content.md`. Intake, task group, issue, review, and execution rules reference it while retaining their applicability and operational responsibilities. Additional review scope detail remains conditional on the review module or an explicit request for the full review flow.
- Rules: creation self-review checks plan completeness, and independent card reviewers read linked plans and attachments. Multi-card plans must preserve the full confirmed plan across their members; temporary handover notes never replace the saved card content.
- herdr-core: the TUI and `kander list --json --agent-status` now observe multiple hc terminals with one `terminal.list` request through `hc connect --json`. The full response preserves OSC 7501 app identity, status, and session labels that the compact `hc ls --json` output omits. A missing terminal is confirmed individually; malformed or duplicate rows fail the observation instead of reporting an agent alive.
- Fix (herdr-core): session reverse lookup now uses the full list response and compares each terminal's actual `kander-session` label. It excludes finished and remote terminals. Validation follows exact JSON paths, so unrelated labels named `status`, `state`, or `address` cannot reject a valid response or make a remote terminal appear local.
- herdr-core: the terminal interface now exposes foreground PID and process name from `hc get` for a matching live terminal. Agent identity and readiness still require OSC 7501 reports; foreground process names never substitute for them.
- Fix (herdr-core): command and notification delivery allow up to 90 seconds for hc's default 60-second draft protection and submission checks, while respecting a shorter caller deadline. A `started: false` response does not trigger a resend; notification acknowledgement still checks its marker. Cancelled sends are not retried.
- Terminal definitions (schema version 1, optional additions): steps accept literal `stdin` of up to 64 KiB, with EOF, process-tree cancellation, and bounded output in the default runner. Step and row field maps accept `json_regex:<dotted.path>:<pattern>` to validate one JSON value without matching unrelated nested fields. Program-status definitions may provide `agent_list` with `agent_app` and `session_marker`.
- Validated against hc 0.1.20 on Linux with isolated real-core lifecycle tests. The launcher remains local and POSIX-only. Focus and native Agent session reporting remain unavailable; Kander uses session labels and polls output for notification acknowledgement.

## v1.1.2 — 2026-11-03

- Fix (#22, `kander resume --adopt`): on tmux, tmux-session, and other launchers whose panes carry the session marker, adoption now writes the marker a failed start left out, then probes again and adopts the running executor. It writes the marker only when it can prove the session: the card `SESSION` names one (for example a `claude` card), or the card is a `codex` card and exactly one Codex rollout names the task, its launch directory, and a creation time not earlier than the start attempt began. The marker goes on the pane only; the card and the start attempt stay unchanged until the adoption is recorded, and a `codex` card keeps `SESSION: codex`, as after a successful start. Adoption prints `session-marker-written: <id> window=<address> session=<session>` before `adopted: ...`.
- Fix (#22, `kander resume --adopt`): adoption refuses without writing anything when zero or several Codex rollouts match or the rollout scan fails, when the card or its start attempt changed after the probe, or when the marker write fails. A marker written before a failed adoption leaves the start unfinished, so `kander resume` and `kander notify` still refuse it, and `kander coordinator recover` refuses it as before (an `unresolved` start now reads `alive` there); run `--adopt` again. `droid` and the agents with `session.mode: discovered` (`devin`, `kimi`, `opencode`) keep the refusal of v1.1.1, because their sessions cannot be tied to one launch, and adoption runs no session discovery for them.
- Fix (#22): `started-unresolved` and the refusals of an unfinished start by `kander resume`, `kander notify`, `kander coordinator recover`, and session repair list `kander resume <id> --adopt --decision <reference>` again for an unmarked pane that adoption can mark, judged from the card `SESSION` and the agent alone; they run no session discovery and write nothing. Every other unmarked pane keeps the hint of v1.1.1.
- Fix (#22, `kander coordinator recover`): a reset refused for a member whose `unresolved` start has not ended now also names `kander resume <id> --adopt --decision <reference>` when adoption can end it: the probe read the recorded pane `alive` or `alive-orphaned`, or unmarked with a session adoption can mark. The probe and the reset rules do not change.
- Fix (`kander terminal test`): a terminal definition without a focus operation now reports focus as unsupported instead of succeeding, so the Focus check no longer fails for every definition whose focus capability is false. Focus returns unsupported before it probes the pane or runs any command.

## v1.1.1 — 2026-11-03

- Fix (#22, `kander start` and `kander resume --agent`): a late failure on tmux, tmux-session, or another launcher whose panes carry the session marker, before the marker was written (failed session discovery or marker write), no longer lists `kander resume --adopt`. Such a pane reads `unknown`, so adoption could never succeed. `started-unresolved` now first tells you to stop the old executor in `WINDOW` by hand, because a takeover leaves it running, then names `kander resume <id> --agent <agent> --decision <reference> --message <message>`. A start that wrote the marker, and herdr and the other launchers, keep both next steps.
- Fix (#22, `kander resume --adopt`): adoption of an unmarked pane is refused with the same hint. The plain `kander resume` and `kander notify` refusals of an unfinished start no longer name `--adopt` for an unmarked pane either.
- Fix (upgrade from 1.0.0): a card whose start attempt stayed `pending` after a 1.0.0 takeover rewrote `OWNER` or `SESSION` is now refused by `kander resume --adopt` before any probe, with a localized error that names `kander resume <id> --agent <agent> --decision <reference> --message <message>`. It used to probe and then fail with `start adoption binding`. The attempt stays `pending`. The plain `kander resume`, `kander notify`, and `kander coordinator recover` refusals of a `pending` start name only the takeover for such a card and for an unmarked pane.
- Fix (#20, `kander coordinator reconcile`): a member blocked by `execution cycle changed without lifecycle handoff` keeps that reason and now adds the next step: ask the user first, and run `kander coordinator recover` only after the user decides.
- Fix (Windows build): a `kander` built from a Windows checkout no longer embeds CRLF line endings in its rules, card templates, and agent files. The repository now has a `.gitattributes` that checks text files out with LF, the Microsoft Store build turns `core.autocrlf` off, and tests fail a build whose embedded files contain a carriage return. A Windows clone made before this change keeps its CRLF files until they are checked out again.
- Fix (`kander update`): a card body whose submission differs from the stored card only in line endings (CRLF against LF) is no longer refused with `Managed field or document cannot be edited through update`. The comparison of managed fields, managed sections, and the frozen contract ignores the line ending, and a real change is still refused. The accepted body is stored with the line ending of the card, CRLF or LF, so a submission no longer leaves mixed line endings. An LF submission to an LF card is stored byte for byte as before.

## v1.1.0 — 2026-11-02

- New (#21): the `install_rules` switch controls whether Kander writes into an agent's own files: the rules file reference, `AGENTS.override.md`, the `.mdc` frontmatter, the replacement of a symlink to the previous entry, and the rules extension. The top-level key covers every agent, and `agents.<name>.install_rules` (built-in agents only) overrides it per agent. Both default to `true`, so existing configs keep their behavior. Only the scope `config.json` sets them; a project overlay value is ignored with a doctor warning.
- New (#21): with an agent's switch off, `kander install`, `kander doctor`, the bare `kander` startup doctor, the TUI environment check, and the options save never write its files, and doctor prints one "turned off" line instead of a missing-integration warning. The rules root is still extracted and repaired. A rules file that several agents read (a project `AGENTS.md`, or one linked to another agent's) stays unwritten while any of them is off.
- New (#21): `kander install` lists every agent file it would write, each marked create, append, rewrite, replace, update, or unchanged, and asks which agents get the rules before it writes anything. A fresh install selects all; a reinstall keeps an agent the user turned off. Cancelling writes nothing. Unselected agents are saved as `agents.<name>.install_rules: false`.
- New (#21): the Options rules page edits the global switch and one switch per covered agent on the scope tab.
- New (#21): `kander uninstall [--yes]` removes the Kander load commands from the agent rules files (other bytes stay), the released rules extensions, and the rule and state files of the rules root, then turns `install_rules` off so a later doctor run injects nothing. It lists the plan first and asks y/N on a terminal; it keeps the binary, `config.json`, the share directory, and the board.
- Fix (#21): a Kander reference that appears only inside an HTML comment, a code fence, or a negated sentence is now reported as inactive by doctor repair and the options save, not as connected.
- Docs: the documentation no longer mentions `kander doctor --repair`; `kander doctor` always repairs.

- Fix (review): review obligations are now exact per member. A drop of a `required` batch no longer hides its role from a later `kander coordinator recover`: the plan keeps the roles of dropped batches per member in `dropped_roles`, also after a `decision` or a `release_obligation`, and the reset owes them in either order. `kander move done` and `kander review progress` name each missing role as `recovery-role:<member>/<role>`.
- Fix (review): a member that reached `done/`, or moved from `done/` into `archived/`, no longer blocks the other members with its recovery obligation, and `kander review progress` suggests no batch for it.
- Fix (review): a batch with no member left now blocks `kander move done` of the other members while an assigned finding of the excluded member has no record, or its latest status is `confirmed` or `unverifiable`. A `withdrawn` record ends that wait and can be written without closing the batch. The same two statuses now count as owed in every batch. A card already in `done/` stays valid when another member leaves later.
- Test (model): the composite state model now tries `move done` while a card owes a review, decides that debt from the history of operations, and fails when the gate stops naming it.
- Fix (`kander coordinator recover`): a Codex card with no session reference and a stale `WINDOW` no longer reads `stopped` beside a running executor. Its session is resolved from the rollouts, only when the recorded address is stale and inside the 10-second probe limit, and the reverse lookup then decides. A resolution that fails reads `unknown`.
- Fix (`kander coordinator recover`): a reset is now refused when the probe finished and saw an executor it could not prove. The cases are 2 or more reverse lookup matches, a pane whose session identity is uncertain for a reason other than the probe deadline, a pane whose agent status cannot be classified, and a tmux pane with no session marker. A failed probe (terminal unavailable, deadline, unfinished lookup, failed resolution) still proceeds. `kander check` output and JSON do not change.
- Fix (`kander coordinator recover`): a reset is now refused while the current execution record is `pending`, so a running starter keeps its executor. The error names the next steps: wait, `kander resume --adopt --decision`, or `kander resume --agent --decision`. An `unresolved` record still follows the probe.
- Fix (`kander coordinator recover`): each refusal now names its evidence and an address when it has one, and only next steps that work. A `review/` member is told to stop the executor at that address and run `recover` again, not to use `kander resume --agent`. Several matches give the count and tell you to stop the executors that match the session.
- Fix (`kander resume --agent`): a task group member in `review/` whose start attempt has not ended now takes a takeover with `--decision`, without a dispatch option. A `running` record keeps the refusal.
- Fix (`kander resume --agent`): a takeover now finds a drifted old executor before the new one starts, and its cleanup ends that executor at the found address. The new executor is never a target. A kept drifted pane is reported by its own address, and a search that does not finish or finds several matches now reports `original container kept`, not a cleaned container.

- Fix (upgrade from 1.0.0): a card that 1.0.0 started and then reclaimed from `review/` with `kander move <id> working --owner <agent>`, with no handoff, works again. It read as a takeover of the old cycle: `kander resume` and `kander resume --agent` failed with `start success binding`, also when `kander coordinator recover` named that way out, and `kander coordinator reconcile` blocked the member. It now reads as a reclaim of the card's cycle, also after the first write. `kander resume --agent --decision` replaces the executor and `kander coordinator reconcile` accepts the member. A plain `kander resume`, `kander notify` and `kander dismiss` refuse it with the error that names `kander resume --agent`, because the record has no session of its own. `SESSION` still shows the old executor.
- Reconcile accepts this cycle change only on a link synthesized for such a card. The cycle change has no decision record, and the user accepted that. The checkpoint shows it per member in `unrecorded_reclaims`. Any other cycle change with no handoff still fails with `execution cycle changed without lifecycle handoff`.
- Fix (upgrade from 1.0.0): a schema 1 dispatch round with no receipt now keeps its real place, by `Input.CreatedAt`. It used to sort last, so `kander coordinator reconcile` failed with `unfinished previous dispatch` or `unbound member lacks dispatch termination`, and a card with several such rounds failed `kander dispatch prepare`. A missing creation time, a time equal to an adjacent round, or times that disagree with the receipts still fail with `legacy dispatch order unknown`.

- Fix (tmux, #26): an agent started through `tmux` or `tmux-session` now runs in the startup directory whatever the tmux server's own directory is. The pane enters the directory before `exec`.
- Fix (start, #26): a container launcher now refuses a startup directory that is missing, is not a directory, or has a line break in its path, before it creates a container. tmux used to exit 0 and open the pane in `$HOME`. `foreground` and `console` are unchanged.
- Fix (start, #26): a tmux launch now succeeds only after the pane has entered the startup directory or shows the agent's `process_name`. A pane that ends first fails the launch and closes only its own window, including for a directory removed after the check. Triage, chat and `kander orchestrate` used to report success. A pane with no answer within the readiness timeout also fails the launch; on a durable dispatch it stays `DeliveryUnknown` and keeps the window.
- Terminal definitions: `run_command` has a new input `cwd_quoted`, and the new optional operation `pane_directory` reports a pane's working directory. Existing definitions stay valid.
- Fix (`kander review`, #27): a rejection for leftover child processes now leaves attributable evidence. On POSIX, before `SIGKILL`, Kander records each observed reviewer process group member (PID, parent PID, process group, start time, executable base name, observation time) in `reviews/<run_id>/process-evidence.json`, with the cleanup result, and the failure message names that path. Argv and paths are never recorded, and at most 64 records are kept. Without a run, the record goes to stderr. Windows produces no records.
- Fix (`kander review`, #27): a reviewer that exited with 0 now gets a recheck of at most 1 second before `SIGKILL`, so a child that exits by itself no longer rejects the result. A child still alive at the end is rejected and killed, and a failed process snapshot rejects the result. A timeout, an interrupt, or a non-zero exit skips the recheck. The root cause of the reported macOS case stays open until new evidence exists.
- A run with `process-evidence.json` is rejected by older versions, so finish such a card with this version.
- Fix (execution ledger): a card that v1.0.0 started keeps working after the first ledger write. `kander resume`, `kander notify`, `kander dispatch prepare` and `kander coordinator reconcile` failed on such a card with `start result original`, or with `start attempt original` when a v1.0.0 takeover had changed `OWNER`, once a window, session or process write stored its record. The stored record now keeps the finish of the start attempt. A v1.0.0 takeover gets its own record and a handoff link on the first write, and the originals of the attempt stay as they are. This defect was never released, and a board that already wrote such a record through a `develop` build stays damaged.
- Breaking (`kander resume`): a plain `kander resume` now refuses a `working/` or `review/` card whose start attempt has not ended (current execution record `pending` or `unresolved`), also with `--dispatch-id`. It used to start a second process on the same session and rewrite `WINDOW`, so a later adoption or takeover used the wrong pane. Nothing starts and nothing is written, and the error names `kander resume <task-id> --adopt --decision <reference>` and `kander resume <task-id> --agent <agent> --decision <reference>`. Scripts that resume right after a start must wait for `kander start` to return.
- Fix (`kander notify`): the same check now refuses a card whose start attempt has not ended before any dispatch ID is printed or bound. `kander dismiss` is unchanged.
- Fix (`kander coordinator recover`): a reset now searches a stale `WINDOW` by session. An executor found at a new address reads `drifted` and the reset is refused, and the error names the result. It used to read `stopped`, so a reset passed a running executor. `stopped` and `unknown` still proceed. A session with no reference has nothing to search by and still reads `stopped`.
- Fix (`kander coordinator recover`): the probe stops after 10 seconds. A hung terminal reads `unknown` and the reset finishes, where the probe could use the whole 30-second command deadline and fail the reset.
- Breaking (`kander review`): a run now records the execution cycle of each member (`member_cycles`), and a new closure needs a conclusion run of the current cycle. A run of an old cycle no longer closes an open batch or a batch a plan adopted, whether the cycle changed through `kander coordinator recover`, a reclaim, or a rebind. `kander review close` refuses, and `kander review progress` and `kander move done` name `stale-run:<batch>/<role>/<member>`. Run the role in the new cycle: on a new commit with `--advance-file` and `--previous-run-id`, or on the same commit with `superseded_runs`. A closed batch keeps its runs. A run from an older binary counts only while the cycle of the member never changed, so a card reclaimed mid-review needs one more review after this upgrade.
- Breaking (`kander review extend-plan`): `drop_batches` on a `required` batch no longer ends that review. The role stays owed for each member until a later batch that requires it, names the member, and closes. `seal` refuses without such a batch, and `kander review progress` and `kander move done` name `dropped-review:<member>/<role>`. An optional `decision` on the drop leaves no obligation.
- New (`kander review extend-plan`): `release_obligation` with `kind`, `task_ids`, and `decision` ends a drop obligation on a user decision, also on a sealed plan. With `kind` `recovery` it ends the obligation of a member reset with no plan, only under a plan that requires no role. Each `decision` stays in `plan-history`.
- Fix (`kander coordinator recover`): a reset of a member with no plan now leaves a recovery obligation. A plan created afterwards needs a real review of every role it requires, and an all N/A plan needs `release_obligation` before `kander move done`.
- A plan with `drop_obligations`, a run with `member_cycles`, and a recovery record with `release_decision` are rejected by v1.0.0, so finish such a card with this version.
- New (`kander review extend-plan`): `resolve_batch` recovers a card from a batch an older binary ran outside its plan. Such a batch failed `kander check`, `kander review progress`, and `kander move done` with `unplanned execution batch` and had no way out. The request names one closed planned batch that covers the range, every role and every remaining member, and gives each finding a result. A must-fix finding needs a verified `fix_commit` or a user `decision`, and basis text alone never closes one. Works on a sealed plan, changes no batch and no run evidence, and records itself in the plan and in `plan-history`. `kander review progress` prints the record, and a later run in the batch fails the gate again. A plan with such a record is rejected by v1.0.0, so finish the card with this version.
- Fix (review, #20): `kander review advance` and a review run with `--advance-file` now refuse to move a batch target while an assigned finding has no author disposition, and the error lists each task, run, and finding. Mechanical items count. An advance could previously overtake a member's fix round and leave its fix dispatch rejected at every base.
- Fix (dispatch, #20): a batch already advanced past a finding recovers without any board edit. A fix dispatch with `--base` set to the current batch target may reference a run on the batch's recorded advance chain, and `kander coordinator reconcile` accepts the completed round.
- Fix (coordinator, #20): reclaiming a `review/` card that never held a dispatch now records a handoff, so `kander coordinator reconcile` follows the cycle change instead of failing with `execution cycle changed without lifecycle handoff`.
- Breaking (`kander move`): `kander move <id> working --owner <agent>` from `review/` now requires `--decision <reference>`. Scripts that omit it are rejected with no change. A card that a plain reclaim already moved keeps its old failure; this release has no repair for an existing checkpoint.
- New: execution ledger. Every change of `OWNER`, `SESSION`, `WINDOW` or the execution cycle now writes a producer record beside the card. `kander coordinator reconcile` walks these records, so missed reconciles no longer strand a member, and a change no record carries fails.
- Fix (start, #22): a late launch failure no longer destroys an executor that already worked. Before it closes anything, `kander start` compares the card with its own last write. With executor evidence it keeps the container and the card, writes the start attempt as `unresolved`, prints `started-unresolved: <task-id> window=<address> reason=<reason>` with two next steps, and exits 3. Without evidence it closes the container and rolls back as before, and exits 1. A failed read of the card keeps the container too. Scripts must treat exit 3 as "do not retry `kander start`". The TUI start dialog shows the same result.
- Fix (start): when closing the container fails, the card no longer rolls back, because a second `kander start` would run a second executor. The start ends unresolved.
- New: `kander resume <task-id> --adopt --decision <reference>` keeps the running executor of a `pending` or `unresolved` start. It starts nothing and needs an executor confirmed `alive` or `alive-orphaned`. A tmux pane with no session marker reads `unknown`, so such a start needs a takeover.
- Breaking (`kander resume --agent`): a takeover of a `pending` or `unresolved` start now requires `--decision <reference>`. On a `running` record it stays optional. A takeover uses the same results as a start, including exit 3.
- New: a launcher that a takeover or an adoption overtook prints `superseded: <task-id> ...` and exits 0. It closes nothing and rolls nothing back.
- Breaking (`kander dispatch prepare`, `kander notify`): both refuse a card whose start attempt has not ended, and the error names the next step. This covers the short window while `kander start` still runs, so a script that notifies right after a start must wait for `kander start` to return. A start attempt an old binary left in `pending` ends the same way, through adoption or takeover.
- New: `kander dispatch settle <task-id> <dispatch-id> <revision>` ends the binding of a completed round. `kander move` into `archived/` or `trash/` settles a completed binding by itself, and a settlement counts as a release for a reclaim.
- Fix (`kander start`, `kander resume --agent`): an executor that writes the card early no longer fails session confirmation, the `WINDOW` write of a pane-delivery agent such as Kimi or Droid, or the session write-back of a takeover. A failed launch still restores nothing over newer executor work.
- Fix (coordinator): reconcile no longer fails after a dispatch was discarded between two reconciles, after a claim followed by `kander move ... trash`, after `trash` of a member that finished wrap-up, or after a plain `kander move <id> working` that followed a rollback. A member in `archived/` or `trash/` is checked only for its result and its execution records, and its Git facts are no longer verified again.
- Breaking (`kander update`): a `TASK_GROUP` change is refused while the old or the new group has a coordinator checkpoint.
- Breaking (`kander dispatch fail|cancel`): ending an accepted round now requires `--decision <reference>`.
- Breaking (`kander resume`, `kander notify`, `kander dismiss`): a card claimed or reclaimed with `--owner` is refused with a next step, before any dispatch binds. `kander resume --agent` still works, and now also replaces a claimed card that has no `SESSION`.
- Breaking (dispatch records): a dispatch is refused when its recorded execution cycle differs from the card's. Dispatches from an older version have no cycle and keep working.
- New (#23): `foreground` and `console` starts record a process identity beside the card: boot, agent PID, kernel start time, and executable. The identity is written once the agent reads its task file, because only then is its final executable known; until then the card reads `unknown`. On Windows it is written at once. On a mount with `noatime` a read is not visible, so the card stays `unknown` until the agent removes its task file while it still runs. `kander check` and `kander subscribe` now answer for these cards instead of always saying `unknown`, on Linux, macOS, and Windows. Other platforms report `unprobeable`.
- New (#23): the liveness result set adds `alive-orphaned` (the agent runs, its foreground Kander process is gone), `identity-mismatch` (a process holds the recorded identity but is not this execution, or the card moved on), and `unprobeable` (the platform has no process identity or refused the probe). Scripts that read `status` from `kander subscribe` must accept these values. `unprobeable` and `unknown` never count as alive. A card started by an older binary reads `unknown` with the reason "old card has no process identity".
- New (#23): `kander resume --adopt` works on `foreground` and `console`. It uses the process identity and accepts `alive` and `alive-orphaned`.
- Breaking (`kander resume`, `kander notify`, #23): `foreground` and `console` have no native resume. Plain `kander resume` and the recovery channel of `kander notify` refuse a card that runs on either of them, and a relaunch through either of them, with the next step: adoption or a takeover. This also covers cards from older binaries. `kander resume --agent` is not refused.
- Breaking (`kander notify`, `kander resume`): a `review/` card of a task group, or with a binding, now refuses a message with no dispatch option, and the error gives the `--kind` usage. The message no longer turns into a fix dispatch, which always failed with `fix binding required`.
- Breaking (`kander review`): a run in a batch outside the plan of a member is refused before the batch exists, and the error names `kander review extend-plan`. `kander review plan` refuses a member that already has a run outside the new plan.
- Breaking (`kander review plan`): several planned batches must form a continuous chain. Each base must equal the target of the batch before it.
- Breaking (`kander review advance`, `--advance-file`): a batch with a planned successor refuses to advance. `kander review extend-plan` with the new `drop_batches` removes trailing batches that have no run. This reopens a sealed plan, and the batch IDs stay used.
- Breaking (`kander move done`): a member rebound after all its batches closed needs a new batch. `kander review extend-plan` appends one, also to a sealed plan, and that batch may record every role as N/A with a reason. `kander review progress` lists `cycle-batch:<task-id>` and the action `append-cycle-batch`.
- New: `kander move` into `archived/` or `trash/` of a plan or task group member writes a member exclusion record in the same transaction. `kander coordinator reconcile` requires this record for a terminal member with a stored execution chain. A move from `done/` into `archived/` writes none. A move from `done/` into `trash/` does.
- Fix (review): a member that left no longer blocks the others. Plan, batch, and closure writes skip the copies of excluded and archived members, completion covers the members that remain, a run names the members that remain, a run prepared before the exit settles without that member, and a batch with no member left neither closes nor blocks.
- Fix (review): `kander review extend-plan` no longer fails with `plan member is terminal` when a group has a `done/` member. A later batch of another member leaves a `done/` member, its checkpoint mirror, and its completed wrap-up unchanged.
- New: `kander review disposition` accepts `withdrawn` for an assigned finding of an excluded member. The orchestrator writes it with `withdrawal.exclusion_id` and `withdrawal.decision`. It is never a fix, and the aggregate view shows it apart in `runs[].withdrawn`.

The run's findings and failures still bind the close. Entries without `decision` keep the parallel duplicate rule.
- Fix (errors): the messages for a stale dispatch, an expired or too narrow wrap-up grant, an interrupted run with changed inputs, a frozen task context, a review pin conflict, and a moved plan worktree now name the real way out. A frozen task context error no longer says to start a new batch: it names the snapshot, also before the first run finalized.
- New: `kander coordinator reconcile` judges each member alone. A member that fails stays at its last mirror with `blocked.reason` in the checkpoint, and the other members advance. The next reconcile that accepts the member clears the field. A stale card revision still fails the whole request.
- Breaking (`kander coordinator reconcile`): the JSON output adds `result`. Exit 0 means `complete`. Exit 3 means `partial`: the checkpoint is committed and some members are blocked. Exit 1 with JSON means `failed`: the checkpoint is committed and every member is blocked. Exit 1 with no JSON means the request was refused. A failed Git verification or a wrong dispatch observation no longer leaves the checkpoint unchanged, so the next request needs the new revision. Scripts must read `result` and the exit code.
- New: `kander subscribe` events carry `blocked`, with the reason of each blocked member. A change of the set emits `member-blocked`. Consumers must accept the new event.
- Breaking (`kander dispatch prepare`, `kander notify --kind wrap-up`, `kander dispatch authorize-wrap-up`): each refuses a wrap-up while any member of the group is blocked.
- New: `kander coordinator recover <absolute-request.json>` ends a block that stays. It needs group_id, member, expected_revision, expected_epoch, decision, and reason, and it writes an immutable record that `kander coordinator show` lists under `recoveries`. A `working/` or `review/` member is reset: it gets a new execution cycle, a `review/` card returns to `working/`, and the next step is `kander resume --agent`. An N/A batch does not count, a later reclaim does not end this, and `kander review progress` lists `recovery-review:<task-id>`. A role the plan never required may stay N/A.
- Fix (coordinator, DE-18): a completed wrap-up is verified against Git once and recorded as immutable evidence. `kander move done` of a wrap-up verifies, and it refuses the move when that fails or when no checkout in reach holds the target commit, so a board set by `KANBAN_DIR` completes a wrap-up from a checkout. - Fix (`kander move`): a reclaim of a card an older binary changed without a record no longer breaks its execution chain for good.
- Upgrade: old and new binaries cannot share a board. A new binary reads old boards in place and writes schema 2 execution and dispatch records and schema 3 checkpoints with `recover` records, which an old binary rejects. Upgrade every session that touches a board together.
