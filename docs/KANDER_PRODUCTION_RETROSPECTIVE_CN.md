# Kander 生产实践回顾

[English](KANDER_PRODUCTION_RETROSPECTIVE.md) | **简体中文**

Kander 不是一个多 Agent 演示项目, 而是一套在真实软件开发中打磨出来的工作流系统.

自 2026 年 8 月起, Kander 一直用于开发 **QuickTUI**. 这是一个真实的跨平台产品, 涵盖 iOS、Android、后端服务、网络、鉴权、代码生成、测试与集成. 截至 2026-10-07, 这套工作流在 QuickTUI 上完成了 **1,317 个真实开发任务**, 在 5 个项目中合计超过 1,700 个. 数字与统计口径见 [Kander 实战数据](production-stats-cn.md).

这一点很重要: Kander 的许多核心设计不是在白板上想出来的, 而是来自日常开发中真实遇到的失败、审核发现、竞态条件、被推翻的假设、集成冲突和恢复场景.

## 不只是「同时跑几个 Agent」

Kander 基于一个简单的判断:

> 一旦编码 Agent 强到能实现真实功能, 难点就从「生成代码」转向「协调、验证和控制这些工作」.

一个典型的 Kander 任务更接近这样:

```text
任务
↓
计划
↓
冲突检查
↓
Agent 执行
↓
测试 / 验证
↓
独立审核
↓
核实审核意见
↓
修复
↓
增量复审
↓
集成
↓
完成
```

目标不是让并发 Agent 越多越好, 而是在每个任务都可追溯、可恢复的前提下, 让 **安全且有用的并行** 最大化.

## 测试通过不等于工程质量

一个生产任务很能说明问题.

一次 Android 网络与连接保活改动, 进行到这一步时:

- **2,889 个测试全部通过**
- lint 通过
- 构建检查通过

在常规流程里, 这通常就算完成了.

Kander 的独立审核仍然找出了几个真实问题, 包括:

- 旧一代连接的过期回调影响了新连接;
- 心跳挂起 / 恢复的状态错误;
- 迟到的回调重新启动了已经停止的保活逻辑;
- 鉴权租约的生命周期问题;
- 测试是绿的, 但根本没有验证要求的行为.

这些审核意见经过核实, 转成具体的修复工作, 再次审核. 任务最终达到 **2,935 个测试通过**, 并通过最终的 PM/QA 审核.

这是生产历史中最清楚的一条经验:

> **测试全绿是必要条件, 但并不总是充分条件.**

## 审核是工作流的一部分, 不是最后补一句评语

Kander 不把审核当成「问另一个模型代码看起来行不行」.

一次审核可以绑定到:

- 任务;
- 审核角色;
- 审核 Agent / 模型 / 推理档位;
- base commit;
- target commit;
- 审核批次与审核运行;
- 审核意见和后续修复.

审核意见不会被自动当成事实. 它们要先经过独立核实, 才会变成修复工作.

于是工作流更接近这样:

```text
审核员提出意见
        ↓
独立核实
        ↓
确认 / 驳回
        ↓
修复
        ↓
增量复审
```

这很重要, 因为审核员也会出错. Kander 把审核当成可审计的工程流程, 而不是一次神谕式调用.

## 控制并行, 而不是堆 Agent 数量

真实项目里有共享契约、生成文件、项目配置、鉴权状态、协议定义等热点.

让更多 Agent 同时改这些热点, 很容易造成:

- 合并冲突;
- 语义冲突;
- 重复劳动;
- 架构漂移;
- 契约不一致.

所以 Kander 在派发工作之前, 会先关注任务依赖和改动面的重叠.

有些任务应该并行.

有些不应该.

目标不是「更多 Agent」, 而是 **更好的编排**.

## 失败是常态, 所以执行必须可恢复

长时间运行的 Agent 工作会以很多普通方式失败:

```text
终端崩溃
Agent 崩溃
网络断开
Kander 重启
提示已发出, 但状态还没持久化
Agent 已完成, 但控制方丢失了会话
```

Kander 持久记录派发信息, 让这些工作可以被对账, 而不是悄悄变成一笔糊涂账.

这是演示和生产工作流的重要区别: 失败与恢复被当作正常运行状态来对待.

## 不同模型可以担任不同角色

Kander 不绑定某一个模型或某一个编码 Agent.

生产任务已经在实现和审核中使用了不同的 Agent 和模型家族. 这让下面这样的工作流成为可能:

```text
实现模型
        +
PM/QA 审核员
        +
Security 审核员
```

目标不是找一个什么都最强的模型, 而是让不同模型在各自最擅长的地方发挥作用. 配置示例见 [多模型路由](multi-model-routing.md).

## 工作流本身是被生产训练出来的

在超过 1,700 个真实任务中, Kander 积累了这些经验:

- 哪些任务可以安全并行;
- 隐藏的生命周期和并发缺陷会出现在哪里;
- 哪些测试会变成假绿;
- 为什么审核意见必须独立核实;
- 什么时候增量复审比重做完整审核更好;
- 为什么精确的 commit 来源很重要;
- 失败的派发和会话应该如何恢复.

这段历史是这个项目最重要的部分之一.

Kander 不打算取代你的编辑器、终端、Git 客户端或编码 Agent.

它位于它们之上一层:

> **Kander 是编码 Agent 的工作流运行时.**

一个开发者. 多个编码 Agent. 一套受控的工程工作流.
