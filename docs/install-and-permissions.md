# Installation and Permission Boundaries

How the binary installs itself and which filesystem boundaries the configuration, board, Git exclude, and review runtime enforce. The released rules (`rules/KANDER-BASE-RULES.md`) keep only the boundaries an agent must respect; the mechanics below are implementation contracts for this repository, verified by the tests of `internal/install`, `internal/config`, `internal/board`, and `internal/fs`.

## Installation

### Automatic updates

Bare `kander` TUI startup checks GitHub for a newer release in the background. The request has a five-second deadline and does not delay the first screen. CLI subcommands do not perform this check.

The check follows the release channel of the running version:

- The release channel holds `2.Y.Z`. Such a binary updates only to a newer `2.Y.Z` release whose GitHub release is not marked prerelease, even when GitHub's Latest release is a 1.x release.
- The prerelease channel holds `2.Y.Z-alpha.N`, `2.Y.Z-beta.N`, and `2.Y.Z-rc.N` (`N` without leading zeros). Such a binary updates only to a newer 2.x prerelease whose GitHub release is marked prerelease. It is never offered a release, so moving from a prerelease to `2.0.0` takes one manual reinstall.
- Every other version belongs to no channel and sends no update request: development builds (`dev`, `2.0.0-dev+<commit>`), git describe builds (`2.0.0-beta.1-5-g<hex>`), versions with build metadata, other prerelease names, and every major other than 2, including 1.x.

Kander reads one page of the GitHub releases list (`releases?per_page=30`), not `releases/latest`, because a prerelease never becomes Latest and a later 1.x patch makes 1.x Latest again. Older entries are not compared. Drafts are ignored, and an entry whose prerelease flag does not match its tag's channel is ignored. A response above 4 MiB, one that is not a JSON array, or one with an item that lacks a non-empty string `tag_name` or a boolean `draft` or `prerelease` fails the check instead of being read in part. A tag counts only with exactly one leading `v`. The candidate with the highest version wins.

The Homebrew tap publishes only releases. A Homebrew-managed executable on the prerelease channel therefore neither checks nor applies an update; install prereleases from the GitHub release archives.

One machine has one global `kander`. Installing v2 replaces the 1.x executable at the global path; when 1.x was installed with Homebrew, run `brew uninstall kander` first, otherwise PATH holds two `kander` executables.

When a newer release supports the current OS and architecture, Kander waits for active dialogs and overlays to close before asking for confirmation. Homebrew-managed executables refresh the tap metadata with `brew update` and then run `brew upgrade dualface/tap/kander`, both with direct argv execution. Other installations download the fixed release archive and `checksums.txt` from GitHub, enforce response and extracted-binary size limits, verify SHA-256, reject unsafe archive entries, run the staged binary's `version` command, and atomically replace the running executable. Windows uses a rename-aside replacement and restores the original if writing the replacement fails.

After a successful update, Kander waits for a key, restores the terminal, then starts the verified executable. The version refresh of the new process (below) refreshes the embedded rules and reruns doctor. Update-check failures only produce a transient TUI notice; they never block offline use.

- Installation is done by the binary itself: `kander install` runs the interactive wizard (language, then the agent files). Kander is installed globally only, once per user; there is no project install. Bare interactive `kander` with no scope `config.json` skips the wizard, lets doctor create a usable config, and opens the board options interface section; when a config already exists, bare `kander` opens the board directly.
- `kander install` writes configuration and rules. When the first `kander` on PATH does not identify the running executable, it copies that executable to the global entry and replaces a file already there; it also deletes retired onevoke/kanban entries in that bin directory. Bare interactive `kander` with an existing scope config asks a Y/N question (default no) for the same copy; declining continues this launch and does not persist a skip. A binary that runs from a directory named `.kander/bin/` (left by a retired project install) is not offered as the copy.
- Copying never changes shell configuration. If PATH still selects another entry or omits the destination directory, the command prints instructions. Windows does not modify `PATH` automatically.
- Version refresh. `version` in the client home's `host.json` records the kander version that last completed a version refresh. Before the body of every command except `version`, `help` (and `--help`), `uninstall`, `worker`, a foreground server (also the one a managed service runs), and `guard-write`, kander compares its running version with that record. When they differ, or nothing is recorded, and the running binary is the global entry (both resolve to the same file: the copied entry, a Homebrew bin link to the running Cellar binary, or a Microsoft Store package), it refreshes once, in this order: the rules root (missing and outdated files), the `kander-leader` skill and the agent extensions (both under `install_rules`), the global part of the doctor repair (the stale binary an update left and the schema of an existing scope `config.json`), the host scan, and the global injection cleanup of the current configuration directories whatever its marker says (the marker is updated). The scan resolves the agents with the `PATH` and `config_home.env` values `host.json` recorded, not with the triggering process's, keeps both, and updates only the agent and launcher lists; without a recorded `PATH` it is skipped. The refresh never copies a binary, never creates `config.json`, never replaces an agent or a launcher (that choice depends on the environment doctor probes), never writes a Git repository or a project file, and never asks a question. What an interactive doctor would ask about (a locally changed rule file, an agent session file declaration, several `kander` on the recorded `PATH`), a skipped scan, and a registered project whose configuration cannot be read are listed as pending items that name `kander doctor`; they are not failures. When every other step succeeded, it removes `kander-startup-state.json`, which earlier releases wrote into the rules root, and records the version. After a failure nothing is recorded, the command runs as usual, and the next command tries again. The refresh holds `version-refresh.lock` in the client home and never waits for it: a process that finds it taken skips the refresh, and the holder reads the record again before it starts. Its outcome is one line on stderr, or with `--json` one `notices` entry (`version_refreshed` or `version_refresh_failed`, with the elapsed time and the pending items), followed by the notices of the global injection cleanup; the command's own output and result fields do not change. A binary that is not the global entry (a development build, `go run`) never refreshes and only reports the mismatch (`version_refresh_skipped`). The worker never refreshes.
- Bare `kander` runs the same refresh after the copy question, so a copy the user accepted is refreshed from the global entry it starts. When the refresh ran, or no scope config exists, it runs doctor and holds the report until the user presses Enter, then opens the board. A failed health check never blocks the board.
- Doctor also enumerates every distinct `kander` executable reachable through PATH, deduplicated by file identity and listed with its `kander version` result. Several installs mark the check unhealthy. A Homebrew-managed binary (a resolved path inside a Cellar) older than the newest one offers `brew upgrade kander`; in an interactive terminal the user may then pick one executable to keep — every other non-Homebrew file is deleted — or skip. Non-interactive callers, including the TUI doctor report, only get the listing.
- The installer copies the same English Markdown rule originals to the rules root and generates no customized rule files. `kander-rules-state.json` records the installed hashes; when it is absent, doctor distinguishes outdated official copies from local edits with the registry in `internal/install/legacy_hashes.go`.
- The rules root is `~/.agents/kander/`. Earlier releases wrote the files directly into `~/.agents/`. An install or `kander doctor` retires that location silently: every file named like a rule file, plus the state file, is deleted whatever its content or link status; only a directory under such a name stays. The global injection cleanup (below) runs first and removes an agent rules file that was a symlink to the previous entry as a link. While any agent's global rules target cannot be resolved (for example an invalid scope `config.json`), the retirement waits for the next successful run, so no such symlink is left dangling. `kander uninstall` removes the rules root, the Kander load commands in each agent's global rules file, and the pi rules extension at `<Pi agent directory>/extensions/kander-rules.ts` (the config directory resolution is described below); see "Uninstall" below.
- When a rules file is named `AGENTS.md` and an `AGENTS.override.md` sibling already exists in the same directory, `kander init`, doctor's project reference check, and the global injection cleanup all treat it as a second rules file: the same pipeline runs on it, and each file's result is reported separately. A missing reference in the override alone reports that file as unconnected, because an agent honoring the override reads it instead of `AGENTS.md`. Kander only ever edits the file — it is never created, since it expresses the user's own choice to shadow `AGENTS.md`.
- The embedded pi rules extension (`internal/config/agents/extensions/kander-rules.ts`) ships with the binary and injects `KANDER-AGENTS.md`, `KANDER-BASE-RULES.md`, and `KANDER-LOADING-RULES.md` into pi's system prompt on every turn in which a loaded context file references `KANDER-AGENTS.md`; the injected block names the rules root and still requires `kander config --json`. The install and `kander doctor` write it to `<Pi agent directory>/extensions/kander-rules.ts` only when that directory already exists. Writes refuse a target chain containing any symlink, junction, or other reparse point. Doctor classifies the file as installed, missing, outdated (its digest is on the released-version list in `internal/install/extension_hashes.go`), or modified (no known digest, never overwritten). A project-level copy that a retired project install wrote to `<main worktree>/.pi/extensions/kander-rules.ts` is removed by the doctor repair when its digest is a released one.
- Every global agent rules file, and the Pi extension, lives below that agent's config directory. The global injection cleanup, uninstall, and the extension install all resolve it the same way, first match wins:
  1. `agents.<name>.config_dir` in the scope `config.json` (or `KANDER_CONFIG`), built-in agents only: an absolute path or a `~`/`~/` path. The project `.kander-config.json` never supplies it: the key is dropped before the overlay merge, so it never fails validation or appears in the effective configuration, doctor warns about it with the overlay path, and every write ignores it. A checked-out repository therefore cannot redirect changes to the user's global agent files.
  2. The environment variables the agent itself reads: `CODEX_HOME` (codex), `CLAUDE_CONFIG_DIR` (claude), `GROK_HOME` (grok), `KIMI_CODE_HOME` (kimi), `PI_CODING_AGENT_DIR` (pi), `OPENCODE_CONFIG_DIR` then `$XDG_CONFIG_HOME/opencode` (opencode), and `$XDG_CONFIG_HOME/devin` (devin). An empty value counts as unset; `XDG_CONFIG_HOME` counts only when absolute. Other values expand `~` and `~/` to the user home, resolve relative paths against the command working directory, and keep spaces literal.
  3. The embedded default below the home directory, such as `~/.codex` or `~/.pi/agent`.

  Cursor is fixed at `~/.cursor`: it declares no variable and rejects `config_dir`, because cursor-agent reads global rules only from `<ancestor>/.cursor/rules/**/*.mdc` while walking up from the workspace root. Earlier releases wrote the always-applied rule `~/.cursor/rules/kander.mdc` there. The cleanup deletes that file when it holds only the `---` / `alwaysApply: true` / `---` frontmatter and the reference Kander wrote; a rule the user changed keeps its other content and is reported, and a rule that is a symlink is left untouched and reported.

  Droid is fixed at `~/.factory` the same way: it declares no variable and rejects `config_dir`, because Droid reads personal rules only from fixed home directories. Its global target is `~/.factory/AGENTS.md`.

  Antigravity CLI (`agy`) is fixed at `~/.gemini` the same way: it declares no variable and rejects `config_dir`, because its global rules file is read from that directory. Its global target is `~/.gemini/AGENTS.md`, which comes from the reference design (GitHub PR #29) and has not been verified against a real agy; its project target is `AGENTS.md`.

  A relocated directory can be outside home. The extension install covers the agent only when the resolved directory already exists and never creates it. The entire Pi extension target chain of a relocated directory, including that directory and its ancestors, must be free of symlinks and reparse points. A compatibility symlink at the unused default location is not inspected, and Kander does not migrate files at the old location; the cleanup of a directory another environment selects runs when Kander runs in that environment.
- The extension reads its rules only from the global rules root `~/.agents/kander/`, resolved at prompt time. A `.kander/rules/` directory a retired project install left in a checkout is never read, so an old checkout loads the same rules as every other project; extension version 1, which tried those copies first, is on the released-version list and is replaced by the install or the doctor repair. It re-reads the three fixed file names every turn and injects nothing when one is missing or empty, or when no loaded context file references `KANDER-AGENTS.md`. `/kander-rules on|off|status` toggles it per session and `PI_KANDER_RULES=0` disables it for the process; review invocations allow normal extension loading, so the same conditions apply there. Only the fixed file names are read, never arbitrary project code.

### Project References

Kander writes no agent's global rules file. The Kander rules apply in a project whose committed project rules files reference the rules entry, so a project opts in by running `kander init` and committing the result:

- `kander init` writes, after the binding succeeded and only in a Git checkout, the project reference into the project rules file of every built-in agent below the main worktree: `CLAUDE.md` gets the one-line import `@~/.agents/kander/KANDER-AGENTS.md`; `AGENTS.md`, which every other built-in agent reads, gets a `## Kander Rules Entry` block that names `~/.agents/kander/KANDER-AGENTS.md` and asks a reader to skip the section when that file does not exist, so the committed text is harmless where Kander is not installed. The spelling is the same on every machine and never an absolute path.
- A missing file is created, a shared file is written once (the claude-import style first, so a `CLAUDE.md` that is a symlink to `AGENTS.md` is settled before the other agents check the file), a file that already references the entry is left byte for byte, and invalid or duplicate load commands, such as the `.kander/rules/KANDER-AGENTS.md` reference of a retired project install, are dropped before the block is appended. The write is atomic and anchored at the main worktree. A rules file that resolves outside the main worktree, directly or through a symlink, is never written: init reports it and keeps the binding.
- `kander init` runs no Git write command. It lists the files it wrote and asks the user to commit and push them; until then, task worktrees, which check out the start base, and other hosts do not load the rules.
- `kander start` checks the start base before the claim: the executing agent's project rules file in that commit must reference the entry, following symlinks inside the commit tree and, for `CLAUDE.md`, a whole-line `@` import of another file of the tree. An `AGENTS.override.md` that the commit holds next to that `AGENTS.md` shadows it and must carry the reference too; the refusal then names the override. Without it the start is refused with `rules_reference_missing`, and the card stays in `todo/`. An agent whose switch is off, or one without a project rules file, is not checked; the start prints `project_rules_check_skipped`.
- `kander doctor` reports, in a checkout bound to a project, each project rules file without the reference or with the retired one, with the hint to run `kander init`. Doctor never writes a project rules file.

### Global Injection Cleanup

Earlier releases wrote a Kander load command or reference block into each agent's global rules file, sometimes replaced that file with a symlink to the rules entry, and created `~/.cursor/rules/kander.mdc`. Every kander command, except `version`, `help`, `uninstall`, the background `worker`, a foreground `server start`, and `guard-write`, removes that content once per agent configuration directory before its own work:

- For each built-in agent it resolves the configuration directory (the order above, including the environment variables), plans the cleanup of the global rules file and an existing `AGENTS.override.md` sibling with the uninstall planner, and removes only Kander load commands and reference blocks, a symlink to the current or previous rules entry (the link itself), and a `kander.mdc` holding only what Kander wrote. Other bytes stay. A global rules file that is a symlink to another file (such as `~/.claude-account2/CLAUDE.md` pointing at `~/.claude/CLAUDE.md`) is edited in the real file, never deleted through the link; a file left with only blank lines is deleted when it is no link.
- In a home without the rules root `~/.agents/kander/`, the automatic cleanup runs only when its plan edits or removes a file, such as the references and links of the flat layout earlier releases used (`~/.agents/KANDER-AGENTS.md`); a home without Kander content gets no marker or lock. `kander install` and `kander doctor` clean anyway.
- The marker `kander-global-cleanup.json` in the rules root records the configuration directories finished. A command whose current environment resolves only recorded directories skips the cleanup; a new directory (another `CLAUDE_CONFIG_DIR`, for example) runs it again for that environment.
- A lock file next to the marker serializes the cleanup. A command that cannot take the lock skips the cleanup and runs as usual; one that takes it plans again, because another process may have finished meanwhile.
- The cleanup never asks a question. Its result is one stderr line, or a notice with `--json`: `global_rules_cleaned` names the files and asks for `kander init` in each project that uses Kander, `global_rules_kept` names a file kept by design (a changed `kander.mdc`, a symlinked `.mdc` rule), and `global_rules_cleanup_failed` reports a failure. A failure never fails the command and writes no marker, so the next command tries again.
- `kander install` and `kander doctor` run the cleanup every time, whatever the marker says, and record the marker on success. `kander uninstall` runs the same planner without the marker and removes the marker and lock with the rules root.
- Tests run the cleanup only when they opt in: a test that runs a kander command never touches the user's home.

### Retired Project Install

Earlier releases could install Kander into a Git main worktree (`.kander/bin/`, `.kander/rules/`, `.kander/config.json`, `.kander/share/`), with project-level copies of the leader skill and the pi extension and a `/.kander/` line in `.git/info/exclude`. That mode is gone:

- A binary that runs from a directory named `.kander/bin/` uses the global paths and configuration, and prints the `project_install_retired` notice that names the directory and points at `kander doctor`.
- `kander doctor` reports each leftover of the main worktree. Its repair removes a `.kander/bin/kander` (`kander.exe` on Windows) whose `version` output starts with `kander ` (the repair runs that file with `version` and a 10-second limit, the only file of the checkout it executes, so repair only a checkout you trust like its own code), the files of `.kander/rules/` whose digest is a released version and Kander's state files there, the project skill directories that carry their install receipt and unchanged files, a project `.pi/extensions/kander-rules.ts` with a released digest, the `/.kander/` exclude line, and the directories left empty. Removals never follow a symlink, junction, or other reparse point; a `.kander` that is a link is reported and not read.
- The repair moves the top-level settings of `.kander/config.json` that the project overlay allows into `.kander-config.json` with an overlay compare-and-swap. A key the overlay already sets keeps the overlay value and is reported; `install_rules`, `agents.<name>.install_rules`, and `agents.<name>.config_dir` cannot live in the overlay, are not moved, and keep the file when they differ from the default. The bookkeeping keys `schema_version` and `welcome_complete` are dropped. The file is removed once nothing stays in it.
- Terminal definitions below `.kander/share/terminals/` stay and are reported: Kander reads definitions only from the embedded set and the global share, so move a definition you still use into `~/.local/share/kander/terminals/`.
- A project rules file that still references `.kander/rules/KANDER-AGENTS.md` is reported; `kander init` replaces it.

### Rules Integration Providers

How a reference to the Kander entry is written, detected, cleaned, and removed is decided by two provider kinds in `internal/install`, so `kander init`, the doctor check, the start check, the global injection cleanup, and uninstall share one implementation and none of them branches on a style name or a file extension:

- A reference style provider (`markdown-reference`, `claude-import`) is selected by the `rules_integration` value of the agent's embedded definition. It produces the reference block, says whether a file references the entry, recognizes a whole-line load command (the cleaner and uninstall ask every style for every file), says whether `kander init` writes its files first, and says whether a project rules file that is a symlink not pointing at the entry may still be read as a file.
- A file format provider (`markdown`, `mdc-rule`) is selected by the extension of the target file, in one registry. It checks and completes the existing text before a write (the `alwaysApply` frontmatter of a `.mdc` rule), says whether the file refuses symlinks, and says whether what is left after the load commands is only what Kander wrote, so the cleanup deletes the file.

Providers decide what is written, not whether or where. `kander init` goes through the `install_rules` gate, the shared-file check, the escape check, and the `internal/fs` atomic write anchored at the main worktree. The global injection cleanup and uninstall do not use the switches: they cover the global rules file of every built-in agent whatever its switch, keep a symlinked `.mdc` rule and report it, remove a symlink to the rules entry as a link, and use the `internal/fs` atomic write and no-follow removal. So the boundaries of this document do not depend on the provider. Output equivalence is pinned by golden transcripts in `internal/install/testdata/`, which also run the real uninstall. Adding a provider is described in [Custom execution agents](custom-agents.md#rules-integration-providers).

### Bundled leader skill

`kander install` includes `kander-leader` and its three reference documents in the binary. The Codex install choice writes the shared `.agents/skills/kander-leader/` directory under the user's home. The Claude choice writes `skills/kander-leader/` under an existing Claude configuration directory. The install preview shows the payloads for each choice. Installing makes the skill discoverable; project leadership, supervision, and deployments require the delegation described by the skill.

An existing skill directory or link without a receipt for this install and exact destination stays user-owned, even if its files match the bundle. A common Claude link to the shared directory continues to work. If an ancestor of a skill directory is a link, the installer reports the path, keeps its contents, and continues with the other selected destinations. Rerunning `kander install` restores missing managed files and updates unchanged ones using the installed digests in `.kander-install.json`. Doctor repair does the same, so the skill follows the binary like the rules root: `kander doctor`, and the first bare `kander` start after a binary upgrade (which runs doctor), install the skill at every covered destination where it is missing and update a managed copy, under the same `install_rules` switches and ownership rules. Doctor reports each destination as installed, missing, out of date, edited locally, not installed by Kander, or skipped; a missing or out-of-date skill fails the read-only check, the other states are hints. Like the extensions and the project reference check, this check and repair run only once `welcome_complete` is true. Locally edited files stay in place. Uninstall retains a locally edited bundle together with its references. For an unmodified bundle it removes its managed files and receipt, then prunes empty skill directories. Other files in those directories stay in place.

### Rules Injection Switch and Uninstall

- Rules injection is every write Kander makes to an agent's own files: the project reference `kander init` writes into a project rules file (creating it, appending the reference, or dropping invalid or duplicate load commands), and writing or updating the rules extension or bundled leader skill. The global injection cleanup is not part of it and ignores the switches. The rules root itself is not part of it either: it is extracted and repaired whatever the switches say, because the prompts of sessions Kander starts point at it.
- The top-level `install_rules` switch and the per-agent `agents.<name>.install_rules` (built-in agents only) gate it. Both are booleans; a missing key means `true`, so older configs keep their behavior. An agent's own value wins; an agent without one follows the global value. The switches are read only from the scope `config.json` (or `KANDER_CONFIG`) through `config.ScopeInstallRules`: the project overlay may carry the keys so a shared file still loads, but the merge drops them, they never reach the effective configuration or `kander config`, and doctor warns once per key with the overlay path.
- The gate sits in the write primitives (`install.EnsureProjectReference`, `install.EnsureExtension`), so `kander init`, the install, `kander doctor`, the bare `kander` startup doctor, and the options save all honor it. The options save gates on the switches being saved, before they reach `config.json`. A project rules file read by several agents (`AGENTS.md`, or a `CLAUDE.md` that resolves through a symlink to it) stays unwritten when any of them is off, and `kander start` skips its reference check for such an agent. For an agent whose switch is off, doctor neither reads nor writes its files and prints one "turned off" hint per file; that line does not make doctor unhealthy.
- A reference that appears only inside an HTML comment, a code fence, or a negated sentence still blocks another append (the strict literal gate), but `kander init` and doctor report the file as inactive and doctor unhealthy instead of connected.
- `kander install` asks before writing: after the language it lists every rules extension and bundled skill document of the covered agents, each marked create, update, or unchanged, then a multi-select of the agents and a confirmation. An agent starts selected when it is on, so a fresh install selects all and a reinstall keeps an agent the user turned off. Cancelling writes nothing. Before anything is written, the install stores `agents.<name>.install_rules: false` for every unselected agent and `true` for a selected agent that was off, in the scope `config.json`, creating it from the defaults with `welcome_complete` false when it is missing.
- The Options rules page shows the global switch and one switch per covered agent on the scope tab only; an agent switch set back to the global value drops the agent's own value. The save keeps every other hand-edited `agents.*` field.
- `kander uninstall [--yes]` removes the global install and stops the background processes of this host; the data directories stay. See "Uninstall" below.

### Uninstall

- Plan first. `kander uninstall` lists, before it changes anything: the managed services it unregisters (each with its definition file or task), the processes it stops (the local server and the worker of the client home, each with its PID), every path it edits or deletes (each rule file of the rules root too, with their count), every path it keeps or skips with the reason, the three kept data directories, and the unreleased leases of this host. On a terminal it then asks y/N (default no); any other answer than `y` changes nothing. Without a terminal it requires `--yes` and otherwise exits 2; `--json` without `--yes` is refused with `interactive_required`, exit 2, before anything changes.
- Leases in use do not refuse the uninstall. Every execution credential of the client home that is neither released nor lost is listed with its project ID, task ID, generation, kind, and agent PID when there is one, followed by the impact: while Kander is uninstalled these leases are not renewed and the `kander` commands their agents run fail; after a new install, once a worker runs again, the leases nobody took over renew again.
- Services. A server or worker service that `kander service install` registered (a definition with the Kander marker) is unregistered first, as `kander service uninstall` does, so no service manager starts the process again while uninstall stops it; a definition without the marker is not touched. See [Services](distributed-server.md#services).
- Server. The planner asks the loopback server at the `server.url` of the scope `config.json`, the one the project overlay of the working directory binds (`kander init --server` writes it there; the overlay is read without the cleanup of a normal configuration read, which would remove an empty `.kander-config.json`), and the one the default data directory recorded in `server-listen.json`, read-only, which data directory each serves. A server whose administration key is readable is stopped exactly like `kander server stop` (authenticated loopback shutdown, then a wait for the data directory lock). A server whose key cannot be read is listed as skipped; a remote server is never touched.
- Worker. When a process holds `worker.lock` of the client home, uninstall writes the stop request `worker.stop` next to it (atomically, with its creation time) and probes the lock every 250 milliseconds for at most 30 seconds. No process is signaled. The worker checks the request on every tick: a request created after the worker started ends both loops through the normal shutdown, and the worker deletes the request before it releases the lock; an older request, left by an interrupted uninstall, is deleted and the worker runs on. When the lock is free uninstall removes a request the worker did not read. A lock still held after 30 seconds is a failed stop that names the lock file; the request stays, so the worker still exits when it reads it. The behavior is the same on Linux, macOS, and Windows.
- A failed stop is reported, the other steps still run, and the command exits 1.
- Agent files. Uninstall drops every Kander load command (claude imports, `## Kander Rules Entry` blocks, bare entry paths, whatever entry they name, outside comments and fences) from each built-in agent's existing global rules file and `AGENTS.override.md`, keeping every other byte, including comment text on the same line as a load command: the planner of the global injection cleanup. A file left blank, or a `.mdc` rule left with only Kander's `alwaysApply` frontmatter, is deleted; a symlink to the rules entry is removed as a link; an override, another symlinked rules file, and a file whose directory is reached through a symlink are only edited. Rules extensions with a released digest are deleted, a modified copy stays. Unmodified managed `kander-leader` skill files go with their receipt; a modified bundle stays.
- Rules root. Below `~/.agents/kander/` only the embedded rule names, the two state files, and the cleanup marker and lock are deleted, through no-follow removal; other files stay and are reported, and directories go once empty.
- Global entry, deleted last. The entry is the copy the installer writes to `~/.local/bin/kander` (`kander.exe` on Windows). It is deleted only when it is a regular file whose `kander version` output starts with `kander `; another file, a symlink, or a reparse point is kept and reported. A Homebrew install (the entry, or the first `kander` on PATH, or the running binary resolves into a `Cellar`) is skipped with `brew uninstall kander`; a Microsoft Store install (`install.Packaged`) is skipped with the hint to uninstall in Windows Settings. On Windows a running entry cannot be deleted: it is renamed to `kander.exe.old` in the same directory and a hidden, detached PowerShell waits for the uninstall process to exit and deletes it; when the helper cannot start, the leftover path is printed, and the next install removes it. A failed skill removal keeps the binary so a later run can finish the bundle.
- What stays. Uninstall deletes nothing in the configuration directory (`~/.config/kander/`), the share directory (`~/.local/share/kander/`, with the client home `client/`, or `KANDER_CLIENT_HOME` when set), and the server data directory (`$XDG_DATA_HOME/kander-server/`, default `~/.local/share/kander-server/`), and writes nothing there except `worker.stop`; the logs and records the stopped processes write themselves are theirs. It does not change `config.json` (earlier releases wrote `install_rules: false` there) and runs no Git command, so the project references committed in repositories, the task branches, and the evidence refs stay; run `kander gc` before uninstalling to reclaim the local ones. The output ends with this list.
- `--json` with `--yes` returns `mode` (`global`), `rules_dir`, `items` (each with `action`: `unregister`, `edit`, `remove`, `stop`, `keep`, or `skip`; `path` for a file or a service definition, `service` for a service, `process` and `pid` for a process; and `reason`), `leases` (`project_id`, `task_id`, `kind`, `generation`, `agent_pid`), and `failures`; a failure exits 1 with the result.

## Task Files

- On every platform the executing agent and the reviewer read the complete task from a UTF-8 temporary file; the launch arguments contain only the CLI's required control options and a one-line instruction with the file path. The file asks the agent to try deleting it when done; a failed deletion or a leftover file does not affect the result.
- Automation involving special characters must invoke the command root's `kander` through a process API argv array; PowerShell/cmd command strings are never assembled.

## Review-Private Files

- Review-private directories and files are accessible only to the current user: POSIX `0600`/`0700`. Windows applies a protected DACL with inheritance disabled at creation time; publishing first and tightening later is forbidden. The one exception is a read-only entry on the review runtime for local sandbox groups that an embedded reviewer definition names (Codex: `CodexSandboxUsers`); see [Review runtime isolation](review-runtime-isolation.md#runtime-directory-contract).
- The Windows review root handle does not share DELETE and is held until sensitive files are written, the reviewer has run, the process tree is collected, and the contents are removed, which blocks renames and in-place reparse switches. It holds no DELETE access itself, so other processes may enter the runtime as their working directory; the empty directory is removed through a reopened handle whose identity must match the lease. Cleanup rejects reparse points level by level from the pinned handle, with a bounded budget; failure means the review fails. See [Review runtime isolation](review-runtime-isolation.md).

## Configuration, Board, and Git Exclude

- The configuration does not check, migrate, or tighten permissions: POSIX keeps the existing mode, new objects follow the umask; on Windows, new config files and directories inherit the parent ACL.
- On Windows, the configuration rejects reparse points component by component from the volume/UNC anchor and uses pinned handles for reading and atomic replacement. The kanban board and Git exclude likewise reject symlinks, junctions, and other reparse points; `kander` reads, writes, and moves through validated Win32 handles, and POSIX keeps using no-follow file operations. Any failed safety check stops the operation. Atomic replacement uses POSIX rename semantics where the system supports them and retries a busy error with a bounded backoff (at most about one second), and it still goes only through the pinned source and parent handles, never through a path again. On Windows, a read of a file that is being replaced atomically that succeeds returns the whole file from before or after the replacement and never fails with an identity change between two opens (it can still fail with a sharing violation while the writer holds its temporary handle), because a read-only open of a regular file opens it once through the pinned parent handle and validates the returned handle; a reparse point is still rejected, and opens that write, delete, change ACLs, list, or traverse still compare the probed and the reopened object.
- `init` creates the seven state directories under these boundaries: on Windows, new directories are created with `CREATE_NEW` relative to a pinned parent handle with a protected DACL exclusive to the current user applied at creation, and a creation race rejects the operation; existing directories only get their leaf directory ACL migrated. Git projects only update the local `info/exclude`: the parent chain rejects reparse points component by component, existing ACLs are unchanged, and deduplicating read and append happen within the same pinned leaf handle and file lock.
- Bypassing the command to operate on these boundaries directly is forbidden; see [Card transactions and recovery](card-transactions.md) for the transaction protocol behind board writes.

## Distributed executable

v2 installs and updates only `kander`, which also provides `kander server`. No companion binary is probed or copied. Existing no-follow source/destination checks, atomic replacement and Windows busy-file handling apply to this one executable. `kander uninstall` deletes this one executable, or leaves it to Homebrew or the Store. Store installations use Store replacement.

`kander server start` detaches a resident process and appends logs to its private data directory.

`kander service install server|worker` registers the server or the worker with the service manager of the host instead: a systemd user unit below `$XDG_CONFIG_HOME/systemd/user` on Linux, a LaunchAgent in `~/Library/LaunchAgents` on macOS, or a scheduled task on Windows, which runs only after the user logged in. The definition starts the global entry (a Homebrew install: its link, never the Cellar target) and records only the command line, `KANDER_MANAGED=1`, and the `KANDER_CLIENT_HOME` of the installing command; it holds no token or other variable. The unit and plist files are written atomically and never followed through a symbolic link, and the logs stay the private `server.log` and `worker.log`, created before the service manager opens them. A Linux host without a systemd user instance and a Microsoft Store install are refused. See [Services](distributed-server.md#services). Management uses an independent current-user private key created through `internal/fs`, never the claim-signing secret. Stop uses authenticated loopback HTTP without redirects on Linux, macOS and Windows. See [Distributed server](distributed-server.md) for control, startup questions, settings and recovery.
