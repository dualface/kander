# Installation and Permission Boundaries

How the binary installs itself and which filesystem boundaries the configuration, board, Git exclude, and review runtime enforce. The released rules (`rules/KANDER-BASE-RULES.md`) keep only the boundaries an agent must respect; the mechanics below are implementation contracts for this repository, verified by the tests of `internal/install`, `internal/config`, `internal/board`, and `internal/fs`.

## Installation

### Automatic updates

Bare `kander` TUI startup requests the latest stable release from GitHub in the background. The request has a five-second deadline and does not delay the first screen. CLI subcommands do not perform this check.

When a newer release supports the current OS and architecture, Kander waits for active dialogs and overlays to close before asking for confirmation. Homebrew-managed executables refresh the tap metadata with `brew update` and then run `brew upgrade dualface/tap/kander`, both with direct argv execution. Other installations download the fixed release archive and `checksums.txt` from GitHub, enforce response and extracted-binary size limits, verify SHA-256, reject unsafe archive entries, run the staged binary's `version` command, and atomically replace the running executable. Windows uses a rename-aside replacement and restores the original if writing the replacement fails.

After a successful update, Kander waits for a key, restores the terminal, then starts the verified executable. The existing startup version stamp causes the new process to rerun doctor and refresh embedded rules. Update-check failures only produce a transient TUI notice; they never block offline use.

- Installation is done by the binary itself: `kander install` runs the interactive wizard (language, scope). Bare interactive `kander` with no scope `config.json` skips the wizard, lets doctor create a usable config, and opens the board options interface section; when a config already exists, bare `kander` opens the board directly.
- Global `kander install` writes configuration and rules. When the first `kander` on PATH does not identify the running executable, it copies that executable to the global entry and replaces a file already there; it also deletes retired onevoke/kanban entries in that bin directory. Bare interactive `kander` with an existing scope config asks a Y/N question (default no) for the same copy; declining continues this launch and does not persist a skip. Project installs copy into the main worktree's `.kander/bin`.
- Copying never changes shell configuration. If PATH still selects another entry or omits the destination directory, the command prints instructions. Windows does not modify `PATH` automatically.
- Bare `kander` reruns doctor once per binary version per scope: `kander-startup-state.json` in the rules root records the version that last passed this gate, and a mismatch — or a missing config — runs doctor again and holds the report until the user presses Enter, then stamps the version and opens the board. A failed health check never blocks the board.
- Doctor also enumerates every distinct `kander` executable reachable through PATH, deduplicated by file identity and listed with its `kander version` result. Several installs mark the check unhealthy. A Homebrew-managed binary (a resolved path inside a Cellar) older than the newest one offers `brew upgrade kander`; in an interactive terminal the user may then pick one executable to keep — every other non-Homebrew file is deleted — or skip. Non-interactive callers, including the TUI doctor report, only get the listing.
- The installer copies the same English Markdown rule originals to the rules root and generates no customized rule files. `kander-rules-state.json` records the installed hashes; when it is absent, doctor distinguishes outdated official copies from local edits with the registry in `internal/install/legacy_hashes.go`.
- The global rules root is `~/.agents/kander/`; a project install uses `<main worktree>/.kander/rules/`. Earlier releases wrote the global files directly into `~/.agents/`. A global install or `kander doctor --repair` retires that location silently: every file named like a rule file, plus the state file, is deleted whatever its content or link status; only a directory under such a name stays. Agent rules files that import or reference the previous entry path are rewritten to the current one; a rules file that was a symlink to the previous entry is replaced by a reference file, and that replacement is reported. While any agent's rules target cannot be resolved (for example an invalid scope `config.json`), the retirement waits for the next successful run, so no such symlink is left dangling. Removing a global install means deleting `~/.agents/kander/`, the Kander reference line in each agent rules file, and the pi rules extension at `<Pi agent directory>/extensions/kander-rules.ts` (the config directory resolution is described below).
- When an agent rules target is named `AGENTS.md` and an `AGENTS.override.md` sibling already exists in the same directory, the install, `kander doctor`, `kander doctor --repair`, and the options finish all treat it as a second rules file: the same reference-append, legacy-rewrite, and cleanup pipeline runs on it, and each file's result is reported separately. A missing reference in the override alone reports that file as unconnected, because an agent honoring the override reads it instead of `AGENTS.md`. Kander only ever edits the file — it is never created, since it expresses the user's own choice to shadow `AGENTS.md`.
- The embedded pi rules extension (`internal/config/agents/extensions/kander-rules.ts`) ships with the binary and injects `KANDER-AGENTS.md`, `KANDER-BASE-RULES.md`, and `KANDER-LOADING-RULES.md` into pi's system prompt on every turn in which a loaded context file references `KANDER-AGENTS.md`; the injected block names the rules root and still requires `kander config --json`. A global install and `kander doctor --repair` write it to `<Pi agent directory>/extensions/kander-rules.ts` only when that directory already exists, mirroring the rules-reference coverage; a project install always writes `<main worktree>/.pi/extensions/kander-rules.ts`. Writes refuse a target chain containing any symlink, junction, or other reparse point — stricter than the rules reference, which follows user-managed symlinks in the global scope. Doctor classifies the file as installed, missing, outdated (its digest is on the released-version list in `internal/install/extension_hashes.go`), or modified (no known digest, never overwritten). Pi discovers project extensions only under the session cwd's own `.pi/extensions/`, so sessions started inside a linked task worktree do not see the main worktree's copy; the global extension still covers those sessions, and the project `AGENTS.md` reference remains the fallback.
- Every global agent rules target, and the Pi extension, lives below that agent's config directory. Install coverage, doctor inspection and repair, the options finish, reference cleanup, and the legacy-symlink replacement all resolve it the same way, first match wins:
  1. `agents.<name>.config_dir` in the scope `config.json` (or `KANDER_CONFIG`), built-in agents only: an absolute path or a `~`/`~/` path. The project `.kander-config.json` never supplies it: the key is dropped before the overlay merge, so it never fails validation or appears in the effective configuration, doctor warns about it with the overlay path, and every write ignores it. A checked-out repository therefore cannot redirect writes to the user's global agent files.
  2. The environment variables the agent itself reads: `CODEX_HOME` (codex), `CLAUDE_CONFIG_DIR` (claude), `GROK_HOME` (grok), `KIMI_CODE_HOME` (kimi), `PI_CODING_AGENT_DIR` (pi), `OPENCODE_CONFIG_DIR` then `$XDG_CONFIG_HOME/opencode` (opencode), and `$XDG_CONFIG_HOME/devin` (devin). An empty value counts as unset; `XDG_CONFIG_HOME` counts only when absolute. Other values expand `~` and `~/` to the user home, resolve relative paths against the command working directory, and keep spaces literal.
  3. The embedded default below the home directory, such as `~/.codex` or `~/.pi/agent`.

  Cursor is fixed at `~/.cursor`: it declares no variable and rejects `config_dir`, because cursor-agent reads global rules only from `<ancestor>/.cursor/rules/**/*.mdc` while walking up from the workspace root. Its global target is the always-applied rule `~/.cursor/rules/kander.mdc`, so only workspaces below the home directory load it; `~/.cursor/AGENTS.md`, the previous target, is never read nor written again. A new rule starts with the `---` / `alwaysApply: true` / `---` frontmatter. Repair prepends that frontmatter to a rule without one and appends a missing reference after an existing one; a rule whose frontmatter lacks `alwaysApply: true`, or a rule that is a symlink, is reported as unconnected and left untouched.

  Droid is fixed at `~/.factory` the same way: it declares no variable and rejects `config_dir`, because Droid reads personal rules only from fixed home directories. Its global target is `~/.factory/AGENTS.md`.

  A relocated directory can be outside home. A global install covers the agent only when the resolved directory already exists and never creates it; a target in a subdirectory of it, such as cursor's `rules/`, is created with the file. The entire Pi extension target chain of a relocated directory, including that directory and its ancestors, must be free of symlinks and reparse points. A compatibility symlink at the unused default location is not inspected. Project targets are unchanged, and Kander does not migrate or remove files at the old location.
- The extension resolves its rules root at prompt time: `<cwd>/.kander/rules/`, then the Git common dir's main-worktree `.kander/rules/` (so task worktrees read the project rules), then `~/.agents/kander/`. It re-reads the three fixed file names every turn and injects nothing when one is missing or empty, or when no loaded context file references `KANDER-AGENTS.md`. `/kander-rules on|off|status` toggles it per session and `PI_KANDER_RULES=0` disables it for the process; review invocations allow normal extension loading, so the same conditions apply there. Injecting a project `.kander/rules/` file is the same trust level as pi loading that repository's `AGENTS.md`: only the fixed file names are read, never arbitrary project code.

## Task Files

- On every platform the executing agent and the reviewer read the complete task from a UTF-8 temporary file; the launch arguments contain only the CLI's required control options and a one-line instruction with the file path. The file asks the agent to try deleting it when done; a failed deletion or a leftover file does not affect the result.
- Automation involving special characters must invoke the command root's `kander` through a process API argv array; PowerShell/cmd command strings are never assembled.

## Review-Private Files

- Review-private directories and files are accessible only to the current user: POSIX `0600`/`0700`. Windows applies a protected DACL with inheritance disabled at creation time; publishing first and tightening later is forbidden. The one exception is a read-only entry on the review runtime for local sandbox groups that an embedded reviewer definition names (Codex: `CodexSandboxUsers`); see [Review runtime isolation](review-runtime-isolation.md#runtime-directory-contract).
- The Windows review root handle does not share DELETE and is held until sensitive files are written, the reviewer has run, the process tree is collected, and the contents are removed, which blocks renames and in-place reparse switches. It holds no DELETE access itself, so other processes may enter the runtime as their working directory; the empty directory is removed through a reopened handle whose identity must match the lease. Cleanup rejects reparse points level by level from the pinned handle, with a bounded budget; failure means the review fails. See [Review runtime isolation](review-runtime-isolation.md).

## Configuration, Board, and Git Exclude

- The configuration does not check, migrate, or tighten permissions: POSIX keeps the existing mode, new objects follow the umask; on Windows, new config files and directories inherit the parent ACL.
- On Windows, the configuration rejects reparse points component by component from the volume/UNC anchor and uses pinned handles for reading and atomic replacement. The kanban board and Git exclude likewise reject symlinks, junctions, and other reparse points; `kander` reads, writes, and moves through validated Win32 handles, and POSIX keeps using no-follow file operations. Any failed safety check stops the operation.
- `init` creates the seven state directories under these boundaries: on Windows, new directories are created with `CREATE_NEW` relative to a pinned parent handle with a protected DACL exclusive to the current user applied at creation, and a creation race rejects the operation; existing directories only get their leaf directory ACL migrated. Git projects only update the local `info/exclude`: the parent chain rejects reparse points component by component, existing ACLs are unchanged, and deduplicating read and append happen within the same pinned leaf handle and file lock.
- Bypassing the command to operate on these boundaries directly is forbidden; see [Card transactions and recovery](card-transactions.md) for the transaction protocol behind board writes.
