# Launch, Delivery, and Terminal Cleanup Mechanics

This document records how `kander start`, `resume`, `notify`, `dismiss`, and the launchers behave at the terminal and process level. The released rules (`rules/KANDER-KANBAN-RULES.md`) state only what an agent must do with these commands; the mechanics below are implementation contracts for this repository and are verified by the tests of `internal/launch`, `internal/notify`, `internal/takeover`, `internal/liveness`, and `internal/terminal`.

## Start Metadata

- The agent, launcher, and model tier of `start` default to the configuration; `--agent` and `--launcher` override only this invocation. `SIZE: large` uses `kanban_agents.large`, `SIZE: small` uses `kanban_agents.small`, both falling back to `kanban_agent`. On success the command prints the scale and the actual agent.
- Card pins (`EXEC_AGENT`, `EXEC_MODEL`, `EXEC_EFFORT`, read only from the card header) replace the configured agent, model, and effort for `start`, `PreviewStart`, plain `resume`, takeover, and `notify` recovery. Resolution lives in `internal/launch/pins.go`: an explicit `--agent` must equal `EXEC_AGENT`, a relaunch refuses when the session agent differs from it, and a forced agent without a model or effort pin takes that agent's configured values for the card's scale. The checks run before any claim, session allocation, or container. Parsing, validation, and the record writer are in `internal/board/pins.go`.
- A card that pins anything gets `EXEC_RESOLVED: agent=<v>(<src>) model=<v>(<src>) effort=<v>(<src>)` in the same write that already records start metadata, takeover metadata, or the foreground `WINDOW`; container launches write it with `WINDOW` once the container exists. A rollback restores the pre-call text, record included. Cards without pins are written byte for byte as before. Older Kander binaries ignore these fields and launch from the configuration.
- `start` writes the session identifier into `SESSION`: Claude/Grok/Pi a UUID, Cursor the chat id, Devin the exact id found by its declarative `session.discovery` (`devin list --format json` enumerated before launch and polled after for up to 30 seconds, because one call can take several seconds), OpenCode likewise (`opencode session list --format json`, matching the record whose `directory` equals the launch directory), Kimi likewise (`kimi session list --json --all`, matching the record whose `workDir` equals the launch directory), Droid the exact id found by its `hook:droid-sessions` hook (the one new `~/.factory/sessions/*/<id>.jsonl` whose `session_start` header names the launch directory), and Codex the exact newly discovered ID on a session-reporting launcher such as herdr (other launchers retain the existing persistence policy). The discovery contract — argv-only enumeration, `{cwd}`/`{task_id}` matches, bounded output and polling, exactly-one-new-candidate, rollback on failure — is defined in [Session Policies](custom-agents.md#session-policies). The adjacent `WINDOW` field holds the delivery address: herdr `herdr:<tab-id>:<pane-id>`; tmux/tmux-session `<launcher>:<session-id>:<window-id>:<pane-id>`; foreground/console the launcher name.
- tmux/tmux-session first create a placeholder window/pane, persist `WINDOW`, then start the agent with `respawn-pane`, and write the pane marker with `tmux set-option -p -t <pane-id> @kander_session <session-id>`. Failure to write the address, start, or write the marker closes this invocation's window and rolls back the card.
- When an old card lacks the two fields, they are inserted in order after `OWNER`; unstarted old cards are not batch-rewritten.
- When start or liveness validation fails, the original document is restored only while the operation still owns the current revision; otherwise the newer text is preserved and a conflict reported. When restoring the document fails, the error states the directory where the card actually is.

## Transition Entrances

`internal/launch`, `internal/notify` and `internal/window` never render `OWNER`, `SESSION` or `WINDOW`. Those fields change only through the entrances of `internal/board`, and each entrance writes the matching execution transition in the same transaction. See [Execution Ledger and Chain Walk](coordinator-recovery.md#execution-ledger-and-chain-walk).

An entrance writes on the latest snapshot and changes only its own fields. It checks the execution record and the cycle of the caller's cursor, never the card revision, so a write by the executor cannot make the launcher fail. `BeginTaskStart` and `BeginTakeover` bind the cursor to the record they create; any other writer calls `BindExecutionCursor` once. A cursor bound to a record that is no longer current is refused.

| Entrance | Transition |
| --- | --- |
| `BeginTaskStart` | `start`: the move to `working/`, the metadata, and a `pending` record |
| `ConfirmTaskStart`, `ConfirmTaskStartSession` | `confirm`: the record becomes `running` |
| `BeginTakeover` | `handoff`: the old record becomes `handed-off`, and a new `pending` record starts |
| `UnresolveExecution` | `unresolve`: the launcher that holds a `pending` record ends it as `unresolved`, with the failure and the container address |
| `AdoptExecution` | `adopt`: a `pending` or `unresolved` record becomes `running`, with the decision reference |
| `RecordExecutionWindow` | `window-update` |
| `RecordExecutionSession` | `session-repair` |
| `RecordExecutionProcess` | `process-identity`: the one-time `process.json` original |
| `RollbackDocument` | `rollback`, or `window-update` for a relaunch that only wrote `WINDOW` |

An entrance returns `ExecutionResult.Advanced`: the card revision or column differed from the cursor before this write. The entrance then moves the cursor forward, so without this fact the launcher's own successful write would hide an earlier executor write. `Entry.AdvancedPastCursor` keeps the fact for the whole operation, and `RollbackDocument` refuses once it is set, so a rollback cannot erase executor work behind a current cursor.

## Task Files and Command Lines

- `start`, `resume`, and a `notify` that needs to recover a process write the full prompt to a UTF-8 temporary task file on all platforms, containing the task ID, fixed requirements, and the message body. The agent command line receives only one instruction containing that absolute path. The file asks the agent to try to delete it when done; failure to delete or leftover files do not affect the result. These files get no POSIX permission or Windows ACL check or tightening.
- Every filesystem path shown to an agent goes through `process.AgentPath`. This covers:
  - the task file path in the one-line instruction and in the cleanup sentence;
  - the project-install `kander` entry, the rules entry, the command contract, and the issue rules path;
  - the project `AGENTS.md`;
  - the issue evidence files of triage and result sessions;
  - the notify message file in the direct delivery line;
  - the reviewer's one-line prompt pointer.

  On Windows these paths use forward slashes (`C:/Users/x/proj/.kander/bin/kander`), because claude and grok run shell commands through Git Bash, which consumes backslashes as escapes. Forward slashes also work in PowerShell and in the agents' file tools; cmd is not guaranteed. POSIX output is byte-for-byte unchanged. Kander still opens files, builds argv, writes card metadata, and compares paths with native paths; only the displayed text changes. Paths containing spaces are not quoted, so an agent must quote them itself for its shell. The review bootstrap body (contract, evidence, and spec snapshot paths) is read by file tools rather than a shell and keeps native paths.
- The delivered one-line instruction ends with one space and a language reminder: one sentence, written in the agent language itself, to communicate in that language (`config.LanguageReminder`). This covers start, resume, takeover, notify recovery, orchestrate, triage, refinement, issue result, and chat sessions, the `# kander-notify:` line of direct and dispatch delivery, and the reviewer's instruction (argv or the `stdin.txt` it is piped from). Each path uses the language of its existing `language.md` directive: the card `LANGUAGE`, or `agent_language` when the field is missing; the anchor card for issue results; the cards' shared `LANGUAGE` for orchestrate, else `agent_language`; `agent_language` for triage and chat; the report language for review. The reminder covers `en`, `zh-CN`, `zh-TW`, `ja`, `ko`, `es`, `fr`, and `de` by primary subtag (Chinese picks the traditional sentence for script `Hant`, or region `TW`/`HK`/`MO` without script `Hans`) and falls back to English for other languages. A value that fails the `agent_language` rule (control characters, empty, over 64 characters) adds no reminder. The reminder never enters a task file or a notify message file; the English `language.md` directive in those files is unchanged.
- When `prompt_delivery.mode` is `pane`, that instruction is not an argv element: after `pane run`, Kander waits for the agent TUI using the definition's `ready` / `blocked` marks (`blocked` is checked in parallel and wins immediately), then delivers the prompt with the same primitives as notify (herdr or luvus `agent prompt`; tmux `send-keys -l`, a 500ms wait, then a separate Enter).
- Native Windows prefers the agent `.exe`. When Codex, Claude, Grok, Cursor, Pi, Devin, OpenCode, Kimi, or Droid only has a `.cmd`/`.bat`, it is launched through an explicit `cmd.exe /d /s /v:off /c` with the agent adapter layer's argument encoding.
- The agent command sent into a terminal container is parsed once more by that container's shell: POSIX joins per sh; Windows assumes the herdr pane is PowerShell, always encodes argv into `%VAR%` variables restored by `cmd.exe /d /s /v:off /c`, and does not rely on PowerShell to pass arguments to native programs. A command containing a newline or NUL refuses to start; half a command is never sent.

## Launchers

- Seven built-in launchers, plus the launchers provided by loaded terminal definitions (JSON files in the global or project share directory `terminals/`; the project copy replaces the global one, which replaces an embedded one of the same name). `auto` is resolved at start time and never written back to the configuration.
- `auto` resolves only among container launchers and never falls back to `foreground` or `console`: it takes the launcher with the highest `auto_priority` among the definition launchers that run inside an existing session and whose required environment for auto holds. Built-in values: `herdr` has priority 200 and needs `HERDR_ENV=1` (its `HERDR_WORKSPACE_ID` stays a precondition checked when preparing the launch and is excluded from auto); `luvus` has priority 150 and needs `LUVUS_ENV=1` (its `LUVUS_PANE_ID` is checked when preparing the launch and excluded from auto); `tmux` has priority 100 and needs `TMUX` (its `TMUX_PANE` is checked when preparing the launch). Inside both herdr and tmux, herdr wins unless a loaded definition declares a higher priority; when none applies, the start fails without claiming and does not fall back to `tmux-session`, `foreground`, or `console`.
- `tmux` creates the task window in the background of the starter's current session and requires `start` itself to run inside tmux.
- `tmux-session` determines a dedicated session by the main worktree path (`kb-<dir-name>-<path-digest>`): created when absent, reused when it exists and `@kander_project` or `@onevoke_project` matches this project; one session per project with one background window per card; no requirement to run inside tmux; the client is not switched after launch; the command prints the session name, window id, and an attach hint.
- `herdr` requires `HERDR_ENV=1`, `HERDR_WORKSPACE_ID`, and herdr on PATH; it creates a new tab in the background of the current workspace (`--no-focus`, label reusing `window_name()`), first waits for the root pane to be ready, then runs the same agent command as tmux in that pane, without using `herdr agent start`. Command text sent before the shell of a new tab takes over the terminal is discarded, so `pane run` happens only after the pane renders its first frame of output; the readiness wait has an upper bound, and a timeout is a failure.
- `luvus` (POSIX only) requires `LUVUS_ENV=1`, `LUVUS_PANE_ID`, and luvus on PATH; it splits the calling pane with `--no-focus --cwd`, verifies the new pane's directory, moves the pane to a new tab, names it with `window_name()`, and focuses the calling pane again. A luvus that ignores `--cwd` fails the start after the new pane is closed. See [Terminal backends](terminal-backend.md#8-the-built-in-luvus-launcher).
- `foreground` runs in the foreground of the current terminal and waits for the agent to exit. `console` is supported only on native Windows; it starts the agent in a separate console window and returns the PID immediately, with no session/window reuse, attach, or output capture.
- POSIX defaults to `auto`; Windows defaults to `console`, rejects `tmux`, `tmux-session`, and `luvus`, supports `herdr` (native Windows build), and resolves `auto` only to herdr.

## Late Failures

A launcher judges a failed launch before it closes anything. `launchAgent` calls the judge of `LaunchPlan` at its failure point; `settleAfterLaunch` does the same for a step that fails after `launchAgent` returned (liveness validation, the confirmation). `kander start` and `resume --agent` set the judge. Plain `resume`, notify recovery and the board-free sessions own no start attempt and always clean up.

`board.ReadExecutionStanding` is read-only and gives two facts:

- `Superseded`: a `handoff`, `adopt` or `reclaim` link leaves the launcher's record. The launcher closes nothing and rolls nothing back, and `kander start` exits 0 with `superseded`.
- `Evidence`: `Entry.AdvancedPastCursor`, or the card differs from the cursor by revision or column. The launcher's own writes keep the cursor current, so they do not count. An entrance moves the cursor, so `Advanced` keeps a write the entrance covered up.

| Judgement | Container or process | Card | Attempt |
| --- | --- | --- | --- |
| Superseded | untouched | untouched | owned by its successor |
| Evidence | kept | kept | `unresolved` |
| Read failed | kept | kept | `unresolved` |
| No evidence, close succeeds | closed | rolled back | `rolled-back` |
| No evidence, close fails (T-01) | unknown | kept | `unresolved` |
| No evidence, rollback refused | closed | kept | `unresolved` |

The last row is the window between the judgement and the rollback. `RollbackDocument` refuses, so the write survives, and the attempt still ends.

`settleFailedLaunch` writes the result. `UnresolvedError` carries the fixed line and the two next steps, and `exitLaunch` prints them with exit status 3. A takeover with a durable dispatch never cleans up after the send, so its delivery-unknown and validation failures end as `unresolved`.

The judgement looks only at the card. Two limits follow:

- A dispatch or a manual `kander update` counts as evidence. The result is `unresolved`, which is a misjudgment on the safe side: the user adopts or takes over.
- An executor that runs but has not written the card counts as no evidence. The container closes and the executor ends with it. Kander adds no process probe for this case.

`unresolved` writes one more thing: the container address when the card lacks it, so the next owner can reach the executor. A card that already left `working/` and `review/` keeps its text. The cycle never changes.

Until the attempt ends, `PrepareDispatch` and `RepairMissingSession` refuse the card with the next step, and `BeginTakeover` requires a decision. The launcher is the only writer during `pending`; a repair of `SESSION` would break the exact comparison in `ConfirmTaskStartSession`. A launcher that died leaves a `pending` record with the same two exits. Replaying a dispatch by its ID stays allowed, because a retried takeover needs it.

`kander resume --adopt` binds a cursor to the record, probes the recorded address without reverse lookup, and calls `AdoptExecution`. Only `alive` passes. A handoff during the probe moves the record, so the fence refuses the write. `AdoptExecution` also compares `OWNER`, `SESSION` and `WINDOW` with the probed snapshot, so a new address on the same record refuses too.

## Start Success Conditions and Rollback

- Precondition checks before launch: a definition launcher's `requires` (platform, required environment variables, its program on PATH, in the order the definition declares); `herdr` needs `HERDR_ENV=1`, herdr on PATH, and `HERDR_WORKSPACE_ID`; `foreground` needs all three standard streams to be TTYs; `console` needs native Windows. A failed precondition does not claim. An agent whose `prompt_delivery.mode` is `pane` is rejected before claiming when the resolved launcher is `foreground` or `console`.
- Every failure below passes the judgement of [Late Failures](#late-failures) first.
- When process creation, tmux session, tmux window, herdr tab, herdr pane readiness wait, or `pane run` fails, the document is restored and the card moved back to `todo/`. A failed herdr readiness wait or `pane run` also closes the newly created tab; failed Codex discovery and pane session marker failures on tmux/tmux-session also close the newly created window. Failed Devin/OpenCode/Kimi/Droid discovery closes the created tmux window or herdr tab, or terminates a foreground/console process started by this invocation, before rollback.
- For `prompt_delivery.mode` `pane`, a second-stage TUI ready failure (`blocked` match, prompt-delivery rejection, or ready timeout) is the same class of failure: capture the pane output, close this invocation's tab/window, restore the document, and move back to `todo/`, without keeping the container or writing `WINDOW`/`SESSION`. Failures that need a person to answer a dialog say to run that CLI once manually and retry; a pure ready timeout reports the captured output without that instruction.
- tmux/tmux-session count as started only after session discovery and pane marker write succeed (with `pane` delivery, only after prompt delivery also succeeds). herdr counts as started once `pane run` and any required session discovery succeed (with `pane` delivery, once prompt delivery also succeeds); an agent declaring `session.file` gets no proactive session identity report — its own integration reports the path-kind identity — while for other agents the subsequent session identity report and read-back are best-effort. foreground/console normally count as started once the process is created, while Devin, OpenCode, Kimi, and Droid additionally require exact-session discovery and persistence; a later exit does not roll back automatically. `console` prints the PID and returns immediately.

## herdr Session Reporting

- For an agent that declares `session.file`, `start` and `resume`/`notify` recovery send no `pane.report_agent_session` call: the agent's own integration reports a `kind: "path"` identity that the shared session-file resolution maps to the session id the card records. A pane that has not been reported yet is left to that native report instead of racing it with an incompatible id-kind identity, so no read-back warning appears during the launch window.
- For other agents, when herdr `pane run` succeeds and the session reference is non-empty, `start` and `resume`/`notify` recovery share the session reporting path: call `pane.report_agent_session` through the herdr control channel named by `HERDR_SOCKET_PATH` (a unix socket on POSIX, the named pipe `\\.\pipe\` plus that path on Windows; see [Terminal definitions](terminal-definitions.md)), passing this invocation's pane id, the card agent, the reference, `source=herdr:<agent>`, and a monotonically increasing `seq`, then read back the reported identity with `pane get` within a bounded budget. The read-back shares the terminal session identity resolution: an `id` (or a legacy value without kind) must equal the reference verbatim, while a `path` resolves through the agent's `session.file` declaration to the session id inside the file.
- Codex discovery on herdr reads no rollout before launch; only a sessions root that exists but is not a directory fails before claiming. Kander records the launch time right before launching the agent. Discovery then reads only the `YYYY/MM/DD` directories from one UTC day before the launch to one UTC day after now, because Codex names directories and files in its own time zone. It skips a file whose name time is more than 26 hours before the launch without opening it, and it decides by the UTC creation `timestamp` of the `session_meta` header: a session created before the launch, or a header without a valid timestamp, is never a candidate, and such files are not reopened on later polls. The prompt prefixes are built once per discovery. It accepts exactly one new ID whose header's `cwd` identifies the physical launch directory and whose user prompt begins with this task's start/resume/takeover instruction. It persists that ID through `ConfirmTaskStartSession` before reporting. Zero or multiple candidates fail discovery and follow the existing launch rollback; a global latest rollout or an orchestrator mentioning the task is never a candidate. An empty reference is not reported. Devin discovery completes before reporting, so herdr receives its exact id. Socket, response, or read-back failures print one warning and do not fail the start, roll back the card, or close the tab (they never enter the `LaunchFailure` tab close and card rollback path). herdr's own integration may still report the same identity; Kander's path exists to fill in launchers that do not trigger the integration hooks.

## Resume

- `resume` wakes up the original agent by the card `SESSION`, preserving context: Claude/Grok `--resume <uuid>`; Cursor `--resume <chat-id>`; Pi `--session <uuid>`; Devin `--resume <session-id>`; OpenCode `--session <session-id>`; Kimi `--session <session-id>`; Droid `--resume <session-id>`; Codex `codex resume <session-id>`. The Codex session id is looked up in the rollout records under `CODEX_HOME` (default `~/.codex`), matching only user messages that begin with this task's start/resume prompt, never orchestrator sessions that merely mention the task ID; it fails when not found. Cards without a `SESSION` record cannot be resumed.
- Devin cards started by older Kander builds contain a synthetic UUID rather than Devin's real id. Kander does not fall back to `--continue` for those cards because that could select another card's most recent conversation; the CLI instead reports that the recorded session cannot be resumed.
- Accepts only `review/` or `working/` cards; exactly one non-empty `--message` or `--message-file`; `--timeout` a finite number of seconds greater than 60, default 120. The launcher is the same as for `start`.
- After launch, liveness reuses the `notify` recovery criteria: herdr and tmux/tmux-session validate an addressable terminal; foreground and console require the process not to exit during the full timeout observation window. herdr validates the pane directly returned by this invocation's `tab create`: `agent` must match and only the states `idle`, `working`, `blocked` are accepted; the reported session identity is decided by the shared resolution — an `id` compares verbatim to the card session, a `path` resolves through the agent's `session.file` declaration, and an undecidable identity counts as unconfirmed rather than a mismatch, while an absent identity alone is not failure. What is judged is whether the known new pane is alive, which differs from the duty of direct delivery and reverse lookup to determine the target by session identity; this relaxation is not a same-user security boundary.
- On an immediate exit, the new instance is cleaned up and the command exits non-zero with whatever raw agent output can be obtained; only after validation does it report `resumed` in the `start` output format.

## Takeover (`resume --agent`)

- An explicit `--agent <name>` allocates a brand-new session even when the name equals the original agent; the old CLI context is not migrated. When new-session preparation such as Cursor `create-chat` fails, the card is unchanged. Before launch, `OWNER`/`SESSION`/`WINDOW` are overwritten with the new agent, session, and launcher; `STARTED_AT` is unchanged.
- A Codex takeover on tmux/tmux-session or a session-reporting launcher such as herdr discovers this invocation's exact session id, writes it as `codex <id>`, and sets the pane marker when supported. Process-type Codex launchers retain `codex` and resolve by rollout mtime in later recoveries. Devin and OpenCode takeovers discover and persist the exact id on every launcher; Kimi and Droid takeovers do so on the container launchers they support.
- A takeover of a `pending` or `unresolved` record needs `--decision`, and the `handoff` link records it. The launcher of the replaced record steps aside. A failed takeover follows [Late Failures](#late-failures); without evidence, `rollback` restores the replaced record with its status and failure.
- After the new agent passes liveness validation and before printing `taken over`, the command attempts a graceful exit and closes the original herdr/tmux container under the identity and single-pane topology gate of `dismiss`. When the original agent is already dead, it closes only when the container topology can be proven; when the original address is empty, foreground/console, or the same as the new address, it records N/A. When validation, exit, or close fails, it prints only `original container kept` with the reason, does not force-kill, does not roll back the new agent, and still succeeds. Cleanup and liveness observation may each use one full `--timeout`, so the worst case takes about 2x timeout. On success it prints `cleaned up original container: ...` first, then `taken over: ...`.

## Missing Identity Repair

Repair refuses a card whose current execution record is `pending` or `unresolved`. The attempt ends first ([Late Failures](#late-failures)), so only one path writes `SESSION`.

Before normal notification or an unaccepted durable dispatch resolves its target, Kander attempts reporting only when the recorded pane has the card's agent and an empty direct identity (`id` or absent kind). If reporting already took effect but an agent-only card was not saved, retry proves the currently open rollout against the existing direct pane ID and only completes the card binding; a conflicting proof remains uncertain and never enters stale-target recovery. Existing mismatches, unknown kinds and unresolved native `path` identities stay with the shared tri-state rules and are never overwritten. Accepted/completed dispatch retries retain their existing receipt and stopped-executor reconciliation.

The current implementation supports Codex on Linux with a backend that exposes `ProcessInspector` and session reporting. The embedded herdr definition uses `pane process-info --pane <pane-id>` and validates the returned pane. Exactly one foreground process must match the configured agent process name. `/proc/<pid>/stat` supplies its process start time, and `/proc/<pid>/fd` identifies the rollout it actually holds open. Kander safely reopens a regular file inside the configured `CODEX_HOME/sessions` root, verifies its inode, and reads at most 64 records / 1 MiB for a valid session header, a `cwd` bound to the physical launch directory, and this task's exact execution prompt prefix. Historical WINDOW, agent name alone, newest rollout, and task-name mentions are insufficient. Multiple bound rollouts, mismatched recorded IDs, inaccessible process evidence, and unsupported platforms/backends produce specific uncertainty diagnostics.

Kander checks the pinned card revision and execution epoch and repeats the process/file proof before reporting and after read-back. Native identity appearing during repair must match the proof. For an old agent-only `SESSION`, a controlled board transaction persists the proven ID while preserving dispatch authorization and advancing only this operation's cursor. Normal target and readiness checks then run again; identity repair does not make a blocked agent ready. Failed or stale evidence preserves the executor and pending dispatch and never creates an accepted receipt or a second executor.

Repair, terminal probes, socket cancellation and board lock contention share the invocation's remaining notification/acceptance deadline. Journal publication finishes under the existing recovery protocol; kernel filesystem operations are not a hard real-time guarantee. Repair calls the structured backend report directly: it does not install/replay native hooks, change user configuration, inherit a different `CODEX_THREAD_ID`, or send extra agent input. A missing report channel remains diagnosable even when startup already recorded the real session ID.

## Notify Probe Classes

When `notify` probes the recorded `WINDOW`, it handles three classes, and this classification takes precedence over the recovery overview of the rules:

- **Ready**: the pane exists and the agent/session match; herdr additionally reports `idle`, `done`, or `working`, and tmux additionally is not in copy-mode. A `working` agent receives the prompt while its current turn runs and handles it afterwards, so the acknowledgement may arrive after `--timeout`; that only yields the delivered-but-unconfirmed warning. A durable dispatch accepted after its persisted deadline is still rejected and follows the expiry handling.
- **Busy**: the pane exists and the agent/session match, but herdr reports any other status (such as `blocked`, which may be a permission or confirmation dialog that typed text would answer) or tmux is in copy-mode. The probe is retried at a fixed interval within the same `--timeout` budget; on timeout the command returns non-zero with "target agent busy, not delivered" and starts no recovery instance, creates no body payload, and changes neither card state nor message body; verified identity metadata may already have been repaired. A missing tmux session marker means identity cannot be proven; it counts as neither busy nor stale and goes through the recovery channel.
- **Stale address**: the pane does not exist or has exited, the agent/session does not match, or the tmux foreground process does not match. herdr does a reverse lookup from `pane list` by agent and session identity — every same-agent row is a candidate whose reported session kind and value are resolved like the direct check (`id` verbatim, `path` through the agent's `session.file` declaration); tmux uses `list-panes -a -F` with a triple filter: non-empty `@kander_session` or `@onevoke_session`, `pane_dead=0`, and the agent executable name. After a unique resolved hit, the full target validation reruns; only on success is the compatible address written back (`tmux` the session id, `tmux-session` the session name) and delivery done directly. Old tmux cards with an empty `WINDOW` get no reverse lookup.
- **Reverse lookup failed**: 0 or multiple decided hits, lookup unavailable, or the re-check of the new pane fails; recovery goes through the existing chain, reporting both the reason the original address is stale and the reverse lookup reason.
- **Undecidable identity**: a same-agent candidate whose reported session cannot be resolved (missing value, unknown kind, or an unreadable/malformed session file) leaves the lookup incomplete; an undecidable reported identity in the direct check does likewise. Undecidable evidence proves neither a match nor absence: the command fails with the reason and never delivers, recovers another executor, or treats the pane as exited.
- An explicit `--pane` override does no stale-address reverse lookup.

## Notify Delivery

- Accepts only `review/` or `working/` cards, exactly one message source, and a `--timeout` greater than 60 seconds (default 120).
- Address priority: explicit `--pane` override, the card `WINDOW` fast path, and, when no window is recorded, scanning `herdr pane list` by agent and session identity. Both the override and the reverse lookup use `pane get` to verify that the pane exists, the agent matches, the reported session identity resolves to the card session (an `id` verbatim, a `path` through the declared session file), and the pane state is `idle`, `done`, or `working`. Claude/Grok/Cursor/Pi/Devin/OpenCode/Kimi/Droid cards with a recorded id are compared directly; only old Codex cards without an id reuse the rollout lookup of `resume`. Kander has no agent whitelist; herdr reverse lookup coverage depends on the herdr version and on whether each `source: herdr:<agent>` integration reports session identity. After a unique resolved hit, `herdr:<tab-id>:<pane-id>` is written back to `WINDOW`; 0 or multiple decided hits do not deliver. Old tmux/tmux-session cards without a window cannot be reverse looked up.
- Direct delivery and reverse lookup establish the identity of an existing target, so when the pane reports a session identity that cannot be decided the command fails with the reason and never recovers another executor; it does not use the relaxed criteria of recovery liveness validation.
- For a tmux address the command also verifies `pane_dead=0`, `pane_in_mode=0`, `pane_current_command` equal to the agent executable name, and requires at least one of `@kander_session` or `@onevoke_session` to be non-empty and exactly equal to the session id resolved from the card. When both are empty, identity cannot be proven: no direct delivery channel, fall back, never relax to process-name-level approval. A mismatched option is a stale address handled per the three-class probe. tmux user options and herdr `agent_session` sit within same-user permissions; they avoid misdelivery and are not a security boundary against malicious same-user forgery.
- The body payload is created only after a direct delivery address exists and the probe passes. The Windows temporary root takes only the lexical path returned by `GetTempPathW`, and the no-follow boundary rejects reparse points component by component. The body is written to a `0700` temporary directory and `0600` file accessible only to the current user and tightened at creation; the foreground/console fallback creates no payload.
- The terminal receives only one line starting with `# kander-notify:` (also recognized as `# onevoke-notify:`) that contains the absolute path of the message file and asks the agent to output the acknowledgement line the file names, followed by the language reminder of the card (see "Task Files and Command Lines"). The line never contains the marker: a pane shows the delivered line whether or not the agent submitted it, so a marker in the line would confirm an unsubmitted composer. The message file starts with the fixed English request `Acknowledge this notification: before anything else, output this line exactly:` followed by the marker `KANDER-NOTIFY-ACK:<32 hex>` on its own line; direct and dispatch delivery write the same request, and a dispatch is still settled only by its receipt.
- herdr must use `agent prompt <pane-id> <instruction>` to deliver to the agent TUI already running in the pane: it sends the body according to the pane's actual bracketed-paste mode, then sends an encoded Enter after a delay, and rejects up front when the agent is stopped at an approval or question UI rather than stuffing the body into that dialog. Do not switch to the shell-oriented `pane run` (the body and trailing CR are written in one batch, TUIs such as Cursor do not treat that as a submit, and the body stays in the input bar), and do not hand text to `pane send-keys`, which only accepts key names. luvus also uses its own `agent prompt`. herdr and luvus submit through that command, and Kander adds no wait of its own. tmux uses `send-keys -l`, waits 500ms (the step `delay` of the tmux definition), and then sends a separate `Enter`: Codex treats an Enter that arrives right after typed text as part of a paste and leaves the instruction unsubmitted in its composer.
- herdr confirms the marker with `pane wait-output --match <marker> --source recent` (literal substring, allowing a TUI rendering prefix); the polling backends read the pane text through their `read_output` operation (tmux `capture-pane`, luvus `pane read`) and apply the same bounded literal match. The marker reaches the pane only after the agent read the message file, either in its own output or in a tool display of the file, both of which prove the line was submitted. A marker timeout only warns "delivered, not confirmed within timeout" and does not recover a second process.
- A successful delivery action returns success without moving the card. The message body for a `review/` card is prefixed with the requirement to perform the `review -> working` move first (plain for an unbound message, ID/epoch-bound for a durable dispatch) and then handle the items.

## Notify Recovery

- Only foreground/console, no direct delivery channel, or a failed probe or delivery action make the command recover the original session internally. A process-type recovery must stay alive during the full timeout observation window; after validation, foreground keeps occupying the current terminal until the agent exits. herdr recovery liveness follows the new-pane criteria of `resume`: the state accepts only `idle`, `working`, `blocked` and rejects `done` and `unknown`.
- When tab/window/process cleanup after a failed recovery validation fails, it is reported together with the original error, noting that the new agent may still be alive. When both paths fail, the command exits non-zero and reports both reasons; the card body and original state are unchanged. After a successful recovery or takeover, the new container address is written back to the card `WINDOW`.

## Dismiss

- `dismiss` accepts only `done/` or `archived/` cards and changes neither body nor state; `--timeout` must be greater than 60 seconds, default 120.
- It locates the herdr pane or tmux/tmux-session pane by the card `WINDOW`. Old herdr cards without `WINDOW`, and stale addresses where the pane does not exist or is dead or the agent, session marker, or foreground process mismatches, reuse the unique session reverse lookup of `notify`; 0 or multiple hits are rejected, and a busy state gets no reverse lookup and is rejected. herdr takes the tab the matched pane actually belongs to as the container; tmux reads the session/window of the matched pane with `display-message`; the card `WINDOW` is not written back.
- Before delivery, the exact agent and session match of `notify` is reused: herdr additionally requires `agent_status` to be `idle` or `done`; tmux additionally requires the pane to be alive, not in copy-mode, and with a matching foreground process. The current tab or session/window of the validated pane must exactly equal the located container, and the container may contain only that pane; a moved pane or extra panes reject before delivery, ownership is verified again while waiting for exit, and the topology is re-checked before closing.
- The pane receives the `exit_command` declared on the agent definition (herdr or luvus `agent prompt`; tmux `send-keys -l`, a 500ms wait, then a separate `Enter`). An agent without that field is refused and the container kept. The herdr tab or tmux window is closed only after confirming the agent process has exited; a tmux window that already disappeared with the agent counts as closed.
- Any identity, state, container ownership, delivery, exit confirmation, or close failure, as well as a timeout, returns non-zero and preserves the working state; the command never force-kills or degrades to closing the container. `foreground`/`console` have no terminal container: the command reports an error without any partial action.

## Check Liveness Classification

- `check` with no arguments or `--all` probes all `working/` cards; targeted checks probe only the specified `working/` cards, never `review/`. Before the summary line it prints a four-state liveness section:
  - `alive`: the agent and available session identity match. It is an observation of presence, not readiness to receive input or evidence of progress; `notify` applies its own readiness checks. A herdr pane with missing identity but a valid agent and state is still `alive`, noted as not directly deliverable.
  - `stopped`: the pane is gone or the agent/process mismatches and a valid reverse lookup confirms zero matches. When lookup is disabled or the session reference is empty, the direct-pane classification applies; a Codex empty reference gets no reverse lookup.
  - `drifted`: the session was uniquely reverse looked up to a new pane, with the new address attached.
  - `unknown`: an invalid session/window, foreground/console, program unavailable, state or probe failure. Reverse lookup errors, invalid output, timeouts, and multiple matches are `unknown`, preserving the stale-address reason and the reverse-lookup stage and reason; they do not prove the session stopped.
- Probe errors count as `unknown`; they do not write the card or affect the `check` exit code. One card's forward probe, session reverse lookup, revalidation, and process cleanup share one deadline (10 seconds by default); exhaustion or cancellation stops subsequent queries and reports `unknown`. The liveness section collects all selected working cards within one 10-second batch budget with at most 4 concurrent probes; unfinished cards retain an `unknown` reason. Output includes observation time, validity, and a separate runtime state. The budget excludes board reads and output writes and is not a hard real-time guarantee. See [Probe deadlines and cancellation](probe-deadlines.md) for the process ownership contract, and [Subscription facts and member sets](subscription-facts.md) for the event schema and output lifecycle of `subscribe`.
