# Launch, Delivery, and Terminal Cleanup Mechanics

This document records how `kander start`, `resume`, `notify`, `dismiss`, and the launchers behave at the terminal and process level. The released rules (`rules/KANDER-KANBAN-RULES.md`) state only what an agent must do with these commands; the mechanics below are implementation contracts for this repository and are verified by the tests of `internal/launch`, `internal/notify`, `internal/takeover`, `internal/liveness`, and `internal/terminal`.

## Start Metadata

- The agent, launcher, and model tier of `start` default to the configuration; `--agent` and `--launcher` override only this invocation. `SIZE: large` uses `kanban_agents.large`, `SIZE: small` uses `kanban_agents.small`, both falling back to `kanban_agent`. On success the command prints the scale and the actual agent.
- `start` writes the session identifier into `SESSION`: Claude/Grok/Pi a UUID, Cursor the chat id, Codex only the agent name (Codex reuses the `notify`/`resume` rollout resolution later). The adjacent `WINDOW` field holds the delivery address: herdr `herdr:<tab-id>:<pane-id>`; tmux/tmux-session `<launcher>:<session-id>:<window-id>:<pane-id>`; foreground/console the launcher name.
- tmux/tmux-session first create a placeholder window/pane, persist `WINDOW`, then start the agent with `respawn-pane`, and write the pane marker with `tmux set-option -p -t <pane-id> @kander_session <session-id>`. Failure to write the address, start, or write the marker closes this invocation's window and rolls back the card.
- When an old card lacks the two fields, they are inserted in order after `OWNER`; unstarted old cards are not batch-rewritten.
- When start or liveness validation fails, the original document is restored only while the operation still owns the current revision; otherwise the newer text is preserved and a conflict reported. When restoring the document fails, the error states the directory where the card actually is.

## Task Files and Command Lines

- `start`, `resume`, and a `notify` that needs to recover a process write the full prompt to a UTF-8 temporary task file on all platforms, containing the task ID, fixed requirements, and the message body. The agent command line receives only one instruction containing that absolute path. The file asks the agent to try to delete it when done; failure to delete or leftover files do not affect the result. These files get no POSIX permission or Windows ACL check or tightening.
- When `prompt_delivery.mode` is `pane`, that instruction is not an argv element: after `pane run`, Kander waits for the agent TUI using the definition's `ready` / `blocked` marks (`blocked` is checked in parallel and wins immediately), then delivers the prompt with the same primitives as notify (herdr `agent prompt`, tmux `send-keys -l` plus a separate Enter).
- Native Windows prefers the agent `.exe`. When Codex, Claude, Grok, Cursor, or Pi only has a `.cmd`/`.bat`, it is launched through an explicit `cmd.exe /d /s /v:off /c` with the agent adapter layer's argument encoding.
- The agent command sent into a terminal container is parsed once more by that container's shell: POSIX joins per sh; Windows assumes the herdr pane is PowerShell, always encodes argv into `%VAR%` variables restored by `cmd.exe /d /s /v:off /c`, and does not rely on PowerShell to pass arguments to native programs. A command containing a newline or NUL refuses to start; half a command is never sent.

## Launchers

- Six built-in launchers, plus the launchers provided by loaded terminal definitions (JSON files in the global or project share directory `terminals/`; the project copy replaces the global one, which replaces an embedded one of the same name). `auto` is resolved at start time and never written back to the configuration.
- `auto` resolves only among container launchers and never falls back to `foreground` or `console`: it takes the launcher with the highest `auto_priority` among the definition launchers that run inside an existing session and whose required environment for auto holds. Built-in values: `herdr` has priority 200 and needs `HERDR_ENV=1` (its `HERDR_WORKSPACE_ID` stays a precondition checked when preparing the launch and is excluded from auto); `tmux` has priority 100 and needs `TMUX` (its `TMUX_PANE` is checked when preparing the launch). Inside both herdr and tmux, herdr wins unless a loaded definition declares a higher priority; when none applies, the start fails without claiming and does not fall back to `tmux-session`, `foreground`, or `console`.
- `tmux` creates the task window in the background of the starter's current session and requires `start` itself to run inside tmux.
- `tmux-session` determines a dedicated session by the main worktree path (`kb-<dir-name>-<path-digest>`): created when absent, reused when it exists and `@kander_project` or `@onevoke_project` matches this project; one session per project with one background window per card; no requirement to run inside tmux; the client is not switched after launch; the command prints the session name, window id, and an attach hint.
- `herdr` requires `HERDR_ENV=1`, `HERDR_WORKSPACE_ID`, and herdr on PATH; it creates a new tab in the background of the current workspace (`--no-focus`, label reusing `window_name()`), first waits for the root pane to be ready, then runs the same agent command as tmux in that pane, without using `herdr agent start`. Command text sent before the shell of a new tab takes over the terminal is discarded, so `pane run` happens only after the pane renders its first frame of output; the readiness wait has an upper bound, and a timeout is a failure.
- `foreground` runs in the foreground of the current terminal and waits for the agent to exit. `console` is supported only on native Windows; it starts the agent in a separate console window and returns the PID immediately, with no session/window reuse, attach, or output capture.
- POSIX defaults to `auto`; Windows defaults to `console`, rejects `tmux` and `tmux-session`, supports `herdr` (native Windows build), and resolves `auto` only to herdr.

## Start Success Conditions and Rollback

- Precondition checks before launch: a definition launcher's `requires` (platform, required environment variables, its program on PATH, in the order the definition declares); `herdr` needs `HERDR_ENV=1`, herdr on PATH, and `HERDR_WORKSPACE_ID`; `foreground` needs all three standard streams to be TTYs; `console` needs native Windows. A failed precondition does not claim. An agent whose `prompt_delivery.mode` is `pane` is rejected before claiming when the resolved launcher is `foreground` or `console`.
- When process creation, tmux session, tmux window, herdr tab, herdr pane readiness wait, or `pane run` fails, the document is restored and the card moved back to `todo/`. A failed herdr readiness wait or `pane run` also closes the newly created tab; a failed Codex session discovery or pane session marker write on tmux/tmux-session also closes the newly created window.
- For `prompt_delivery.mode` `pane`, a second-stage TUI ready failure (`blocked` match, prompt-delivery rejection, or ready timeout) is the same class of failure: capture the pane output, close this invocation's tab/window, restore the document, and move back to `todo/`, without keeping the container or writing `WINDOW`/`SESSION`. Failures that need a person to answer a dialog say to run that CLI once manually and retry; a pure ready timeout reports the captured output without that instruction.
- tmux/tmux-session count as started only after session discovery and pane marker write succeed (with `pane` delivery, only after prompt delivery also succeeds). herdr counts as started once `pane run` succeeds (with `pane` delivery, once prompt delivery also succeeds); the subsequent session identity report and read-back are best-effort. foreground/console count as started once the process is created; a later exit does not roll back automatically. `console` prints the PID and returns immediately.

## herdr Session Reporting

- When herdr `pane run` succeeds and the session reference is non-empty, `start` and `resume`/`notify` recovery share the session reporting path: call `pane.report_agent_session` through `HERDR_SOCKET_PATH`, passing this invocation's pane id, the card agent, the reference, `source=herdr:<agent>`, and a monotonically increasing `seq`, then read back the same `agent_session.value` with `pane get` within a bounded budget.
- An empty reference (including newly started Codex whose id is not yet discovered) is not reported. Socket, response, or read-back failures print one warning and do not fail the start, roll back the card, or close the tab (they never enter the `LaunchFailure` tab close and card rollback path). herdr's own integration may still report the same identity; Kander's path exists to fill in launchers that do not trigger the integration hooks.

## Resume

- `resume` wakes up the original agent by the card `SESSION`, preserving context: Claude/Grok `--resume <uuid>`; Cursor `--resume <chat-id>`; Pi `--session <uuid>`; Codex `codex resume <session-id>`. The Codex session id is looked up in the rollout records under `CODEX_HOME` (default `~/.codex`), matching only user messages that begin with this task's start/resume prompt, never orchestrator sessions that merely mention the task ID; it fails when not found. Cards without a `SESSION` record cannot be resumed.
- Accepts only `review/` or `working/` cards; exactly one non-empty `--message` or `--message-file`; `--timeout` a finite number of seconds greater than 60, default 120. The launcher is the same as for `start`.
- After launch, liveness reuses the `notify` recovery criteria: herdr and tmux/tmux-session validate an addressable terminal; foreground and console require the process not to exit during the full timeout observation window. herdr validates the pane directly returned by this invocation's `tab create`: `agent` must match and only the states `idle`, `working`, `blocked` are accepted; a non-empty `agent_session.value` must exactly match the card session, while an absent identity alone is not failure. What is judged is whether the known new pane is alive, which differs from the duty of direct delivery and reverse lookup to determine the target by session identity; this relaxation is not a same-user security boundary.
- On an immediate exit, the new instance is cleaned up and the command exits non-zero with whatever raw agent output can be obtained; only after validation does it report `resumed` in the `start` output format.

## Takeover (`resume --agent`)

- An explicit `--agent <name>` allocates a brand-new session even when the name equals the original agent; the old CLI context is not migrated. When new-session preparation such as Cursor `create-chat` fails, the card is unchanged. Before launch, `OWNER`/`SESSION`/`WINDOW` are overwritten with the new agent, session, and launcher; `STARTED_AT` is unchanged.
- A Codex takeover on tmux/tmux-session discovers this invocation's exact session id, writes it as `codex <id>`, and sets the pane marker. herdr and process-type Codex lack a discovery channel; they keep `codex` and resolve by rollout mtime in later recoveries.
- After the new agent passes liveness validation and before printing `taken over`, the command attempts a graceful exit and closes the original herdr/tmux container under the identity and single-pane topology gate of `dismiss`. When the original agent is already dead, it closes only when the container topology can be proven; when the original address is empty, foreground/console, or the same as the new address, it records N/A. When validation, exit, or close fails, it prints only `original container kept` with the reason, does not force-kill, does not roll back the new agent, and still succeeds. Cleanup and liveness observation may each use one full `--timeout`, so the worst case takes about 2x timeout. On success it prints `cleaned up original container: ...` first, then `taken over: ...`.

## Notify Probe Classes

When `notify` probes the recorded `WINDOW`, it handles three classes, and this classification takes precedence over the recovery overview of the rules:

- **Busy**: the pane exists and the agent/session match, but herdr is not `idle`/`done` or tmux is in copy-mode. The probe is retried at a fixed interval within the same `--timeout` budget; on timeout the command returns non-zero with "target agent busy, not delivered" and starts no recovery instance, creates no body payload, and changes neither card state nor body. A missing tmux session marker means identity cannot be proven; it counts as neither busy nor stale and goes through the recovery channel.
- **Stale address**: the pane does not exist or has exited, the agent/session does not match, or the tmux foreground process does not match. herdr does a reverse lookup from `pane list` by agent and session; tmux uses `list-panes -a -F` with a triple filter: non-empty `@kander_session` or `@onevoke_session`, `pane_dead=0`, and the agent executable name. After a unique hit, the full target validation reruns; only on success is the compatible address written back (`tmux` the session id, `tmux-session` the session name) and delivery done directly. Old tmux cards with an empty `WINDOW` get no reverse lookup.
- **Reverse lookup failed**: 0 or multiple hits, lookup unavailable, or the re-check of the new pane fails; recovery goes through the existing chain, reporting both the reason the original address is stale and the reverse lookup reason.
- An explicit `--pane` override does no stale-address reverse lookup.

## Notify Delivery

- Accepts only `review/` or `working/` cards, exactly one message source, and a `--timeout` greater than 60 seconds (default 120).
- Address priority: explicit `--pane` override, the card `WINDOW` fast path, and, when no window is recorded, scanning `herdr pane list` by agent and session id. Both the override and the reverse lookup use `pane get` to verify that the pane exists, the agent and `agent_session.value` match exactly, and the pane state is `idle` or `done`. Claude/Grok/Cursor/Pi cards with a recorded id are compared directly; only old Codex cards without an id reuse the rollout lookup of `resume`. Kander has no agent whitelist; herdr reverse lookup coverage depends on the herdr version and on whether each `source: herdr:<agent>` integration reports session identity. After a unique hit, `herdr:<tab-id>:<pane-id>` is written back to `WINDOW`; 0 or multiple hits do not deliver. Old tmux/tmux-session cards without a window cannot be reverse looked up.
- Direct delivery and reverse lookup establish the identity of an existing target, so when the pane reports no valid session identity the command keeps rejecting and enters the recovery chain; it does not use the relaxed criteria of recovery liveness validation.
- For a tmux address the command also verifies `pane_dead=0`, `pane_in_mode=0`, `pane_current_command` equal to the agent executable name, and requires at least one of `@kander_session` or `@onevoke_session` to be non-empty and exactly equal to the session id resolved from the card. When both are empty, identity cannot be proven: no direct delivery channel, fall back, never relax to process-name-level approval. A mismatched option is a stale address handled per the three-class probe. tmux user options and herdr `agent_session` sit within same-user permissions; they avoid misdelivery and are not a security boundary against malicious same-user forgery.
- The body payload is created only after a direct delivery address exists and the probe passes. The Windows temporary root takes only the lexical path returned by `GetTempPathW`, and the no-follow boundary rejects reparse points component by component. The body is written to a `0700` temporary directory and `0600` file accessible only to the current user and tightened at creation; the foreground/console fallback creates no payload.
- The terminal receives only one line starting with `# kander-notify:` (also recognized as `# onevoke-notify:`) that contains the absolute path and the marker.
- herdr must use `agent prompt <pane-id> <instruction>` to deliver to the agent TUI already running in the pane: it sends the body according to the pane's actual bracketed-paste mode, then sends an encoded Enter after a delay, and rejects up front when the agent is stopped at an approval or question UI rather than stuffing the body into that dialog. Do not switch to the shell-oriented `pane run` (the body and trailing CR are written in one batch, TUIs such as Cursor do not treat that as a submit, and the body stays in the input bar), and do not hand text to `pane send-keys`, which only accepts key names. tmux keeps using `send-keys -l` followed by a separate `Enter`.
- herdr confirms the marker with `pane wait-output --match <marker> --source recent` (literal substring, allowing a TUI rendering prefix); tmux uses a bounded `capture-pane` with the same literal match. A marker timeout only warns "delivered, not confirmed within timeout" and does not recover a second process.
- A successful delivery action returns success without moving the card. The message body for a `review/` card is prefixed with the requirement to perform the `review -> working` move first (plain for an unbound message, ID/epoch-bound for a durable dispatch) and then handle the items.

## Notify Recovery

- Only foreground/console, no direct delivery channel, or a failed probe or delivery action make the command recover the original session internally. A process-type recovery must stay alive during the full timeout observation window; after validation, foreground keeps occupying the current terminal until the agent exits. herdr recovery liveness follows the new-pane criteria of `resume`: the state accepts only `idle`, `working`, `blocked` and rejects `done` and `unknown`.
- When tab/window/process cleanup after a failed recovery validation fails, it is reported together with the original error, noting that the new agent may still be alive. When both paths fail, the command exits non-zero and reports both reasons; the card body and original state are unchanged. After a successful recovery or takeover, the new container address is written back to the card `WINDOW`.

## Dismiss

- `dismiss` accepts only `done/` or `archived/` cards and changes neither body nor state; `--timeout` must be greater than 60 seconds, default 120.
- It locates the herdr pane or tmux/tmux-session pane by the card `WINDOW`. Old herdr cards without `WINDOW`, and stale addresses where the pane does not exist or is dead or the agent, session marker, or foreground process mismatches, reuse the unique session reverse lookup of `notify`; 0 or multiple hits are rejected, and a busy state gets no reverse lookup and is rejected. herdr takes the tab the matched pane actually belongs to as the container; tmux reads the session/window of the matched pane with `display-message`; the card `WINDOW` is not written back.
- Before delivery, the exact agent and session match of `notify` is reused: herdr additionally requires `agent_status` to be `idle` or `done`; tmux additionally requires the pane to be alive, not in copy-mode, and with a matching foreground process. The current tab or session/window of the validated pane must exactly equal the located container, and the container may contain only that pane; a moved pane or extra panes reject before delivery, ownership is verified again while waiting for exit, and the topology is re-checked before closing.
- The pane receives the `exit_command` declared on the agent definition (herdr `agent prompt`; tmux `send-keys -l` followed by a separate `Enter`). An agent without that field is refused and the container kept. The herdr tab or tmux window is closed only after confirming the agent process has exited; a tmux window that already disappeared with the agent counts as closed.
- Any identity, state, container ownership, delivery, exit confirmation, or close failure, as well as a timeout, returns non-zero and preserves the working state; the command never force-kills or degrades to closing the container. `foreground`/`console` have no terminal container: the command reports an error without any partial action.

## Check Liveness Classification

- `check` with no arguments or `--all` probes all `working/` cards; targeted checks probe only the specified `working/` cards, never `review/`. Before the summary line it prints a four-state liveness section:
  - `alive`: the agent and available session identity match. It is an observation of presence, not readiness to receive input or evidence of progress; `notify` applies its own readiness checks. A herdr pane with missing identity but a valid agent and state is still `alive`, noted as not directly deliverable.
  - `stopped`: the pane is gone or the agent/process mismatches and a valid reverse lookup confirms zero matches. When lookup is disabled or the session reference is empty, the direct-pane classification applies; a Codex empty reference gets no reverse lookup.
  - `drifted`: the session was uniquely reverse looked up to a new pane, with the new address attached.
  - `unknown`: an invalid session/window, foreground/console, program unavailable, state or probe failure. Reverse lookup errors, invalid output, timeouts, and multiple matches are `unknown`, preserving the stale-address reason and the reverse-lookup stage and reason; they do not prove the session stopped.
- Probe errors count as `unknown`; they do not write the card or affect the `check` exit code. One card's forward probe, session reverse lookup, revalidation, and process cleanup share one deadline (10 seconds by default); exhaustion or cancellation stops subsequent queries and reports `unknown`. The liveness section collects all selected working cards within one 10-second batch budget with at most 4 concurrent probes; unfinished cards retain an `unknown` reason. Output includes observation time, validity, and a separate runtime state. The budget excludes board reads and output writes and is not a hard real-time guarantee. See [Probe deadlines and cancellation](probe-deadlines.md) for the process ownership contract, and [Subscription facts and member sets](subscription-facts.md) for the event schema and output lifecycle of `subscribe`.
