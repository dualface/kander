# Launch, Delivery, and Terminal Cleanup Mechanics

This document records how `kander start`, `resume`, `notify`, `dismiss`, and the launchers behave at the terminal and process level. The released rules (`rules/KANDER-KANBAN-RULES.md`) state only what an agent must do with these commands; the mechanics below are implementation contracts for this repository and are verified by the tests of `internal/launch`, `internal/notify`, `internal/takeover`, `internal/liveness`, and `internal/terminal`.

## Start Metadata

- The agent, launcher, and model tier of `start` default to the configuration; `--agent` and `--launcher` override only this invocation. `SIZE: large` uses `kanban_agents.large`, `SIZE: small` uses `kanban_agents.small`, both falling back to `kanban_agent`. On success the command prints the scale and the actual agent.
- Card pins (`EXEC_AGENT`, `EXEC_MODEL`, `EXEC_EFFORT`, read only from the card header) replace the configured agent, model, and effort for `start`, `PreviewStart`, plain `resume`, takeover, and `notify` recovery. Resolution lives in `internal/launch/pins.go`: an explicit `--agent` must equal `EXEC_AGENT`, a relaunch refuses when the session agent differs from it, and a forced agent without a model or effort pin takes that agent's configured values for the card's scale. The checks run before any claim, session allocation, or container. Parsing, validation, and the record writer are in `internal/board/pins.go`.
- A card that pins anything gets `EXEC_RESOLVED: agent=<v>(<src>) model=<v>(<src>) effort=<v>(<src>)` in the same write that already records start metadata, takeover metadata, or the foreground `WINDOW`; container launches write it with `WINDOW` once the container exists. A rollback restores the pre-call text, record included. Cards without pins are written byte for byte as before. Older Kander binaries ignore these fields and launch from the configuration.
- `start` writes the session identifier into `SESSION`: Claude/Grok/Pi a UUID, Cursor the chat id, Devin the exact id found by its declarative `session.discovery` (`devin list --format json` enumerated before launch and polled after for up to 30 seconds, because one call can take several seconds), OpenCode likewise (`opencode session list --format json`, matching the record whose `directory` equals the launch directory), Kimi likewise (`kimi session list --json --all`, matching the record whose `workDir` equals the launch directory), Droid the exact id found by its `hook:droid-sessions` hook (the one new `~/.factory/sessions/*/<id>.jsonl` whose `session_start` header names the launch directory), Antigravity CLI the exact conversation id found by its `hook:agy-transcript` hook (the one new directory below `~/.gemini/antigravity-cli/brain/` whose `transcript.jsonl` starts with a user request equal to the launch instruction), and Codex the exact newly discovered ID on a launcher that marks the pane (`pane_metadata`: herdr-core, tmux, tmux-session, dsh) or reports the session (herdr); with a configured server the start confirms `codex <id>` to the card, the execution record, the launch journal, and the local execution credential in one step, while a local-board start records it only on a session-reporting launcher. On other launchers `SESSION` stays `codex`. The discovery contract — argv-only enumeration, `{cwd}`/`{task_id}` matches, bounded output and polling, exactly-one-new-candidate, rollback on failure — is defined in [Session Policies](custom-agents.md#session-policies). The adjacent `WINDOW` field holds the delivery address: herdr `herdr:<tab-id>:<pane-id>`; tmux/tmux-session `<launcher>:<session-id>:<window-id>:<pane-id>`; foreground/console the launcher name.
- tmux/tmux-session first create a placeholder window/pane, persist `WINDOW`, then start the agent with `respawn-pane` as `cd -- <quoted directory> && exec <agent>`, and write the pane marker with `tmux set-option -p -t <pane-id> @kander_session <session-id>`. Failure to write the address, start, or write the marker closes this invocation's window and rolls back the card.
- When an old card lacks the two fields, they are inserted in order after `OWNER`; unstarted old cards are not batch-rewritten.
- When start or liveness validation fails, the original document is restored only while the operation still owns the current revision; otherwise the newer text is preserved and a conflict reported. When restoring the document fails, the error states the directory where the card actually is.

## Transition Entrances

`internal/launch` and `internal/notify` never render `OWNER`, `SESSION` or `WINDOW`. Those fields change only through the entrances of `internal/board`, and each entrance writes the matching execution transition in the same transaction. See [Execution Ledger and Chain Walk](coordinator-recovery.md#execution-ledger-and-chain-walk).

An entrance writes on the latest snapshot and changes only its own fields. It checks the execution record and the cycle of the caller's cursor, never the card revision, so a write by the executor cannot make the launcher fail. `BeginTaskStart` and `BeginTakeover` bind the cursor to the record they create; any other writer calls `BindExecutionCursor` once. A cursor bound to a record that is no longer current is refused.

| Entrance | Transition |
| --- | --- |
| `BeginTaskStart` | `start`: the move to `working/`, the metadata, and a `pending` record |
| `ConfirmTaskStart`, `ConfirmTaskStartSession` | `confirm`: the record becomes `running` |
| `BeginTakeover` | `handoff`: the old record becomes `handed-off`, and a new `pending` record starts |
| `UnresolveExecution` | `unresolve`: the launcher that holds a `pending` record ends it as `unresolved`, with the failure and the container address |
| `AdoptExecution` | `adopt`: a `pending` or `unresolved` record becomes `running`, with the decision reference |
| `RecordExecutionWindow` | `window-update` |
| `RecordExecutionSession` | `session-repair` |
| `RecordExecutionProcess` | `process-identity`: the one-time `process.json` original |
| `RollbackDocument` | `rollback`, or `window-update` for a relaunch that only wrote `WINDOW` |

An entrance returns `ExecutionResult.Advanced`: the card revision or column differed from the cursor before this write. The entrance then moves the cursor forward, so without this fact the launcher's own successful write would hide an earlier executor write. `Entry.AdvancedPastCursor` keeps the fact for the whole operation, and `RollbackDocument` refuses once it is set, so a rollback cannot erase executor work behind a current cursor.

## Task Files and Command Lines

- `start`, `resume`, and a `notify` that needs to recover a process write the full prompt to a UTF-8 temporary task file on all platforms, containing the task ID, fixed requirements, and the message body. The agent command line receives only one instruction containing that absolute path. The file asks the agent to try to delete it when done; failure to delete or leftover files do not affect the result. These files get no POSIX permission or Windows ACL check or tightening.
- The task files of `start`, `resume`, and takeover carry a fixed English waiting reminder (`templates/prompt/waiting.md`): run long commands in the foreground or in a background mode whose completion the runner reports, never detach them with `&` or `nohup`, and never end a turn while waiting on a process the runner will not report. The `orchestrate` task file carries its own reminder that points at `snippets/commands/subscribe.md` "Waking Up" and adds the same long-command rule. Both are unconditional: no module switch removes them, because a stalled wait has nothing to do with the optional modules. A `notify` in the v2 client goes through the server and carries no rules preamble, so it has no reminder; the session already received it with its start, resume, or takeover prompt. As with every prompt template, an installed copy wins over the embedded one and a missing copy falls back to the embedded one. An installation from before this reminder therefore shows the waiting reminder of the execution prompts at once (it has no `waiting.md`), but keeps its old `orchestrate.md`, and so the old orchestrate prompt, and its old rule files, until `kander install` or `kander doctor` refreshes them.
- Every filesystem path shown to an agent goes through `process.AgentPath`. This covers:
  - the task file path in the one-line instruction and in the cleanup sentence;
  - the project-install `kander` entry, the rules entry, the command contract, and the issue rules path;
  - the project `AGENTS.md`;
  - the issue evidence files of triage and result sessions;
  - the notify message file in the direct delivery line;
  - the reviewer's one-line prompt pointer.

  On Windows these paths use forward slashes (`C:/Users/x/proj/.kander/bin/kander`), because claude and grok run shell commands through Git Bash, which consumes backslashes as escapes. Forward slashes also work in PowerShell and in the agents' file tools; cmd is not guaranteed. POSIX output is byte-for-byte unchanged. Kander still opens files, builds argv, writes card metadata, and compares paths with native paths; only the displayed text changes. Paths containing spaces are not quoted, so an agent must quote them itself for its shell. The review bootstrap body (contract, evidence, and spec snapshot paths) is read by file tools rather than a shell and keeps native paths.
- New and imported cards state a hard communication requirement for every related conversation, rendered from their `LANGUAGE` field. That field remains the only language source; older cards fall back to `agent_language` when it is missing. The generated sentence uses the Chinese, Japanese, or English message catalog according to the card language; other languages use English wording with the requested language value preserved.
- Delivered one-line instructions carry no language suffix. The requirement lives inside launch and notification task files, including recovery, orchestrate, triage, refinement and issue result sessions. Chat task files prepend the requirement to the user's unchanged message. Review contracts state the communication and report language requirements. Language selection is unchanged: card language for card sessions, anchor language for issue results, shared card language for orchestrate (configuration when mixed), configuration for triage and Chat, and report language for review.
- When `prompt_delivery.mode` is `pane`, that instruction is not an argv element: after `pane run`, Kander waits for the agent TUI using the definition's `ready` / `blocked` marks (`blocked` is checked in parallel and wins immediately), then delivers the prompt with the same primitives as notify (herdr or luvus `agent prompt`; tmux `send-keys -l`, a 500ms wait, then a separate Enter). On a program status launcher (herdr-core) the screen marks are not read: Kander waits, within the `ready` budget, until the terminal reports through OSC 7501 and the reported `status.app` equals the agent's `program_status.app`, then sends the prompt with `hc send`, run without `HC_TERMINAL_ID` so hc does not tag the prompt as another terminal's message. A terminal that stays unreported, reports another app, or ends first fails the start through the same path as a pane that never became ready: nothing is delivered and the terminal is closed.
- Native Windows prefers the agent `.exe`. When Codex, Claude, Grok, Cursor, Pi, Devin, OpenCode, Kimi, Droid, or Antigravity CLI only has a `.cmd`/`.bat`, that script is launched through an explicit `cmd.exe /d /s /v:off /c` with the agent adapter layer's argument encoding.
- The container shell parses the agent command. POSIX uses sh quoting and rejects carriage return, line feed, and NUL. On Windows, the herdr pane and the shell herdr-core starts use PowerShell. The typed line carries argv in variables that `cmd.exe` expands. PowerShell values are single-quoted with all five single-quote characters (U+0027, U+2018, U+2019, U+201A, U+201B) doubled. Before creating a Windows container, Kander rejects control characters (C0, DEL, C1) in the command values and the forwarded `KANBAN_DIR`, `KANDER_CONFIG`, `KANDER_LANG`, and `KANDER_CLIENT_HOME`. The line editor interprets those characters as keys.
- A native `.exe` in a Windows pane uses `cmd.exe /d /s /v:on /c`. The delayed `!VAR!` references insert the arguments after cmd.exe parses the command, and the native program reads a backslash followed by a double quote as a literal double quote. A `.cmd` or `.bat` uses `/v:off`, `%VAR%`, and doubled quotes so the encoding survives the script's reparse of `%*`. An argument with an odd number of double quotes can still split differently if the batch script forwards it to a program that uses older C runtime rules.

## Interactive Session Naming

With a nonempty `rename_command`, Kander attempts one local slash command
inside each newly launched interactive agent. This includes card starts,
native resumes and takeovers, the process-recovery path of notify,
orchestration, Chat, and issue triage and result. Sending a message to an
already running session and starting a non-interactive reviewer do not
rename. Kander uses the existing launch label to derive the session name
and uses the backend's pane text operation, not a shell command or a startup
`--name` argument. The [agent definition](custom-agents.md#interactive-session-names)
describes the filter and matching rules.

For an agent that must be idle for renaming, a container launch leaves the
initial prompt out of argv and waits for the interactive composer. A matching
startup dialog takes precedence over readiness, even on a program-status
launcher. Kander types nothing while the dialog remains. If it clears and the
composer becomes ready, Kander sends the rename command, checks for the
configured acknowledgement or the ready composer with no pending rename
draft, then sends the prompt. If the startup budget expires, Kander types
nothing and fails with `launch.pane_ready_blocked` for a detected dialog or
`launch.pane_ready_timeout` otherwise. These failures use the pane-prompt
rollback path and do not publish `WINDOW` before the prompt.

A definition with `rename_delivery.after_argv` keeps the prompt in argv. It
uses the same readiness observations but skips renaming with one warning if
the pane is blocked or does not become ready. Otherwise it sends the rename
command without resending the prompt. Program-status launchers require a
matching app and idle or done status, or working status for this explicit
after-argv policy, as well as any configured screen match.

An unsuccessful rename or a missing acknowledgement after three seconds
warns without failing the launch. `foreground` and `console` retain their
original arguments and warn because there is no pane to type into. Without a
rename command, the original delivery mode and readiness behavior are
unchanged, including the existing pane-prompt behavior of Droid and Kimi.

## Launchers

- Eight built-in launchers, plus the launchers provided by loaded terminal definitions (JSON files in the global or project share directory `terminals/`; the project copy replaces the global one, which replaces an embedded one of the same name). `auto` is resolved at start time and never written back to the configuration.
- `auto` resolves only among container launchers and never falls back to `foreground` or `console`: it takes the launcher with the highest `auto_priority` among the definition launchers that run inside an existing session and whose required environment for auto holds. Built-in values, in the resulting order: `herdr-core` has priority 250 and needs a non-empty `HC_TERMINAL_ID` (for auto only: an explicit `--launcher herdr-core` does not need it); `herdr` has priority 200 and needs `HERDR_ENV=1` (its `HERDR_WORKSPACE_ID` stays a precondition checked when preparing the launch and is excluded from auto); `luvus` has priority 150 and needs `LUVUS_ENV=1` (its `LUVUS_PANE_ID` is checked when preparing the launch and excluded from auto); `tmux` has priority 100 and needs `TMUX` (its `TMUX_PANE` is checked when preparing the launch). With `HC_TERMINAL_ID` present herdr-core wins over herdr, luvus and tmux, and inside both herdr and tmux herdr wins, unless a loaded definition declares a higher priority; when none applies, the start fails without claiming and does not fall back to `tmux-session`, `foreground`, or `console`.
- `tmux` creates the task window in the background of the starter's current session and requires `start` itself to run inside tmux.
- `tmux-session` determines a dedicated session by the main worktree path (`kb-<dir-name>-<path-digest>`): created when absent, reused when it exists and `@kander_project` or `@onevoke_project` matches this project; one session per project with one background window per card; no requirement to run inside tmux; the client is not switched after launch; the command prints the session name, window id, and an attach hint.
- `herdr` requires `HERDR_ENV=1`, `HERDR_WORKSPACE_ID`, and herdr on PATH; it creates a new tab in the background of the current workspace (`--no-focus`, label reusing `window_name()`), first waits for the root pane to be ready, then runs the same agent command as tmux in that pane, without using `herdr agent start`. Command text sent before the shell of a new tab takes over the terminal is discarded, so `pane run` happens only after the pane renders its first frame of output; the readiness wait has an upper bound, and a timeout is a failure.
- `luvus` (POSIX only) requires `LUVUS_ENV=1`, `LUVUS_PANE_ID`, and luvus on PATH; it splits the calling pane with `--no-focus --cwd`, verifies the new pane's directory, moves the pane to a new tab, names it with `window_name()`, and focuses the calling pane again. A luvus that ignores `--cwd` fails the start after the new pane is closed. See [Terminal backends](terminal-backend.md#8-the-built-in-luvus-launcher).
- `herdr-core` requires `hc` on PATH and a running herdr-core; it opens a new hc terminal with `hc run --bg --no-parent --rm`, the startup directory, a unique `--name`, and the label `kander.window=<window_name()>`. On POSIX the terminal runs `/bin/sh` under `/usr/bin/env` with the caller's `PATH`, `KANBAN_DIR`, `KANDER_CONFIG`, and `KANDER_LANG`. It omits unset values and invokes the agent by its resolved absolute path. On native Windows (x64), the terminal runs `powershell.exe -NoLogo -NoProfile` in the directory given by `--cwd`. The typed line is `try { <forwarded variables><command> } finally { if ($null -eq $LASTEXITCODE) { exit 1 }; exit $LASTEXITCODE }`. It sets `KANBAN_DIR`, `KANDER_CONFIG`, `KANDER_LANG`, and `KANDER_CLIENT_HOME` to the caller's values and removes an empty or unset value. The client home lets the agent find the v2 execution credentials when the caller uses a custom location. Hc refreshes `PATH` from the Windows registry. PowerShell exits with the agent's exit code or with a nonzero code when the command cannot start. Hc then removes the terminal through `--rm`. A PowerShell prompt left behind can still appear live because hc retains the last reported agent status. Ctrl+C and syntax errors in the line are outside the exit guarantee. Each new terminal opens as its own tab in the calling terminal's Herdr App space and the tab is named for the task: after `hc run`, the launch layer calls the `place_container` hook, which labels the terminal with the caller's `herdr.space` (read from `HC_TERMINAL_ID`) and a new random `herdr.tab`, waits for the App to create the tab and, in one versioned `doc.set` of the `herdr-app` layout document, writes its name and moves it to the end of the space's tabs, so the new tab is last in the space (the App itself inserts it after the active tab). The tab title is the window label for every launch: `kb-<card title>` for a task agent (start, resume takeover, notify recovery), `or-<first task ID>` for an orchestrator, and the chat, issue triage and refinement labels for those sessions. A failure to place or name the tab (layout read or write failure, the tab not appearing within 5 seconds, conflict retries used up) never fails the launch: the terminal runs and a warning is printed (collected into the result warnings when the caller collects them). The calling terminal's `herdr.tab` and `where` labels are not copied. Every start entrance (start, resume, takeover, notify recovery, orchestrate, issue triage, refinement, issue result, and TUI chat) refuses an agent without a reporting `program_status` declaration before any side effect: the TUI start preview refuses before it moves a backlog card; a resume or takeover before it prepares a new durable dispatch, and on a same-ID retry only after a completed or accepted receipt was returned, before any reauthorization; a durable notify before it prepares its dispatch when the executor is observed stopped (a live executor, or an explicit `--pane` target, still gets direct delivery), and before it reauthorizes an accepted dispatch or begins a recovery attempt. See [Terminal backends](terminal-backend.md#9-the-built-in-herdr-core-launcher).
- `foreground` runs in the foreground of the current terminal and waits for the agent to exit. `console` is supported only on native Windows; it starts the agent in a separate console window and returns the PID immediately, with no session/window reuse, attach, or output capture.
- POSIX defaults to `auto`. Windows defaults to `console`. It rejects `tmux`, `tmux-session`, and `luvus`. Its `auto` selection checks herdr-core, then herdr.

## Startup Directory

The startup directory is the parent of the board root. Every launch through `launchAgent` uses it: `start`, `resume`, takeover, triage, chat and orchestrate.

- A container launcher validates the directory before `CreateContainer`. A missing path, a path that is not a directory, or a path with a line break or NUL fails the launch and creates no container. tmux gives no such failure itself: `new-window -c` with a bad directory exits 0 and the pane opens in `$HOME`.
- `foreground` and `console` skip this check. Their process spawn reports a bad directory directly.
- tmux and tmux-session enter the directory in the pane before `exec`, so the agent does not depend on the tmux server's own directory or on how a tmux version treats `respawn-pane`. Quoting stays in `internal/launch` (`posixQuote`); the terminal layer does not escape the value again.
- A `cd` that fails after validation runs after `respawn-pane` already returned 0, and an open pane proves nothing while a slow shell has not reached `cd`. tmux therefore starts that shell in `/` (`respawn-pane -c /`), and the launcher watches the pane through the optional `pane_directory` operation. The watch uses one budget for all its probes and waits: the readiness timeout, 15 seconds or the extended value with `extended_launch_timeouts`. A backend without `pane_directory` (herdr, luvus, a definition that does not declare it) is not watched.
- The pane counts as entered when its directory is the startup directory, compared by file identity, or when its foreground command equals the agent's `process_name`. This covers the launches without a `paneSession` too (triage, chat, orchestrate), which have no later step that would notice.
- `pane_directory` hides the pane's first moment: the fork of a respawned pane still reports the tmux server's directory under the command `tmux`, which would read as entered for a server started in the project.
- A pane that ends first (gone, or dead with `remain-on-exit`) fails the launch. Either the `cd` failed, or the shell or the agent exited between two polls. Nothing is left in the pane, so this is not `DeliveryUnknown`: the launch takes the ordinary failure path through the judge. A gone pane took its window with it, so nothing is closed; a dead pane is closed by its window ID. An agent that started and exited between two polls stays covered on a durable dispatch, because `accept` and `complete` receipts are atomic.
- A pane with no answer when the budget ends also fails the launch, because an open pane is not proof. The agent may be running, so a durable dispatch reports `DeliveryUnknown` and keeps the window; any other launch closes its own window.
- A probe error only defers to the next poll. A pane closing during a probe can fail that probe.

## Late Failures

A launcher judges a failed launch before it closes anything. `launchAgent` calls the judge of `LaunchPlan` at its failure point; `settleAfterLaunch` does the same for a step that fails after `launchAgent` returned (liveness validation, the confirmation). `kander start` and `resume --agent` set the judge. Plain `resume`, notify recovery and the board-free sessions own no start attempt and always clean up.

`board.ReadExecutionStanding` is read-only and gives two facts:

- `Superseded`: a `handoff`, `adopt` or `reclaim` link leaves the launcher's record. The launcher closes nothing and rolls nothing back, and `kander start` exits 0 with `superseded`.
- `Evidence`: `Entry.AdvancedPastCursor`, or the card differs from the cursor by revision or column. The launcher's own writes keep the cursor current, so they do not count. An entrance moves the cursor, so `Advanced` keeps a write the entrance covered up.

| Judgement | Container or process | Card | Attempt |
| --- | --- | --- | --- |
| Superseded | untouched | untouched | owned by its successor |
| Evidence | kept | kept | `unresolved` |
| Read failed | kept | kept | `unresolved` |
| No evidence, close succeeds | closed | rolled back | `rolled-back` |
| No evidence, close fails (T-01) | unknown | kept | `unresolved` |
| No evidence, rollback refused | closed | kept | `unresolved` |

The last row is the window between the judgement and the rollback. `RollbackDocument` refuses, so the write survives, and the attempt still ends.

`settleFailedLaunch` writes the result. `UnresolvedError` carries the fixed line and the next steps, and `exitLaunch` prints them with exit status 3. The steps are adoption and takeover, except for an unmarked pane that adoption cannot mark. A pane is unmarked after a `PaneMetadata` launch whose outcome never set `SessionMarked`, because discovery or the marker write failed; it reads `unknown`. `markerRepairable` decides from static facts whether adoption can write the marker: the recorded `SESSION` has a reference, or the agent's session mode is `hook:codex-rollout`. It runs no discovery and writes nothing. When it is false, the steps are to stop the old executor in `WINDOW` by hand, then the takeover. A takeover with a durable dispatch never cleans up after the send, so its delivery-unknown and validation failures end as `unresolved`.

The judgement looks only at the card. Two limits follow:

- A dispatch or a manual `kander update` counts as evidence. The result is `unresolved`, which is a misjudgment on the safe side: the user adopts or takes over.
- An executor that runs but has not written the card counts as no evidence. The container closes and the executor ends with it. Kander adds no process probe for this case.

`unresolved` writes one more thing: the container address when the card lacks it, so the next owner can reach the executor. A card that already left `working/` and `review/` keeps its text. The cycle never changes.

Until the attempt ends, `PrepareDispatch` refuses the card with the next step, and `BeginTakeover` requires a decision. Replaying a dispatch by its ID stays allowed, because a retried takeover needs it.

`kander resume --adopt` goes through the server. It needs the execution credential of this client, refuses a card whose `OWNER` or `SESSION` differs from the record (`board.CheckAdoptable`, the shape a 1.0.0 takeover of a `pending` attempt left), and refuses a record whose start is not unfinished or whose recorded session and window no longer match the credential. It then observes the local executor and sends the `adopt` execution update with the observation ticket and the decision; only an `alive` observation passes, and a takeover or handoff that lands in between fails at the revision fence of the server.


## Process Identity

`foreground` and `console` have no pane to probe. When the launcher starts the agent it records one process identity in the execution record, as the immutable `process.json` original plus the `process` field of the current record. The write goes through `RecordExecutionProcess`, a `process-identity` link of the chain, and it never touches the card, so it does not race the executor for a revision. Identity is the tuple `(boot_id, agent_pid, agent_start, executable)`. A process ID alone proves nothing.

| Field | Source |
| --- | --- |
| `launcher` | `foreground` or `console` |
| `kander_pid`, `kander_start` | The waiting Kander process. `foreground` only: `console` returns at once, so they stay 0 and empty |
| `agent_pid`, `agent_start` | The process the launcher created, and its start time from the kernel |
| `boot_id` | The boot identifier below |
| `executable` | The base name the kernel reports, never the configured agent name |
| `recorded_at` | RFC 3339 time of the write |

| Platform | Start time | Parent | Executable | Boot identifier |
| --- | --- | --- | --- | --- |
| Linux | `/proc/<pid>/stat` field 22 | `/proc/<pid>/stat` field 4 | Base name of `/proc/<pid>/exe` | `/proc/sys/kernel/random/boot_id` |
| macOS | `kern.proc.pid` `p_starttime` | `e_ppid` | `p_comm` | `kern.boottime` in Unix seconds |
| Windows | `GetProcessTimes` creation time | Toolhelp snapshot | Base name of `QueryFullProcessImageNameW` | Now minus `GetTickCount64`, in Unix seconds |
| Other | Not supported | Not supported | Not supported | Not supported |

- Linux uses `/proc/<pid>/exe` and not `comm`, because a process can rewrite `comm` and `comm` truncates at 15 bytes. The ` (deleted)` suffix is removed, so an agent that updates itself keeps its identity.
- A zombie counts as exited on every platform.
- Numeric boot identifiers compare within 300 seconds, because the Windows value is derived from the wall clock and the macOS value moves with the calendar clock. The tolerance is safe: after a reboot the exact start time of a process cannot match, so only the reason of `stopped` differs.
- Every sample is bound to the process the launcher started: the sample is read first and the start handle is checked after it, and a start time other than the first one ends the step. The ID then names a later process, and that process is never recorded.
- The identity is immutable, so it is written only when the executable is final. A running process can still exec, and nothing announces that: neither quiet nor the name of the started file proves it is done, and a card write does not either, because a person or a dispatch can make one.
- The evidence is the read of the task file. A shim or a wrapper never opens it, and no card update or dispatch touches it, so a read means the agent itself runs. The launcher takes the file's access time before it starts the agent, and a later access time, or a removed file (the executor deletes it when done), counts as the read.
- `foreground` watches in the background every 500ms, because that Kander stays until the agent exits. Until the read the check says `unknown` and adoption is refused. The step ends with the agent. A failure is silent, because the terminal belongs to the agent; the check names the missing identity.
- A mount with `noatime` shows no read through the access time. Such a card stays `unknown` while the task file exists, which is the safe direction: nothing is recorded that could later read `identity-mismatch`. A removed task file still counts, so the identity is recorded when the executor removes it while the process runs. Someone else reading the task file before the exec would record the earlier image.
- Windows has no exec, so the image is final at once and the identity is written right after the start. That is also why `console`, which exists only on Windows and returns at once, needs no watcher.
- A process gone before it could be read, a later process in its ID, or a failed read leaves no `process.json`: the start only warns. On a platform without process identity the record holds only `launcher` and `agent_pid`, so the check says `unprobeable`.
- A probe reads kernel metadata only. It never reads the environment or the command line of a process.

The check runs these steps. The first one that fails decides the result:

1. The current record has no `process`: `unknown`. The reason is "old card has no process identity" for a card without ledger links, otherwise "the launcher recorded no process identity".
2. The platform has no process identity: `unprobeable`.
3. The boot differs: `stopped`.
4. The agent process does not exist: `stopped`.
5. The start time differs: `stopped`, because the ID was reused.
6. The executable differs: `identity-mismatch`.
7. The card `OWNER` or execution cycle differs from the record: `identity-mismatch`.
8. `console`: `alive`. `foreground`: `alive` when the Kander process exists, has the recorded start time, and is the parent of the agent; otherwise `alive-orphaned`.
9. A refused probe at any step is `unprobeable`. A timeout or any other error is `unknown`.

`foreground` and `console` have no native resume. Plain `kander resume` and the recovery channel of `kander notify` refuse a card whose `WINDOW` is one of the two, and a relaunch through either launcher, whether or not the record has an identity. A relaunch on the same record would leave the identity naming the old process, and next to a live executor it would be a second one. The next step is adoption of an unfinished start or a takeover. A takeover opens a new record, so it records a new identity. A failed takeover that restores the replaced record keeps that record's identity.

## Start Success Conditions and Rollback

- Precondition checks before launch: a definition launcher's `requires` (platform, required environment variables, its program on PATH, in the order the definition declares); `herdr` needs `HERDR_ENV=1`, herdr on PATH, and `HERDR_WORKSPACE_ID`; `foreground` needs all three standard streams to be TTYs; `console` needs native Windows. A failed precondition does not claim. An agent whose `prompt_delivery.mode` is `pane` is rejected before claiming when the resolved launcher is `foreground` or `console`.
- Every failure below passes the judgement of [Late Failures](#late-failures) first.
- When process creation, tmux session, tmux window, herdr tab, herdr pane readiness wait, or `pane run` fails, the document is restored and the card moved back to `todo/`. A failed herdr readiness wait or `pane run` also closes the newly created tab; failed Codex discovery and pane session marker failures on tmux/tmux-session also close the newly created window. Failed Devin/OpenCode/Kimi/Droid discovery closes the created tmux window or herdr tab, or terminates a foreground/console process started by this invocation, before rollback.
- For `prompt_delivery.mode` `pane`, a second-stage TUI ready failure (`blocked` match, prompt-delivery rejection, or ready timeout) is the same class of failure: capture the pane output, close this invocation's tab/window, restore the document, and move back to `todo/`, without keeping the container or writing `WINDOW`/`SESSION`. Failures that need a person to answer a dialog say to run that CLI once manually and retry; a pure ready timeout reports the captured output without that instruction.
- A pane that ends right after launch, or a startup directory the launcher refuses, is a failed start; see [Startup Directory](#startup-directory).
- tmux/tmux-session count as started only after session discovery and pane marker write succeed (with `pane` delivery, only after prompt delivery also succeeds). herdr counts as started once `pane run` and any required session discovery succeed (with `pane` delivery, once prompt delivery also succeeds); an agent declaring `session.file` gets no proactive session identity report — its own integration reports the path-kind identity — while for other agents the subsequent session identity report and read-back are best-effort. foreground/console normally count as started once the process is created, while Devin, OpenCode, Kimi, and Droid additionally require exact-session discovery and persistence; a later exit does not roll back automatically. `console` prints the PID and returns immediately.

## herdr Session Reporting

- For an agent that declares `session.file`, `start` and `resume`/`notify` recovery send no `pane.report_agent_session` call: the agent's own integration reports a `kind: "path"` identity that the shared session-file resolution maps to the session id the card records. A pane that has not been reported yet is left to that native report instead of racing it with an incompatible id-kind identity, so no read-back warning appears during the launch window.
- For other agents, when herdr `pane run` succeeds and the session reference is non-empty, `start` and `resume`/`notify` recovery share the session reporting path: call `pane.report_agent_session` through the herdr control channel named by `HERDR_SOCKET_PATH` (a unix socket on POSIX, the named pipe `\\.\pipe\` plus that path on Windows; see [Terminal definitions](terminal-definitions.md)), passing this invocation's pane id, the card agent, the reference, `source=herdr:<agent>`, and a monotonically increasing `seq`, then read back the reported identity with `pane get` within a bounded budget. The read-back shares the terminal session identity resolution: an `id` (or a legacy value without kind) must equal the reference verbatim, while a `path` resolves through the agent's `session.file` declaration to the session id inside the file.
- Codex discovery on herdr reads no rollout before launch; only a sessions root that exists but is not a directory fails before claiming. Kander records the launch time right before launching the agent. Discovery then reads only the `YYYY/MM/DD` directories from one UTC day before the launch to one UTC day after now, because Codex names directories and files in its own time zone. It skips a file whose name time is more than 26 hours before the launch without opening it, and it decides by the UTC creation `timestamp` of the `session_meta` header: a session created before the launch, or a header without a valid timestamp, is never a candidate, and such files are not reopened on later polls. The prompt prefixes are built once per discovery. It accepts exactly one new ID whose header's `cwd` identifies the physical launch directory and whose user prompt begins with this task's start/resume/takeover instruction. It persists that ID through `ConfirmTaskStartSession` before reporting. Zero or multiple candidates fail discovery and follow the existing launch rollback; a global latest rollout or an orchestrator mentioning the task is never a candidate. An empty reference is not reported. Devin discovery completes before reporting, so herdr receives its exact id. Socket, response, or read-back failures print one warning and do not fail the start, roll back the card, or close the tab (they never enter the `LaunchFailure` tab close and card rollback path). herdr's own integration may still report the same identity; Kander's path exists to fill in launchers that do not trigger the integration hooks.

## Resume

- `resume` wakes up the original agent by the card `SESSION`, preserving context: Claude/Grok `--resume <uuid>`; Cursor `--resume <chat-id>`; Pi `--session <uuid>`; Devin `--resume <session-id>`; OpenCode `--session <session-id>`; Kimi `--session <session-id>`; Droid `--resume <session-id>`; Antigravity CLI `--conversation <conversation-id>`; Codex `codex resume <session-id>`. The Codex session id is looked up in the rollout records under `CODEX_HOME` (default `~/.codex`), matching only user messages that begin with this task's start/resume prompt, never orchestrator sessions that merely mention the task ID; it fails when not found. Cards without a `SESSION` record cannot be resumed.
- Devin cards started by older Kander builds contain a synthetic UUID rather than Devin's real id. Kander does not fall back to `--continue` for those cards because that could select another card's most recent conversation; the CLI instead reports that the recorded session cannot be resumed.
- Accepts only `review/` or `working/` cards; exactly one non-empty `--message` or `--message-file`; `--timeout` a finite number of seconds greater than 60, default 120. The launcher is the same as for `start`.
- After launch, liveness reuses the `notify` recovery criteria: herdr and tmux/tmux-session validate an addressable terminal; foreground and console require the process not to exit during the full timeout observation window. herdr validates the pane directly returned by this invocation's `tab create`: `agent` must match and only the states `idle`, `working`, `blocked` are accepted; the reported session identity is decided by the shared resolution — an `id` compares verbatim to the card session, a `path` resolves through the agent's `session.file` declaration, and an undecidable identity counts as unconfirmed rather than a mismatch, while an absent identity alone is not failure. What is judged is whether the known new pane is alive, which differs from the duty of direct delivery and reverse lookup to determine the target by session identity; this relaxation is not a same-user security boundary.
- On an immediate exit, the new instance is cleaned up and the command exits non-zero with whatever raw agent output can be obtained; only after validation does it report `resumed` in the `start` output format.

## Takeover (`resume --agent`)

- An explicit `--agent <name>` allocates a brand-new session even when the name equals the original agent; the old CLI context is not migrated. When new-session preparation such as Cursor `create-chat` fails, the card is unchanged. Before launch, `OWNER`/`SESSION`/`WINDOW` are overwritten with the new agent, session, and launcher; `STARTED_AT` is unchanged.
- A Codex takeover on a launcher that marks the pane (`pane_metadata`: herdr-core, tmux, tmux-session, dsh) or reports the session (herdr) discovers this invocation's exact session id, writes it as `codex <id>` through the same confirmation as `start`, and sets the pane marker when supported. Process-type Codex launchers retain `codex` and resolve by rollout mtime in later recoveries. Devin and OpenCode takeovers discover and persist the exact id on every launcher; Kimi and Droid takeovers do so on the container launchers they support.
- A takeover of a `pending` or `unresolved` record needs `--decision`, and the `handoff` link records it. The launcher of the replaced record steps aside. A failed takeover follows [Late Failures](#late-failures); without evidence, `rollback` restores the replaced record with its status and failure.
- After the new agent passes liveness validation and before printing `taken over`, the command attempts a graceful exit and closes the original herdr/tmux container under the identity and single-pane topology gate of `dismiss`. The gate applies to the located target, and a kept drifted pane is reported by its own address. When the original agent is already dead, it closes only when the container topology can be proven; when the original address is empty, foreground/console, or the same as the new address, it records N/A. When validation, exit, or close fails, it prints only `original container kept` with the reason, does not force-kill, does not roll back the new agent, and still succeeds. Cleanup and liveness observation may each use one full `--timeout`, so the worst case takes about 2x timeout. On success it prints `cleaned up original container: ...` first, then `taken over: ...`.

## Missing Identity Repair

This branch has no identity repair: neither `notify` nor the worker writes a missing session id before delivery. A start or takeover records the discovered id itself (`start` above), so a Codex execution started on a launcher that marks or reports the pane carries `SESSION: codex <id>` on the card, the execution record, and the local execution credential, and delivery proves the pane by that id.

An execution started before that behavior, by a remote start on a launcher with pane metadata, kept only `SESSION: codex` on the card and the execution record while the retained execution holds `codex <id>`. Its requests are not delivered, and native resume refuses it (`launch.start_identity_changed`): take it over with `resume --agent`. `dismiss` accepts it ([dismiss](../rules/snippets/commands/dismiss.md#distributed-cleanup)).

## Notify Probe Classes

When `notify` probes the recorded `WINDOW`, it handles three classes, and this classification takes precedence over the recovery overview of the rules:

- **Ready**: the pane exists and the agent/session match; herdr additionally reports `idle`, `done`, or `working`, and tmux additionally is not in copy-mode. A `working` agent receives the prompt while its current turn runs and handles it afterwards, so the acknowledgement may arrive after `--timeout`; that only yields the delivered-but-unconfirmed warning. A durable dispatch accepted after its persisted deadline is still rejected and follows the expiry handling.
- **Busy**: the pane exists and the agent/session match, but herdr reports any other status (such as `blocked`, which may be a permission or confirmation dialog that typed text would answer) or tmux is in copy-mode. The probe is retried at a fixed interval within the same `--timeout` budget; on timeout the command returns non-zero with "target agent busy, not delivered" and starts no recovery instance, creates no body payload, and changes neither card state nor message body; verified identity metadata may already have been repaired. A missing tmux session marker means identity cannot be proven; it counts as neither busy nor stale and goes through the recovery channel.
- **Stale address**: the pane does not exist or has exited, the agent/session does not match, or the tmux foreground process does not match. herdr does a reverse lookup from `pane list` by agent and session identity — every same-agent row is a candidate whose reported session kind and value are resolved like the direct check (`id` verbatim, `path` through the agent's `session.file` declaration); tmux uses `list-panes -a -F` with a triple filter: non-empty `@kander_session` or `@onevoke_session`, `pane_dead=0`, and the agent executable name. After a unique resolved hit, the full target validation reruns; only on success is the compatible address written back (`tmux` the session id, `tmux-session` the session name) and delivery done directly. Old tmux cards with an empty `WINDOW` get no reverse lookup.
- **Reverse lookup failed**: 0 or multiple decided hits, lookup unavailable, or the re-check of the new pane fails; recovery goes through the existing chain, reporting both the reason the original address is stale and the reverse lookup reason.
- **Undecidable identity**: a same-agent candidate whose reported session cannot be resolved (missing value, unknown kind, or an unreadable/malformed session file) leaves the lookup incomplete; an undecidable reported identity in the direct check does likewise. Undecidable evidence proves neither a match nor absence: the command fails with the reason and never delivers, recovers another executor, or treats the pane as exited.
- An explicit `--pane` override does no stale-address reverse lookup. It addresses a pane of the card's own `WINDOW` terminal when that terminal reports agent identity, and herdr otherwise.
- **herdr-core**: a terminal that has not reported its program status yet is busy (retried within `--timeout`, never delivered to); a reported app other than the agent's declared one is a stale address; `error` is reported as `blocked` and so is busy. The session identity is the `kander.session` label Kander wrote at launch, compared verbatim.

## Notify Delivery

- Accepts only `review/` or `working/` cards, exactly one message source, and a `--timeout` greater than 60 seconds (default 120).
- Address priority: explicit `--pane` override, the card `WINDOW` fast path, and, when no window is recorded, scanning `herdr pane list` by agent and session identity. Both the override and the reverse lookup use `pane get` to verify that the pane exists, the agent matches, the reported session identity resolves to the card session (an `id` verbatim, a `path` through the declared session file), and the pane state is `idle`, `done`, or `working`. Claude/Grok/Cursor/Pi/Devin/OpenCode/Kimi/Droid cards with a recorded id are compared directly; only old Codex cards without an id reuse the rollout lookup of `resume`. Kander has no agent whitelist; herdr reverse lookup coverage depends on the herdr version and on whether each `source: herdr:<agent>` integration reports session identity. After a unique resolved hit, `herdr:<tab-id>:<pane-id>` is written back to `WINDOW`; 0 or multiple decided hits do not deliver. Old tmux/tmux-session cards without a window cannot be reverse looked up.
- Direct delivery and reverse lookup establish the identity of an existing target, so when the pane reports a session identity that cannot be decided the command fails with the reason and never recovers another executor; it does not use the relaxed criteria of recovery liveness validation.
- For a tmux address the command also verifies `pane_dead=0`, `pane_in_mode=0`, `pane_current_command` equal to the agent executable name, and requires at least one of `@kander_session` or `@onevoke_session` to be non-empty and exactly equal to the session id resolved from the card. When both are empty, identity cannot be proven: no direct delivery channel, fall back, never relax to process-name-level approval. A mismatched option is a stale address handled per the three-class probe. tmux user options and herdr `agent_session` sit within same-user permissions; they avoid misdelivery and are not a security boundary against malicious same-user forgery.
- The body payload is created only after a direct delivery address exists and the probe passes. The Windows temporary root takes only the lexical path returned by `GetTempPathW`, and the no-follow boundary rejects reparse points component by component. The body is written to a `0700` temporary directory and `0600` file accessible only to the current user and tightened at creation.
- The terminal receives only one line starting with `# kander-notify:` (also recognized as `# onevoke-notify:`) that contains the absolute path of the message file and asks the agent to output the acknowledgement line the file names; the language requirement lives in the message file (see "Task Files and Command Lines"). The line never contains the marker: a pane shows the delivered line whether or not the agent submitted it, so a marker in the line would confirm an unsubmitted composer. The message file starts with the fixed English request `Acknowledge this notification: before anything else, output this line exactly:` followed by the marker `KANDER-NOTIFY-ACK:<32 hex>` on its own line; direct and dispatch delivery write the same request, and a dispatch is still settled only by its receipt.
- herdr must use `agent prompt <pane-id> <instruction>` to deliver to the agent TUI already running in the pane: it sends the body according to the pane's actual bracketed-paste mode, then sends an encoded Enter after a delay, and rejects up front when the agent is stopped at an approval or question UI rather than stuffing the body into that dialog. Do not switch to the shell-oriented `pane run` (the body and trailing CR are written in one batch, TUIs such as Cursor do not treat that as a submit, and the body stays in the input bar), and do not hand text to `pane send-keys`, which only accepts key names. luvus also uses its own `agent prompt`. herdr and luvus submit through that command, and Kander adds no wait of its own. tmux uses `send-keys -l`, waits 500ms (the step `delay` of the tmux definition), and then sends a separate `Enter`: Codex treats an Enter that arrives right after typed text as part of a paste and leaves the instruction unsubmitted in its composer.
- herdr confirms the marker with `pane wait-output --match <marker> --source recent` (literal substring, allowing a TUI rendering prefix); the polling backends read the pane text through their `read_output` operation (tmux `capture-pane`, luvus `pane read`) and apply the same bounded literal match. The marker reaches the pane only after the agent read the message file, either in its own output or in a tool display of the file, both of which prove the line was submitted. A marker timeout only warns "delivered, not confirmed within timeout" and does not recover a second process.
- The progress line and the result line of a direct delivery name the channel `<definition name>-direct` after the terminal definition, not its binary or launcher: `herdr-direct`, `tmux-direct` for both `tmux` and `tmux-session`, `luvus-direct`, and `<name>-direct` for a user definition. A recovered delivery reports the channel `resume`.
- A successful delivery action returns success without moving the card. The message body for a `review/` card is prefixed with the requirement to perform the `review -> working` move first (plain for an unbound message, ID/epoch-bound for a durable dispatch) and then handle the items.

## Notify Recovery

- No direct delivery channel, or a failed probe or delivery action make the command recover the original session internally. A card on `foreground` or `console` has no direct channel and no recovery ([process identity](#process-identity)), so the command fails with the next step. herdr recovery liveness follows the new-pane criteria of `resume`: the state accepts only `idle`, `working`, `blocked` and rejects `done` and `unknown`.
- When tab/window/process cleanup after a failed recovery validation fails, it is reported together with the original error, noting that the new agent may still be alive. When both paths fail, the command exits non-zero and reports both reasons; the card body and original state are unchanged. After a successful recovery or takeover, the new container address is written back to the card `WINDOW`.

## Dismiss

- `dismiss` accepts only `done/` or `archived/` cards and changes neither body nor state; `--timeout` must be greater than 60 seconds, default 120.
- It locates the herdr pane or tmux/tmux-session pane by the card `WINDOW`. Old herdr cards without `WINDOW`, and stale addresses where the pane does not exist or is dead or the agent, session marker, or foreground process mismatches, reuse the unique session reverse lookup of `notify`; 0 or multiple hits are rejected, and a busy state gets no reverse lookup and is rejected. herdr takes the tab the matched pane actually belongs to as the container; tmux reads the session/window of the matched pane with `display-message`; the card `WINDOW` is not written back.
- Before delivery, the exact agent and session match of `notify` is reused: herdr additionally requires `agent_status` to be `idle` or `done`; tmux additionally requires the pane to be alive, not in copy-mode, and with a matching foreground process. The current tab or session/window of the validated pane must exactly equal the located container, and the container may contain only that pane; a moved pane or extra panes reject before delivery, ownership is verified again while waiting for exit, and the topology is re-checked before closing.
- The pane receives the `exit_command` declared on the agent definition (herdr or luvus `agent prompt`; tmux `send-keys -l`, a 500ms wait, then a separate `Enter`). An agent without that field is refused and the container kept. The herdr tab or tmux window is closed only after confirming the agent process has exited; a tmux window that already disappeared with the agent counts as closed.
- Any identity, state, container ownership, delivery, exit confirmation, or close failure, as well as a timeout, returns non-zero and preserves the working state; the command never force-kills or degrades to closing the container. `foreground`/`console` have no terminal container: the command reports an error without any partial action.

## Check Liveness Classification

- `check` with no arguments or `--all` probes all `working/` cards; targeted checks probe only the specified `working/` cards, never `review/`. Before the summary line it prints a liveness section. Cards with a pane use the first four results below; `foreground` and `console` cards use the [process identity](#process-identity) check:
  - `alive`: the agent and available session identity match. It is an observation of presence, not readiness to receive input or evidence of progress; `notify` applies its own readiness checks. A herdr pane with missing identity but a valid agent and state is still `alive`, noted as not directly deliverable.
  - `stopped`: the pane is gone or the agent/process mismatches and a valid reverse lookup confirms zero matches. When lookup is disabled or the session reference is empty, the direct-pane classification applies; a Codex empty reference gets no reverse lookup.
  - `drifted`: the session was uniquely reverse looked up to a new pane, with the new address attached.
  - `unknown`: an invalid session/window, a foreground or console card without a process identity, program unavailable, state or probe failure. Reverse lookup errors, invalid output, timeouts, and multiple matches are `unknown`, preserving the stale-address reason and the reverse-lookup stage and reason; they do not prove the session stopped.
  - `alive-orphaned`, `identity-mismatch`, `unprobeable`: results of the process identity check only.
- Probe errors count as `unknown`; they do not write the card or affect the `check` exit code. One card's forward probe, session reverse lookup, revalidation, and process cleanup share one deadline (10 seconds by default); exhaustion or cancellation stops subsequent queries and reports `unknown`. The liveness section collects all selected working cards within one 10-second batch budget with at most 4 concurrent probes; unfinished cards retain an `unknown` reason. Output includes observation time, validity, and a separate runtime state. The budget excludes board reads and output writes and is not a hard real-time guarantee. See [Probe deadlines and cancellation](probe-deadlines.md) for the process ownership contract, and [Subscription facts and member sets](subscription-facts.md) for the event schema and output lifecycle of `subscribe`.
