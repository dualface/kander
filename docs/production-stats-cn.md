# Kander 实战数据

[English](production-stats.md) | [日本語](production-stats-ja.md)

统计日期: 2026-10-29. 数据来自 5 个使用 Kander 的项目的 `kanban/done/`, 只读统计; 执行模型另读各 Agent 自己的会话日志.

## 一句话

1 个人, 6 个 Agent, 90 天, 5 个项目, **2,477 张任务卡**. 其中 1,727 张有结构化审核记录: 审核由独立的审核运行完成, 89% 的审核员与执行者不是同一个 Agent. 更早的卡审核记录格式不同, 未计入审核统计.

## 项目介绍

代码量于 2026-10-07 用 `cloc` 统计 git 跟踪的文件, 只计编程语言, 含测试, 不含 protobuf 等生成代码和 JSON / Markdown / YAML 等数据与文档. 本版未重新统计. 创建时间取仓库首次提交.

- **QuickTUI**: 在手机上远程操作电脑上编码 Agent 的终端产品. 仓库创建于 2026-04-14, 8 月起用 Kander 推进.
  架构: 自托管的 Go 服务端 (Linux / macOS / Windows), iOS 客户端 (Swift), Android 客户端 (Kotlin), 客户端共用的 WebView 组件 (TypeScript), 云端中继与账户服务 (Go), Rust 安装器.
  代码约 110 万行: Go 50 万, Swift 24 万, Kotlin 20 万; 其中测试约 40 万行.
- **后端服务**: 一个闭源的线上服务. 仓库创建于 2026-06-22.
  架构: Go 服务端, TypeScript 管理后台, PostgreSQL 与 Redis.
  代码约 21 万行: Go 15 万, TypeScript 4.8 万; 其中测试约 9 万行.
- **Kander**: 本项目. 仓库创建于 2026-09-04.
  架构: Go 单二进制, 包含 CLI 与 TUI 看板 (Bubble Tea), 支持 macOS / Linux / Windows 的 amd64 与 arm64.
  代码约 13.7 万行 Go; 其中测试约 7 万行.
- **Quick Compress**: 一个闭源的 iOS 媒体压缩 App. 仓库创建于 2026-10-02, 第 4 天 (10-05) 发出首个 TestFlight 版本.
  架构: iOS 26 原生 App (Swift), 拆为 QCCore / QCMedia / QCUI 三个包.
  代码约 2.2 万行; 其中测试约 6.5 千行.
- **Ullage**: 查看多家 AI 订阅用量的守护进程与 CLI. 仓库创建于 2026-08-27, 9 月中旬起用 Kander 推进.
  架构: Rust workspace (7 个 crate), 单二进制同时提供守护进程、CLI、TUI 与可选的 HTTP API, 支持 macOS / Linux / Windows.
  代码约 6 万行 Rust (单元测试写在源文件内, 未单独计数).

## 口径

- **完成任务卡**: `kanban/done/` 下的卡, 包括目录卡和单文件卡, 不含 `archived/` 和 `trash/`.
- **项目范围**: 另有 8 个项目各有 1 ~ 12 张卡 (合计 27 张), 未计入.
- **时间**: 按卡 ID 的日期前缀取首末日期, 含首尾两天.
- **结构化审核记录**: 卡下有 `reviews/plan.json`. 其中 1,471 张至少有一次审核运行, 其余按审核计划免审.
- **审核批次**: `reviews/batches/<批次>/disposition.json`, 按批次 ID 去重. 一个批次覆盖任务组里多张卡时, 每张卡下各存一份, 只计一次.
- **审核运行**: 一个审核角色 (如 PMQA / Security) 的一次审核, 按 run ID 去重. 运行次数包含失败和中断的运行. 发现的问题只取正常结束的 2,647 次运行; 「发现必须处理问题的运行」的百分比以这些运行为分母.
- **发现问题的批次**: 批次内任一审核运行报告了必须处理的问题.
- **必须处理的问题**: Kander 把审核意见分为六档. 前三档 (blocking / high / medium) 必须处理, 写在审核报告的 `FINDINGS` 中; 后三档 (low / recommend / suggest) 只是建议, 写在 `NON_BLOCKING` 中, 不计入必须处理的问题. 2,182 个问题中 89% 是 medium 档, 指特定条件下才出错的缺陷, 或文档与实现不一致、死代码等.
- **执行的任务卡**: 卡头 `OWNER` 字段, 较早的卡写作「负责人」. 2,477 张卡都有此字段.
- **执行模型**: 执行者会话日志中使用最多的模型. 会话的来源有三种: 卡的 `SESSION` 字段; 交互式 Claude Code 或 Codex 会话中对这张卡的 `kander pick`; 执行这张卡的 Claude Code 子 Agent. 1,471 张经审核的卡中有 1,106 张 (75%) 解析出了模型, 其余列为「未解析」. Cursor 的 `default` 是 Cursor 自动选择的模型.
- **审核轮次**: 同一批次在同一个被审提交上正常结束的审核运行. 同一提交上的 PMQA 和 Security 算一轮.
- **打回**: 一轮审核中至少有一个必须处理的问题分配给这张卡. 分配取自运行的 `assignment.json`; 没有该文件的运行, 其问题分配给它审核的每一张卡.
- **审核模型**: 审核运行记录的 `model` 字段, 即当时的配置值, 包括 `opus` 这样的别名.
- **处置, 驳回, 推迟**: 每条审核意见取最后一条处置记录, 算在报告它的审核运行名下. 「驳回」与「推迟」以全部处置为分母; 「必须处理问题被驳回」只计 blocking / high / medium. 驳回必须有事实依据或引用用户的决定, 也包括被用户决定取代的意见, 所以驳回率是审核误报率的上限.
- **未列出的行**: 模型表只列经审核的卡不少于 10 张的执行模型, 以及在一个角色下运行不少于 20 次的审核模型. 「全部」与「合计」行包含所有卡和运行.
- **卡数是吞吐, 不代表价值或难度.** 各项目的任务大小不同, 不宜横向比较.
- **模型表不是排行榜.** 各行的卡大小、项目、角色与时间段都不同, 而且 90 天里模型分配调整过.
