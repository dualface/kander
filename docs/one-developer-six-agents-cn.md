# 1 人 + 6 个 Agent, 90 天, 2,477 个任务

作者: [dualface](https://github.com/dualface) · 2026-10-07 · 2026-10-29 更新数据

2026 年 8 月 1 日到 10 月 29 日, 我一个人带着 6 个编码 Agent, 在 5 个项目里完成了 2,477 张任务卡.
平均每天约 28 张, 一张卡从开工到完成中位 57 分钟.

靠的不是某个最强的模型, 而是一套规则: 谁来写, 谁来审, 出了问题怎么拦下来. 这套规则就是 [Kander](https://github.com/dualface/kander).

## 数字

| 项目 | 天数 | 完成任务卡 | 独立审核 | 发现问题的审核批次 |
| --- | ---: | ---: | ---: | ---: |
| [QuickTUI](https://quicktui.ai/) | 90 | 1,980 | 2,039 次 | 51% |
| 后端服务 (闭源) | 79 | 236 | 300 次 | 36% |
| Kander 自己 | 56 | 180 | 347 次 | 66% |
| Quick Compress (iOS App) | 26 | 56 | 98 次 | 55% |
| [Ullage](https://github.com/dualface/ullage-cli) | 34 | 25 | 81 次 | 80% |
| **合计** | **90** | **2,477** | **2,865 次** | **51%** |

这 5 个项目覆盖 Go、Swift、Kotlin、TypeScript、Rust, 从手机 App 到服务端到命令行工具. 其中 QuickTUI 约 110 万行代码, 横跨 iOS、Android 和自托管服务端.

完整数据、各项目的架构与代码量、按模型的统计、统计口径, 见 [Kander 实战数据](production-stats-cn.md).

## 6 个 Agent 怎么分工

| Agent | 执行的任务卡 | 担任审核的次数 |
| --- | ---: | ---: |
| Claude Code | 1,113 | 166 |
| Codex | 646 | 781 |
| Grok | 340 | 906 |
| Cursor | 219 | 390 |
| Pi | 116 | 419 |
| Devin | 42 | 203 |

三条原则:

1. **大卡给强模型, 小卡给快模型.** 每张卡标 large 或 small, 两档各配一个 Agent 和模型, 在质量和成本之间取平衡.
2. **写代码的和审代码的尽量不是同一家.** 每个 Agent 都既写也审. 89% 的审核由另一个 Agent 完成, 换一家模型来审, 盲区不重叠. Grok 审核了 906 次, 是审核最多的 Agent.
3. **审核按角色拆开.** PMQA 看需求和质量, Security 看安全. 每个角色可以单独指定 Agent 和模型.

## 审核发现了什么

1,504 批审核里, 773 批 (51%) 发现了必须处理的问题, 共 2,182 个. 每一个都要先核实, 再修复、驳回或推迟, 全部处理完才能交付. 最终处置中 78% 是修复.

印象最深的一次: 一个 Android 连接保活任务, 2,889 个测试全过, lint 和构建都通过.
按常规流程, 这就可以合并了. 独立审核仍然找出了旧连接回调串到新连接、心跳挂起恢复出错、
鉴权租约泄漏, 还有「测试是绿的, 但根本没测到要求的行为」. 修完再审, 最终 2,935 个测试通过.
(详见 [Kander 生产实践回顾](KANDER_PRODUCTION_RETROSPECTIVE_CN.md))

审核员也会错. 3,328 条审核意见的最终处置里, 206 条 (6.2%) 被执行者核实后驳回.
所以 Kander 要求每条意见都要核实, 不能照单全收.

## 按模型看打回与审核

审核运行记录了审核员用的模型, 执行模型从各 Agent 的会话日志反查. 1,471 张经审核的卡的数据:

- **打回**: 一张卡平均经历 1.8 轮审核, 被打回 0.78 次, 57% 的卡至少被打回一次.
  Claude Code (`claude-opus-5-5`) 执行了其中 765 张, 88% 是大卡, 每卡打回 0.78 次.
- **发现问题的轮次**: 角色比模型影响大. PMQA 有 47% 的运行发现必须处理的问题, Security 只有 16%.
  同是 PMQA, Codex `gpt-6.1-sol` 的 422 次运行中 54% 发现问题, Grok `grok-4.7-build-fast` 的 422 次中 45%.
- **驳回率**: 占全部处置的 6.2%, 占必须处理问题的 3.8%. 被驳回的多是非阻塞意见.
- **推迟率**: 只有非阻塞意见能推迟, 其中 47% 被推迟. 报非阻塞意见多的模型推迟率高, 例如 Devin `swe-2-max` 在 PMQA 中为 40.6%.
  Codex 各模型几乎不报非阻塞意见, 推迟率接近 0.

各模型的完整表格见 [Kander 实战数据](production-stats-cn.md).

## 我每天做什么

- 和 Agent 讨论需求, 让它建任务卡. 卡里写清目标、任务清单和验收清单.
- 确认开工. Agent 用 `kander start` 拉起执行 Agent, 多张卡并行跑.
- 在 TUI 看板上看所有卡的状态, 卡住的去终端里接着推.
- 看审核结论和完成报告, 决定合并.

代码由 Agent 写, 我做的是定任务、定规则、做决定.
离开电脑时, 我用 [QuickTUI](https://quicktui.ai/) 在手机上看这些 Agent.

## 要说清楚的限制

- **卡数是吞吐, 不是价值或难度.** 一张卡可能是一行配置, 也可能是一个跨端功能.
- 结构化审核记录从 9 月中旬开始. 2,477 张卡里有 1,727 张有完整的审核记录, 更早的卡不计入审核统计.
- 执行模型从各 Agent 的会话日志反查, 经审核的卡有 75% 能查到, 其余单列为「未解析」.
- 各 Agent 审的任务和角色不同, 上面的数字不是模型排行榜.
- 本文没有花费数据.
