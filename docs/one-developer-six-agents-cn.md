# 1 人 + 6 个 Agent, 68 天, 1,544 个任务

作者: [dualface](https://github.com/dualface) · 2026-10-07

2026 年 8 月 1 日到 10 月 7 日, 我一个人带着 6 个编码 Agent, 在 4 个项目里完成了 1,544 张任务卡.
平均每天 23 张, 一张卡从开工到完成中位 53 分钟.

靠的不是某个最强的模型, 而是一套规则: 谁来写, 谁来审, 出了问题怎么拦下来. 这套规则就是 [Kander](https://github.com/dualface/kander).

## 6 个 Agent 怎么分工

| Agent | 执行的任务卡 | 担任审核的次数 |
| --- | ---: | ---: |
| Claude Code | 424 | 164 |
| Codex | 193 | 357 |
| Pi | 98 | 158 |
| Cursor | 72 | 223 |
| Grok | 48 | 439 |
| Devin | 42 | 143 |

三条原则:

1. **大卡给强模型, 小卡给快模型.** 每张卡标 large 或 small, 两档各配一个 Agent 和模型, 在质量和成本之间取平衡.
2. **写代码的和审代码的不是同一家.** Grok 只执行了 48 张卡, 却审核了 439 次, 是审核最多的 Agent. 换一家模型来审, 盲区不重叠.
3. **审核按角色拆开.** PMQA 看需求和质量, Security 看安全. 每个角色可以单独指定 Agent 和模型.

## 审核拦下了什么

741 批审核里, 373 批 (50%) 报了阻断问题, 共 1,306 个. 每一个都要逐条处置: 修复, 驳回, 或推迟, 处置完才能交付.

印象最深的一次: 一个 Android 连接保活任务, 2,889 个测试全过, lint 和构建都通过.
按常规流程, 这就可以合并了. 独立审核仍然找出了旧连接回调串到新连接、心跳挂起恢复出错、
鉴权租约泄漏, 还有「测试是绿的, 但根本没测到要求的行为」. 修完再审, 最终 2,935 个测试通过.
(详见 [Kander 生产实践回顾](KANDER_PRODUCTION_RETROSPECTIVE_CN.md))

审核员也会错. 2,213 条审核意见处置记录里, 110 条 (约 5%) 被执行者核实后驳回.
所以 Kander 要求每条意见都要核实, 不能照单全收.

## 我每天做什么

- 和 Agent 讨论需求, 让它建任务卡. 卡里写清目标、任务清单和验收清单.
- 确认开工. Agent 用 `kander start` 拉起执行 Agent, 多张卡并行跑.
- 在 TUI 看板上看所有卡的状态, 卡住的去终端里接着推.
- 看审核结论和完成报告, 决定合并.

代码由 Agent 写, 我做的是定任务、定规则、做决定.
离开电脑时, 我用 [QuickTUI](https://quicktui.ai/) 在手机上看这些 Agent.

## 要说清楚的限制

- **卡数是吞吐, 不是价值或难度.** 一张卡可能是一行配置, 也可能是一个跨端功能.
- 结构化审核记录从 9 月中旬开始. 1,544 张卡里有 855 张有完整的审核记录, 更早的卡不计入审核统计.
- 各 Agent 审的任务和角色不同, 上面的数字不是模型排行榜.
- 本文没有花费数据.
