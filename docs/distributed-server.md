# Distributed server

Kander v2 ships one `kander` executable with a resident board service under `kander server` and REST client commands. Every host that works on one Git repository talks to the same server over REST, so all hosts see one board, task ownership is decided in one place, and each host executes its own tasks. This document is the design contract of the v2 branch. Normal client entry points use the service contract described below.

## Roles

| Side | Owns | Never owns |
| --- | --- | --- |
| `kander server` | Registered projects, card documents and attachments, claims and leases, handoff records, collaboration requests, idempotency receipts, the event log, published review evidence | Code, Git repositories, worktrees, agent sessions, terminals |
| `kander` client and worker | Agent and terminal control, repository location, worktrees, sessions, temporary logs, unpublished output, the private action and request journals | The board; a client never writes a local `kanban/` in normal operation |

The first version trusts its network: there is no login and no role model, one server instance serves one data directory, and storage reuses the board package's file transactions instead of a database. Claim tokens and generations isolate concurrent executions; they do not defend against a malicious client on the network. The server binds `127.0.0.1:7878` by default; serving a LAN is an explicit `--listen` choice.

## Data directory

```text
<data>/
  server.lock            exclusive lock; a second instance is refused
  secret.json            server secret that derives claim tokens (0600)
  projects.json          registry: id, name, remote, created_at
  projects/<name>-<hash>/  lowercase name (first 48 characters) and name hash
    board/               a board in the v1 layout (backlog/ ... trash/)
      .kander/groups/00000000-service-group/
        claims/<task>.json       task claim and handoff history
        group-claims/<group>.json coordinator lease and handoffs
        deliveries/<task>/<commit>.json current authenticated Git publication
        delivery-history/<task>/<digest>.json immutable earlier attestations
        receipts/<sha256>.json   idempotency receipts
        requests/<task>/<id>.json generation-bound collaboration requests
        publications/<id>.json   immutable joint material and confirmations
        review-writers/<id>.json private uploader binding and execution generations
        integrations/<target-id>/current.json target lease and observed Git phase
        integrations/<target-id>/executions/<execution>.json historical target result
        task-integrations/<task>/<generation>.json final delivery receipt
        issue-results/<source-key-digest>.json result CAS and durable external intents
      .kander/groups/00000000-review-archive-group/  review inputs and originals
    control/
      events.jsonl               bounded event diagnostic log
```

A project name is an identifier, never a path: an ASCII letter, then up to 127 ASCII letters, digits, `_` or `-` (`^[A-Za-z][A-Za-z0-9_-]{0,127}$`). Clients (configuration, `kander init --project`) and the server (registration, `import`, `maintain`) refuse any other name and state the rule; nothing is rewritten or filtered.

The project identity derives from the exact name. With `h` the first 16 hex digits of SHA-256(name), the project ID is `p-<h>` and the project directory is `projects/<lowercase name, first 48 characters>-<h>/`; for example `golf` has the ID `p-625fe74cad4600b5` and the directory `projects/golf-625fe74cad4600b5/`. One name has the same ID and directory on every server. Names that differ only in case get different hashes, so they never share a directory on a case-insensitive file system. A registration whose ID already belongs to another name is refused with `project_mismatch` and writes nothing. A registration that finds its directory already present but missing from `projects.json` (left by a registration that failed before writing the registry) reuses it while its board holds no task and is refused with `project_not_empty` otherwise, leaving the directory unchanged.

Project responses (`GET` and `POST /api/v1/projects`, and the import result) carry `board_path`, the absolute board directory on the server host; `projects.json` never stores it. `kander init` prints it after the binding, and the human-readable `kander config` asks the bound server for it with one `GET` bounded to 3 seconds, sending no write and creating no file; an unreachable server, a missing binding or an unregistered name prints it as unavailable without changing the exit code. `kander config --json` stays offline and unchanged.

`kander server projects [--data DIR]` lists every project with its name, ID, remote, creation time and board path. It reads `projects.json` without the data directory lock and writes nothing, so it also runs beside a serving instance. A missing data directory lists nothing.

v2 development data is not migrated. When `projects.json` holds a project whose ID is not derived from its name, or whose name breaks the rule, the server refuses to open and `kander server projects` exits nonzero; remove the data directory and import the boards again.

The first registration of a name may bind a Git remote URL; a later registration with a different remote is refused with `project_mismatch`, so two repositories cannot share a board by a name collision. No record keys on a client's absolute path.

`kander server` opens the data directory, takes `server.lock`, recovers every project's interrupted board transactions (`board.RecoverTransactions`), settles claims from the committed card state, logs one `project` line per project with its name, ID and board path, and only then reports ready. Until ready, domain routes answer `not_ready` (503).

## Offline card maintenance

After an explicit import, legacy file cards stay readable and read-only. Pause executors and external writers, stop the server, and run `kander server maintain --data <data> --project <name>`. If active file cards or a pending active migration exist, the command refuses until `--maintenance` acknowledges the write stop. A serving instance holds the same exclusive data-directory lock, so maintenance cannot run beside it. This command never becomes ready or serves requests.

Maintenance reuses the board migration redo journal, checks the final board and returns JSON with `project`, `changed_tasks`, and the final `snapshot` digest. An interrupted migration resumes from the exact prepared mapping and original operation ID. Original import identity, the source backup and historical report bytes remain unchanged. Repeating a completed migration reports zero changes. Resume writers only after success and a fresh service snapshot. This operation does not prune historical evidence. Normal startup recovers ordinary transactions but refuses an active pending form migration until explicit offline maintenance acknowledges the paused writers.

## Protocol

All routes live below `/api/v1`. Every domain request sends `Kander-Protocol: <n>`; a version outside the server's `[min, current]` range is refused with `protocol_incompatible` (412) before any domain operation. `GET /api/v1/version` returns both ranges so a client can refuse an incompatible server first. The current protocol is 2 and the oldest accepted one is 2: protocol 2 added the claim view status `lapsed` and the error code `taken_over`, and a protocol 1 worker would still stop agents on its own timeout, so mixed versions are refused.

| Route | Purpose |
| --- | --- |
| `GET /health`, `GET /ready`, `GET /version` | Liveness, readiness, protocol range |
| `GET /projects?name=`, `POST /projects` | Resolve or register a project |
| `GET /projects/{p}/tasks[?state=]` | Task list with claim views and the event cursor it is consistent with |
| `POST /projects/{p}/tasks` | `kander new` |
| `GET /projects/{p}/tasks/{t}` | `kander show` |
| `GET`, `PUT /projects/{p}/tasks/{t}/documents/{path}` | Read (`kander show --document`) or publish (`kander update --document`) `spec.md`, `plan.md`, `report.md`, attachments |
| `POST /projects/{p}/tasks/{t}/deliveries`, `GET .../deliveries/{sha}` | Authenticated publication facts for a commit available from the common remote |
| `GET .../tasks/{t}/dispatches/{id}`, `POST .../dispatches/actions/{action}` | Controlled dispatch preparation, attempts, reauthorization, terminal decisions, settlement and wrap-up grants |
| `POST /projects/{p}/tasks/{t}/move` | State moves other than claims |
| `POST /projects/{p}/tasks/{t}/claim`, `/takeover`, `/renew` | Ownership |
| `GET`, `POST /projects/{p}/tasks/{t}/requests`, `POST .../requests/{r}/answer` | Collaboration requests |
| `POST /projects/{p}/tasks/{t}/execution` | Launcher facts of the holder: window, session, confirm, rollback |
| `POST /projects/{p}/tasks/{t}/observation` | Generation-bound agent presence, independent of worker liveness |
| `POST /projects/{p}/snapshot`, `/check` | Coordinated read snapshots and server-side structural/evidence checks |
| `POST /projects/{p}/reviews/plan`, `POST .../reviews/batches/{b}/aggregate`, `GET .../reviews/batches/{b}/view`, `POST .../reviews/close`, `GET .../reviews/progress/{t}` | Review gate evidence |
| `GET /projects/{p}/groups/{g}`, `POST .../claim`, `/renew`, `/observation`, `/release` | Private coordinator lease and its public checkpoint |
| `POST /projects/{p}/groups/{g}/facts`, `/reconcile`, `/recover`, `/remove-member` | Controlled coordinator producers and client Git verdicts; `remove-member` takes one unstarted member out of a checkpointed group (see [Orchestration checkpoints](coordinator-recovery.md#removing-an-unstarted-member)) |
| `GET /projects/{p}/tasks/{t}/evidence-cleanup`, `GET /projects/{p}/groups/{g}/evidence-cleanup` | Read-only scope of the completion cleanup of Git evidence refs: whether the card or group is finished, its `done/` cards, and its integration executions |
| `POST /projects/{p}/issues/results/view`, `/save` | Completed work-set evidence and versioned result publication/decision history |
| `GET /projects/{p}/events?cursor=&wait=` | Long-polled change log |

Errors are JSON `{code, message, board_code}` with stable codes: `invalid_request`, `not_found`, `revision_conflict`, `held_by_other`, `taken_over`, `lease_invalid`, `lease_active`, `claim_required`, `evidence_incomplete`, `protocol_incompatible`, `idempotency_mismatch`, `project_mismatch`, `project_not_empty`, `board_rejected`, `not_ready`, `internal`. `board_code` carries the board package message key of a domain rejection so the client renders the same localized text as v1.

### Idempotency

Every write carries an `Idempotency-Key`. The server writes a pending receipt before the operation. Card creation, updates, moves, launcher facts, claims and takeovers stage the completed receipt in the same board redo transaction as the card and claim. A successful board recovery therefore also recovers the exact answer. Creation freezes the initial task ID, text, revision, operation ID, observation time and HTTP 201 answer; a later title edit, move or date change cannot change that answer or create another card. Review producers, runtime finalization and collaboration requests also stage their exact result receipts in the domain transaction. Dispatch and coordinator producers also stage their exact receipts in the same domain transaction. The same key with the same request returns the stored answer; the same key with a different request is refused with `idempotency_mismatch`. A pending receipt makes the retry inspect durable operation evidence before running again. Internal failures and pending board recovery stay pending; the latter returns `not_ready` without replacing the original receipt. The client retries transport failures and `not_ready` with the same key.

Pending receipts now carry schema 1. An older prototype's unversioned pending creation has no stable binding to a card or its original response, so it is preserved and refused with `evidence_incomplete` for operator inspection. The service never infers that binding from a mutable title or state. Previously completed receipts remain readable with their exact original bodies.

### Documents

`PUT .../documents/{path}` carries the full text, its SHA-256, the expected card revision, and an optional contract decision. The server checks the digest of the received bytes before publishing, so an interrupted upload never becomes a visible partial document. Publication goes through `board.UpdateDocument`, which keeps every v1 rule: frozen contract fields, managed fields, managed paths, line endings.

## Claims and leases

A claim is the server-side ownership of one task by one execution, kept in `board/.kander/groups/00000000-service-group/claims/<task>.json` outside the card:

- `client_id` (the persistent host identity), `execution_id` (one execution on that host), `owner` (the agent), `generation` (monotonic per task, distinct from the dispatch execution epoch), the lease expiry, and a token.
- The token is an HMAC of the project, task, execution, and generation under the server secret. The server stores only its hash; a replayed claim receipt derives it again, so the token is never written to disk or to a log.
- `POST .../claim` moves a `todo` card into `working` with the owner and grants generation `n+1` in one step under the project lock. A plain move into `working` is refused with `claim_required`; `review -> working` stays a move of the live holder.
- `POST .../renew` with the claim headers (`Kander-Claim-Token`, `Kander-Claim-Generation`) extends the lease by the TTL. A renewal writes no card, so it never changes the card revision. Default TTL 90 s and renewal interval 15 s; the server announces both in the grant and decides time with its own clock.
- Safety rests on the generation and token fence, not on the clock. Holder authority is an active record with the token and the generation header of its current generation; the lease clock only decides whether another execution may take the task over. A lease past its expiry that nobody took over reads as `lapsed`: its holder keeps writing, moving and renewing at the same generation, and a renewal makes it `active` again. `lapsed` is a view value and is never stored.
- The task is never reassigned automatically. Once the lease lapsed, or the record is no longer active, `POST .../takeover` with a decision reference and the generation the caller observed hands the task to a new execution with generation `n+1`, appends a handoff record, and supersedes the open requests of older generations. In the same project lock the card's execution ledger hands off (`board.BeginTakeover`): `OWNER`, `SESSION`, and `WINDOW` name the new execution, the old record is retired as handed off, and the new executor reports and confirms its start through `POST .../execution` like a start. A live lease refuses a foreign takeover with `lease_active`. Its current client can perform an explicit owned handoff with the old private proof, exact card revision and a service-clock ticket around a fresh stopped observation. A claimed card without any claim record (a migrated board) can be taken over from generation 0.
- Every write of a `working` or `review` card (document, move, request answer) checks inside the project lock that the presented token and generation are the current claim. A token other than the current one with an older generation header is `taken_over`, whatever the record's status is now: a newer generation replaced that execution for good. The server keeps only the current token hash, so this answer does not authenticate the old token and grants nothing. Another token is `held_by_other`, and a header of another generation with the current token, or a record that is not active, is `lease_invalid`. Card updates and moves additionally run the ownership check under the board transaction locks. Their receipts and any claim release are staged in that same redo record. Server read routes share the project lock, so a snapshot cannot mix a newly committed card with an older claim. A presented execution credential is also checked when its card is no longer claimed; a released execution cannot publish a late result to a todo card. A user-authorized `archived`/`trash` termination may end a task whose record is no longer active, or present the holder's own credential; another execution's token is refused while the record is active, lapsed or not, so it takes the task over first.
- A move into `done`, `archived`, or `trash` stages the claim release in the card transaction. Startup recovers the whole redo record before serving reads. It also reconciles pending records left by the earlier prototype.
- After that reconciliation, project startup gives every active lease (task claims, group leases and integration target leases) an expiry of at least one TTL from the start, through each kernel's `startup` event, so the server's downtime never opens a takeover. A lease that had already lapsed before the server stopped is extended as well, because a crashed server records no stop time; a takeover then waits one more TTL. A failed write stops the project from opening, and opening it again repeats the same writes.
- Checks of another task's claim (a joint publication member, a member of a coordinator review write, a review writer or review input, a collaboration request target, an integration contributor or actor) call the `standing` event of the claim or group kernel, which accepts exactly the generation that may still write as the holder, and never compare `ExpiresAt` in the shell.

The acceptance or refusal of a claim, a renewal, a holder write, a takeover, a lease release, a launch rollback, a termination, and a startup reconciliation is decided by the generated `serverclaim` kernel ([Formal verification](formal-verification.md#card-lifecycle-execution-ownership-and-server-claims-m1-m2)). The server maps the claim headers to kernel arguments and keeps the token derivation, its hash, and the constant-time comparison. A request that presents the token of an older execution is refused whenever the record is active, valid or lapsed. The termination exemption above applies when the record is not active, and also to a termination that presents the current token with a generation header of another generation, which `requireHolder` answers `lease_invalid`. The claim view's status comes from the kernel's `shown` query.

A claim and its receipt are staged with the todo-to-working move and execution ledger. A takeover similarly stages the next claim generation, handoff and receipt with the new execution record. The transaction extension declares the service control lock before taking task locks. Startup retains recovery of legacy pending claims: a committed working card with that owner activates the claim; an uncommitted move releases it. Old executions therefore cannot overwrite a newer one: their token hash and generation no longer match, whatever order their late renewals, writes, rollbacks, or queued submissions arrive in.

## Starting an agent

`kander start` in server mode claims the `todo` card with a start input (initial session, window, resolved pins); the server runs `board.BeginTaskStart`, so the move, the start metadata, and the pending execution record land in one board transaction, and it keeps the launcher's board cursor in memory for the holder (a restart rebinds a cursor from the current execution record). The client then launches the agent on its own host with a fresh `KANDER_EXECUTION_ID` (in the environment of a spawned process, as an `env NAME=value` prefix of a POSIX container command, or a PowerShell assignment), reports `WINDOW` and the discovered session through `POST .../execution`, and confirms the start. A launch failure posts `rollback`: the server restores the card text from before the claim, returns it to `todo`, and releases the claim in the same transaction. Confirmation clears rollback authority in that transaction as well. The spawned process PID, kernel start token and boot identity are stored in the credential. Container launches retain their local window and resolved session there as well. Concurrent renewals merge these facts rather than erasing them.

The claim also persists the launch record ID, the launcher's last content revision and a monotonic executor-evidence flag. `GET .../execution` requires the current holder and returns the execution record and launch standing. After a server restart it reconstructs only the exact saved launcher cursor. Executor progress remains evidence even after subsequent launcher window/session writes; a rollback rechecks that evidence under the mutation transaction. A missing prototype cursor is treated conservatively as evidence.

Remote launches reserve uncertain delivery by the existing durable launch path. A failed command after it may have started the agent preserves the pane, task file, credential and executor updates, and records `unresolved` when the service is available. Failed or interrupted service reads preserve the executor. A superseded launch touches no successor. A repeated `start` cannot relaunch the already claimed task. Task launch intents now freeze the execution identity, claim body, idempotency key and private predecessor proof before calling the service. Recovery reuses the original request and checks the current execution instead of starting another agent. If the journal proves no physical launch boundary was crossed, recovery rolls back an initial claim or audit-releases a failed takeover generation. Otherwise it restores the private credential and retains the unresolved execution for inspection. A completed start is never physically replayed.

`resume --adopt --decision <reference>` uses the current host's private task credential and exact local process incarnation or terminal session. It does not read a local card path or probe a foreign pane. Adoption binds an explicit decision and the unchanged card revision to a short-lived HMAC observation ticket issued by the server before the local probe. The ticket uses the service clock and generation, so a client's wall-clock offset neither grants freshness nor prevents valid observation. Unknown local identity refuses adoption. `resume --agent <agent> --decision <reference>` starts a fresh generation from the latest verified shared delivery. A same-client owned restart additionally proves the old executor has stopped. `resume` without an agent queues collaboration while the agent is alive or unknown; a locally confirmed stopped executor resumes its native session through a new generation. A group review card still needs a durable dispatch except during unfinished-start recovery.

For Git-backed projects, start publishes an explicitly labelled `baseline` commit to its generation evidence reference, prepares a fresh private worktree/branch `kander-task/<project>/<task>/g<generation>` (the task branch), and records that branch through the controlled execution producer before launching the agent. Earlier releases named the branch `kander/<project>/<task>/g<generation>`. That name cannot coexist with the evidence refs of its own generation, which live below `refs/heads/kander/<project>/<task>/g<generation>/`: Git cannot hold a branch and a directory of the same name, so the old name could never be pushed to the common remote. The task branch lies outside `refs/heads/kander/`, which holds evidence refs only. The server accepts both names for a generation, a retried start keeps the name its worktree intent recorded, and cards that already record the old name are not migrated. A baseline carries no completion authority. A working-to-review move needs a separate `delivery` attestation of the implementation's current content revision. The CLI and TUI publish the managed worktree's HEAD even when the invoking view runs in the main checkout.

Worktree intent files live in the client's project-private `worktree-intents/`; the worktrees live in `worktrees/<task>/g<generation>`. On Windows the Git commands that go through the client's `gitCommand` (delivery, worktree and integration steps) run with `-c core.longpaths=true`, so a checked-out file path longer than `MAX_PATH` works; the direct `git apply` of a continuation restore does not get the option. Git for Windows still refuses `git worktree add` when the worktree path plus `/.git` is longer than 220 bytes (`'$GIT_DIR' too big`), which the option does not change, so keep `KANDER_CLIENT_HOME` short. A failed Git command reports Git's own message (sanitized, at most 300 characters) on the machine that ran it, never in a request to the server. A Git command that could not start, was cut off by its deadline or a cancellation, or whose process cleanup failed reports that cause the same way. Creation records intent first, then reconciles Git's actual worktree registration, common directory, branch and base ancestry. A same-generation retry reuses the exact workspace and preserves dirty content. Partial or conflicting Git state stops with the intent path and retains every artifact. A later generation has a different branch and directory. An independent-clone takeover test verifies the successor starts from the fetched commit while the predecessor's uncommitted changes remain intact. Both fresh takeover and native continuation use this provisioning. Before native continuation, the client freezes the index patch, working-tree patch and non-ignored untracked regular files into a private snapshot. It verifies the stopped source again before handoff and restores into the new generation only. Ignored files remain in the predecessor workspace. Concurrent edits, oversized snapshots, untracked links or a partial restore stop with both worktrees retained. Restore records intent first and only recognizes an exact completed snapshot on retry; it never reapplies patches over changed content.

The private credential registry retains a monotonic generation head even after release. Delayed initial saves cannot replace a newer interactive credential or revive an older pointer after the successor exits. Bound processes still read only their own execution record; they never borrow the current head's token. Concurrent worker writes merge the immutable worktree, branch and base facts with process/session observations.

## Review gate

The client runs every Git check of `kander review plan`, `aggregate`, `close`, and `progress` against its own repository, exactly as v1 does, and sends the board request together with the Git facts. The server revalidates structure and bindings with the board package and publishes atomically; it never runs Git. A batch with no delivery commit closes at any HEAD of the client's repository that still holds its target; the client sends the HEAD it observed (`git.observed_head`) with the marker `git.no_delivery`, and the server checks only that the marker belongs to such a batch and that the HEAD is a full SHA (see [Review disposition](review-disposition.md#batches-with-no-delivery-commit)). A single-card mutation supplies that card's claim proof. A group coordinator process, which holds the group coordinator credential, writes the review evidence of review-state members itself (the coordinator write authority) when every condition below holds for the whole operation, and otherwise uses the joint publication. The server checks the conditions for every live member of the operation (a card in `working` or `review` with a standing claim): (1) the writer holds the group's lease, the same decision as `kander coordinator reconcile` (`requireGroup`); a lease that lapsed on the clock but was not taken over still holds, because a holder's authority does not read the lease clock; (2) every live member is in `review/` and belongs to that group (`TASK_GROUP` equals the lease's group); (3) no live member has a dispatch in progress, meaning its `DISPATCH_ID` names a dispatch that is `prepared`, `delivery-unknown` or `accepted` (a bound dispatch that is `completed` and not yet settled is not in progress: the holder handed its work back, and fix rounds leave such a binding on the card in `review/`); (4) the request declares the revision and execution generation of every live member in the `Kander-Coordinator-Basis` header, and the write transaction checks both again (the card revision compare-and-swap and the claim kernel's standing event). The write is all or nothing: one card that fails a condition sends the whole operation back to the joint publication, and there is no mixed mode. `review disposition` stays with the holder, and the server refuses it under this authority. A holder's own proof comes first: a process that holds the current credential of a live member does not use the coordinator write authority. Under it one command publishes: no joint publication and no collaboration request exist, the task events it raises carry generation 0 as those of the joint publication do (a group lease generation is not a card's), and the server logs one record per write with the operation, group, group generation and members, never a token. The authority does not cover dispatches: a foreign `dispatch prepare` stays a proposal, and only the live holder prepares or settles formal dispatch evidence. When the server refuses the write (a changed revision, card or dispatch, a taken-over lease or member, or a server older than the client, which ignores the header and refuses the group token as it refuses any write without the card's own proof, with an error of the claim path such as `held_by_other`, `taken_over` or `lease_invalid`) the client neither retries nor falls back to the joint publication: the error says to rerun the command, which reads the cards again and selects the flow anew, and to upgrade the server first in the old-server case. The choice of the client only selects the flow; the server decides the authority from the group lease and the card state, so a process that merely claims to coordinate gains none. The trust boundary moves with it: the holder of a member no longer has a veto over the review evidence the group's coordinator writes under these conditions, but it still controls the card's revision (a card it changed makes the write fail), `review disposition` and the card state. When a condition fails, a process that coordinates the card's task group (it holds the group coordinator credential but none for the card's current execution generation, even when it still holds the credential of a replaced one) prepares a one-member publication instead, asks the holder to confirm it, and ends with `evidence_incomplete` naming the publication ID; once the holder confirmed with `kander review confirm`, rerunning the same command succeeds. A reviewer run that waits this way names its run ID, and the rerun passes the same `--run-id`: without it the command generates a new run ID, prepares new material and waits for a new confirmation. Any other process without a credential for a claimed card, and a coordinator submitting `review disposition` without any credential for the card, is refused with `held_by_other` after reading the cards and before any write request is sent, naming the holder's execution ID, owner and generation. A process other than a group coordinator that holds only the credential of a replaced generation sends it as it is, and the server answers `taken_over`; a coordinator in that state asks the current holder like one without a credential, except for `review disposition`, which it sends with the replaced credential and the server refuses with `taken_over`. A saved result of a one-member publication is routed the same way for the calling execution before it is reused. When the coordinator write authority does not apply, an operation with several live members first prepares immutable material (an operation with one live member keeps the holder's direct proof or the one-member publication described above) and an exact revision/generation member set at `/projects/{p}/publications`. Each holder confirms its member through `POST .../publications/{id}/confirm`; partial confirmations survive restart. The coordinator then supplies `Kander-Publication` to publish the confirmed operation. The transaction checks every current lease and version, rejects changed membership and writes outside the confirmed set, and commits all member copies, the publication receipt and the operation result together. A completed publication returns its saved result on retry. The client finds a completed publication through a private replay record keyed by the operation and its material. `review aggregate` sends only the batch ID, so its record is also keyed by the hash of the view the client reads first: an unchanged view replays the saved result, while a view changed by an advance, a disposition or another run is published again under the current member versions and needs fresh holder confirmations, unless the coordinator write authority applies. A reused publication whose saved view differs from the view just read is refused as stale and prints nothing.

The client auto-confirms locally owned members and creates generation-bound collaboration requests for other holders. An `extend-plan` that carries `add_members` adds its new members to the set: the client normalizes the list and joins it to the plan's members with `board.ReviewPlanExtensionTasks`, the server takes the same set for authority, locks, and the confirmed member list, so every started new member is covered by the same operation: the holder of each confirms the same publication, or the coordinator writes it under its authority when the conditions hold. An older server rejects the unknown field, so upgrade the server first. A holder reads the prepared material first with `kander review publication <absolute-CWD> <publication-id>`, then confirms with `kander review confirm <absolute-CWD> <publication-id> <task-id>`. `review publication` is read-only: it sends no credential, only GET requests, creates no client identity file and registers no project (a project the service does not know is `not_found`); it reads `GET .../publications/{publication}`, which the server answers for any client of the project, and it reads the card of each member to tell whether the publication is stale. It prints the operation, the status, the digest, the members and the stored material. A member is `confirmed` when the publication holds a confirmation whose digest, revision and generation match the publication and the member, and `stale` when its card has another revision or execution generation now or no live claim. The orchestrator wrote the material, so the command cleans every string and key of it (control characters, complete CSI and OSC escape sequences, also in their 8-bit form, and bidirectional marks become `<U+XXXX>` markers, `sanitized` is `true`), cuts a string above 4096 characters to its start with its length and digest, and prints the files of a `review-prepare` material as name, length and digest only. The material of a prepared publication cannot change (the same ID with other material is `idempotency_mismatch`), and a confirmation is valid only for the digest of that material, so the material the holder read is the material it confirms. A confirmation binds the task revision, the execution generation and the digest. `review confirm` also prints the `operation` and `pending`, the members that still lack a confirmation. The client creates one review request per holder and publication: before it creates one it reads the requests of the card and treats a review request of the member's generation that names the publication, and is not superseded, as the question already asked, so a retry after an upgrade or in another interface language does not meet `idempotency_mismatch` and does not ask twice. The key of a new request names the text of the request too. The `Kander-Claims` header supports a separate proof per task; one task's token is never authority for another. Author dispositions require only their assigned card's holder, even when the run has several members.

`extend-plan`, `advance`, `assign`, `disposition`, `interpret`, `map-legacy`, and `abandon` have controlled service producers. New server plans use `project:<id>` as their evidence identity rather than a client's absolute CWD. Clients still verify Git in their own repositories. Historical unplanned-batch resolution has a read-only facts producer that freezes plan/batch revisions, original report hashes, membership, evidence identity and ancestry edges. The client obtains required commits from the common remote and verifies every edge locally. Resolution rechecks those exact originals inside its transaction, applies the authority of any review write (the holder, the joint publication, or the coordinator write authority), and commits the audited plan resolution and exact receipt together. Migrated evidence keeps its historical CWD bytes; the client repository used for Git verification is separate. Reviewer invocations use the service for their frozen inputs, runtime phases, prompt artifacts, final originals and publication. `POST .../reviews/runtime/prepare` freezes a private uploader hash and the member generations. A prepared identity never authorizes another reviewer launch, including a retry of a successful joint preparation. The version of the client binary that sent the prepare is not part of the run identity: a same-ID retry compares every other input (`input`, `requirements`, `advance`, `originals`) and is a recovery, so a client upgraded between the first prepare and the retry still finishes the run. The run keeps the `kander_version` of its first prepare, and the server recomputes the stored prepare digest with that recorded version, which also covers writer records of earlier binaries. The client keys its replay record of a prepare joint publication without the version, so a retry finds the completed publication instead of asking the member holders to confirm a new one, and it also finds a record an earlier client keyed by version through the recorded version. Frozen material and publication IDs keep the version, so a new run never reuses another run's. The digest covers the whole JSON of `api.ReviewPrepare` and `board.ReviewInput`: a field added to either that appears in the JSON makes the same-ID retry of every existing run fail with `idempotency_mismatch`, so such a field needs its own compatibility rule. Phase and artifact uploads require that private writer and the still-live generations; a takeover fences them independently of card content changes. Audited member exclusions remove only that member from writer validation; remaining generations must still be live, and publication still obtains the authority of the live members (their holders' confirmation, or the coordinator write authority); neither replaces the private writer secret. Runtime uploads revalidate the writer before committing their receipts.

`POST .../reviews/actions/abandon` retires a finalized run that no process can publish (`kander review abandon`, [Review evidence](review-evidence.md#abandoning-a-run-that-cannot-be-published)). It is not under `reviews/runtime/{run}/` and needs no writer credential, because it exists for the run whose writer secret was lost, whose client differs, or whose member was taken over. It is an ordinary review write (`review-abandon`, the members of the run): the holder of the only live member proves it directly, a group coordinator process writes it itself when the conditions of the coordinator write authority hold, and otherwise goes through the joint publication, where every holder of a live member confirms, any other process is refused with `held_by_other`, and a run with no live member is refused for every caller. The kernel refuses it when a member holds a copy, the batch is closed, or another run names the run as its predecessor, and then refuses every later publish of the run. The `prepare` of the same run ID is refused too. An older server answers the action with `unsupported review action`: upgrade the server first, and then every client that handles a batch with an abandoned run: an older client ignores the new run and view fields, so the aggregate view it prints lacks `abandoned_runs`, and a close request built from that output carries a view hash the server refuses.

`POST .../reviews/runtime/{run}/finalize` validates every uploaded file digest and allowed filename, then commits all output bytes, immutable originals and its receipt together. A client saves the exact pending finalization in its private runtime directory before transport. After an outage, a retry uploads that saved result without rerunning the reviewer. An interrupted invocation without a completed saved result records interrupted facts. Formal run publication uses the authority of the other review writes (fresh holder confirmations, or the coordinator write authority) and `PublishReviewRunAtomic`, committing all member copies and indexes together. Runtime output and writer secrets never create a local board. The client prints each answer through its board type, so the aggregate bytes a close request hashes are the same as in v1.

## Git delivery and dispatch

For a project registered with an origin, the normal CLI and TUI working-to-review move first publishes the chosen full SHA (HEAD when omitted). The client verifies the registered origin and its push URL, pushes only `refs/heads/kander/<project>/<task>/g<generation>/<commit>`, and rereads that exact remote ref. The client deletes these evidence refs in the completion cleanup once the card or its group is finished ([Distributed Git integration](distributed-integration.md)). A retry inspects the ref before pushing and reconciles even a nonzero push result against the remote facts. This never advances the integration branch or force-rewrites another execution's reference. Shared remote identities refuse embedded passwords, HTTP userinfo, query tokens, ambiguous origins and executable Git helpers.

`POST .../deliveries` authenticates the holder and checks the execution, generation and inspected card revision under the same transaction as the publication receipt. The service records an authenticated client's transport observation; it does not independently query Git. The state-changing transaction checks those bindings again. A content edit or takeover invalidates an earlier attestation. Another clone fetches the recorded reference and confirms it still names the expected SHA before accepting the local object. Missing remote refs block it even when that SHA is cached locally. Review invocations fetch their exact base and target through the registered remote before launching a reviewer.

Dispatch lease generations and business epochs fence separate authorities. Preparation, attempt reservation, explicit terminal decisions, completed settlement and wrap-up grants reuse the board's existing evidence producers through REST. Their card changes and exact result receipts commit together. A dispatch is never accepted merely because a transport succeeded. New wrap-up evidence stores `project:<id>` while local verification uses the caller's checkout; historical CWD bytes remain unchanged. The service's own move never runs the client's Git verifier, also in the complete binary that links both sides; see [Distributed Git integration](distributed-integration.md). Explicit target-integration authority is described in [Distributed Git integration](distributed-integration.md).

A foreign `dispatch prepare` becomes a generation- and card-version-bound collaboration proposal with the original typed input. It returns a request object with `status=open`, not a prepared dispatch. The holder inspects it using `kander request show <task-id> <request-id> --json`. Only the live holder can prepare or settle formal dispatch evidence. Requests remain proposals until the holder takes a controlled action.

An explicit takeover of a bound task names the inspected dispatch ID, epoch and revision. It retains an unfinished binding without authorizing business replay, or settles a completed binding in the same transaction as the new lease and execution handoff. This avoids requiring an expired execution to settle before its successor can take over. An old execution identity cannot reacquire its own lost lease. Fresh stopped evidence is still required for accepted-round reauthorization; lease expiry alone proves no agent exit.

## Coordinator authority

A group's public checkpoint `authority.token` is a session label, not a bearer credential. The service keeps a separate private group lease in `group-claims/`. Concurrent claims have one winner; a live lease cannot be preempted. An explicit claim after expiry or a reported coordinator exit requires the observed generation and a decision, advances both lease ownership and checkpoint authority atomically, and records the handoff. The same coordinator execution, from its own client and with its credential, reuses its active lease, also after it lapsed; once the lease was taken over, lost or released, reusing the old execution ID cannot revive it. The service words its refusal of an identity it already knows by the state of its record (sent by another client, released, lost) and keeps the code `lease_invalid`. Checkpoint epochs and lease generations remain separate fields, including after migration.

`kander coordinator claim` stores the returned private credential and starts the same background worker used by tasks. Group renewals change no card or checkpoint version. Every checkpoint mutation checks that private lease inside its producer transaction. A recovery of a live member additionally requires that member's private credential and a fresh service-clock ticket around a confirmed local stop. Explicit recovery after lease loss uses the observed task revision and generation, the current private coordinator lease and the user decision. It atomically resets the business cycle, supersedes old requests and records a released audit generation; it neither starts an agent nor grants runnable ownership. The old scene remains recorded and its unprobed presence stays unknown. A pending task start or active dispatch must settle before recovery. `remove-member` is a plain group write: it needs the current private coordinator lease (standing, not released, lost, or taken over), refuses a member the service holds a claim record for, and publishes a task change event for the card beside the group event. Its request and routes are additive, so the protocol version stays and an older service answers 404 to the new route. Target-branch integration has a separate private lease.

`kander coordinator release` is final for the execution that runs it, so it needs `--end-execution`; without the flag the client sends nothing, exits 2 and states the consequences and the confirmed syntax. The execution cannot claim the group again and cannot dismiss its members afterwards, because the worker removes its group credential once it confirmed the release. A process bound to a coordinator execution (`KANDER_COORDINATOR_EXECUTION_ID`, or `KANDER_EXECUTION_ID`) is refused by the client with `lease_invalid` after it read the group view and before it sends a claim request, when its lease was released (the service record says so, or the private `<execution>.released` tombstone exists), lost (the record or the local credential says so; the text carries the reason when there is one), or taken over (the record names another execution at a higher generation than the local credential; the text states that generation took the group over, not that it still runs it, because it may have ended since). Each case has its own text and says that a new orchestrator session takes the group over with the observed checkpoint revision, epoch and a decision. The service refuses a released or lost execution itself. For a taken-over execution, or one with a tombstone after a successor took the group, the service could grant a new generation to a request that observes the current generation and carries a decision, but the client could not keep it: the credential store refuses an execution with a tombstone and a changed generation, so the grant would leave a lease nobody renews. The client refuses that request first. The checkpoint kernel still refuses nothing new. A process that is not bound takes a fresh execution ID whenever it cannot reuse its lease, and the refusals do not apply to it. While the execution holds its lease it needs no claim: the same request replays the stored checkpoint unless `remove-member` reset the replay record since, and a changed one, or a repeat after such a reset, is refused by the checkpoint kernel (it reuses the token of that generation) with `board_rejected`; the client adds the generation held and points at `kander coordinator show` and `reconcile`.

For reconcile, the client first reads the exact Git facts the producer needs, verifies them in its own clone, and sends the facts with its verdicts. The server repeats the producer pass and accepts only a verdict for the exact current facts. Missing or changed Git facts block the member instead of manufacturing delivery. The server never executes Git. Whole-request CAS failures preserve the checkpoint; per-member failures retain their blocked mirrors and the existing partial/failed CLI exit statuses.

The reconcile command has three deadlines. Opening the session and the facts request share the 30-second deadline of the other coordinator subcommands. The local verification has 5 minutes (`reconcileVerifyTimeout`), and the reconcile request has 60 seconds (`reconcileRequestTimeout`) that start when the verification ends, so a slow origin never uses up the time of the request. The single Git steps keep their own limits: 10 seconds for one observation of an integration target and 60 seconds for any other Git process. A wrap-up fact gets one full verification: the integration execution, every member delivery, the kept commits, and the target. After the review closures are checked, the client observes the target ref on origin once more; only a head that moved is fetched and tested, so a rewound target still fails the fact. Within one command a fetch from origin with the same ref name or SHA runs once (`remote.WithFetchOnce`); an `ls-remote` always asks origin, and nothing from an earlier command counts as evidence. Equal facts are verified once.

A deadline or a cancellation during the verification is not a verdict: the client sends no reconcile request and fails with `reconcile_verify_interrupted`, naming the local Git verification, the member or wrap-up fact, the cause, and the verification deadline. Other verification failures, including a transient network error that is not a deadline, remain verdicts and block the member until a later reconcile clears them. A reconcile request whose deadline ends without an answer fails with `reconcile_result_unknown`: the request may have reached the server. Running the same request file again is safe, because the coordinator state machine accepts a request whose hash equals `last_request_hash` as a replay and refuses any other stale request with `checkpoint CAS`. A command whose context ended before the request fails with `reconcile_not_sent` and sends nothing. Only a transport failure while the request deadline still runs is `unreachable`. A longer verification makes it more likely that the facts or the checkpoint change meanwhile; the request is then refused with `evidence_incomplete` or `checkpoint CAS`, and the caller reads the checkpoint and reconciles again.

Distributed `orchestrate` reads cards and expands groups through a service snapshot. Its task file carries a fresh fixed execution identity in both `KANDER_COORDINATOR_EXECUTION_ID` and `KANDER_EXECUTION_ID`. Its PID incarnation or window/session is retained below the private client `sessions/` directory before later group claims. A group credential binds to that context, so the worker can observe coordinator exit independently of TUI lifetime. A separate task executor clears inherited coordinator authority and receives its own task execution ID. The orchestrator identity may also `kander dismiss` the members of the group whose group credential this host holds ([Retained local execution routing](#retained-local-execution-routing)); the list and detail views built through `SceneIsLocal` (`kander list`, the TUI and the dsh view) still hide the `WINDOW` and `SESSION` of those members from it; `kander show` prints the server's card text as before. Neither orchestration nor checkpoint claim creates a local board or mutates member cards.

## Client and worker

The client reads `server.url` and `project.name` from the scope config or the project overlay `.kander-config.json`. The client always requires this binding. Use `kander init --server http://127.0.0.1:7878 --project <name>` in each checkout after starting the server. `init` validates protocol and canonical origin before saving only those fields to the project overlay. An explicit project-path argument targets that checkout. Missing configuration or an unreachable service fails without a local board fallback.

`list`, `show`, `new`, `update`, `move`, `pick`, `start`, `dispatch`, `notify`, `resume` (including `--adopt` and `--release`), `dismiss`, issue import/triage, the TUI board and start actions, `check`, `subscribe`, and the review gate commands above use the server project. Issue result reconciliation also uses the service; the remaining provider effects keep durable intents and central CAS receipts. Board-free orchestrators also keep private launch intents. A completed logical retry returns its recorded result, and an uncertain retry reports the retained receipt without creating another terminal. `orchestrate --operation-id <stable-id>` distinguishes an intentionally new confirmed session; a new ID does not settle any prior uncertain effect. The client directory (`~/.local/share/kander/client/`, or `KANDER_CLIENT_HOME`) is private to the user and never part of Git:

- `client-id`: the persistent host identity, created on first use.
- `executions/<namespace>/<task>/<execution>.json`, where `<namespace>` is the SHA-256 hex of the server URL and project ID (project IDs derive from names, so two servers can serve one ID; `sessions/<namespace>/` and `retained-executions/<namespace>/` use the same namespace): the credential of each claim this host made (server URL, generation, token, lease timings, the managed agent PID when known), plus `latest`. Per-execution locks merge renewals and launch facts; release tombstones prevent a late writer from recreating a removed credential or erasing a successor pointer. On Windows, a lock-free read of a credential or its `latest-generation` / `latest` pointer (`remote.Credentials` and `Session.Credential`) that meets a sharing violation, because an atomic replacement still holds its temporary handle, is retried with a bounded backoff of at most 630ms in total; if the violation persists, the read reports a busy error that still wraps the system error. Reads under a credential lock never retry, and no other error is retried.
- `worker.lock`, `worker.log`, `worker.json`: the background worker: its lock, its log and its record ([Worker record and version mismatch](#worker-record-and-version-mismatch)).

A process started for one execution carries `KANDER_EXECUTION_ID` and presents only that execution's credential, so an agent of an older generation cannot pick up a newer claim made on the same host. An interactive command without the variable uses the task's latest credential. `move <task> working --owner <agent>` claims a `todo` task; with `--decision` it takes over a lost claim.

A fixed executor whose task has a release tombstone cannot submit new document or lifecycle writes without a bearer. That refusal also applies to terminal cards: credential removal never converts the old executor into an anonymous editor. Read-only task inspection and exact completed-dispatch receipt replay remain available. An unbound interactive operator can still use normal CAS on an unclaimed card, and a coordinator can collect joint confirmation for a member it never held.

After a claim, and when any command opens a session while the client home holds a renewable credential (a credential record without a release tombstone whose lease is not marked lost), the client starts `kander worker` detached unless one already holds `worker.lock`. The session-open check looks at the credentials first, probes the lock without waiting and without creating it, and runs only after the server answered; a failed start prints the `worker_start_failed` notice and the command continues. The worker runs in its client home and without `KANDER_EXECUTION_ID` and `KANDER_COORDINATOR_EXECUTION_ID`, which belong to the execution that started it. A damaged credential record stops the session-open check without starting a worker, as it fails the worker's own credential scan. One worker runs per client home, independent of the TUI and of the command that started it, and exits after two minutes without a live claim. It runs two loops:

- The renewal loop renews every credential whose renewal interval passed. Every tick it makes one batch: at most eight renewals are in flight at once (the server serializes the renewals of one project, so a higher cap would only turn server queueing into client timeouts), and the batch waits for all of them. It never waits for an observation, a report, a delivery or an agent stop, so a slow terminal of one credential cannot cost another credential its lease. When every renewal runs into its 10 s timeout, a batch of N credentials spends at most `ceil(N/8) * 10` s on the network; the local writes of the credential files, which take milliseconds, come on top. Stopping the loop cancels the renewals in flight, and a cancelled renewal is not counted as an outage.
- The work loop serves the credentials one after the other, once per tick: it observes the agent, reports the observation, delivers requests and stops lost agents. A credential is served once per renewal the server confirmed. A later renewal that reached no decision, or the release of the claim, withdraws the work still owed, so nothing is observed, reported or delivered for a lease the server did not confirm. The work loop never renews.

A round of either loop that takes longer than the renewal interval is logged as a warning with its duration, the interval and the number of credentials: `renewal round exceeded the renewal interval` for a batch of renewals, `work round exceeded the renewal interval` for a round of the work loop. The loops keep their records per credential, identified by server URL, project, resource kind, task and execution ID, not by execution ID alone: a task that coordinates its own group holds a task credential and a group credential under one execution ID, and a failed renewal of one does not delay the other. The renewal loop does the following with the answer of the server:

- A successful renewal records the local receipt time rather than comparing a client wall clock to the server timestamp. The worker observes the managed process incarnation or local terminal session separately. A confirmed exit is reported through `/observation` without changing the card revision. A healthy worker continues renewing working/review ownership after the agent exits; agent presence and task ownership are separate. `resume <task> --release --decision <reference>` explicitly releases a locally confirmed stopped executor using a fresh service-clock ticket, exact version and holder proof. Release records an audit event and makes the task lost for an explicit successor; it never reassigns automatically. Missing identity, observation failure, waiting for input, and lack of output never prove an exit. Public claim views retain the generation-bound observation.
- A refusal of a claim the server shows as released at the credential's generation (the card reached `done`, `archived`, or `trash`) removes the credential.
- `taken_over`, or a refusal while the server's view shows the generation `lost` or replaced, persists the lost state; the work loop then persists a target-specific stop intent before attempting to stop the agent. The renewal loop only marks the credential lost. The work loop checks for such marks before every work step, so the stop waits for at most the work step or the handover probe in progress, plus the stop attempts of other lost credentials ahead of it (each takes up to about 30 s), and the agent of one credential is stopped once. The server refuses every write of the old execution during that time. So do a stopped group coordinator observation, an integration `revision_conflict`, and `not_found`. Linux pins a pidfd and Windows verifies and terminates through one process handle; a reused PID never receives that signal. Other platforms refuse unpinned process termination and record the limitation. Terminal stops revalidate the locally recorded session, use observed process identity when supported or the configured agent exit command, and retain the container. Missing or uncertain identity records an unresolved stop; the service still refuses every later write of that generation. A later launch observation can trigger one stop attempt for its newly known target, but a worker restart never blindly repeats an uncertain external effect. Worktrees, branches and uncommitted changes stay untouched.
- Only the server decides that an execution ended. A renewal that reaches no such decision is retried every renewal interval and logged with the start of the outage, however long the outage lasts: a transport failure or an unready server, a client that cannot be built, a refusal whose claim view cannot be read, and a refusal while the view still shows this generation `active` or `lapsed`. None of them marks the credential lost or stops the agent. When the server is back, the lapsed lease is renewed at its generation unless a takeover happened, which the next renewal answers `taken_over`.

### Handover to a replaced binary

A worker does not keep running old code after an upgrade. At start, with `worker.lock` held, it records the path `os.Executable()` returned and the identity of the file there, read through an open handle (`os.SameFile` on a path-only `FileInfo` can compare two reads of the new file on Windows). It writes its [worker record](#worker-record-and-version-mismatch) and logs `worker started` with `version`, `pid`, and `executable`. After every work round it reads the identity again. An unreadable path (missing during the replacement, no permission) changes nothing; the worker tries again at the next tick.

When the identity differs, the worker probes the new file with `<executable> version` through the bounded process runner of `internal/probe` (10 s, process tree reaped). The probe passes when the exit code is 0 and stdout starts with `kander `. The renewal loop keeps renewing while the probe runs. A failed probe logs a warning and the worker keeps serving. The same file identity is not probed again for one minute; another replacement is probed at once.

After a passing probe the order is fixed:

1. The worker stops the agents of leases the renewal loop marked lost while the probe ran, and goes on until no mark is left. The renewals run meanwhile, so a slow stop delays no renewal. Such a stop saves its stop intent and result in the credential, as it does at any other time. Then the worker stops its renewal loop and releases `worker.lock`: only the worker that holds the lock acts on credentials. A lease that was marked lost in the last moment before the loop stopped sends the worker back to the stops with the renewals running. When a mark is still left after three rounds, for example because the credentials cannot be read, the worker keeps the lock and the renewals and tries the handover again at a later tick.
2. It starts `<recorded executable> worker` detached for the same client home, as `EnsureWorker` does (`remote.StartWorker`).
3. It waits up to 10 s, polling every 250 ms, until another process holds `worker.lock`. A started process that has already exited fails the wait, for example a same-path build that has no `worker` command.
4. On success it logs `worker handed over` (old version, path, new PID) and exits with 0. The new worker continues from the credentials on disk: generation, delivered request IDs, lost state, stop intents, and unresolved stops stay as they were; apart from the stop attempts of step 1, the handover writes none of them. The new worker does not repeat an uncertain external effect.

When the start or the wait fails, the worker logs an error, takes `worker.lock` back, and continues with its own code; if another worker already holds the lock it exits, because that worker serves the home. The failed identity is left alone for one minute. The renewal loop restarts after the lock is taken back. Lease renewal pauses between the stop of the renewal loop and the confirmation (or the restart). The confirmation waits at most 10 s; its timer starts when the call that starts the new process has returned, and taking the lock back takes a moment more. A lease that an earlier outage of the server has brought close to its TTL can lapse in that time, as it can at any other time, and the worker renews it when it is back.

Limits:

- A worker started before this behavior existed cannot hand over. Restart it once by hand (`kill` the `kander worker` process; the next command that needs it starts one from the current binary).
- The check follows the file at the recorded path. If the installation is a symlink to a versioned directory (for example a Homebrew `Cellar/kander/<version>/bin/kander`), Linux reports the resolved real path, an upgrade changes only the symlink, and the worker does not hand over. An installation that replaces the file at its path (`mv` over `~/.local/bin/kander`, `kander update`) does.

### Worker record and version mismatch

A worker runs the binary it started from until it hands over, so a worker can run another version than the `kander` command a user types. The worker therefore writes `worker.json` into the client directory, and the commands that need a worker and `kander doctor` compare it with their own binary.

`worker.json` is written atomically and privately through `internal/fs`, after the worker took `worker.lock` and before its first renewal. Every worker writes it at start, a worker that took over from an older binary too, and it replaces the record of the worker before it. A worker leaves it in place when it exits idle; it deletes it only when it cannot write its own record, so that the record of the worker before it does not pass for its own. The record only serves diagnostics: no authorization, lease or delivery decision reads it. A failed write logs one `worker record could not be written` ERROR to `worker.log` (and a second ERROR when the older record cannot be removed), and the worker renews as usual. Schema 1 has these fields:

| Field | Meaning |
| --- | --- |
| `schema` | `1`. |
| `version` | The version string of the binary the worker runs (`kander version`). |
| `pid` | The process ID of the worker. |
| `executable` | The path of the file the worker started from; empty when it could not be read. |
| `handover` | `true` when the worker recorded the identity of its executable and so hands over to a replaced file; `false` otherwise. |
| `started_at` | The start of the worker, UTC, RFC 3339. |

The file is a contract between processes that can be different versions. A reader accepts unknown fields; a later change adds fields without changing the meaning of these, and an incompatible change raises `schema`. A reader that finds another schema, JSON that is not valid, or a file it cannot read treats the version of the worker as unknown and never fails because of it. A missing file means a worker that is older than the record, or one whose write failed. A reader trusts the record only while a worker holds `worker.lock`; `worker.lock` does not tell which process holds it, so the `pid` is not verified. In the short time between a new worker taking the lock and writing its record, a reader can read the record of the worker before it.

**Commands that need a worker.** `kander start` (and the takeover start of `kander resume`), a claim in server mode (`kander move <task> working --owner <agent>`) and `kander coordinator claim` make sure a worker runs (`remote.EnsureWorkerChecked`). When no worker holds `worker.lock`, they start one from their own binary and say nothing about versions. When one runs, they read its record:

- The version is the same: nothing is printed. Two builds without an injected version both report `dev` and count as the same version.
- The version differs: a warning names both versions, the pid and path of the worker and the path of this binary. When both paths are the same and `handover` is `true`, the warning says the worker hands over on its next round and that the user stops the pid when the warning still appears after a minute (a failed or backed-off handover is retried at most once a minute). Otherwise, with another path or `handover` false, the worker does not hand over: the warning asks the user to stop the pid, and says the next `kander start`, claim or `kander coordinator claim` starts a worker from this binary. On Windows the paths are compared without regard to case.
- No record exists: one line says the worker has no version record, that it may be an older worker that cannot hand over, and what to stop. A record of another schema or an unreadable record prints nothing; `kander doctor` reports it.

Every message that asks for a stop also says what the stop costs: until the next `kander start`, claim or `kander coordinator claim` starts a worker no lease of this host is renewed, and a lease that lapses meanwhile can still be recovered, because only an explicit takeover hands a lapsed lease to a new execution. The commands never stop or restart a worker themselves. `kander start` prints the message among its warnings. A claim and `kander coordinator claim` print it on stderr; with `--json` they put it in the `notices` of the result object instead (code `worker_version_warning`, or `worker_start_failed` when the worker did not start), and stderr stays empty, see [JSON output](json-output.md). The other callers (integration claims, launch receipt recovery and the later worker checks of one command) stay silent.

**`kander doctor`** reads the same record without creating or changing anything: it creates no client directory, no lock file and no record, and it stops no process. With no client directory it prints no worker line. With no lock holder it prints one `not running` line and stays healthy. With a holder and the same version it prints one line with the version and the pid. With a holder and another version it prints the warning above and the doctor result fails. With a holder and no usable record (missing, another schema, unreadable) it prints a `version not recorded` warning with what to stop, and the result fails.

**Session identity text.** The liveness text `session identity was not reported` no longer tells the user to reopen the container. It says that the terminal shows no session marker this `kander` reads (for herdr-core the label `kander.session`), that direct delivery is unavailable, and that `kander doctor` compares the version of the background worker. A worker generates this text and stores it in the execution observation on the server, in the language of the worker's configuration; `kander list --json` and `kander show --json` carry the stored reason in `claim.observation.reason`, and `kander check` and the TUI show it. The new text therefore appears after the worker runs the new version, and the text stored earlier is replaced at the next observation the worker reports.

## Collaboration requests

A non-holder asks the holder to act through `POST .../requests` with a kind (`fix`, `sync`, `wrap-up`, `review`, `stop`, `note`), a message, and the generation it targets; a request for a generation that is not current is refused. Only the live holder of that generation answers it (`accepted`, `done`, `rejected`). A takeover marks the open requests of older generations `superseded` instead of handing them to the new execution. `kander request <task> fix|sync|review|stop|note <message>` asks, `kander request list <task>` lists, and `kander request answer <task> <id> accepted|done|rejected [note]` answers with this host's execution credential. After each confirmed renewal the work loop of the worker reads the requests for its generation that are open or that it reserved but never typed (see below). For each deliverable request it resolves the target first: a read-only probe (`notify.ResolveTarget`) that finds the pane the card's `WINDOW` and `SESSION` name and checks that the agent, its session identity and its state allow a line. The resolution types nothing. Only a resolved target gets a reservation, an accepted answer whose request ID the worker persists locally, and only then does the worker type one sanitized line into that pane. A failed resolution is a failure before sending: no answer is written, the ID is not persisted, the request keeps the state it had (`open`, or `accepted` with the reservation note when its reservation answer was lost or its local list entry could not be saved, see below), and the delivery of that execution is blocked (see below). A request reserved earlier counts as waiting in the blocked state like an open one. A failed or interrupted typing remains explicitly uncertain and is not automatically typed again. The local list is the only evidence that typing may have started: the worker adds a request ID to it after the reservation and before typing, and never types an ID that is on it; when saving the list fails, the ID is taken back out of memory, so the request is again one that was never typed. If the reservation answer is lost (a timeout, a transport error or a gateway error) after the server committed it, the request is `accepted` with the reservation note (`automatic delivery reserved before typing; outcome is uncertain until observed`) and its ID is not on the list, so nothing was typed. On a later renewal the worker confirms the request with an answer that changes nothing, which fails if the claim or the generation is no longer current, and then types it once. (A request whose local list entry could not be saved is in the same state.) A dispatch proposal found this way passes the same acceptance-window and card-version checks as an open one, once when the requests are sorted and again after the target resolution, which may take as long as the window had left; it is rejected without typing when it fails either. A request that an older worker left `accepted` carries the older note (`automatic delivery reserved; outcome is uncertain until observed`) and is never resumed: the older worker cannot tell whether typing began, and the holder may have pasted the line by hand. If the sender or the holder already pasted the line by hand between the loss and the next renewal, the agent sees the same request ID twice. The holder can inspect the request and execution facts. Answer revisions support CAS; settled answers cannot regress to accepted. A move into `done` that completes a dispatch releases the claim, so the same transaction settles the request that proposed that dispatch for the same generation as `done`. An exact replay of the completed move settles a request an earlier server left `accepted`; a replay with any other payload is refused and settles nothing. Request state, answer receipts and takeover supersession share the board redo journal without changing card content versions. A card without a usable terminal target keeps its request for manual inspection.

A client created by `kander notify`, by a `kander resume` that turns into a notify, or by a non-holder `kander dispatch prepare` gives the request the kind of its dispatch, or `note` when it has none. A dispatch kind other than `fix`, `sync` and `wrap-up` is refused before the request is created; the client may already have contacted the server to read the card. The server accepts more combinations than these clients create:

| Kind | Dispatch | Source |
| --- | --- | --- |
| `fix` | dispatch kind `fix` (a dispatch proposal), or none | `kander notify --kind fix` (the default with dispatch options), non-holder `kander dispatch prepare`, `kander request <task> fix` |
| `sync` | dispatch kind `sync`, or none | `kander notify --kind sync`, non-holder `kander dispatch prepare`, `kander request <task> sync` |
| `wrap-up` | dispatch kind `wrap-up`, always | `kander notify --kind wrap-up`, non-holder `kander dispatch prepare` |
| `note` | none | `kander notify` without dispatch options, `kander request <task> note`, `kander resume` that turns into a notify without dispatch options |
| `review` | none | joint review material confirmation |
| `stop` | none | `kander request <task> stop` |

The server refuses a `note` that carries a dispatch and a `wrap-up` request whose dispatch is missing or is not a `wrap-up` dispatch (`invalid_request`). It does not check the older kinds against their dispatch: before this change a client sent a `wrap-up` dispatch proposal as kind `sync`, and a server that held that check back would fail the proposals of clients not yet upgraded. A repeated dispatch ID returns the first proposal whatever kind the retry carries. The worker types a `note` with the extra text `no dispatch is attached: handle the message within the card contract; do not run kander dispatch prepare for it and do not use it as the grant of a dispatch-bound move`; the line of every other kind keeps its form. A `note` is for status, requirements, answers and for sending an idle executing agent back to its unmet acceptance criteria. It is not the grant of a dispatch-bound move.

The client checks the message before it sends anything: not blank and at most 64 KiB (`api.MaxRequestMessage`). A server that predates the `note` and `wrap-up` kinds answers `invalid_request` with its single combined message `request needs kind, client and a message of at most 64 KiB`. Since the client has checked the message and fills the client identity itself, only the kind can cause this answer for those two kinds. The client then reports that the server does not know the kind and has to be upgraded and restarted first, and the same command runs again after that. Upgrade the server before the clients; stored requests are not rewritten, so older requests keep kind `sync` for plain notifications and wrap-up proposals.

`kander notify` submits a request to the owning worker through REST. Plain working messages are `note` requests. Dispatch options add the full typed proposal and inspected card revision; a group review card still requires them. The JSON result describes the request's queue/answer state, never asserts dispatch business acceptance. A pane override is accepted only when it names the exact private execution on this host and never probes a foreign terminal. The holder can inspect every full message with `kander request show <task> <request> --json`.

When a non-holder creates a new proposal of kind `fix`, the server checks its fix evidence once, in the same write transaction as the creation and after the request checks and the dispatch ID slot accepted the creation, before it writes anything. A proposal whose evidence fails creates no request: the answer is `board_rejected` (`board.dispatch_evidence_invalid`, HTTP 422), the message lists every problem of the evidence, one line each, and the last line says how to send again (`kander notify`: correct the evidence file and run again without `--dispatch-id`, or with a new dispatch ID; non-holder `kander dispatch prepare`: correct the intent and update or remove `created_at` and `confirm_by`). The stored receipt keeps the refusal, so replaying the same key with the same content returns it. The check reads the review control group and the batch member cards, so it takes their locks in that transaction; readers of those cards wait for it as they do for a prepare. A proposal for a dispatch ID that already has one returns that proposal without a check, and `sync`, `wrap-up` and plain requests are not checked. The holder's `prepare` still checks everything again: state that changed after the creation is refused there with the same problem list. See [Durable dispatch](durable-dispatch.md#3-fix-review-evidence-binding).

A dispatch proposal ID identifies one immutable payload. Repeating a known ID reuses its original version and deadline; changing material requires a new ID. A relative acceptance window is stamped by the service, is bounded to 24 hours, and cannot be reset by a retry. The worker refuses stale or expired proposals before terminal effects. Reserving their first delivery checks the card revision, deadline, request revision and live generation in one transaction. Formal dispatch preparation checks the same frozen material and version, then stages its proposal acknowledgement with the dispatch and its exact receipt. Existing formal dispatch retries remain receipt-only reads.

The client keeps private request-operation receipts under `request-calls/` before transport. An uncertain response retains the original operation key and target generation; a restarted command inspects that exact request before resubmitting the saved domain operation. It never builds a new request for a successor from the old uncertainty. A successful response or matching central facts completes the private receipt. Unknown outcomes preserve it for inspection; known rejection permits a later deliberate request. This is domain recovery, not a claim that terminal effects are exactly once. The worker separately reserves each terminal attempt before typing and never automatically repeats an uncertain attempt.

Worker delivery requires a usable local target and refuses server routing that differs from this execution's saved window/session. It strips control characters and Unicode line separators, links the full request for inspection, warns the agent to reject another generation or a superseded request, and carries no language suffix. The task contract and the launch task file establish the card language for the session.

A blocked delivery is the state of one execution after a failed resolution; it ends only when a resolution and the typing after it both succeed. It lives in the memory of the worker, so a worker that starts again resolves at once, which is safe because nothing was typed. While an execution is blocked:

- The next resolution waits for a backoff of `min(30 s × 2^(n-1), 300 s)` after the `n`-th failure in a row: 30, 60, 120, 240, then 300 seconds. The deliveries of an execution all go to one pane, so the backoff counts per execution, and a failed resolution ends the delivery of that execution for the work step. A card whose `WINDOW` or `SESSION` differs from the last failure is tried at the next work step and counts from one again; the start of the block does not change.
- One work round stops starting resolutions once they have used 30 seconds; the check runs before each resolution, so a resolution that starts just under the threshold runs to its end. An execution that waits for the next round keeps its state and is judged again at its next work step. The renewal loop does not wait for any of this.
- A dispatch proposal with an acceptance window (`ConfirmBy` is not zero) opens the gate by itself at its attempt time: the remaining window as the server read it at the card read, moved to the worker clock, minus two renewal intervals. The delivery runs once per renewal, so at the default interval of 15 seconds and a window of 120 seconds, at least one resolution starts 15 to 30 seconds before `ConfirmBy`, whatever the backoff says. A proposal without an acceptance window follows the backoff only. A late attempt can reserve a proposal with less than 30 seconds of its window left; if the holder's `prepare` is then told that the window has elapsed, it answers the request `rejected` and the sender proposes again with a new dispatch ID.
- A proposal that expires during the block is rejected as before, and the note adds `; delivery was blocked before sending since <UTC time>: <reason>`. The rejection key is `expired-` followed by the first 32 hex characters of the SHA-256 of the execution ID, the request ID and the note, so a note that changes between two attempts never meets `idempotency_mismatch` and a rejection that ended in a server error is still repeated by a worker that started again. The block, and its start time, stay as they were.
- Every failure writes a WARN to `worker.log` with the request, the number waiting, the reason, the attempt, the start of the block and the next attempt. A block that has lasted ten minutes with requests waiting writes one ERROR, judged at the end of each work step. The first typing after a block writes an INFO with `blocked_for`.
- While requests wait, the reason of the execution observation the worker reports ends with a localized suffix (`worker.request_delivery_blocked`): the start of the block in UTC, the number of requests waiting, the first request ID and the last reason. It appears in `claim.observation.reason` of `kander list --json` and in the worker observation of `kander check`, and on other hosts in the `agent.reason` derived from it; the holder's host replaces `agent` with its local observation under `--agent-status`, so it reads `claim.observation.reason`. An observation with status `unknown` is not reported, so its suffix stays in `worker.log`.

Each server call of a delivery has a time limit of 10 seconds of its own, so a slow resolution does not take the time of the reservation after it. Requests that an earlier worker left `accepted` and uncertain are not migrated and not typed again.

Event cursors resume within a running server's bounded window. A service restart always changes the epoch and requires a full snapshot, including when a crash occurred after a domain commit but before event append. An append failure also rotates the epoch and wakes observers; missing invalidation hints never silently preserve a current-looking cache.

## Client views and issue import

`internal/remote.ProjectService` is the typed REST boundary shared by client commands and views. It has no local board implementation. The TUI binds its board, detail, action and start callbacks to that service on every normal launch. A captured task-action revision fences the move at the server; a stale dialog cannot overwrite a newer task.

The TUI writes only a private list cache under the client home, keyed by the server URL and project ID. A transport failure may display that cache with a persistent stale label and its observation time. It never turns the cache into a writable board or queues an offline move. Detail reads and mutations still require the server. The executing worker is independent of the view lifetime.

The TUI keeps one bounded event poll from its last successful snapshot cursor. A change or reset wakes the asynchronous snapshot reader; it adopts the next snapshot cursor only after that read completes. The poll does not occupy pending terminal work. Error backoff survives successful list reads, stale caches use bounded snapshot retries, and quitting cancels only view reads. Periodic refresh remains a fallback for lease expiry and read recovery; see [TUI board refresh](tui-board-refresh.md#distributed-event-wakeups).

`kander list --json` keeps the schema-1 CLI snapshot consumed by dsh and adds project ID, event cursor and public claim observations. The change token ignores renewal timestamps and pure observation timestamps. Local terminal observation and focus require this host's exact saved execution, generation, session and window; a public client ID alone grants no routing. Foreign tasks display their owning worker's service observation; their terminal addresses never reach this host's backends. Lease loss remains visible but never invents evidence of process exit. Observation and renewal timestamps are excluded from the change token.

`subscribe` expands membership from a coordinated `/snapshot` response and resumes `/events` from that snapshot's cursor. Its in-memory board view contains resource identities and no write cursor; it creates no local card directories. Group expansion, task revisions, dispatch summaries and blocked members come from the service. Public liveness uses generation-bound worker observations and translates service-clock age for local display. Cursor resets trigger a fresh snapshot and an explicit `snapshot-reset` event. Claim generation/status changes emit `claim-change`. Group checkpoint or authority changes emit `coordinator-change` with public coordinator summaries; ordinary renewal timestamps do not. The bounded output worker cancels an outstanding event poll when output closes.

The ordinary `check` route performs the board's structural, prerequisite and review-evidence checks on the server and appends the reported agent observations on the client. Delivery and overlap checks continue to inspect local Git without a board.

dsh resolves the Git main worktree or a non-Git project's configuration directory, without requiring `kanban/`. Its subprocess environment removes inherited `KANBAN_DIR`; kander resolves the server binding from the repository and configuration. dsh keeps its existing schema-1 list consumer and asynchronous start boundary.

`POST /projects/{p}/issues/import` receives a bounded source snapshot, type choice, language and size. The server validates the canonical repository and issue identity, sanitizes the source again, authors the fixed contract itself, and reuses the exclusive-board source-key transaction. It never accepts client-authored contract sections or puts issue bodies/comments into them. Concurrent imports return one anchor with both source attachments. `GET .../issues/index` returns canonical bindings with resource locations instead of server filesystem paths.

Issue triage and refinement run on the client. Their refreshed or downloaded source evidence lives in the client's project-private data directory. The launch request distinguishes that evidence directory from the local Git repository; no local card-state directories are created. Result inspection, publication, consent and recovery use the independent central CAS described in [Distributed Issue results](distributed-issue-results.md).

## Events

Each project keeps `control/events.jsonl`. Events carry identities (`task_changed`, `claim_changed`, `request_changed`, `group_changed` with task or group, state, revision, generation), never bodies. A cursor is `<epoch>:<seq>`; the task list returns the cursor it is consistent with. `GET .../events?cursor=&wait=` long-polls up to 60 s. An unknown epoch, a future sequence, or a cursor older than the retained window answers `reset`; the client re-reads the task list and continues from its cursor. The TUI reads server snapshots and keeps a private read-only offline snapshot. `subscribe` resumes the stream and refreshes after a cursor reset. The TUI runs one bounded long poll that wakes its existing asynchronous snapshot reader. A reset waits for that fresh snapshot before adopting a new cursor; endpoint failures back off, and periodic refresh remains a fallback for lease expiry. Closing the UI cancels its reads without stopping the independent worker.

## Logging

The server logs JSON lines with method, path, status, client ID, operation ID (derived from the idempotency key), claim generation, and duration; claim transitions log project, task, and generation. Claim tokens are never logged.

## Migrating a v1 board

`kander server import [--data DIR] --project NAME [--remote URL] [--from KANBAN_DIR]` imports one v1 board into a project. Before running it, stop the v1 executing agents and other writers of the source board, as for `kander server maintain`. The server itself does not need to stop.

- Without `--from`, the command locates the source as v1 commands do: `KANBAN_DIR`, then the main worktree's `kanban/`, then an upward search from the current directory. A relative `--from` is resolved in the command's directory. The located path must be an existing directory; otherwise the command fails and asks for `--from`. Links are refused later by the board reads.
- When no process holds the data directory lock, the command opens the data directory and imports offline.
- When the lock is held (`server.ErrDataDirInUse`), the command imports online: it reads `server.url`, which must be a loopback URL, asks that server for its data directory, and requires it to equal the target. It then loads `admin-token.json` from that directory and sends `POST /api/v1/server/import` with the absolute source path. The running server performs the same import in process and keeps serving every other project.
- Online import fails without changing data, and names the data directory and URL, when no server answers at `server.url` (another offline command holds the lock, or the server listens on another address), when `server.url` is not loopback, or when the server serves another data directory. A server that predates the route answers 404 or 405; the command then asks for `kander server restart`.
- Both paths print the same JSON result on stdout and nothing else there. `source` is the absolute source path of this request, also when the snapshot was imported earlier. The result may carry `defaulted_size` and `warnings` (see below); both are omitted when empty, and an `existing: true` answer repeats the lists of the first import of that snapshot.
- Progress goes to stderr, from the first moment of the command, so a long import never looks stalled. The phases of a first successful import are, in order: `lock` (waiting for the source board lock, which includes the recovery of its interrupted transactions), `scan` (digesting the source board), `copy` (copying into staging, with the files and bytes copied so far and in total), `verify` (digesting the staged copy), `check` (defaulting `SIZE` and checking the staged board) and `publish` (the second source digest, the intent and the rename). An import answered from its record reports `lock` and `scan` only. On a terminal stderr the progress is one status line rewritten in place and ended with a newline. On any other stderr each phase gets one plain line, and the counts of a long phase add at most one line every 2 seconds, with no carriage returns or escape codes. The server reports counts at most once per second and repeats its latest report once per second while one step runs long (a large file, a slow disk, the check), so the stream never stays silent longer than that.
- Online, the progress is streamed by the server (see "Streamed import response" below); offline, the command reports it directly.
- Only the snapshot lock wait and the copy observe cancellation: they stop after 5 minutes or when the caller disconnects, and nothing is published then. The initial recovery of the source board waits for the source lock without a deadline, and validation and publication run to completion once the copy is done. After a timeout or a lost connection, run the same command again: when the import was published, the same snapshot answers `existing: true`; when it stopped before publication, the rerun imports it.
- Ctrl+C is handled by phase, from the progress the command has seen:
  - Online, before the copy has finished: the command drops the request, says on stderr that the import was cancelled and nothing was published, and exits with 130. The server stops at its next file.
  - Online, after the copy has finished, or when the server has sent no progress (a server older than the stream): the command drops the request and says that the server may still complete verification and publication, and to run the same command again to see the result (`existing: true` once published). It exits with 130. The server does not observe the disconnect in those phases, and the command cannot tell how far a server without progress got.
  - Offline, before the copy has finished: the command says it is cancelling, stops the copy, says that nothing was published, and exits with 130. The first Ctrl+C restores the default signal handling, so a second Ctrl+C ends the process at once; this is the way out while the command still waits for the source lock, which does not observe cancellation.
  - Offline, after the copy has finished: the command says the import will complete verification and publication, finishes, and prints the result as usual.
  The progress the command has seen decides the message, so an interrupt that arrives at the boundary of the copy can be reported one phase early.

1. It refuses overlapping source/data paths, recovers the source board's interrupted transactions, then holds the board-exclusive lock while copying a consistent snapshot. Every regular file is digested by path and SHA-256, including empty lock files. For an empty lock file, validated handle metadata supplies its zero length without a byte-range read, which Windows forbids while the source lock is held. Nonempty lock files retain their bytes and receive normal read validation. A symlink, junction, or other entry refuses the import. A second source digest detects non-cooperating writers before publication.
2. The project must have no tasks. Importing the same snapshot into the same project again answers with the earlier import; any other import into a project with tasks is refused with `project_not_empty`. Two existing boards are never merged.
3. Every file is copied byte for byte into a staging directory beside the project board, and the staged copy must equal the source snapshot. A directory card whose `spec.md` has no `SIZE` line then receives the default `- SIZE: large`, the size v1 reads such a card with; the staged tree must differ from the source only by those single inserted lines, each checked against its source file. Legacy file cards get no `SIZE`, as they stay read-only until `kander server maintain`. The staged board must then pass the full structural, dependency, contract and immutable-evidence checks. An unresolved historical execution batch may remain pending business work; migration grants no closure or completion. New empty validation locks are removed, and the staged tree must again equal the expected tree, before anything is published.
   A check problem whose cards are all in `done`, `archived` or `trash` does not stop the import: the card is imported as it is and the problem is listed in `warnings`. This covers outdated prerequisite syntax, historical review evidence that no longer agrees with itself, and any other check problem of such cards, including a damaged review original of a closed card. A problem belongs to the cards its check names. A plan target that differs from its batch names the cards of that batch, and only them, however many cards of the plan the checks reached it from, and it is reported once. So it blocks when a card of that batch is active, and otherwise it is one warning whose `task_ids` hold every card of the batch. Warnings and blocking lines come in a fixed order. A problem that concerns a card in `backlog`, `todo`, `working` or `review`, or whose cards cannot be determined, refuses the whole import with the same error as before, naming only the blocking problems, and publishes nothing. The default `kander check` skips `done` and `archived` cards but checks `trash` cards, so the problems of a card in `trash` that the import accepted as warnings are still reported there; `kander check --all` reports the problems of every closed card.
4. Only then is `control/import-pending.json` committed. It records the digest of the staged board next to the source snapshot (`staged_digest`; an intent written before it existed has none, and its staged board equals the source snapshot). The old empty destination is renamed to a private backup, staging is renamed into place, and `control/import.json` records the source snapshot, the defaulted cards and the warnings before recovery material is removed. Startup completes an interrupted publication before board initialization and readiness, comparing the staging and published boards with `staged_digest`. Missing, conflicting or changed prepared material refuses startup; it is never replaced with an empty board.

The result lists what the import changed or accepted:

- `snapshot` is the digest of the source board, exactly as before. The published board equals that snapshot except for the `SIZE` lines named in `defaulted_size`.
- `defaulted_size` holds the IDs of the cards that received `- SIZE: large`, in order. The spec of such a card is longer than its source by that one line.
- `warnings` holds one entry per accepted problem: `task_ids` (the closed cards it concerns) and `message` (the check text, in the language of the server process).

Inside a serving instance the import holds the project lock (`p.mu`) from the project check through publication, so every request of that project waits instead of reading a missing or partial board. Only a project without tasks reaches that lock: for a project with tasks, a cheap check under the lock either refuses with `project_not_empty` at once (no `control/import.json`) or releases the lock before digesting the source to decide between `existing: true` and `project_not_empty`. A project without tasks keeps the full flow, including after an earlier import of an empty board.

When an import fails after `control/import-pending.json`, the server recovers the publication in the same lock hold and still reports the failure; the same command then answers `existing: true`. When that recovery also fails, the project refuses every board request, including requests that queued behind the import and new imports, with `not_ready` until a restart retries the recovery at startup. The event stream (`/events`) and project lookup do not read the board and stay available.

A successful publication starts a new event epoch and wakes long polls at once, so the TUI and `kander subscribe` read `reset` and re-read the task list.

The source board is never changed and stays as the local backup; review originals, journals, and their hashes keep their bytes. Claimed cards of the old board have no claim record, read as generation 0, and need an explicit takeover. Afterwards each clone sets `server.url` and `project.name` (for example in `.kander-config.json`) and stops using the local `kanban/`.

### Streamed import response

`POST /api/v1/server/import` answers in one of two forms. Every check that precedes the import (protocol handshake, readiness, body limit, administration token, request body, absolute source path) answers with the single JSON error and its status, whatever the `Accept` header says.

- Without `application/x-ndjson` in `Accept`, the answer is the single JSON of the result, with the status codes and fields of earlier versions (plus the optional `defaulted_size` and `warnings`). An older client keeps working against a newer server.
- With it, the server answers `200` with `Content-Type: application/x-ndjson` at once, then one JSON object per line, each flushed: `{"progress":{"phase":"copy","done":120,"total":18949,"bytes":3100000,"total_bytes":563000000}}` for progress (`done`, `total`, `bytes` and `total_bytes` are omitted when zero), and a last line that is either `{"result":{...}}` with the `ImportResult`, or `{"status":409,"error":{"code":"...","message":"..."}}` with the `api.Error` fields and the HTTP status the single-response form would have used. A stream that ends without a last line is a lost connection, and the import may or may not have been published: run the command again. No line contains the administration token.
- Progress is queued without blocking the import, which holds the project lock: counts of the phase being reported replace each other, every phase change is kept, and a client that stops reading cannot slow the import. A write to a client that has gone is dropped; cancellation still follows the request context. The access log records the final status (`200`, or the error's status) and the whole duration.
- A client that sends `Accept` for the stream and reaches a server that predates it receives the single JSON; the new client then shows no server progress and the import completes as before. The client reads a stream line by line with a 1 MiB limit per line.

## Build and release

`make build` and `make-windows.cmd` build only `kander` (`kander.exe` on Windows). Release archives and MSIX bundles contain that one executable. `kander install` copies only it; uninstall also removes an obsolete standalone service file. There is no separate service alias, installer or updater. Alpha tags remain prereleases, never replace stable releases or sync the Homebrew formula, and skip MSIX publication. Store installations use Store updates.

## Local service lifecycle

```text
kander server start [--data DIR] [--listen ADDR] [--ttl D] [--renew D] [--foreground]
kander server status
kander server stop
kander server restart
```

Start normally detaches from the terminal (a new Unix session, or a detached Windows process), appends stdout and stderr to `<data>/server.log`, and waits up to 10 seconds for `/api/v1/health`. An already healthy instance is reused. Concurrent starts share the existing exclusive data-directory lock; callers that observe a winner reap their own losing child before returning, preventing it from taking over after a later stop. A timeout kills and reaps only the child this caller launched and reports the log path and last 20 lines. Foreground mode writes JSON logs to stderr and gracefully shuts down on SIGINT, SIGTERM, or an authenticated administration request.

The default data directory remains `$XDG_DATA_HOME/kander-server` when absolute, otherwise `~/.local/share/kander-server`. Default listen is the effective loopback URL's address, otherwise `127.0.0.1:7878`. Explicit `--data` and `--listen` override these. TTL and renewal default to 90s and 15s; both must be positive and renewal shorter than TTL. Status reads the actual data directory from the running server. Restart reads and preserves its data directory, listening address, TTL and renewal interval.

`GET /api/v1/server` reports version, PID, data directory, log path, listen address, TTL, renewal interval, start time and project count. It never returns a secret. `POST /api/v1/server/shutdown` accepts only a loopback peer with the correct `Kander-Admin-Token` header, compared with `crypto/subtle.ConstantTimeCompare`. This management key is a separate random 32-byte token in private `admin-token.json`, created through `internal/fs`; it never reuses the claim-signing `secret.json`. Stop reads the running server's data directory, loads the key locally, sends it to that same loopback URL without redirects, and waits up to 10 seconds for health to fail and the data lock to be released after active requests drain. Already stopped succeeds. Rejected requests return 403 and never echo or log the key. Information and shutdown routes stay independent of the board protocol handshake so a protocol upgrade can restart the old process. `POST /api/v1/server/import` uses the same loopback and key check, but because it changes board data it also passes the protocol handshake, the readiness gate, the body limit and the access log of the domain routes; its source must be an absolute path on the server host. The client sends it without redirects and with a 6-minute timeout, longer than the server's 5-minute bound on the snapshot lock wait and the copy. A client that sends `Accept: application/x-ndjson` receives the streamed response described under "Streamed import response". Validation and publication have no bound, so a client timeout does not tell whether the import was published; run the command again to find out.

When `server.url` is absent, mandatory client commands use `http://127.0.0.1:7878`. Missing project binding reports `kander init --project <name>`; init may bind without an explicit URL. Human-readable config marks the default URL, while JSON remains the stored effective configuration.

Before opening a project session (and before the TUI starts), an unreachable loopback server is started by the client itself when the project board directory `<data>/projects/<ProjectDirName(project.name)>/board` exists in the default data directory. Every caller is treated alike: interactive, Agent (`KANDER_EXECUTION_ID` or `KANDER_COORDINATOR_EXECUTION_ID` set), `--json`, without a terminal, and the TUI. Nothing is asked. The client starts the server with the default data directory, the listen address of the configured URL, and the default TTL and renew interval, then checks compatibility again and continues with a fresh operation budget. It reports one notice (`server_self_started`, on stderr, or in `notices` with `--json`). The board directory is the sign that the default data directory is the project's; without it a start would register an empty project in the wrong directory, so the earlier rule still holds there: the question shows URL, default data directory, board path, and log path, and only an interactive caller (stdin and stderr are terminals, neither execution variable set) may answer; empty line, `y`, or `Y` authorizes background start, `n`, `N`, or EOF fails without starting, and noninteractive calls fail with `kander server start` and the data path. Before a self-start the client probes `<data>/server.lock` without waiting and without creating it. A held lock means a server runs but cannot be reached from here (a sandbox without network, another listen address), or an offline `import` or `maintain` is running; the client waits at most 750 ms in case a concurrent client's server is still starting, then fails with the unreachable error and a line about the lock (that is on top of the normal connection attempt of the client, which retries for about 1.4 seconds before it counts the server unreachable), because a start would only fail on the lock and the start wait would run its full 10 seconds. Concurrent self-starts converge on one server through the existing start rules above; a server that needs more than the 750 ms to listen (a slow project recovery; the client waits at most 750 ms from the moment it finds the lock held) makes the concurrent client fail with the unreachable error, and the command is retried once the server is up. A command that was canceled before the server starts never self-starts. An explicit cancellation (Ctrl+C) while a self-started server is being awaited ends the wait at once, and the command starts no worker and registers nothing; the start kills and reaps only the server process this command launched, as it does on a timeout, and the next command starts the server again. An expired deadline does not end the 30 second start budget. A test binary never self-starts unless a test supplied its own starter. Configuration/help/install commands and server commands never trigger a start. Remote unreachable servers are never started and retain the usual failure behavior. A version mismatch keeps the restart question above.

The self-started server and worker are detached children of the command that started them. They run in the data directory and the client home, not in the working directory of the caller, so an Agent worktree is never pinned (the worker therefore finds no project-install share directory of the checkout that started it, so terminal definitions that exist only there are not seen by it; a worker serves every project of its client home, so no checkout is its own), and their environment lacks `KANDER_EXECUTION_ID` and `KANDER_COORDINATOR_EXECUTION_ID`. `kander server start`, `restart`, and a worker started after a claim build their children the same way.

A local version mismatch, including incompatible protocols, prompts for restart once per endpoint per client process. Noninteractive compatible clients warn once and continue; incompatible ones fail with `kander server restart`. Declining restart keeps a compatible connection and refuses an incompatible one. Questions do not consume the caller's short connection deadline: start/restart and the retried handshake use independent bounded contexts, Open renews its context for registration after a question, and consumers call Session.OperationContext to renew their bounded budget for the actual command operation while preserving explicit cancellation.

The remaining service API retains the existing unauthenticated trusted-network boundary. Log rotation and remote process administration are outside this contract; the boot-time case is covered by the self-start of the client below. A local attacker who occupies a stopped server's port can obtain the administration token when the operator sends stop to that port; the accepted impact is later service shutdown, not board access beyond the existing network boundary.

## Implementation boundaries

The service owns board transactions and execution authority. The client owns Git verification, agent effects and private recovery journals. Native platform and packaging verification are recorded separately from cross-builds; a successful build does not prove native behavior.

## Retained local execution routing

After task completion or explicit release, the client removes the bearer credential and leaves a release tombstone. A separate private `retained-executions/` record keeps the final window, session, worktree, branch and base without a token. A delayed removal cannot erase those latest facts. Remote `dismiss` reads final state and the execution record through REST, then uses only the owning host's exact retained routing. It resolves that routing through `Session.RetainedForDismiss`, which only `kander dismiss` calls; `Session.Retained`, and with it `SceneIsLocal` behind the list and detail views of `kander list`, the TUI and the dsh view, is unchanged. A process with no execution binding resolves as before. A task executor process (`KANDER_EXECUTION_ID` set, `KANDER_COORDINATOR_EXECUTION_ID` empty) whose execution is not the claim's is refused. An orchestrator process (both variables equal) may dismiss a member of its task group when this host holds the group's valid group credential: the card's `TASK_GROUP` names the group, and the private `executions/<namespace>/<group>/<orchestrator execution>.json` has no `.released` tombstone, has kind group, is not lost, and matches the server, client and project of the session. A credential that is missing, released, of another kind, lost, damaged or of another identity is refused in the same way, with the reason named. Dismiss does not ask the server whether the group lease is still current: between a takeover and the next renewal, in which the worker marks the credential lost, a replaced orchestrator can still pass this check, and every other check still applies. The orchestrator must dismiss before `kander coordinator release`, which ends the lease. The orchestrator is refused whenever its local group credential is no longer valid: the worker removes it after it confirmed the release, or marks it lost after another orchestrator took the group over; an orchestrator for a card outside any task group has no credential and is refused, so the user runs `kander dismiss` in a shell without the two variables. Every refusal that needs the retained execution keeps the common sentence and appends the failed condition and its values, never a token. If the recorded terminal no longer exists, dismiss records the receipt as complete, prints one line naming the task and the `WINDOW`, and exits 0. It rechecks revision/generation and pane identity, then runs every pre-send check of the pane (delivery probe, agent status, session match, single-pane container) before it records its private exit intent, immediately before the first exit command is sent. A failed pre-send check sends nothing and leaves the receipt prepared, so dismiss can run again once the pane accepts delivery; a failure after the first send keeps the exit intent. It never reverse-searches a stale pane. Completed cleanup replays its receipt; an uncertain cleanup recognizes an already absent target but never blindly repeats an exit or close. Worktrees remain intact.

## Joint material retry

A joint operation privately freezes its verified material against the operation and each member's current revision/generation. For closure and historical resolution, a retry may recheck identical immutable Git facts at another instant; the first verified payload, including its original timestamp, remains the material holders confirm. The REST client sends that exact frozen payload with its publication identity. A changed revision, generation or substantive fact produces a different proposal and needs new confirmation. This prevents a fresh verification timestamp from abandoning partial approvals on every retry.

The private review operation index also remembers prepared publication identities before sending them. Once one of them is published, a retry returns that exact frozen result before considering versions advanced by the publication itself or by later exclusions/takeovers. The service validates the operation and material digest, then replays the immutable result without executing a producer or requiring old holders again. Prepared publications still require the full current member/version/generation checks. This receipt path cannot grant a new write.

## Stopped executors and native command recovery

The worker continues renewing ownership after an agent exit. It leaves that generation's requests queued instead of delivering to a stopped pane or spawning a replacement. The holder can explicitly resume a locally proven stopped native session; a new handoff generation supersedes the old requests. A fresh proposal is a separate explicit instruction to the successor.

An implicit native resume saves its decision and normalized launch input before handoff. Another command process reopens that intent before probing the new generation. Unknown responses reconcile the original key and predecessor proof. A proven no-launch attempt audit-releases its generation and remains settled; a deliberate new attempt needs an explicit new decision. Once launch and proposal publication complete, retries return a historical receipt without changing authority. A later confirmed stop of that exact successful execution permits an intentionally new native continuation; the child launch receipts remain immutable.

## CLI move receipts and completion advice

A move's exact dispatch result and replay flag are captured inside its board transaction and stored in the service receipt. CLI durable moves retain the `{dispatch, replayed}` JSON output; other moves print the logical `kander-server:<project>/<task>` location. An identical completed dispatch may be read after claim release, but any changed payload still refuses and the old execution gains no mutation authority.

For a non-replayed CLI terminal move, the reporting switch prints the completion template on stderr using the committed service snapshot and logical resource location. The Issue module compares central work-set readiness before and after that move, honors `issue.result_on_done`, and prints the explicit result handoff when the last member completes or is withdrawn. Advice failures never change a successful move. The TUI invokes no CLI advice hooks.

`kander request --help` uses the supplemental collaboration forms in the notify contract. Root help lists `notify` and `request` as separate commands, and `kander request --help` prints the summary, arguments, and examples of the `## Request command` section and the request lines of that contract; the installed historical command index remains the user's manually maintained file.

### Self-start after a reboot

No service manager (systemd, launchd) is needed to bring the local server and the worker back. After a reboot the first kander command on the machine that opens a session starts the local server (when the project board directory exists in the default data directory, see the rules for an unreachable loopback server above) and then, because the client home holds a renewable credential, the worker. From then on the claims are renewed again.

What the self-start does not cover:

- A reboot with no kander command afterwards leaves the leases lapsed. That is harmless: a lapsed lease is only a view value, its holder keeps writing and renewing at the same generation, nothing takes the task over by itself, and a server start extends every active lease by one TTL (the lease rules above).
- An Agent that exited is not restarted. Only the lease renewal resumes.
- A server that needs a custom `--data`, `--ttl`, or `--renew` is started by hand with `kander server start`. The data directory does not record the lease settings, so the client starts with the defaults.
- Someone who normally uses a custom `--data` and still has an old board of the same project name in the default data directory gets that old board served silently by the self-start. Move or delete the old board, or use the default data directory.
- `kander server stop` leaves no mark. While an Agent runs, a stop is in effect a restart: the next Agent command starts the server again. Pause every executor before the offline `kander server maintain`, or a self-start can take the data directory lock between the stop and the maintenance command. While an offline command holds the lock, client commands fail at once with the unreachable error described above.
- A process started from an Agent pane stays in that pane's process group or cgroup, and a terminal or sandbox that closes the pane may end it. The next command starts it again.
